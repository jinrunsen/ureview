## 0. 先把评估标尺定下来

选型题容易变成「优点罗列大赛」。先把「规范条目」这个东西要求知识库做到什么，拆成可证伪的问题，再拿三个方案去撞。

一条编码规范条目，至少要能表达：

| 要素 | 例子 | 形状 |
|---|---|---|
| 标识 | `go-error-wrap-001` | 短字符串，稳定 |
| 正文 | 「错误向上传递时必须用 `%w` 包装，不要用 `%v`」 | **长自然语言文本**，几百到几千字符，可能带正反例代码块 |
| 作用域 | 语言=Go；仓库=`payment-*`；目录=`internal/**`；框架=gin | **多维、可通配** |
| 状态 | 候选 / 试运行 / 生效 / 废弃 | 枚举，且有流转规则 |
| 版本 | v3，谁在什么时候为什么改的 | 有历史、可回滚、可归因 |
| 归属 | 团队 X 拥有，团队 Y 继承 | 引用组织结构 |
| 可执行性 | 有对应 semgrep 规则 / 纯人读 | 可选挂载 |

八个评估维度由此推出：**实体模型契合度、检索能力、版本化、作用域表达、状态机、接入成本、维护成本、可被 agent 调用的便利度**。

一个贯穿全文的判断先摆在这里，后面所有细节都在为它服务：

> 现成方案的核心语义是**「给已存在的实体挂文档」**，而我们要的核心语义是**「给条目挂适用条件」**。前者的主键是实体，规范是附属物；后者的主键是规范条目，实体是它的作用域取值之一。这个方向是反的。

## 1. Backstage

### 1.1 Software Catalog 的实体模型

官方定义了 10 个内建 kind（[Descriptor Format](https://backstage.io/docs/features/software-catalog/descriptor-format)）：

| Kind | 语义 | spec 必填 |
|---|---|---|
| `Component` | 有可部署产物的软件单元 | `type`、`lifecycle`、`owner` |
| `API` | 组件暴露的接口 | `type`、`lifecycle`、`owner`、`definition` |
| `Resource` | 运行所需基础设施 | `type`、`owner` |
| `System` | 组件与资源的集合 | `owner` |
| `Domain` | 共享业务语汇的 System 集合 | `owner` |
| `Group` | 团队 / 组织单元 | `type`、`children` |
| `User` | 人 | `memberOf` |
| `Location` | 指向其他 catalog 数据源的标记 | `spec`（可为空对象） |
| `Template` | Scaffolder 脚手架 | `type`、`parameters`、`steps` |
| （自定义 kind） | —— | —— |

所有实体共享同一个信封：`apiVersion` / `kind` / `metadata` / `spec` / `relations`（只读）/ `status`（只读）。

注意 `System` 这个词在 Backstage 里的含义 —— 它是「组件与资源的集合」，不是「一套规范」。整个模型是围绕**「谁拥有什么、什么依赖什么」**建的，`relations` 只有 `ownedBy` / `partOf` / `dependsOn` / `providesApi` 这类结构关系。模型里没有任何位置天然对应「一条规则适用于哪些代码」。

### 1.2 字段格式约束：这是作用域表达的硬天花板

这是本次调研最有决定性的一组事实，来自源码 [`FieldFormatEntityPolicy.ts`](https://github.com/backstage/backstage/blob/master/packages/catalog-model/src/entity/policies/FieldFormatEntityPolicy.ts)（错误信息里直接写死了期望格式）：

| 字段 | 校验器 | 允许的格式 |
|---|---|---|
| `metadata.name` | `isValidEntityName` | `[a-zA-Z0-9]` 以 `[-_.]` 分隔，**最长 63 字符** |
| `metadata.labels` 的**值** | `isValidLabelValue` | `[a-zA-Z0-9]` 以 `[-_.]` 分隔，**最长 63 字符** |
| `metadata.annotations` 的**值** | `isValidAnnotationValue` | 任意字符串（无长度限制） |
| `metadata.tags` | `isValidTag` | `[a-z0-9+#]` 以 `-` 分隔，最长 63 字符 |
| `kind` | `isValidKind` | `[a-zA-Z][a-z0-9A-Z]`，最长 63 字符 |

直接后果：

- **label 装不下 glob**。`src/**/*.java` 含 `/` 和 `*`，两者都不在 `[a-zA-Z0-9-_.]` 里，写进 label 会被 catalog 拒收。而 label 恰恰是官方文档里说「用来过滤实体」的那个字段。
- 目录级作用域只能塞进 annotation（任意字符串）。但 annotation 的过滤能力有另一层限制，见 1.4。
- `tags` 连大写字母都不允许，只能做粗粒度的 `java` / `go` 这种标签。

官方文档在 [Extending the Model](https://backstage.io/docs/features/software-catalog/extending-the-model) 里对 label 的态度也很保守，原文：*"At the time of writing this, the use of labels is very limited and we are still settling together with the community on how to best use them."*

### 1.3 扩展机制的四个档位

同一篇 [Extending the Model](https://backstage.io/docs/features/software-catalog/extending-the-model) 列了七种扩展方式，按代价从低到高实际是四档：

1. **加 annotation / label**：零代码。catalog 对未知 annotation 不做校验，直接存。
2. **往已有 kind 的 `spec` 里加字段**：零代码。文档明说 catalog 接受未知字段不做校验，但同时告警 *"we want to caution against extending the metadata excessively"*，理由是和未来核心模型字段撞名。
3. **自定义 relation 类型**：要写 processor。建议用 `myCompany-` 前缀。
4. **自定义 kind**：最重。要建一个 isomorphic common 包（TS 类型 + JSONSchema），再写一个 backend module 注册 `CatalogProcessor`，实现 `getProcessorName()` / `validateEntityKind()` / `postProcessEntity()`。`apiVersion` 必须用自己的命名空间（如 `my-company.net/v1`）。

文档对自定义 kind 的态度是明确劝退的，而且给了具体理由：

> *"There will be a large number of plugins and processors — and even the core itself — that make assumptions about the shape of the data and import the typescript data type from the `@backstage/catalog-model` package."*

> *"If you want to model something that doesn't feel like a fit for either of the builtin kinds, feel free to reach out to the Backstage maintainers to discuss how to best proceed."*

也就是说：**自定义 kind 在 Backstage 里是可以做的，但它是一条「你自己承担全部生态不兼容后果」的路**。前端 UI 不会认识你的 kind（文档对前端注册只字未提，只说了插件里硬编码的实体形状假设意味着前端也要改），搜索、关系图、ownership 页面都要自己补。

### 1.4 查询接口：能力边界比想象的窄

catalog REST API（[Software Catalog API](https://backstage.io/docs/features/software-catalog/software-catalog-api)）的主力端点是 `/entities/by-query`，GET / POST 都支持。

**GET filter 语法**：点号路径，多个条件逗号分隔为 AND，多个 `filter=` 参数之间为 OR。

```
GET /entities/by-query?filter=kind=component,spec.type=service&filter=kind=api
→ (kind=component AND spec.type=service) OR (kind=api)
```

支持存在性检查（只给 key 不给值）、relation 匹配（`relations.memberof=group:default/ops`）。**全部大小写不敏感**。

**POST 支持的操作符**（比 GET 强）：`$not`、`$all`、`$any`、`$exists`、`$in`、`$hasPrefix`、`$contains`。

没有的东西同样重要：**没有比较操作符**（大于 / 小于）、**没有正则**、**没有 glob 匹配**。`$hasPrefix` 是唯一的模糊匹配，只能做前缀。

**`fullTextFilterTerm` 不是全文检索**。官方描述是 *"case-insensitive substring match"*，且默认只搜排序字段（`orderField`，未设时是 `metadata.uid`），必须显式传 `fullTextFilterFields` 指定搜哪些字段。它和 cursor 分页互斥。

**200 字符上限 —— 这条最关键。** 从 [`buildEntitySearch.ts`](https://github.com/backstage/backstage/blob/master/plugins/catalog-backend/src/database/operations/stitcher/buildEntitySearch.ts) 源码：

```ts
// The maximum length allowed for search values. These columns are indexed, and
// database engines do not like to index on massive values. For example,
// postgres will balk after 8191 byte line sizes.
const MAX_KEY_LENGTH = 200;
const MAX_VALUE_LENGTH = 200;
```

`mapToRows()` 的行为是：值超过 200 字符时，**写入一行 `original_value: null, value: null`** —— 键还在（存在性过滤仍能命中），但值被丢弃，任何按值的过滤都匹配不到。

对我们的直接含义：**规范正文永远无法被 catalog 的 filter 检索到**。一条像样的规范正文一定超过 200 字符。它可以被存（`final_entities` 存完整 JSON），可以被读出来，但不能被查。

**GraphQL**：官方的 `@backstage/plugin-catalog-graphql` 已废弃，官方推荐转向第三方 [`@frontside/backstage-plugin-graphql-backend`](https://www.npmjs.com/package/@frontside/backstage-plugin-graphql-backend)（Frontside 维护）。也就是说 **Backstage 本身没有一等公民的 GraphQL 接口**，要上就是引一个社区插件。

**Backstage Search 是另一套东西**。[Search](https://backstage.io/docs/features/search/) 是独立子系统，靠 collator 把各插件内容索引进搜索引擎。`SearchQuery` 的结构（[`search-common/src/types.ts`](https://github.com/backstage/backstage/blob/master/plugins/search-common/src/types.ts)）是 `{ term, types?, filters?: JsonObject, pageLimit?, pageCursor? }`，`IndexableDocument` 必须有 `title` / `text` / `location`。引擎三选一（[Search Engines](https://backstage.io/docs/features/search/search-engines)）：

- **Lunr**：内存引擎，零配置。官方原话 *"its use is highly discouraged when running Backstage in production"*。
- **Postgres**：社区支持，要 PG 12+，用 PG 全文检索。文档称可处理 *"ten thousands of indexed documents"*。
- **Elasticsearch / OpenSearch**：只确认支持 ES 7.x。

结论：**要做规范正文的语义检索，得额外上 Backstage Search + ES，而这实质上已经是在 Backstage 旁边自建一套检索系统了** —— 只是壳子挂在 Backstage 名下。

**`/entity-facets`**（GET/POST）可以做分面聚合计数，对「某语言下有多少条规范」这类统计有用。

### 1.5 写入模型：catalog 是只读投影，不是数据库

从 [`createRouter.ts`](https://github.com/backstage/backstage/blob/master/plugins/catalog-backend/src/service/createRouter.ts) 枚举全部路由后可以确认一件事：

**没有任何 `POST /entities` 或 `PUT /entities` 路由。实体不能通过 API 直接创建或更新。**

写入路径只有一条：注册 Location（`POST /locations`、`PUT /locations/:id`、`DELETE /locations/:id`），然后由处理循环去拉取、解析、校验、缝合。`DELETE /entities/by-uid/:uid` 存在，但那是清理孤儿记录用的 —— 只要 location 还在产出这个实体，处理循环会把它再建回来。

处理循环的节奏由 `catalog.processingInterval` 控制（[Configuration](https://backstage.io/docs/features/software-catalog/configuration)），文档明说这只是**建议下限**：*"this is only a suggested minimum, and the actual interval may be longer"*。默认值量级是分钟级。

对我们的含义分两面：

- **好的一面**：这天然就是 GitOps。实体的真源是 git 里的 YAML，版本化、归因、回滚全由 git 提供，`backstage.io/managed-by-location` annotation（[Well-known Annotations](https://backstage.io/docs/features/software-catalog/well-known-annotations)）自动记录实体来自哪个文件，可以直接追回去。
- **坏的一面**：**产品内不可能做「在 UI 上编辑一条规范然后立刻生效」**。任何写操作都得绕成「改 git → 等处理循环 → 数据可见」，延迟是分钟级且不可控。对一个要在 review 过程中沉淀规范、要让 owner 点一下就把候选规范转正的产品来说，这是个正面冲突。

### 1.6 存储后端与外部可读性

生产库是 PostgreSQL（[Architecture Overview](https://backstage.io/docs/overview/architecture-overview)，SQLite 只用于开发/测试）。catalog 的表结构在 [`tables.ts`](https://github.com/backstage/backstage/blob/master/plugins/catalog-backend/src/database/tables.ts)：

| 表 | 关键列 | 作用 |
|---|---|---|
| `final_entities` | `entity_id`、`entity_ref`、`final_entity`（完整实体 JSON 字符串）、`hash` | 缝合后的最终实体 |
| `refresh_state` | `entity_ref`、`unprocessed_entity`、`processed_entity`、`cache`、`errors`、`next_update_at` | 处理循环状态 |
| `search` | `entity_id`、`key`、`original_value`、`value` | 扁平化索引（就是那个 200 字符受限的表） |
| `relations` | `source_entity_ref`、`target_entity_ref`、`type` | 关系边 |
| `locations` | `id`、`type`、`target` | 注册的数据源 |

**外部系统确实能直接读**：连 PG，`SELECT final_entity FROM final_entities WHERE entity_ref = ...` 就拿到完整实体 JSON。

但这是**未文档化的内部 schema**。从迁移目录能看出它一直在动 —— 仅 2026 年就有 `20260214000000_search_fk_final_entities`、`20260215000000_move_stitch_queue`、`20260510000000_search_indices_and_dedup`、`20260904000000_fix_search_entity_id_ndistinct` 等多次变更。直接读库等于把自己焊死在一个会变的私有结构上。

### 1.7 规范往哪儿放：三个选项各自的问题

**选项 A：TechDocs。** [TechDocs](https://backstage.io/docs/features/techdocs/) 是 MkDocs 驱动的 docs-like-code：markdown 与代码同仓，通过 `backstage.io/techdocs-ref` annotation（值形如 `dir:.` 或 `url:https://...`）挂到实体上。[架构](https://backstage.io/docs/features/techdocs/architecture)是 generator（mkdocs + techdocs-core）产出静态 HTML，publisher 存到本地盘或 S3/GCS/Azure Blob，backend 按需取回。

问题有三个：

1. **产物是 HTML 不是结构化数据**。TechDocs Reader 还会跑 Transformer 改写 HTML（比如把 JavaScript 全部剥掉）。agent 要用就得反向解析 HTML。
2. **它是「挂在实体上的文档」**，主键仍然是实体。一条跨 20 个服务的 Go 规范，在这个模型里没有自己的位置 —— 要么复制 20 份，要么建一个假实体来挂它。
3. **粒度太粗**。一个 TechDocs 站点是一棵 markdown 树，没有「条目」这个单位。agent 要取「适用于本次 diff 的 7 条规范」，TechDocs 给不了，只能给「整个规范站」。

**选项 B：自定义 kind（如 `Standard`）。** 语义上最对，代价见 1.3 —— 要写 common 包 + backend module + processor，还要自己补前端，且官方明确劝退。而且做完之后，正文仍然受 1.4 的 200 字符检索限制，作用域仍然受 1.2 的 label 格式限制。**付出了自定义 kind 的全部成本，却没有解决最核心的两个问题。**

**选项 C：annotation 挂在 Component 上。** 比如给每个服务加 `mycompany.com/standards: go-error-001,go-log-002`。这个可行、零成本，但它只是把「服务 → 规范 id 列表」存进了 catalog，规范本体还得存在别处。**这条路的真实含义是：Backstage 只当组织结构与服务元数据的来源，规范库另建。** 这一点后面会回来。

### 1.8 接入与维护成本

**Backstage 不是装好就能用的产品，是要你 scaffold 出自己的 app 的框架。** [Architecture Overview](https://backstage.io/docs/overview/architecture-overview) 把它分成 core / app / plugins 三层，app 是「你部署并维护的那个实例」。

- **插件形态**：文档原话，一个典型插件*最多五个包* —— 两个前端包（含一个 `-react`）、两个后端包、一个 isomorphic 包。要做一个既有 UI 又有 API 的规范插件，就是这个量级的双端 TypeScript 工程。
- **升级负担**：[Keeping Backstage Updated](https://backstage.io/docs/getting-started/keeping-backstage-updated) 说主线**每月**发版，next 线每周。`yarn backstage-cli versions:bump` 只升包版本；`@backstage/create-app` 模板本身的演进**要人工比对 changelog 或用 Upgrade Helper 逐版本看 diff 再手动改**。这是一项持续的、不产生业务价值的月度工作量。
- **基础设施**：PostgreSQL 必备；要用像样的 Search 还要加 Elasticsearch；要用 TechDocs 的推荐部署还要加对象存储和 CI 流水线。

对一个团队规模不大、主线是 AI code review 的项目来说，**为了「存规范」引入 Backstage，等于顺带接下一个每月要维护的内部开发者门户**。

## 2. EventCatalog

### 2.1 定位与技术栈

[EventCatalog](https://github.com/event-catalog/eventcatalog) 自述是「为软件架构而生的文档工具」，核心包 `@eventcatalog/core` 基于 **Astro + React**。[介绍页](https://www.eventcatalog.dev/docs/development/getting-started/introduction)列的建模对象是：domains、systems、services、messages（events / commands / queries）、schemas、data stores、data products、entities、flows、ADR、agents、teams、users。

它同时支持静态构建（Static Mode）和 SSR（Server Mode）。内容以 markdown / MDX + frontmatter 编写，**文件系统就是数据库**。

值得注意：EventCatalog 这两年扩得很快，早就不只是「事件文档」了 —— ADR 和 AI agent 都已经是一等资源类型。所以「它只管事件」这个直觉是过期的，得按现状评估。

### 2.2 许可证结构 —— 这是本节的决定性事实

[LICENSE](https://github.com/event-catalog/eventcatalog/blob/main/LICENSE) 是混合授权：大部分 MIT，但两个目录走 EventCatalog 商业许可：

- `packages/core/eventcatalog/src/enterprise/`
- `packages/core/src/federation/`

`enterprise/` 目录下实际有什么（GitHub Contents API 列出）：

```
ai/  analytics/  api/  auth/  collections/  custom-documentation/
custom-pages/  directory/  fields/  integrations/  mcp/  tools/  visualizer-layout/
```

该目录 [README](https://github.com/event-catalog/eventcatalog/blob/main/packages/core/eventcatalog/src/enterprise/README.md) 原文：

> *"Usage of files in this directory and its subdirectories, and of EventCatalog Plugin / Enterprise features, is subject to the EventCatalog Commercial License, and conditional on having the right license from EventCatalog. Access to files in this directory and its subdirectories does not constitute permission to use this code or EventCatalog Enterprise Edition features."*

对照[定价页](https://www.eventcatalog.dev/pricing)：Community 免费，Business（Scale）**$449/月**（年付）起，上限 250 人；Enterprise 另议。被 Business 档锁住的功能里，**恰好包含我们这个用途需要的全部四样**：

| 我们需要的 | 在哪个档 |
|---|---|
| 自定义文档（custom documentation） | Business |
| 自定义页面 / API 路由 | Business |
| MCP server | Business |
| AI Assistant / BYOK | Business |

Community 档能用的 LLM 相关能力只有「LLM optimizations」和「Schemas for LLMs」—— 即自动生成的 `.txt` 摘要文件（`/docs/llm/llms-full.txt` 之类的全量 feed）。**全量 feed 恰恰就是 ticket 里要避免的「整包塞进上下文」。**

一句话：**在 EventCatalog 里放编码规范，唯一合适的载体（custom docs）和唯一合适的检索接口（MCP）都在付费墙后面。**

### 2.3 custom docs 的 schema：能表达的东西非常少

这是我认为最有说服力的一手证据。custom docs 的 frontmatter schema 就在 [`enterprise/custom-documentation/collection.ts`](https://github.com/event-catalog/eventcatalog/blob/main/packages/core/eventcatalog/src/enterprise/custom-documentation/collection.ts)，全文如下：

```ts
export const customPagesSchema = z.object({
  title: z.string(),
  summary: z.string(),
  slug: z.string().optional(),
  sidebar: z.object({ label: z.string(), order: z.number() }).optional(),
  owners: z.array(ownerReference).optional(),
  badges: z.array(badge).optional(),
});
```

六个字段。**没有 `version`、没有状态字段、没有任何作用域字段、连 `tags` 都没有。** 归属只有 `owners`。

也就是说：EventCatalog 里那些丰富的能力（版本化、deprecated 标记、owner 关系、可视化）**都长在 service / message / domain 这些「架构资源」上，而不在 custom docs 上**。规范要蹭到那些能力，就得被硬塞成一个「服务」或「消息」，那是纯粹的语义扭曲。

作为对比，[Service 的 frontmatter](https://www.eventcatalog.dev/docs/api/service-api) 有 `id` / `name` / `version` / `summary` / `owners` / `sends` / `receives` / `entities` / `writesTo` / `readsFrom` / `specifications` / `repository`（含 `language`）/ `badges` / `attachments` 等等，并且官方文档明说支持 **`x-` 前缀的自定义字段**扩展。这套 schema 是为「服务」量身定制的，字段名本身就带着事件驱动架构的语义。

### 2.4 检索接口

**SDK（`@eventcatalog/sdk`，MIT）** 提供 `getEvent()` / `getService()` / `writeEvent()` / `writeService()` / `versionEvent()` 等读写函数，**直接操作磁盘上的 markdown 文件**，不走服务端。这对程序化生成规范文件是够用的，但它是构建期工具，不是运行期查询接口。

**custom pages / API routes**（付费）基于 Astro endpoint：`pages/api/services.ts` → `/custom/api/services`，通过 `@catalog/utils` 别名导入 `getServices` / `getDomains` / `getEvents` 等 helper（[参考文档](https://www.eventcatalog.dev/docs/development/customization/custom-pages-and-api-routes/reference)）。**生产环境要求 `output: 'server'`**，静态构建带 API 路由会直接失败。

**MCP server**（付费，[文档](https://www.eventcatalog.dev/docs/development/ask-your-architecture/mcp-server/introduction)明确标注 *"This feature requires an EventCatalog Scale license"*）。从源码 [`mcp-server.ts`](https://github.com/event-catalog/eventcatalog/blob/main/packages/core/eventcatalog/src/enterprise/mcp/mcp-server.ts) 能读到注册的工具名：`getResources`、`getResource`、`getMessagesProducedOrConsumedByResource`、`getSchemaForResource`、`findResourcesByOwner`、`getProducersOfMessage`、`getConsumersOfMessage`、`getC4Diagram`、`analyzeChangeImpact`、`explainBusinessFlow`、`getTeams`、`getUsers`、`findMessageBySchemaId`、`explainUbiquitousLanguageTerms`，以及和我们相关的三个：

```ts
server.registerTool('getCustomDocs', {
  inputSchema: z.object({
    cursor: z.string().optional(),
    search: z.string().optional()   // 按 title / id / summary 过滤，大小写不敏感
  })});

server.registerTool('searchCustomDocs', {
  inputSchema: z.object({
    query: z.string(),              // 全文检索
    limit: z.number().optional()    // 默认 10
  })});

server.registerTool('getCustomDoc', {
  inputSchema: z.object({
    id: z.string(),
    section: z.string().optional()  // 只取某个小节
  })});
```

**这个检索面其实设计得不错** —— 全文检索 + 按 id 取 + 按小节取，正是「按需检索而非整包塞入」想要的形状。但有三个硬约束：

1. 付费。
2. 源码里这三个工具包在 `if (!scope) { ... }` 里 —— **scoped MCP 连接（按 domain / system 限定的那种）不暴露 custom docs**。
3. 检索维度只有全文，**没有按语言 / 仓库 / 目录 / 状态过滤的入口**，因为 schema 里压根没有这些字段（见 2.3）。

### 2.5 版本化

EventCatalog 的版本化是[目录约定](https://www.eventcatalog.dev/docs/development/guides/domains/versioning)：在资源目录下建 `versioned/<版本号>/index.mdx`，把旧版整份挪进去，再把根目录 `index.mdx` 的 `version` 字段升上去。版本号支持 semver，引用时可用 `^1.0.0` / `~1.2.0` / `0.0.x` / `latest` 这类范围。

这是**快照式版本化**：历史版本是整份文件的副本。谁改的、为什么改，仍然只能靠 git。而且如 2.3 所述，**custom docs 的 schema 里根本没有 `version` 字段**，这套版本化机制对规范用不上。

### 2.6 小结

EventCatalog 对「编码规范」是**硬套**。理由不是「它只管事件」（这个说法已经过时），而是三条更具体的：

1. 它的能力（版本、状态、关系、可视化）长在架构资源上，规范够不着；唯一够得着的 custom docs 只有 6 个字段。
2. 唯一像样的 agent 检索接口（MCP）和唯一合适的内容载体（custom docs）都要 $449/月起。
3. 就算付了钱，检索维度仍然只有全文，表达不了我们最需要的多维作用域。

## 3. 相邻方案：整个生态是怎么理解「规范」的

这一节回答 ticket 的加分项，也顺带给出一个比前两节更有信息量的结论。

### 3.1 Backstage Tech Insights：官方给出的答案，以及它揭示的东西

[Tech Insights](https://github.com/backstage/community-plugins/blob/main/workspaces/tech-insights/plugins/tech-insights-backend/README.md)（现位于 `backstage/community-plugins` 的 `workspaces/tech-insights`）是 Backstage 生态里**最接近「工程标准」的官方答案**。它的模型：

| 概念 | 形状 |
|---|---|
| `FactRetriever` | `id` + `version`（semver）+ `schema` + 异步 `handler` + 可选 **`entityFilter`**（限定作用于哪些 kind / type） |
| Fact | `{ entity: {namespace, kind, name}, facts: {factName: value}, timestamp }` |
| `Check` | `type`（如 `json-rules-engine`）+ `name` + `description` + `factIds` + `rule`（**纯布尔条件**） |
| `CheckResult` | 某 check 对某实体的 pass / fail |

Check **可以在 `app-config.yaml` 里声明式定义**（[jsonfc 模块](https://github.com/backstage/community-plugins/blob/main/workspaces/tech-insights/plugins/tech-insights-backend-module-jsonfc/README.md)，底层是 json-rules-engine）：

```yaml
checks:
  groupOwnerCheck:
    type: json-rules-engine
    name: Group Owner Check
    factIds: [entityOwnershipFactRetriever]
    rule:
      conditions:
        all:
          - fact: hasGroupOwner
            operator: equal
            value: true
```

事实采集按 cron 调度（如 `cadence: '*/15 * * * *'`），带 `lifecycle`（TTL 或 maxItems）做保留期管理。

REST 端点（源码 [`router.ts`](https://github.com/backstage/community-plugins/blob/main/workspaces/tech-insights/plugins/tech-insights-backend/src/service/router.ts) 确认）：

```
GET  /checks                                  取全部 check 定义
POST /checks/run/:namespace/:kind/:name       单实体运行
POST /checks/run                              批量运行
GET  /fact-schemas
GET  /facts/latest
GET  /facts/range
```

**这套模型对它自己的用途是好的，而且 `entityFilter` 确实提供了一层作用域。但它建模的是「对实体做布尔断言」，不是「规范条目」。** 一条 check 里没有正文、没有状态机、没有版本历史、没有「为什么有这条规则」。规范在这个模型里的存在方式是：被拆解成一组可执行的布尔判断，规范原文则消失了（最多塞进 `description`）。

社区的 `tech-insights-maturity` 插件补了 `category` / `rank`（Bronze-Silver-Gold）/ `solution` 字段做软性归类，仍然不是强类型的规范模型。

补充：`community-plugins` 仓库里**没有独立的 scorecard workspace**（拉全量 `workspaces/` 目录核实过，111 个 workspace 里只有 `adr` 和 `tech-insights` 沾边）。Red Hat Developer Hub 在 2025-11（1.8 版）推出了官方 Scorecard 插件（Tech Preview，在 `redhat-developer/rhdh-plugins`），聚焦 KPI 指标而非布尔 check（[发布说明](https://developers.redhat.com/blog/2025/11/12/whats-new-red-hat-developer-hub-18)）。

### 3.2 Backstage ADR 插件：「挂一个 markdown 目录」的标准做法

[ADR 插件](https://github.com/backstage/community-plugins/tree/main/workspaces/adr)（`adr` / `adr-backend` / `adr-common` / `search-backend-module-adr`）的做法值得记一笔，因为它就是「把一堆 markdown 放进 Backstage」的官方范式：

给实体加 `backstage.io/adr-location` annotation，值是相对 `catalog-info.yaml` 的路径或绝对 URL，指向一个存放 ADR markdown 的目录；前端加一个 `EntityAdrContent` tab；`search-backend-module-adr` 负责把这些 markdown 索引进 Backstage Search。

注意这个形状：**annotation 指向目录 + 独立的 search collator 做检索 + 前端 tab 做展示，四个包**。这正是 1.7 选项 A 和 1.4 结尾推演出的那条路的实物。它也再次确认了同一件事 —— **内容仍然锚定在实体上**（annotation 长在 Component 上），一份跨 20 个仓库的文档在这个模型里没有自己的位置。

### 3.3 公开案例：一个明确的否定结论

**没有找到任何公开案例，把「编码规范」作为结构化条目（自定义 kind 或一等实体）放进 Backstage 或 EventCatalog。**

找到的真实案例全部是同一种形态 —— 把规范**拆解成一组独立的布尔 check**：

- Paddle：2024 年从自托管 Backstage 迁到 Roadie 后，用 Tech Insights 建 check（[案例](https://roadie.io/case-studies/from-self-hosted-backstage-to-roadie/)）
- Uplight：用 Tech Insights 建了 10 个软件标准类别的布尔 check（[案例](https://roadie.io/case-studies/improving-software-standards-with-roadie/)）
- Dexcom：用它做 catalog 完整性检查（[案例](https://roadie.io/case-studies/dexcom-automating-catalog-completeness-backstage/)）

Spotify 的 **Soundcheck**（商业插件）数据模型是 `Check` / `Track` / `Level` / `Certification`，比开源 Tech Insights 多一层分级结构，但本质仍是「标准 = 一组 Check」。**Soundcheck 作为独立付费产品存在这件事本身就是个信号：Backstage 原生 catalog 不足以表达工程标准，需要在它之上单独加一层。**

否定结论的搜索边界（据实说明）：backstage.io 官方博客与 ADOPTERS.md、Roadie 全部公开案例研究、community-plugins 相关 README、多组关键词的 Web 搜索（"coding standards" / "engineering standards" / "golden path" + Backstage）。**未做穷尽式搜索**，不排除有未被搜索引擎收录的内部工程博客。EventCatalog 侧同样未找到非「事件 / 服务 / 消息」领域的用例。

### 3.4 这个否定结论说明了什么

整个生态在「工程标准」这件事上收敛到了同一个建模选择：

> **标准 = 一组对实体的可执行布尔断言（check）。**

这个选择在它的语境里是对的 —— IDP 关心的是「合规度记分卡」：这个服务有没有 owner、有没有 README、测试覆盖率够不够。这些都能自动测量，答案是 yes/no。

但我们的语境不同。uReview 的规范里，**可自动判定的只是一小部分**，大量条目是「错误信息不要暴露内部实现细节」「新增公开接口要考虑向后兼容」这类需要 LLM 读代码做判断的自然语言规则。对这部分，check 模型无处安放正文，而正文恰恰是 agent 要消费的东西。

**一个有用的推论**：我们的规范其实是**两类东西**，不该用同一个模型：

| | 可执行规范 | 判断型规范 |
|---|---|---|
| 例子 | 「不许用 `panic` 做流程控制」 | 「错误信息不要暴露内部实现细节」 |
| 判定者 | linter / semgrep | LLM |
| 合适的模型 | **Tech Insights / semgrep 那一套是对的** —— 规则即代码，结果是布尔 | 条目模型 —— 正文 + 作用域 + 状态 |
| 存在哪 | 规则文件进 git，跟着 CI 跑 | 规范库 |

这一点应该反馈给 [规范的表达形式与可执行性谱系](09-规范表达形式谱系.md) 和 [规范的领域模型与生命周期](../../.agents/notes/proposed/architecture/2026-09-12-rule-domain-model.md)：规范模型里需要一个「可执行性」维度，可执行的那部分挂到外部引擎（`rule_check` 表），不可执行的那部分才是规范库的主体。

### 3.5 真正对味的先例不在 IDP 领域，在 AI 编码工具和 linter 里

把视线从开发者门户挪开之后，会发现「带作用域的规则条目 + 按需加载」这个问题**已经被解过，而且解法高度收敛**。

**Cursor 的 `.cursor/rules/*.mdc`**（[官方文档](https://cursor.com/docs/context/rules)）—— 这是和我们需求最贴近的一个先例。三个 frontmatter 字段：`description`、`globs`、`alwaysApply`。四种加载模式由这三个字段的组合决定：

| 类型 | 配置 | **何时进上下文** |
|---|---|---|
| Always Apply | `alwaysApply: true` | 每次会话都带上 |
| Apply Intelligently | 有 `description`，无 `globs` | **agent 读 description 自行判断是否相关** |
| Apply to Specific Files | 有 `globs` | **上下文里出现匹配文件时自动挂载** |
| Apply Manually | 三者皆无 | 只有 `@rule-name` 显式引用时 |

glob 语法是标准的：`*` 匹配单段，`**` 递归，多个模式逗号分隔（`docs/**/*.md, docs/**/*.mdx`）。规则文件可以按目录嵌套，**更具体的指令优先**。

这套设计几乎是逐条命中我们的需求：`globs` 就是路径作用域，`alwaysApply` 就是全局层，「更具体的优先」就是冲突消解策略，而 Apply Intelligently 那一档**正是 ticket 要的「按需检索而非整包塞入」的语义** —— 先给 agent 一份轻量的 description 清单，让它自己决定拉哪几条正文。这比「先检索再塞」多了一层，值得直接照抄。

**Claude Code 的 `.claude/rules/*.md`** 是同构机制，而且把道理说得更直白。它支持 `paths:` frontmatter，[官方文档](https://code.claude.com/docs/en/memory)原文：*"they only load into context when Claude works with matching files, reducing noise and saving context space"*。文档还特意区分了两种引入方式：`@path` import 在启动时全量展开（**不省上下文**），`paths:` 才是真正的按需触发。这个区分正是我们要的那条线。

**这两个先例的共同缺口**（推断）：都没有团队维度（只能靠仓库的物理归属间接表达）、没有状态机（存在即生效，二元）、没有版本化字段（依赖外部 git 历史）。语言 / 框架维度也是靠文件扩展名和路径规约间接表达，不是一等字段。**这三块业界没有现成先例，是我们必须自建的部分** —— 也正好是 uReview 相对通用规则文件的增量价值所在。

**Semgrep rule 的 YAML schema**（[官方文档](https://docs.semgrep.dev/writing-rules/rule-syntax)，权威 schema 在 [`rule_schema_v1.yaml`](https://github.com/semgrep/semgrep-interfaces/blob/main/rule_schema_v1.yaml)）—— 可执行规范那一侧的范例：

| 字段 | 必填 | 对应我们的 |
|---|---|---|
| `id` | 是 | 稳定标识 |
| `message` | 是 | **规范正文**（为什么匹配、怎么改） |
| `severity` | 是 | `LOW` / `MEDIUM` / `HIGH` / `CRITICAL`（旧的 `ERROR`/`WARNING`/`INFO` 向后映射） |
| `languages` | 是 | **语言作用域** |
| `paths.include` / `paths.exclude` | 否 | **路径作用域，glob 语法**（`*.py`、`/src/tests`、`**/backend/*_test.go`） |
| `metadata` | 否 | **自由形式，可加任意自定义键** |
| `category` | 否 | 分类（如 `best-practice`） |

补充两个细节：`languages` 除了 40 多种编程语言，还有 `generic` / `regex` / `none` 三个特殊模式（`generic` 可匹配任意文本文件）；`paths` 的 glob 带前导 `/` 时锚定项目根，官方示例：

```yaml
paths:
  exclude: ["*.jinja2", "**/backend/*_test.go", "/src/tests"]
  include: ["*_test.go", "/app/server"]
```

`metadata` 官方定义是 *"Arbitrary structured data for your own reference"*，核心引擎不做子 schema 约束，可以自由塞自定义键（Registry 投稿有一层社区 lint schema 要求 `category` / `technology` / `references`，但那是投稿门槛不是引擎强制）。

**Semgrep 的边界**：pattern 类字段（`pattern` / `patterns` / `pattern-either` / `pattern-regex`）**至少要有一个，不能整体省略**。所以它能覆盖「存储与筛选」，覆盖不了纯自然语言条目的「检测」—— 拿它当规范库存不可执行条目是走不通的。

把 Semgrep 的 `id + message + severity + languages + paths + metadata` 和第 4.1 节我提的表放在一起看，会发现**形状几乎一样**。差的只有 `status`（状态机）和 `version`（版本历史）—— 而这两样 Semgrep 不需要，因为它的规则是代码，状态和版本由 git 和 CI 配置管。

**这个收敛本身是个有力的旁证**：当一个工具真的要表达「带适用条件的规则条目」时，它长出来的 schema 就是「id + 正文 + severity + 语言 + 路径 glob + 自由 metadata」。Backstage 和 EventCatalog 长不出这个形状，不是因为它们做得差，而是因为它们要解的不是这个问题。

### 3.6 OPA / Rego：METADATA 可以单独用，但那就不是在用 OPA 了

OPA 的 [METADATA 注解块](https://www.openpolicyagent.org/docs/policy-language)（写在 Rego 文件里的 `# METADATA` YAML 注释）官方字段：`scope`（rule / document / package / subpackages）、`labels`、`title`、`description`、`related_resources`、`authors`、`organizations`、`schemas`、`entrypoint`、`compile`、`custom`。其中 `custom` 的官方定义是 *"a mapping of user-defined data, mapping string keys to arbitrarily typed values"* —— 可以塞任意嵌套结构。

本次调研用官方 opa v1.20.2 二进制**实测验证**了一件有意思的事：写一个只有 `package` 声明 + METADATA、**零条 rule** 的 `.rego` 文件，`opa check` 能通过；[`opa inspect`](https://www.openpolicyagent.org/docs/cli) 加 `-a -f json` 能把注解完整导出成结构化 JSON，还带精确到行号的 `location`：

```json
"annotations": [{
  "annotations": {
    "description": "...",
    "custom": {"applies_to": ["*.go","*.py"], "scope": "global",
               "severity": "high", "status": "active"},
    "scope": "package", "title": "..."
  },
  "location": {"file": "rule_no_leak.rego", "row": 13, "col": 1}
}]
```

所以技术上**可以**把规范写成纯注解的 Rego 文件，用 `opa inspect -a -f json` 当元数据批量导出工具，构建外部检索索引。OPA 的 bundle 机制还自带分发和签名。

**但这条路的性价比很差**：这样做的话，文件里 90% 的内容和 Rego 语言本身无关，只是借用了它的文件格式解析器和 inspect 工具链，完全没用到策略求值引擎 —— 而策略求值引擎正是 OPA 的全部价值。为了一个 JSON 导出器引入 OPA，不如直接写 YAML。

对我们的真实用途：**OPA/Rego 属于「可执行规范」那一侧的候选引擎**（和 Semgrep 并列，各自擅长的输入不同：Rego 擅长结构化配置，Semgrep 擅长源码），不是规范库的候选。

### 3.7 ADR 工具：状态字段像，但语义是反的

[MADR](https://adr.github.io/madr/) 的 frontmatter 只有 5 个字段：`status`、`date`、`decision-makers`、`consulted`、`informed`。

`status` 的[官方模板](https://github.com/adr/madr/blob/main/template/adr-template.md)取值写作 `proposed | rejected | accepted | deprecated | … | superseded by ADR-0123` —— **中间的省略号是官方写的**，说明这是开放字符串而非封闭枚举，没有定义合法迁移路径。它**不是状态机**，只是一个自由标签。而且 `superseded by ADR-0123` 把「终态」和「指向另一条记录的引用」耦合进同一个字符串，不利于程序化解析。

更根本的错配在语义（推断，但有直接佐证）：

- **ADR 是一次性决策记录，不可变、append-only，用新记录 supersede 旧记录。** log4brains 的 README 原文说得很死：*"an ADR is immutable. Only its status can change."*
- **规范条目是持续生效、可就地修订、有多维作用域的。**

硬套的后果：「措辞澄清式的小修」（不改变结论）和「真正的规则反转」会混进同一条 supersede 链，事后无法区分哪次才是实质变更 —— 而这恰恰是「规范演进可追溯」要回答的核心问题。

检索能力也不行：`adr-tools` 的 [`adr list`](https://github.com/npryce/adr-tools/blob/master/src/adr-list) 源码就是 `find | grep | sort`；log4brains 的「按 status 过滤 UI」至今还是个未合并的 PR（#143）。ADR 生态**没有任何工具提供结构化的字段级检索**。

顺带：Backstage 的 ADR 插件（3.2 节）也只是把 ADR markdown 索引进 Backstage Search，没有改变这个语义。

**但 ADR 对我们仍有一个位置**：规范**变更的理由**适合用 ADR 形态记录（「我们为什么在 2026-09 把 Go 错误包装从建议改成强制」），它挂在 `rule_revision.change_reason` 上。ADR 记决策，规范条目记现行规则 —— 两者互补，不是二选一。

### 3.8 商业开发者门户：都不开源

Port、Cortex、OpsLevel 均为闭源 SaaS（官方定价页无自托管社区版）。Roadie 是 Backstage（Apache-2.0）的商业托管版本，不是独立产品 —— 3.3 节那几个案例正是它的客户。

**专门做「工程规范治理」的成熟开源项目是空白领域。** 找到的只有 Mneme、Data Olympus、Repo Rules Agent 等 2025~2026 年的早期小项目，可以参考设计思路，成熟度不足以依赖（未做深入评估）。

这个空白本身值得注意：**如果存在一个显然正确的现成方案，它应该已经存在了。** 它不存在，或者说明这个问题不够普遍（可能），或者说明它太耦合于各家的具体流程而难以通用化（更可能）—— 后者对自建是个支持论据。

## 4. 自建

### 4.1 最小可用的数据模型

把第 0 节的要素直接落成表，不需要多复杂：

```sql
-- 规范条目（当前版本的投影）
rule(
  id            text primary key,      -- 'go-error-wrap-001'，稳定、人可读
  tenant_id     uuid,
  owner_team_id uuid,
  title         text,
  body          text,                  -- markdown 正文，含正反例
  rationale     text,                  -- 为什么有这条（给 agent 判断边界用）
  severity      text,                  -- blocker / major / minor / info
  status        text,                  -- candidate / trial / active / deprecated
  version       int,
  created_at, updated_at
)

-- 作用域：一条规范 N 个作用域断言，断言内 AND，断言间 OR
rule_scope(
  rule_id    text,
  dimension  text,   -- language / framework / repo / path / team / tenant
  operator   text,   -- eq / in / glob / regex
  value      text    -- 'go' | 'internal/**' | 'payment-*'
)

-- 版本历史：append-only
rule_revision(
  rule_id, version, body, status, changed_by, changed_at, change_reason,
  diff_from_prev
)

-- 状态流转与审批
rule_transition(
  rule_id, from_status, to_status, actor, decided_at, note
)

-- 可执行挂载（可选）
rule_check(
  rule_id, engine,   -- semgrep / eslint / custom
  ref                -- 规则文件路径或 id
)
```

### 4.2 最小可用的检索能力

review 时 agent 的查询长这样：「Go 语言、payment-api 仓库、改动路径 `internal/billing/*.go`、团队 X、状态为 active 或 trial 的规范」。

两步就够：

1. **结构化预筛**：按 `language` / `repo` / `team` / `status` 做 SQL 过滤，`path` 维度用 glob 在应用层或 PG 的 `LIKE` / `~` 上匹配。这一步把几百条规范砍到几十条。
2. **语义排序**：对剩下的条目，用 diff 的内容做向量相似度或 BM25 排序，取 top-N 进上下文。PG 自带 `tsvector` 全文检索，向量用 pgvector 扩展，都不需要新组件。

这套东西的工作量是**一张表 + 一个查询函数 + 一个 MCP tool 封装**，不是一个项目。对照之下，Backstage 要达到同样效果，得引 ES、写 collator、写 5 个包的插件，还绕不开 200 字符和 label 格式两道墙。

### 4.3 省下什么、多花什么

**省下的（相比接现成）：**

- 不用为了绕开别人的数据模型而做形状适配，每一个字段都是我们要的语义。
- 不用背 Backstage 的月度升级。
- 不用受 200 字符检索上限、label 63 字符格式、无写 API 这三条约束。
- 规范的写入可以是实时的 —— 这对「review 中沉淀规范」的产品主线是硬需求，Backstage 的 GitOps 模型直接堵死了这条路。

**多花的：**

- **一套 UI**。规范的增删改查、评审、状态流转界面要自己写。这是最大的一块，Backstage 至少白送一个能看的壳。
- **权限模型**。谁能改团队规范、谁能审批转正。Backstage 有现成的 permission framework，自建要从零想。
- **组织结构数据**。团队、人、仓库归属，得有来源。
- **搜索质量**。ES / pgvector 的调优是持续投入。

**一个重要的非零和观察**：上面「多花的」四项里，**权限模型、组织结构、UI 三项，是这个产品本来就要做的**。AI code review 平台必然有自己的租户、团队、仓库、用户模型（见 map 里「核心数据模型」条目），必然有自己的 Web 界面（finding 展示、反馈收集）。规范管理复用这三样，边际成本远低于「从零建一个规范系统」的估计。真正的净新增只有「规范条目的 CRUD 界面」和「检索函数」。

### 4.4 语义错配到底有多大

把「实体目录」和「规范条目」两套语义并排放：

| | 实体目录（Backstage/EventCatalog） | 规范条目（我们） |
|---|---|---|
| 主键是什么 | 一个**存在的东西**（服务、API、团队） | 一条**约束**，本身不对应任何实体 |
| 基数关系 | 一个实体一条记录 | 一条规范适用于 N 个实体，一个实体适用 M 条规范，**多对多** |
| 核心关系 | 拥有 / 依赖 / 从属（结构） | 适用 / 覆盖 / 例外（条件） |
| 正文的地位 | 附属说明，短 | **就是数据本体**，长 |
| 变更语义 | 实体属性变了 | 规则变了，**且历史判定要能解释**（当时按哪版判的） |
| 状态 | `lifecycle`：实验/生产/废弃（描述实体成熟度） | 候选/试运行/生效/废弃（**描述规则的执行力**，要挂审批） |

错配点最尖锐的是**基数**和**正文地位**这两条。实体目录假设「记录 ≈ 实体」，所以 200 字符的索引上限、63 字符的 label、按实体挂文档的 TechDocs 全都成立且合理 —— 对它自己的用途是合理的。我们的记录是「条件 → 长文本」的映射，恰好在它每一条设计假设的反面。

## 5. 三个硬需求横向对比

### 5.1 版本化

| 方案 | 机制 | 能追溯 | 能回滚 | 能归因 | 缺口 |
|---|---|---|---|---|---|
| Backstage | GitOps。实体来自 git 中的 YAML，`backstage.io/managed-by-location` 记录来源文件 | git log | git revert | git blame | **只是 git 的版本化，不是产品的版本化**。查历史要出到 git 去查，API 里拿不到；且这意味着改规范必须走 PR 流程 |
| EventCatalog | `versioned/<ver>/` 目录快照 + `version` frontmatter，支持 semver 范围引用 | 文件副本 | 拷回来 | 靠 git | **custom docs 的 schema 里没有 `version` 字段**，规范用不上这套机制 |
| 自建 | `rule_revision` 表 append-only + `changed_by` / `change_reason` | 直接查 | 写回 | 表里就有 | 要自己写，约一张表的量 |

**「GitOps 算不算天然版本化」的回答**：算，而且质量不低 —— git 的追溯、回滚、归因都是一流的。但它有两个副作用要认：

1. **它把版本化和写入路径绑在一起了**。要 git 的版本化，就得接受「改规范 = 提 PR = 等处理循环」。产品里想做的「owner 在界面上点一下把候选规范转正」，在这个模型下要么变成「机器人自动提 PR」（可行但链路长、延迟分钟级），要么破坏 GitOps 一致性。
2. **git 的历史 API 不友好**。agent 要回答「这条规范上个月是什么样」，得去 clone/调 GitLab API 解析 commit，而不是查一行 SQL。

自建也完全可以选 git 做真源（规范存仓库里的 YAML/markdown），但把**索引和历史投影进自己的库**，两头都拿到 —— 这其实是最实用的折中，后面结论里会提。

### 5.2 作用域

这是三个硬需求里差距最大的一项。

| 方案 | 表达方式 | 能表达 glob 吗 | 冲突怎么解 |
|---|---|---|---|
| Backstage | label（**63 字符、`[a-zA-Z0-9-_.]`，装不下 `/` 和 `*`**）或 annotation（任意字符串，但**超 200 字符不可检索**，且只支持 `eq` / `$in` / `$hasPrefix`，无 glob） | **不能**。只能存成 annotation 字符串，然后**全部拉到客户端自己匹配** | 无机制。要自己写 |
| EventCatalog | custom docs schema 里**没有作用域字段**。service 有 `repository.language`，但那是服务的属性不是规范的适用范围 | 不能 | 无机制 |
| 自建 | `rule_scope` 表，维度 × 操作符 × 值，天然支持 glob / regex | 能 | 自己定：按特异性排序（path > repo > framework > language > team > global），同层冲突走显式 `overrides` 字段 |

Backstage 这条最值得展开。表面上 catalog 有 label 这个「用来过滤」的字段，但：

- label 值的格式校验（`isValidLabelValue`）**排除了路径分隔符和通配符**，这不是配置能放宽的，是 `catalog-model` 里的策略；
- 退而用 annotation，值虽然不限长，但一旦超 200 字符就**在 `search` 表里退化成 null**，`filter` 再也匹配不到；
- 即使值在 200 字符内，filter 也**只有前缀匹配没有 glob**，`internal/**/*.go` 这种模式匹配做不了。

所以在 Backstage 里做路径级作用域，实际路径只能是：把作用域表达式塞进 annotation 或 spec 字段 → **把所有候选规范实体全量拉出来 → 在自己的代码里做匹配**。那 catalog 在这条链路里就只剩「一个会分钟级延迟同步的 YAML 存储」这一个作用了。

冲突消解三家都没有现成机制 —— 这是必须自己定的策略，不构成选型差异。但有个现成的参照：Cursor 对嵌套规则的规定是**「更具体的指令优先」**（3.5 节），Claude Code 的 `.claude/rules` 同理。「按特异性排序」是这个领域已经收敛的默认答案，不必另起炉灶。

另外要注意，**「语言」和「框架」这两个维度在所有现成方案里都不是一等字段** —— Cursor 和 Claude Code 靠文件扩展名和路径规约间接表达，Semgrep 只有 `languages` 没有框架，Backstage 只有 `spec.type` 和 tags。框架维度（gin / spring / react）**需要我们自己从依赖清单或代码特征推断**，这是一块没有先例的工作，应该在领域模型 ticket 里单独讨论。

### 5.3 状态机

| 方案 | 能表达状态吗 | 能表达流转吗 | 能挂审批吗 |
|---|---|---|---|
| Backstage | 能存：`spec.lifecycle` 是自由字符串，或自定义 spec 字段 | **不能**。catalog 没有状态机概念，只存当前值 | **不能**。但因为写入必须走 git，**PR review 天然就是审批** |
| EventCatalog | service/message 有 `deprecated`、`draft` 字段；**custom docs 一个都没有** | 不能 | 不能（同样可退化为 PR review） |
| 自建 | `status` 列 | `rule_transition` 表 + 应用层校验合法迁移 | `rule_transition.actor` + 产品里的审批流 |

Backstage 的「PR 即审批」值得认真对待 —— 它免费提供了一个成熟的、大家都熟的审批界面（GitLab MR）。但它只能表达「这次变更被批准了」，表达不了「这条规范现在处于试运行，试运行期两周，期间只记录不拦截，到期自动提醒 owner 决定转正还是废弃」这种**和状态绑定的行为差异**。而试运行态恰恰是我们这个产品抑制噪声的关键手段之一。

## 6. agent 按需检索：各方案的接口够不够用

ticket 明确要求「按需检索而不是整包塞进上下文」。逐个对：

| 方案 | 接口 | 按需检索能力 | 判定 |
|---|---|---|---|
| Backstage catalog API | `GET/POST /entities/by-query` | 能按 kind、annotation、label 精确过滤和分页；**不能按正文语义检索**（200 字符墙）；不能 glob | **不够**。能取「哪些规范 id 适用」，取不出「和这段 diff 相关的规范」 |
| Backstage Search | `SearchQuery{term, types, filters}` + ES | 能做正文检索，`filters` 是 `JsonObject` 可带过滤 | 够，**但这等于在 Backstage 里自建一套检索系统**，还要写 collator 把规范索引进去 |
| EventCatalog Community | `llms-full.txt` 全量 feed + `.md` 原文端点 | **只有整包** | **不够**，正好是要避免的形态 |
| EventCatalog Business | MCP `searchCustomDocs` / `getCustomDoc(id, section)` | 全文检索 + 小节级取回，形状对 | 形状够用，但付费、且无作用域维度 |
| 自建 | 自己的 MCP tool | 结构化预筛 + 语义排序，两段式 | 够，且**可以为 review 场景定制**（比如按 diff 的文件扩展名自动推断 language 维度） |

有一个容易被忽略的点：**不管选谁，最后 agent 用的都是一个自己写的 MCP tool 或函数调用。** 差别只在这个 tool 背后是查自己的 PG，还是去调 Backstage 的 REST API 再在本地做 glob 匹配和排序。后者多一次网络往返、多一层数据模型翻译、少一半查询表达力。这让「接现成方案能省下 agent 侧集成工作」这个预期基本落空 —— agent 侧的工作量是差不多的。

## 8. 倾向性结论

**倾向：规范库自建，但不要自建「一个知识库系统」，而是在 uReview 自己的数据模型里加一张规范表；真源放 git，索引和状态投影进自己的库。**

理由按权重排：

1. **最硬的两条约束都卡在现成方案的设计假设上，绕不过去。** Backstage 的 `MAX_VALUE_LENGTH = 200` 和 `isValidLabelValue` 的 63 字符标识符格式，不是配置项，是 `catalog-model` 里的策略代码。而「长正文要能检索」和「路径作用域要能 glob」恰恰是规范这个领域最核心的两个需求。EventCatalog 那边，custom docs 六个字段的 schema 同样是硬编码。**这不是「需要多写点代码」的问题，是数据模型方向相反。**

2. **接现成方案省不下预期的那部分工作。** 直觉上接 Backstage 能省「存储 + UI + API」。实际上：作用域匹配要在客户端做，正文检索要另上 ES + 写 collator，前端要为自定义 kind 补页面，agent 侧的 MCP tool 一样要自己写。省下的主要是「一个能看的实体列表页」，换来的是一个五包插件工程加月度升级维护。

3. **写入路径是产品主线的硬冲突。** 这个产品的三条主线约束之一是「规范冷启动 —— 在使用中把规范持续沉淀出来」。Backstage catalog **没有实体写 API**，唯一写入路径是注册 Location 后等分钟级处理循环。「agent 在 review 中提炼出一条候选规范 → owner 确认 → 立刻生效」这条链路，在 GitOps 模型下只能退化成「机器人提 PR」，延迟和复杂度都不可接受。

4. **边际成本比表面低。** 自建的四项开销里，权限模型、组织结构、Web UI 三项是这个产品本来就要建的（见 map 的「核心数据模型」「权限与 RBAC」）。净新增只有规范 CRUD 界面和检索函数。

5. **生态给出的是否定答案，而且是一致的否定。** 找不到任何公开案例把编码规范作为结构化条目放进 Backstage 或 EventCatalog（3.3）；整个 IDP 生态对「工程标准」的建模选择收敛到「一组可执行布尔 check」（3.4）；而真正对味的 schema 出现在 Cursor 规则文件和 Semgrep 规则里，不在知识库产品里（3.5）；专门做规范治理的成熟开源项目是空白（3.8）。**当四个方向的证据都指向同一个结论时，它比任何单条技术论据都更可信。**

**一个必须同时做出的配套决策：规范要分两类，别用同一个模型。**

3.4 节推出的这一点，会直接影响 [09 表达形式](09-规范表达形式谱系.md) 和 [11 领域模型](../../.agents/notes/proposed/architecture/2026-09-12-rule-domain-model.md)：

- **可执行规范**（「不许用 `panic` 做流程控制」）→ 规则即代码，交给 semgrep / linter，结果是布尔。Tech Insights 和 Semgrep 的模型在这一侧是对的，不必自己发明。规范库里只留一条 `rule_check` 引用。
- **判断型规范**（「错误信息不要暴露内部实现细节」）→ 正文 + 作用域 + 状态，由 LLM 读代码判断。**这一侧才是规范库的主体，也是自建的理由所在。**

如果不做这个切分，会犯两个方向的错：要么用 check 模型去装自然语言（正文无处安放），要么用规范库去装本该跑 CI 的东西（白白让 LLM 做 linter 的活，既贵又不准）。

**但要吸收现成方案已经证明对的东西**，别从零发明：

- **真源放 git，版本化直接复用 GitOps。** 规范以 YAML/markdown 存在仓库里（可以就在被管理的仓库里，像 `catalog-info.yaml` 那样就近放置），由同步器摄入到 PG 做索引和查询投影。追溯、回滚、归因由 git 提供，查询性能和表达力由自己的库提供。这是 Backstage 最值得抄的一条设计。**代价要认**：这会让「UI 上点一下改规范」变成「机器人提 PR」，和第 3 条理由存在张力 —— 折中做法是双写：候选态规范先落库（低门槛、快沉淀），转正时才生成 PR 落 git（有审批、有归因）。状态机正好卡在这个分界上。
- **`backstage.io/managed-by-location` 的思路**：每条规范记住自己来自哪个文件的哪一行，让「这条规则哪来的」永远可追。
- **EventCatalog MCP 的 tool 形状值得直接借鉴**：`search(query, limit)` + `get(id, section?)` 这组签名，尤其是 `section` 参数 —— 按小节取回而不是整篇返回，正是控制上下文预算的正确粒度。
- **Cursor `.mdc` 的 `globs` + 四种加载模式，以及 Claude Code `.claude/rules` 的 `paths:`**（3.5 节）是「按路径作用域 + 按需加载」目前最成熟的公开先例，作用域字段和加载语义可以直接对齐。
- **Semgrep 的 `id + message + severity + languages + paths + metadata`**（3.5 节）几乎就是我们要的 schema，照抄字段命名能省掉一轮设计。

**Backstage 仍然可能有两个角色，但都不是装规范。**

1. **组织结构与服务元数据来源。** 如果公司已经在跑 Backstage，它能提供团队、人、仓库归属、服务的语言与框架 —— 这些正是我们作用域匹配的输入。用法是 uReview 定期从 catalog API 拉 `Group` / `User` / `Component`，填充自己的作用域维度取值。**消费它的实体目录，而不是把规范塞进去。** 不需要写任何插件，只调 REST API。
2. **可执行规范那一侧的落点。** 如果已有 Backstage，Tech Insights 是「服务级合规记分卡」的现成实现（有没有 owner、有没有 README、覆盖率够不够）。它和 uReview 的规范库是**互补而非竞争**：Tech Insights 管「这个服务达标了吗」，uReview 管「这个 diff 违反了哪条规则」。粒度和时机都不同，可以并存。

**关于 EventCatalog：不建议。** 不是因为它做得不好 —— 它在事件驱动架构文档这件事上做得相当完整。而是因为对「编码规范」这个用途，唯一合适的载体（custom docs，6 个字段）和唯一合适的检索接口（MCP）都在 $449/月的付费墙后，且付费之后仍然表达不了多维作用域和状态机。付了钱也解决不了问题，那就没有付的理由。

### 这只是建议

以上是基于数据模型契合度、检索表达力和接入代价的技术判断。有几个我不掌握的前提可能会翻转结论，需要人来定：

- **公司是否已经在跑 Backstage。** 如果已经有了且有专人维护，那「维护成本」这一维的权重要大幅下调，第 1、2 条理由仍然成立但第 4 条会变弱。
- **是否已有 EventCatalog 商业许可。** 如果已经买了 Business，成本论点消失，但语义错配论点不变。
- **「规范必须由人在 git 里写」是不是一条组织要求。** 如果是，GitOps 的权重会压过实时写入的需求，结论会向「git 为主、库为索引」的纯粹形态偏移。
- **规范条目的预期规模。** 如果最终只有几十条而不是几百上千条，检索能力这一维的差距会缩小，简单方案的吸引力上升。

最终决策留给 grilling ticket。

## 0. 先把问题拆对

题面是「跨仓库的契约不一致」。但这四个字底下其实压着两个完全不同的问题，市面上的工具几乎全都只解前一个：

**问题 A：契约本身变了吗，变得破坏兼容吗？**
输入是两份 schema（旧的和新的），输出是一组违规。这是纯粹的 schema-to-schema 比较，**不需要知道任何消费方的存在**。buf breaking、oasdiff、graphql-inspector diff 全在这一档。

**问题 B：这次变更打到谁了？**
输入是一个变更点（`payment.v1.PaymentService/Charge` 被删了），输出是**一组仓库、文件、行号**。这需要一张覆盖全组织的调用关系图。

两个问题的难度差着一个数量级。A 是本地可判定的：把两份 `.proto` 喂给一个进程就出结果。B 需要「统一的代码视图」——而这正是你说的、polyrepo 下最缺的那个东西。

再往下拆一层，B 其实还能分成两级粒度：

| 粒度 | 问题 | 数据来源 |
|---|---|---|
| B1 **包级** | 哪些仓库依赖了 `payment/v1` 这个生成包？ | 构建系统的依赖清单（go.mod / pom.xml / package.json）、proto import 图 |
| B2 **调用点级** | 哪一行代码调了 `Charge`？ | 符号解析 或 文本检索 |

**这个拆分是本文的主轴**：B1 廉价到几乎白送，B2 昂贵；但 B2 只要先被 B1 筛过，成本会塌掉一个量级。后面第 11 节的方案建议全部建立在这条上。

还有一个容易被忽略的判据，先摆在这里，第 1 节会用一手证据砸实它：

> **「契约破坏兼容」和「调用方会挂」不是同一件事，而且前者是后者的真子集之外还漏掉了最要命的一类。** 删掉一个 RPC 方法，在 wire 层面完全不是破坏性变更（旧客户端发过去只会拿到 `UNIMPLEMENTED`），所以按 wire 档跑的 breaking 检测**会放行**。而这恰恰是「改了 proto 没改调用方」最典型的形态。

## 1. Protobuf / gRPC 侧

### 1.1 buf breaking 的四档规则集：到底判什么

buf 把 breaking 规则分成四档，官方描述（[Breaking change detection overview](https://buf.build/docs/breaking/)）：

| 档 | 官方定义 | 保护对象 |
|---|---|---|
| `FILE`（默认） | "Detects breakage to generated source code on a per-file basis. Important for languages with file-specific generated imports like C++ or Python." | 生成代码，按文件 |
| `PACKAGE` | "Detects breakage to generated source code on a per-package basis. More lenient than `FILE` because moving a definition between files in the same package doesn't break consumers that import the package as a whole." | 生成代码，按包 |
| `WIRE_JSON` | "Detects breakage to the binary wire format or JSON encoding." | 编码 |
| `WIRE` | "Detects breakage to the binary wire format only." | 编码 |

关系是严格包含：官方原话 "Passing a stricter category implies passing every looser one: schemas that pass `FILE` also pass `PACKAGE`, `WIRE_JSON`, and `WIRE`."（[同页](https://buf.build/docs/breaking/)）

`FILE` 是 `buf.yaml` 里 `breaking.use` 缺省时的默认值。另一处官方文档把 `WIRE_JSON` 称作 "the recommended minimum level"，理由是 JSON 编码在很多 transport 上都会用到（[Rules and categories](https://buf.build/docs/breaking/rules/)）。

**最关键的一条事实，是从源码里核出来的，不是从文档。** 规则到档位的映射写在 [`private/bufpkg/bufcheck/bufcheckserver/bufcheckserver.go`](https://github.com/bufbuild/buf/blob/main/private/bufpkg/bufcheck/bufcheckserver/bufcheckserver.go)：

```go
bufcheckserverbuild.BreakingServiceNoDeleteRuleSpecBuilder.Build(true, []string{"FILE"}),
bufcheckserverbuild.BreakingRPCNoDeleteRuleSpecBuilder.Build(true, []string{"FILE", "PACKAGE"}),
bufcheckserverbuild.BreakingPackageServiceNoDeleteRuleSpecBuilder.Build(false, []string{"PACKAGE"}),
```

读出来是：

- **`RPC_NO_DELETE` 只在 `FILE` 和 `PACKAGE` 两档里，`WIRE` 和 `WIRE_JSON` 都没有。**
- **`SERVICE_NO_DELETE` 更极端，只在 `FILE` 这一档里。**

也就是说：**如果你听了官方那句「WIRE_JSON 是推荐最低档」，那么删掉整个 service、删掉任意 RPC 方法，`buf breaking` 全部放行。** 这两件事在 wire 层面确实不破坏编码——旧客户端把请求发出去，服务端返回 `UNIMPLEMENTED`，是个运行时故障，不是反序列化故障。但对「改了 proto 没改调用方」这个具体命题来说，它就是最常见的那一种。

**这条直接产出一个可执行的配置决策：这个场景下必须跑 `FILE` 档（或至少 `PACKAGE`），不能听「WIRE_JSON 起步」的通用建议。** 通用建议服务的是「我要保证历史数据能解开」，我们要的是「我要保证调用方能编译并能跑通」，目标不同。

完整的规则-档位对照表（[Rules and categories](https://buf.build/docs/breaking/rules/)），挑几组说明分档逻辑：

| 规则 | FILE | PACKAGE | WIRE_JSON | WIRE | 读法 |
|---|:--:|:--:|:--:|:--:|---|
| `FILE_NO_DELETE` | ✓ | | | | 删文件只碎「按文件 import」的语言 |
| `MESSAGE_NO_DELETE` | ✓ | | | | 同上 |
| `SERVICE_NO_DELETE` | ✓ | | | | **删 service 只在最严档被拦** |
| `RPC_NO_DELETE` | ✓ | ✓ | | | **删方法在 wire 档被放行** |
| `FIELD_NO_DELETE` | ✓ | ✓ | | | 删字段 |
| `FIELD_NO_DELETE_UNLESS_NUMBER_RESERVED` | | | ✓ | ✓ | wire 档只要求 reserve 编号 |
| `FIELD_SAME_TYPE` | ✓ | ✓ | | | 严格同类型 |
| `FIELD_WIRE_COMPATIBLE_TYPE` | | | | ✓ | wire 档允许 `int32`→`int64` 这类兼容变换 |
| `FIELD_SAME_NAME` | ✓ | ✓ | ✓ | | 改名不碎 wire，但碎 JSON |
| `RPC_SAME_REQUEST_TYPE` | ✓ | ✓ | ✓ | ✓ | 换请求类型四档全拦 |
| `FILE_SAME_GO_PACKAGE` | ✓ | ✓ | | | 改 `go_package` 只影响生成代码 |
| `PACKAGE_SERVICE_NO_DELETE` | | ✓ | | | PACKAGE 档用「包内还在不在」替代「文件内还在不在」 |

分档逻辑一句话概括：**`FILE`/`PACKAGE` 保护的是「调用方能不能编译」，`WIRE`/`WIRE_JSON` 保护的是「历史字节能不能解开」。** 跨仓库契约一致性关心的是前者。

顺带一个佐证：protobuf 官方的 [Do's and Don'ts](https://protobuf.dev/best-practices/dos-donts/) 通篇只讲字段——不要复用 tag 号、不要改字段类型、删字段要 reserve、不要加 required、不要 repeated 改 scalar——**整篇没有一条关于删除或重命名 RPC 方法与 service 的规定**。protobuf 生态的兼容性纪律几乎全部长在消息的 wire 格式上，服务面（service surface）是个规范真空。这不是 buf 的疏漏，是整个生态的重心就在那儿。

### 1.2 怎么跑在 CI 上，能不能对着远端基线比

**能，而且不需要任何注册表。** buf CLI 的 `--against` 接受的 input 形态见 [Inputs reference](https://buf.build/docs/reference/inputs/)，覆盖 `dir` / `mod`（BSR 模块）/ `git`（本地或远端）/ `tar` / `zip` / `protofile` / `binpb|json|txtpb` image。git input 支持 `branch` / `tag` / `ref` / `depth` / `subdir` / `filter` 参数。

对我们最有用的两条：

```sh
# 对着本地 clone 的 main 分支比（CI 里最常用，零网络依赖）
buf breaking --against '.git#branch=main'

# 对着远端仓库比（自托管 GitLab 同样适用）
buf breaking --against 'https://gitlab.internal/org/repo.git#branch=main'

# 巨型仓库里只取 proto 子目录 + 无 blob 部分克隆
buf build 'https://github.com/envoyproxy/envoy.git#subdir=api,filter=tree:0'
```

`subdir` + `filter=tree:0` 那条对 300 仓库场景很值钱：它让基线获取不必拉全量历史。

官方 GitHub Action 的默认行为也印证了「不需要 BSR」这条。[`bufbuild/buf-action` 的 `action.yml`](https://github.com/bufbuild/buf-action/blob/main/action.yml)：

```yaml
  breaking_against:
    description: |-
      Input to compare against for breaking change detection.
      Defaults to the base branch of the pull request or the commit before the push.
  breaking_against_registry:
    description: |-
      Whether to use the Buf Schema Registry for breaking change detection.
      If true, the `breaking_against` parameter is ignored.
      Defaults to false.
    default: "false"
```

`breaking_against_registry` 默认 `false`，默认基线是 PR 的 base 分支。**官方推荐路径本身就是 git 基线。** GitLab CI 没有官方 action，但 `buf breaking --against '.git#branch=$CI_MERGE_REQUEST_TARGET_BRANCH_NAME'` 是直译，只要 CI 里 clone 深度够（GitLab 默认 `GIT_DEPTH=20`，proto 仓库通常够用，不够就调大或设 `GIT_STRATEGY: clone`）。

**成本结论：`buf breaking` 在 300 仓库上的落地成本接近零。** Apache-2.0，单个静态二进制，`buf` 仓库 2026-09-10 仍有提交、v1.72.0 发布于 2026-07（[bufbuild/buf](https://github.com/bufbuild/buf)）。每个含 proto 的仓库加一段 CI job 就完事，没有中心化组件，没有许可证成本。

### 1.3 Buf Schema Registry：自托管有没有开源方案

**没有。** 这条要说死：

- BSR 的定位是 "a Protobuf-aware registry for Buf modules"（[BSR docs](https://buf.build/docs/bsr/)）。
- 自托管只在 **Enterprise** 档，官方定价页（[buf.build/pricing](https://buf.build/pricing)）写的是 "Self hosted, on-prem deployments available" 属于 Enterprise 特性，**Custom pricing，需要联系销售**。
- 没有开源的 BSR 服务端实现。buf CLI 是 Apache-2.0，注册表服务端不是。

定价本身也值得摆出来，因为它决定了这条路在 300 仓库规模上直接不成立：

| 档 | 价格 |
|---|---|
| Community | Free |
| Teams | **$0.50 per type / month** |
| Pro | **$5 per type / month，最低消费 $3000/month** |
| Enterprise | Custom（含 on-prem） |

计价单位是 **type**（每个 message / enum / service 类型）。一个有大量 gRPC 的 300 仓库组织，类型数轻松上万。按 Teams 档 10000 个类型就是 $5000/月，Pro 档是 $50000/月。**这不是「贵一点」，是数量级不对。**

再退一步问：**就算买了 BSR，它能回答「谁依赖了这个 package」吗？** BSR 概览页讲的是发布模块、解析依赖、生成文档、生成 SDK、强制规范，**通篇没有反向依赖视图（谁依赖了我）的描述**（[BSR docs](https://buf.build/docs/bsr/)）。它知道的是「模块 X 声明了依赖 Y」——而这只对**在 `buf.yaml` 里显式声明了 proto 依赖的仓库**成立。一个纯消费方（只调 gRPC、不自己定义 proto、直接用生成好的 SDK 包）**根本不会出现在 BSR 里**。

这是本节最重要的一句：**BSR 的依赖图是 proto-to-proto 的，不是 code-to-proto 的。** 而「改了 proto 没改调用方」里的那个「调用方」，绝大多数时候只是 proto 的 code-level 消费者，不是 proto-level 依赖者。

### 1.4 替代品：protolock、prototool 还活着吗

**prototool 已死，而且是 Uber 自己宣告的。** 仓库 [uber/prototool](https://github.com/uber/prototool) 已 archived，最后一个 release `v1.10.0` 停在 2020-05-19，最后一次 push 是 2022-03-01。README 第一行就是：

> **Update: We recommend checking out [Buf](https://github.com/bufbuild/buf), which is under active development. There are a ton of docs for getting started, including for [migration from Prototool](https://buf.build/docs/migration-prototool).**

这是一手的官方弃用声明，不用再评估了。（顺带：buf 的作者就是 prototool 的作者，这是同一条血脉的迭代，不是竞品替代。）

**protolock 半死。** [nilslice/protolock](https://github.com/nilslice/protolock)，BSD-3-Clause，631 star。最后一个 release `v0.17.0` 发在 2023-12-19，最后一次提交 2024-02-12（`feat: support inline c style comments in fields`），到调研时点已经停了约两年半，未 archived 但也没有维护迹象，23 个 open issue。

protolock 的模型和 buf 有个实质差异值得记一笔：它维护一个 `proto.lock` 文件当作提交进仓库的基线快照，`protolock commit` 更新它、`protolock status` 对比当前状态。**好处是基线是仓库内自包含的，不需要在 CI 里去取历史版本**；坏处是多了一个需要人工维护并可能漏更新的文件。在 buf 支持 `--against '.git#branch=main'` 之后，这个好处基本被抹平了。

**结论：protobuf 侧只有 buf 一个活着的选项，没有取舍空间。** 这反而是好消息——选型不用纠结，只要把档位配对（见 1.1）。

### 1.5 这些工具能不能回答「哪个仓库的哪一行代码调用了这个方法」

**不能，而且是原理上不能，不是功能缺失。**

`buf breaking` 的输入是两份 schema（两个 image / 两棵 proto 树），它的世界里只有 `.proto` 文件。它看不到任何 `.go` / `.java` / `.py`。它唯一能表达的「依赖」是 proto 之间的 `import` 和 `buf.yaml` 里的模块依赖声明。

用一个具体例子说清楚这个盲区有多大。假设：

- 仓库 `payment-proto` 定义 `payment.v1.PaymentService`，含 `rpc Charge(...)`。
- 仓库 `order-service`（Go）通过生成好的 SDK 调 `Charge`。
- 仓库 `billing-service`（Java）也调 `Charge`。

删掉 `Charge` 之后：

| 工具 | 看到什么 |
|---|---|
| `buf breaking`（FILE 档）在 `payment-proto` 的 CI 里 | ✅ 报 `RPC_NO_DELETE`，但只说「你删了方法」，**一个字不提 order-service 和 billing-service** |
| `buf breaking`（WIRE_JSON 档） | ❌ 静默通过 |
| BSR | 只在 `order-service` 显式声明了 proto 模块依赖时才知道包级边；Java 侧走 Maven 依赖，BSR 完全看不见 |
| 任何 proto 工具 | ❌ 不知道 `order/internal/pay.go:88` 这一行的存在 |

**这个能力必须从别处来。** 从哪来，是第 3 节（运行时）、第 6 节（代码索引）和第 11 节（方案）的内容。先把 protobuf 侧的边界钉死在这里：

> **buf 解决的是「契约本身合不合法」，它是一个前置质量门，不是影响面分析器。把它当影响面分析器用，会在最常见的那类破坏（删方法）上静默漏掉。**

### 1.6 一个被低估的副产品：descriptor set 是最便宜的全局契约索引

这条是调研过程中冒出来的，值得单列，因为它是「中心化契约注册表」这个需求的一个近乎免费的实现。

`buf build` 产出的 image 是 protobuf `FileDescriptorSet` 的超集。官方原话（[Images reference](https://buf.build/docs/reference/images/)）：

> "An image is Buf's custom extension to the Protobuf `FileDescriptorSet`. Due to the forwards- and backwards-compatible nature of Protobuf, we add a field to `FileDescriptorSet` while maintaining compatibility in both directions."

而且可以退化成纯粹的标准格式：

```sh
buf build -o image.binpb --as-file-descriptor-set
```

意味着：**每个含 proto 的仓库在 CI 里加一条 `buf build -o` 并把产物推到一个中心位置（对象存储 / 一个 git 仓库 / GitLab Package Registry），你就得到了一份全组织的、机器可读的、随每次合并自动刷新的契约全集。** 没有许可证成本，没有服务端要运维，产物是标准 protobuf 二进制，任何语言都能读。

这份东西能直接回答的问题：

- `payment.v1.PaymentService/Charge` 这个全限定名在全组织里存在吗、定义在哪个仓库？
- 全组织一共有多少个 service / method？（顺便把 BSR 的计价单位算出来了）
- 某个 message 被哪些 proto 文件 import 了？（proto-to-proto 的正向与反向依赖，因为 `FileDescriptorProto.dependency` 就在里面）
- 每个 method 的请求/响应类型是什么？（AI review 时给 LLM 的「两端签名」，这里直接就有）

它**不能**回答的仍然是 B2：哪行代码调用了。但它把 B 的另外半边——「契约那一端长什么样」——变成了一次本地文件读取，而不是一次跨仓 clone。**对照 ticket 背景里「只带两端的签名和调用点」那条设计约束：descriptor set 就是「签名」那一端的现成供给。**

## 2. 生成代码长什么样：决定「文本检索够不够」的那组事实

在评估任何索引方案之前，得先知道要找的东西长什么样。「谁调用了这个 gRPC 方法」在源码里的物理形态，是各语言 codegen 插件写死的，可以从生成器源码里直接读出来。这一节的结论会反过来决定第 6 节里「精确索引 vs 文本检索」的取舍。

### 2.1 Go

`protoc-gen-go-grpc` 的生成逻辑在 [`cmd/protoc-gen-go-grpc/grpc.go`](https://github.com/grpc/grpc-go/blob/master/cmd/protoc-gen-go-grpc/grpc.go)。三个关键片段：

**全限定方法名常量**（`genFullMethods`，源码约 54–66 行）：

```go
g.P("const (")
for _, method := range service.Methods {
    fmSymbol := helper.formatFullMethodSymbol(service, method)         // "PaymentService_Charge_FullMethodName"
    fmName := fmt.Sprintf("/%s/%s", service.Desc.FullName(), method.Desc.Name())  // "/payment.v1.PaymentService/Charge"
    g.P(fmSymbol, ` = "`, fmName, `"`)
}
g.P(")")
```

**客户端接口**（`genService`，约 204–228 行）：类型名固定为 `<ServiceGoName>Client`，工厂固定为 `New<ServiceGoName>Client(cc grpc.ClientConnInterface)`。

**方法实现**（约 355–359 行）：

```go
g.P("func (c *", unexport(service.GoName), "Client) ", clientSignature(g, method), "{")
g.P(`err := c.cc.Invoke(ctx, `, fmSymbol, `, in, out, cOpts...)`)
```

于是一个 Go 消费方仓库里，可被检索的锚点按「假阳性从低到高」排是：

| 锚点 | 例子 | 出现位置 | 假阳性 | 假阴性 |
|---|---|---|---|---|
| 全限定名字符串 | `/payment.v1.PaymentService/Charge` | **只在生成文件里** | 零 | **高**——消费方仓库里根本不会有这个字符串，除非它 vendor 了生成代码 |
| 生成包的 import 路径 | `company.com/gen/go/payment/v1` | 消费方每个用到的 `.go` 文件顶部 | 零 | 低 |
| 客户端接口名 | `PaymentServiceClient` | 消费方的字段声明、函数签名、mock | 极低（名字含 proto service 名，天然带命名空间） | 低 |
| 工厂函数 | `NewPaymentServiceClient(` | 消费方的 wiring 代码，通常一处 | 极低 | 中——依赖注入框架可能藏起来 |
| 方法名 | `.Charge(` | 真正的调用点 | **高**——任何叫 `Charge` 的方法都命中 | 低 |

**这张表直接推出了两段式漏斗的形状**：用 import 路径或接口名在全组织范围筛（假阳性几乎为零），拿到十来个候选仓库；再在这十来个仓库内部用方法名定位到行（假阳性高，但候选集已经小到人/LLM 能收拾）。

注意那个反直觉的第一行：**全限定名 `/payment.v1.PaymentService/Charge` 看起来是最理想的搜索键——全局唯一、跨语言一致——但它只出现在生成代码里，在手写的调用方代码里一次都不出现。** 拿它去全组织搜，搜到的全是各仓库 vendor 进来的 `_grpc.pb.go`，而不是调用点。这是一个很容易踩的坑，值得写死在这里。

### 2.2 Java

`grpc-java` 的生成逻辑在 [`compiler/src/java_plugin/cpp/java_generator.cpp`](https://github.com/grpc/grpc-java/blob/master/compiler/src/java_plugin/cpp/java_generator.cpp)。命名规则：

- 外层类名 = `<ServiceName>Grpc`（约 1399 行：`return std::string(service->name()) + "Grpc";`）
- 服务全名常量（约 1248 行）：`public static final String SERVICE_NAME = "<full.proto.package.Service>"`
- 方法描述符（约 505、518 行）：`fullMethodName = SERVICE_NAME + '/' + "<method_name>"`，以及 `.setFullMethodName(generateFullMethodName(SERVICE_NAME, "<method_name>"))`
- Stub 工厂（约 1284 行）：`public static <ServiceName>BlockingStub newBlockingStub(...)`
- Stub 类：`<ServiceName>Stub` / `<ServiceName>BlockingStub` / `<ServiceName>FutureStub`（约 623–629 行）

检索锚点是 `PaymentServiceGrpc` 和 `PaymentServiceBlockingStub`——两者都带 proto service 名做前缀，**天然自带命名空间，假阳性极低**。Java 的情况甚至比 Go 更好：因为 Java 没有 Go 那种「短方法名直接挂在接口上」的写法，调用点通常写成 `stub.charge(request)`，而 `stub` 变量的类型声明离得不远。

注意 Java 的方法名首字母会被 lowerCamelCase 化（proto 里的 `Charge` → Java 的 `charge()`），做跨语言检索时要处理这个大小写变换。

### 2.3 Python

`grpcio-tools` 生成 `<proto>_pb2_grpc.py`，消费方写法固定为：

```python
stub = payment_pb2_grpc.PaymentServiceStub(channel)
resp = stub.Charge(request)
```

锚点是 `PaymentServiceStub` 和 `payment_pb2_grpc` 这个模块名。Python 保留 proto 原始的方法名大小写，所以 `stub.Charge(` 和 proto 里的 `Charge` 直接对得上。

但 Python 是三者里**假阴性风险最高**的：动态语言，stub 可以被存进 dict、可以被 `getattr` 拿方法、可以被工厂函数包一层。精确索引（scip-python）在这里的边际价值比 Go/Java 大，但也同样打不穿动态构造。

### 2.4 把这节收成一条判断

**gRPC 生成代码的命名是高度结构化且带命名空间的**，这是这个场景相对于「泛泛的跨仓引用分析」的一个巨大便利。`PaymentServiceClient` / `PaymentServiceGrpc` / `PaymentServiceStub` 这类符号，在一个 300 仓库的组织里几乎不可能被偶然撞名。

**推论：在服务粒度上（B1），文本检索的精度就已经够用了，不需要精确索引。** 精确索引的边际价值集中在两处：一是方法粒度的消歧（`.Charge(` 的假阳性），二是「通过接口间接调用」这类动态形态。而第一处恰好可以被漏斗的第二级——在已经缩小到十来个仓库后的局部分析——用更贵但更准的手段（本地跑一次 `go list`、或者干脆让 LLM 读那几个文件）解决掉。

**这条判断是本文后半部分方案建议的支点。** 它把「要不要为 300 仓库建全局符号表」这个昂贵问题，降级成了「要不要为 300 仓库建全局文本索引」——而后者的成本要低一到两个数量级（数字见 4.3）。

## 3. 运行时信号：工具清单里没有、但可能最便宜的一条路

ticket 把问题框成了静态分析题（索引、符号表、契约 diff）。但有一整类答案来自另一个方向：**服务已经在跑，调用关系是可观测的。** 这条路在 GraphQL 世界是主流做法（Apollo 的 schema checks 就是拿运行时上报的 operation usage 去判断一次 schema 变更会不会打到真实客户端），在 gRPC 世界反而很少被当成 code review 的输入。先把能力摆出来，第 10、11 节再判它值不值。

### 3.1 OpenTelemetry：客户端 span 自带全限定方法名

OTel 的 RPC 语义约定（[RPC spans](https://opentelemetry.io/docs/specs/semconv/rpc/rpc-spans/)、[gRPC 约定](https://opentelemetry.io/docs/specs/semconv/rpc/grpc/)）定义：

- `rpc.system.name`：Required，gRPC 场景取值 `grpc`。
- `rpc.method`："The fully-qualified logical name of the method from the RPC interface perspective"，示例 `com.example.ExampleService/exampleMethod`。**在 client span 上是 Required**，在 server span 上是 Conditionally Required。
- span 名规则："The span name SHOULD be `{rpc.method}` if it is available and not set to `_OTHER`."

这几条合起来的含义相当直接：**一条 gRPC client span 同时携带了「谁在调」（发出 span 的那个 service 的 `service.name`）和「调了哪个方法」（`rpc.method` 的全限定名）。这正好就是 B2 问题的答案，只是粒度停在服务而不是代码行。**

而且它是 Required 级别——只要消费方接了 OTel 的 gRPC instrumentation（各语言都有开箱即用的拦截器），这个数据是自动产生的，不需要任何人额外写代码。这跟第 5 节要讲的 Pact 形成尖锐对比：**Pact 要求消费方主动写测试，OTel 只要求消费方开了 tracing。后者在企业里的已有覆盖率通常高得多。**

### 3.2 Envoy / Istio：mesh 层的调用边

如果跑了 service mesh，同样的信息在代理层也有，而且不需要应用改一行代码。

[Envoy gRPC statistics filter](https://www.envoyproxy.io/docs/envoy/latest/configuration/http/http_filters/grpc_stats_filter) 会按方法维度出计数器：

> "Depending on the configuration, the stats may be prefixed with `<grpc service>.<grpc method>.`"

指标形如 `<grpc service>.<grpc method>.success` / `.failure` / `.total`。开关是 `stats_for_all_methods`（全量）或 `individual_method_stats_allowlist`（白名单）——这个二选一的设计本身就是官方对基数爆炸的提醒。

Istio 侧要麻烦一点。[标准指标](https://istio.io/latest/docs/reference/config/metrics/)的默认维度里有 `source_workload`、`destination_service`、`request_protocol`、`grpc_response_status`，**但默认没有 path / method 维度**。也就是说开箱即得的是「服务→服务」这一级的边，要拿到方法级需要用 Telemetry API 加自定义维度（[customize metrics](https://istio.io/latest/docs/tasks/observability/metrics/customize-metrics/)）：

```yaml
apiVersion: telemetry.istio.io/v1
kind: Telemetry
spec:
  metrics:
  - providers: [{name: prometheus}]
    overrides:
    - match: {metric: REQUEST_COUNT}
      tagOverrides:
        destination_port: {value: "string(destination.port)"}
        request_host: {value: "request.host"}
```

对 gRPC 来说 HTTP 的 `:path` 就是 `/pkg.Service/Method`，所以 `request.path` 是可用的表达式。但这会把 `istio_requests_total` 的基数乘上方法数——官方示例页只演示了 `request_host` 和 `destination_port`，**没有给关于基数的明确警告，也没有给 path 维度的例子，这条属于「可行但官方没背书」，标为未证实的部分是它在大规模下的实际开销**。

### 3.3 这条路的三个硬伤

必须同时把代价说清楚，否则它会显得比实际更香：

1. **只能看到跑过的，看不到没跑过的。** 一个每月执行一次的对账任务、一个灾备分支里的调用、一段刚合进 main 还没上线的代码，运行时全都看不见。**运行时数据的假阴性是不可控的**，而 code review 场景恰恰最关心「刚写的那行代码」。
2. **粒度停在「服务」，不是「仓库」也不是「行」。** 从 `service.name` 或 `source_workload` 映射回 GitLab 仓库需要一张额外的对照表——而这张表，恰恰是第 7 节服务目录要解决的东西。两者是互补而不是替代关系。
3. **数据在别人手里。** trace 后端、Prometheus、mesh 控制面通常归 SRE 管，不归研发效能平台管。跨部门拿一个持续查询权限的组织成本，在很多公司比技术成本高。

### 3.4 但它有一个别的方案给不了的东西

**它能给「这条依赖边到底有没有活人在用」。**

这是一个在噪声抑制上极有价值的信号，而且静态分析永远给不出来。设想 AI review 报了「你删的这个方法有 5 个仓库在调」——如果其中 3 个仓库的调用在过去 90 天的 trace 里一次都没出现过，那这条 finding 的措辞、优先级、甚至该不该报，都应该不一样。

参照 map.md 里已定的主线：**最难的问题不是找出问题而是抑制噪声。** 静态分析负责召回，运行时数据负责给每条召回附一个「真实性权重」。这个组合值得在后续设计里留一个口子，即使 v1 不做。

## 4. 自托管 GitLab 本身给了什么（这一节可能是本次调研最有用的部分）

题面问的是「哪些能落地」。既然环境已经定死在自托管 GitLab 上，先查清楚这个平台自己带了什么，比先去挑外部工具划算——因为它不需要新增一个系统的运维、认证、权限对接。

### 4.1 Search API 的 `blobs` scope：现成的跨仓代码检索

这是最直接的一击。[Search API](https://docs.gitlab.com/api/search/) 提供三级作用域：

- `GET /search`（全实例）
- `GET /groups/:id/search`（含子组）
- `GET /projects/:id/search`

`blobs` scope 就是代码检索，返回的结构里**恰好包含我们要的三元组**：

| 字段 | 含义 |
|---|---|
| `project_id` | **哪个仓库** |
| `path` / `filename` | **哪个文件** |
| `startline` | **哪一行** |
| `data` | 命中的代码片段 |
| `ref` | 分支 |

也就是说：`GET /groups/<top-group>/search?scope=blobs&search=PaymentServiceClient`，一次 HTTP 调用，返回全组织范围内的仓库+文件+行号列表。**第 2 节论证过 `PaymentServiceClient` 这类符号的假阳性极低，所以这一次调用基本就是 B1+B2 的答案。**

代价在这一句上（官方原文）：

> "This scope is available only when advanced search or exact code search is enabled."

也就是说 `blobs` 检索依赖两个后端之一，而两者都**不在 Free 档**。这是整条路的唯一门槛，必须先确认环境的授权档位。

### 4.2 两个后端：Advanced Search（Elasticsearch）与 Exact Code Search（Zoekt）

[Exact code search](https://docs.gitlab.com/user/search/exact_code_search/) 的官方描述：

> "With exact code search, you can use exact match and regular expression modes to search for code in all GitLab or in a specific project." … "powered by Zoekt and is used by default in groups where the feature is enabled."

- **档位**：Premium、Ultimate；GitLab.com 与 GitLab Self-Managed 都有。功能状态标注为 **Limited availability**。
- **API**：「With the Zoekt search API, you can use the search API for exact code search」，**GitLab 18.4 起 GA**。
- **语法**：`foo file:\.js$`、`test repo:(?i)foo`、`foo lang:ruby`、`sym:foo`、否定 `foo -bar` / `-file:test`。
- **限制**（这三条必须记住，会影响方案设计）：
  1. 只索引 **小于 1 MB 且 trigram 数少于 20000** 的文件；
  2. **只索引默认分支**；
  3. 功能仍处于 Limited availability。

「只索引默认分支」这条看起来像限制，**但对影响面分析恰恰是正确的语义**：我们要问的是「当前线上/主线的消费方里谁会挂」，而不是「谁的某个 feature 分支里写过这行」。它是特性不是缺陷。

`sym:` 前缀值得单独点出来：Zoekt 靠 universal-ctags 建了一层符号索引（见 4.3），所以 `sym:PaymentServiceClient` 能把「符号定义处」和「普通文本出现」区分开，比纯文本检索的精度高一档。

### 4.3 如果是 Free 档：自己跑 Zoekt，成本算得出来

GitLab 那两个后端都要钱，但 **Zoekt 本身是 Apache-2.0 的独立开源项目**：[sourcegraph/zoekt](https://github.com/sourcegraph/zoekt)，最后一次提交 2026-09-11（即调研当天），活跃。README 明确它是 2017 年从 `github.com/google/zoekt` fork 出来后的维护主线。

它自带把一批本地 git 仓库同步进索引的命令：

```sh
go install github.com/sourcegraph/zoekt/cmd/zoekt-local-sync@latest
go install github.com/sourcegraph/zoekt/cmd/zoekt-git-index@latest
```

README 还给了一条容易被忽略但对我们很关键的建议：

> "It is also recommended to install [Universal ctags](https://github.com/universal-ctags/ctags), as symbol information is a key signal in ranking search results."

**成本有一手数字**，来自 [`doc/design.md`](https://github.com/sourcegraph/zoekt/blob/main/doc/design.md)：

> "In practice, the shard size is about 3.5x the corpus size, composed of original content, posting lists, and other metadata."

> "Since the posting lists for a trigram can be stored on SSD, searching with positional trigrams only requires 1.2x corpus size of RAM."

以及一条硬约束：

> "The format uses uint32 for all offsets, so the total size of a shard should be below 4G. Given the size of the posting data, this caps content size per shard at 1G."

代入 300 仓库算一笔：

| 假设的平均源码体积/仓库 | 语料总量 | 索引磁盘（3.5x） | 内存（1.2x） |
|---|---|---|---|
| 20 MB | 6 GB | 21 GB | 7.2 GB |
| 50 MB | 15 GB | 53 GB | 18 GB |
| 100 MB | 30 GB | 105 GB | 36 GB |

**结论：一台中等配置的 VM（16–32 GB 内存 + 一块 SSD）就能装下 300 个仓库的全文+符号索引。** 这个量级低到几乎不需要立项讨论。这个数字是后面第 11 节方案建议的成本底座——它意味着「为跨仓关联建一个专用索引」不是一个昂贵决策。

需要自己写的部分是**同步器**：定期从 GitLab 列出项目、拉默认分支、喂给 `zoekt-git-index`。300 个仓库的浅克隆（`--depth 1`）增量刷新，是个几百行的活。

### 4.4 GitLab 自带的 Code Intelligence：查了，用不上

为了不留下「是不是有现成的精确索引没用上」的疑问，把这条也钉死。

[Code Intelligence](https://docs.gitlab.com/user/project/code_intelligence/) 是 GitLab 内建的 go-to-definition / 类型签名功能。事实三条：

1. **格式是 LSIF，不是 SCIP**：「Code intelligence is built into GitLab and powered by LSIF (Language Server Index Format)」。SCIP 只能通过 SCIP CLI 转成 LSIF 再上传，没有原生支持。
2. **产出方式是 CI artifact**：在 `.gitlab-ci.yml` 里加一个 `code_navigation` job，产物作为 artifact 上传。
3. **致命的那条**：「GitLab processes one LSIF file per project, and Code intelligence does not support different LSIF files per branch.」

**每项目一个 LSIF 文件，文档里没有任何跨项目引用的描述。** 它是严格的项目内功能。对「谁调用了这个方法」这个跨仓问题，**GitLab 自带的精确索引完全不适用**。

（顺带这也是「SCIP vs LSIF 谁赢了」的一个数据点：GitLab 是 LSIF 的钉子户，而它的 SCIP 通路是「转成 LSIF」而不是原生支持。详见第 6 节。）

### 4.5 两个被忽略的原生机制：MR 依赖与多项目流水线

这两条不解决「谁调用了」，但直接服务于 map.md 新加的第四条主线（一个需求横跨多仓库），值得在这里记一笔，免得后续 ticket 重复调研。

**Merge Request Dependencies**（[文档](https://docs.gitlab.com/user/project/merge_requests/dependencies/)）：

- 官方对这个功能的定位原文就是我们的场景：「A single feature can span several merge requests, spread out across multiple projects, and the order in which the work merges can be significant.」
- **档位 Premium / Ultimate**，但有个便利：「A GitLab Premium project's merge request can depend on any other merge request, even in a GitLab Free project.」
- **跨项目可用**。
- **硬上限：每个 MR 最多 10 个 blocker，最多 block 10 个 MR。**
- 会真的挡合并（作为一条 merge check）。

这是平台原生的「把几个 MR 绑成一组」的表达。**但那个 10 的上限要注意**：一个横跨十几个仓库的大需求会撞墙。而且文档里没有提供管理依赖关系的 API——如果要让平台自动建立这些依赖，得先确认 API 存不存在（本次未证实）。

**Multi-project pipelines**（[文档](https://docs.gitlab.com/ci/pipelines/downstream_pipelines/)）：

```yaml
trigger_job:
  trigger:
    project: project-group/my-downstream-project
    strategy: mirror   # 让上游 job 的状态镜像下游流水线的真实状态
```

**档位 Free**，这条很重要——它是少数不要钱的跨仓机制。意味着：**proto 仓库的 CI 可以在 MR 阶段主动触发下游消费方仓库的编译/测试，并把真实结果拿回来挡住这个 MR。** 这是一条「不做任何索引也能验证跨仓一致性」的暴力路径，代价是延迟和算力，前提是你已经知道下游是谁（又绕回 B1）。

## 5. 消费者驱动契约测试（Pact）：模型对了，前提不成立

Pact 在这个题目里是个诱人的答案，因为它的模型**天生就是「关联本身是一等公民」**——broker 里存的就是 consumer↔provider 的边，跟 ticket 背景里「把关联单独建模成一类评审单元」那条结论同构。所以它值得认真评，而不是随手划掉。

### 5.1 模型

四个概念：**consumer**（消费方）、**provider**（提供方）、**pact**（契约文件）、**verification**（提供方对契约的验证结果）。核心流转是：

1. 消费方**跑自己的测试**，测试执行过程中录下它对 provider 的期望，产出 pact 文件；
2. pact 文件发布到 **Pact Broker**；
3. 提供方 CI 拉取所有指向自己的 pact，逐条重放，回写 verification 结果；
4. 任一方发布前跑 `can-i-deploy`，查 matrix 决定这个版本和目标环境里的对端是否兼容。

**第 1 步是整座大厦的地基，也是它的死穴。** 官方原话：

> "The contract is generated during the execution of the automated consumer tests."（[docs.pact.io](https://docs.pact.io/)）

而 broker 里的参与方（pacticipant）**只有一个来源**：发布 pact 时从 URL 自动创建（[pacticipant 文档](https://docs.pact.io/pact_broker/advanced_topics/pacticipant)）。没有别的注册途径。

### 5.2 自托管成本：意外地低

这一节是 Pact 的加分项，得如实记：

| 项 | 事实 |
|---|---|
| 许可证 | **MIT** |
| 仓库活跃度 | [pact-foundation/pact_broker](https://github.com/pact-foundation/pact_broker/releases) 最新 `v2.121.0`（2026-09-04），此前 v2.120.0（2026-07）、v2.119.0（2026-04）、v2.118.0（2026-01）——**季度节奏，在维护** |
| 容器镜像 | [pact-broker-docker](https://github.com/pact-foundation/pact-broker-docker/releases) `v2.143.0`（2026-09-07） |
| 部署形态 | 一个容器 + PostgreSQL ≥ 9.4，无需 root |
| 收购后的命运 | 2022-04 PactFlow 被 SmartBear 收购，官方博客承诺继续投入 OSS（[公告](https://docs.pact.io/blog/2022/04/06/pactflow-joins-smartbear)），2023 年起用 `smartbear-supported` 标签分配工程师处理 issue（[说明](https://docs.pact.io/help/smartbear)）。**未找到任何停止维护开源 Broker 的公告。** |

开源版功能比想象中全——webhooks（6 种事件）、environments 与 deployments/releases 记录、`can-i-deploy`、matrix、pending pacts、WIP pacts、数据自动清理都在开源版里。

商业（PactFlow）独占的是（[官方对比表](https://pactflow.io/features/)）：Bi-Directional Contract Testing、drift detection、AI 生成测试、RBAC/teams/SAML SSO、加密的 secrets 存储、完整审计、on-prem 支持。定价（[pricing](https://pactflow.io/pricing/)）：Starter 免费（2 integrations）、Team $127/月（50 integrations）、Enterprise 联系销售。

**自托管一个开源 Broker 的运维成本是「一个容器加一个库」的量级，这不是拦路的地方。**

### 5.3 gRPC 支持：能用，但边界很窄

插件是 [pactflow/pact-protobuf-plugin](https://github.com/pactflow/pact-protobuf-plugin/releases)（Rust）：

- 最新 `v0.8.0`（2026-05-13，内嵌 proto 编译器，不再需要外部 `protoc`）；2025 年 6–10 月有一轮密集修 bug。
- **17 star，12 个 open issue。** 没有打 beta/experimental 标签，插件目录里标 "Official"，但版本号仍停在 `0.x`。
- 支持：proto3 全部字段类型、`oneOf`、`map`（string key）、**gRPC service method calls**、gRPC metadata、gRPC error 验证。
- **不支持且不计划支持：gRPC streaming（单向与双向都不支持）、proto2。**（[Supported features](https://github.com/pactflow/pact-protobuf-plugin#supported-features)）

值得肯定的一点：**它确实能表达「调用了哪个方法」**——交互里显式写 `"pact:proto-service": "Calculator/calculate"`，走 V4 同步消息格式，pact 文件里内嵌 descriptor。这比 OpenAPI 侧的工具做得都细。

语言矩阵（[官方 feature_support 表](https://docs.pact.io/roadmap/feature_support)）：

| 语言 | 插件支持 |
|---|---|
| Pact-JVM | Y（≥4.3.0，当前 4.7.5） |
| Pact JS | Y（v17.1.4） |
| Pact Go | Y（v2.7.1，含 `examples/grpc`） |
| Pact Python | *（底层 FFI 有 `using_plugin`，Python 包装未完整暴露） |
| Pact .NET | * |
| Ruby | 无 |
| Rust 包装 | N |

插件框架本身也还没定型：[pact-plugins](https://github.com/pact-foundation/pact-plugins) 的 README 仍把仓库内示例插件标为 "prototype"，matcher/generator 插件标 "TODO"。

**另一条直接否掉一个思路：Bi-Directional Contract Testing 对 gRPC 不可用。** 官方原文 "BDCT is a feature exclusive to Contract Testing and is not available in the Pact OSS project."，且 provider 契约只接受 OAS 2/3.x 与 AsyncAPI 3.x，**不支持 protobuf**（[SmartBear 文档](https://support.smartbear.com/swagger/contract-testing/docs/en/user-guide/contract-testing/bi-directional-contract-testing/overview.html)）。BDCT 本来是「不用消费者写测试也能验证」的希望所在——这条路在 gRPC 上是断的。

### 5.4 决定性的那条：没写过测试的消费者，在 Broker 里不存在

这是本节的判决。事实链是完整的，而且最后一环是从源码里挖出来的：

1. pacticipant 只在发布 pact 时创建（[文档](https://docs.pact.io/pact_broker/advanced_topics/pacticipant)）。
2. pact 只能由消费者测试生成（[docs.pact.io](https://docs.pact.io/)）。
3. **`can-i-deploy` 在没有任何依赖行时返回成功。** `deployment_status_summary.rb` 里 `deployable?` 的最后一行是：

   ```ruby
   considered_rows.all?(&:success)  # true if considered_rows is empty
   ```

   无 matrix 行时的 reason 是 `NoDependenciesMissing`，源码注释写着 "There aren't any rows, but there are also no missing provider verifications"，类型标为 success。
   （[deployment_status_summary.rb](https://github.com/pact-foundation/pact_broker/blob/master/lib/pact_broker/matrix/deployment_status_summary.rb)、[reason.rb](https://github.com/pact-foundation/pact_broker/blob/master/lib/pact_broker/matrix/reason.rb)）
4. Broker 与 CLI 里**没有 "unverified consumer" 或 "unknown consumer" 概念**。最接近的 pending pacts 说的是「已发布但 provider 还没成功验证过的 pact」，`--retry-while-unknown` 说的是「验证结果还没到」——两者都以「这个消费者已经接入了」为前提（[pending pacts](https://docs.pact.io/pact_broker/advanced_topics/pending_pacts)、[CLI](https://docs.pact.io/pact_broker/client_cli/readme)）。
5. 官方 FAQ 自己讲明白了："Contract tests aren't intended to provide any particular percentage coverage of the provider"（[question archive](https://docs.pact.io/faq/question_archive)）。

**翻译成我们的场景**：provider 删掉 `Charge` 方法，5 个消费方仓库里有 1 个写过 pact 测试 → broker 报 1 个失败，另外 4 个静默通过，而且 `can-i-deploy` 会因为「没有依赖行」直接放行。**Pact 给出的是一个看起来绿的、实际覆盖率未知的门禁。**

这比「没有门禁」更危险，因为它制造确定性的幻觉。

### 5.5 官方自己划了这条界

最后一击来自 Pact 官方的「什么时候别用 Pact」页面（[What is Pact good for](https://docs.pact.io/getting_started/what_is_pact_good_for)）。它明确列为不适用的场景包括：

> "Testing APIs where the team maintaining the other side of the integration will not also be using Pact"

以及消费者数量多到 provider 团队无法逐一维护关系的场景。

**300 个仓库的企业环境，正好同时命中这两条。** 这不是我的推论，是官方对自己适用边界的声明。

### 5.6 那还要不要用

**作为「回答谁调用了这个方法」的手段：不要。** 前提（每个消费方都主动写并维护契约测试）在 300 仓库规模上不成立，而且它的失败模式是静默假阴性。

**作为「核心链路的强契约保障」：可以，但那是另一个项目。** 挑 5–10 条最要命的服务间调用，让两边团队都接 Pact，享受强验证。这是一个有价值但独立的工程，跟 AI code review 的跨仓关联没有依赖关系，不该塞进 v1。

**对本项目真正有用的，是它的建模而不是它的实现**：consumer / provider / 这条边被验证过没有——这个三元组正好是我们要在自己的库里建的东西。**Pact 教给我们的是数据模型，不是工具选型。**

（未证实：企业大规模落地 Pact 的失败模式，没找到一手材料；开源版 webhook 凭据是否加密存储，文档未说明。）

## 6. 代码索引与跨仓符号解析：这一档的现状比预期糟

这是「统一代码视图」这个需求最正面的答案，也是本次调研里**坏消息最集中**的一节。

### 6.1 Sourcegraph 不再是一个可自托管的开源选项

这条必须先说，因为它是很多人对这个问题的默认答案。

`github.com/sourcegraph/sourcegraph` **现在返回 404**。它被改名为 [`sourcegraph/sourcegraph-public-snapshot`](https://github.com/sourcegraph/sourcegraph-public-snapshot)，**已归档，最后一次 push 是 2024-09-02**，10296 star 停在那里。README 第一段是官方声明：

> **NOTE**: Sourcegraph transitioned to a private monorepo. This repository, `sourcegraph/sourcegraph-public-snapshot` is a publicly available copy of the `sourcegraph/sourcegraph` repository as it was just before the migration.

> **TIP**: If you are interested in working with the code, this [commit](https://github.com/sourcegraph/sourcegraph-public-snapshot/commit/1cd36d2dbbd2a9ab638cc437d208d2717eaefb0b) is the last one made under an Apache License.

读法：**2024 年 9 月，Sourcegraph 把主仓库转私有单体仓库。公开的只是迁移前的一份冻结快照，最后一个 Apache 许可的 commit 被明确标了出来。** 「基于开源 Sourcegraph 自托管一个跨仓代码智能平台」这条路，从这一天起就不成立了——你能拿到的是一份两年前的、不再收安全补丁的代码。

（商业版仍然卖自托管，但那是采购决策，不是本文要评的技术选项。）

### 6.2 但 SCIP 生态活得很好

反直觉的是，Sourcegraph 关掉主仓库的同时，**把索引格式与索引器留在了开源里，而且一直在更新**：

| 仓库 | 许可 | 最后 push |
|---|---|---|
| [sourcegraph/scip](https://github.com/sourcegraph/scip) | Apache-2.0 | 2026-09-10 |
| [sourcegraph/scip-go](https://github.com/sourcegraph/scip-go) | Apache-2.0 | 2026-09-10 |
| [sourcegraph/scip-java](https://github.com/sourcegraph/scip-java) | Apache-2.0 | 2026-09-11 |
| [sourcegraph/scip-typescript](https://github.com/sourcegraph/scip-typescript) | Apache-2.0 | 2026-09-11 |
| [sourcegraph/scip-python](https://github.com/sourcegraph/scip-python) | 见仓库 | 2026-09-11 |
| [sourcegraph/zoekt](https://github.com/sourcegraph/zoekt) | Apache-2.0 | 2026-09-11 |

**这是一个重要的结构性事实：产品闭源了，但「生产索引」和「文本检索」这两块基础设施仍是开源的、活跃的。** 也就是说「自己攒一个」是可行的，只是没有现成的产品外壳。

### 6.3 SCIP 的 symbol 字符串能不能跨仓 join——这是决定性的技术细节

如果每个仓库各自产出一份 SCIP 索引，能不能把它们 join 起来回答跨仓 references？答案全在 symbol 字符串的格式里。[`scip.proto`](https://github.com/sourcegraph/scip/blob/main/scip.proto) 的注释给了完整文法：

```
<symbol>    ::= <scheme> ' ' <package> ' ' (<descriptor>)+ | 'local ' <local-id>
<package>   ::= <manager> ' ' <package-name> ' ' <version>
<descriptor>::= <namespace> | <type> | <term> | <method> | ...
<namespace> ::= <name> '/'
<type>      ::= <name> '#'
<term>      ::= <name> '.'
<method>    ::= <name> '(' (<method-disambiguator>)? ').'
```

关键结论有两条，方向相反：

**好消息：symbol 是全局可寻址的，不是仓库本地的 ID。** 它由 `scheme`（如 `scip-go`）+ `manager`（如 `gomod`）+ 包名 + 版本 + 一串描述符组成。对 Go 来说 `manager=gomod` 加模块路径是全组织一致的；对 Java 是 `maven` 加 groupId/artifactId。这跟 LSIF 那种「图里的整数 node id，出了这个索引就没意义」有本质区别——**LSIF 的 result set 天生是文件内/索引内的，SCIP 的 symbol 天生是跨索引可比的。这正是 Sourcegraph 造 SCIP 的核心动机之一。**

**坏消息：`<version>` 是 symbol 字符串的一部分。**

这一条在实践中会直接把 join 打碎。提供方仓库的索引里，`Charge` 的 symbol 带的是它当前的版本（比如 `v1.3.0`）；消费方仓库 pin 的是 `v1.2.0`，它的索引里同一个符号的字符串是**不相等的**。**要跨仓 join 就必须自己做版本归一化**——把 symbol 字符串拆开、抹掉 version 段、再比。这是可行的（格式是规整的、有文法的），但它意味着「把 300 份 SCIP 索引扔进一个库就能查 references」这个想法是错的，中间必须有一层自己写的归一化与关联逻辑。

还有一条限制要一起读：注释说描述符串起来「should serve as a unique identifier **across the package**」——**唯一性的保证范围是包，不是世界**。全局唯一靠的是 `package` 那一段。所以归一化时不能连包名一起抹，只能抹版本。

### 6.4 LSIF：没死透，但 GitLab 是它最后的大客户

- [microsoft/lsif-node](https://github.com/microsoft/lsif-node)：MIT，198 star，最后 push 2026-08-13。有活动，但星数和体量说明它早已不是主线。
- **GitLab 仍然用 LSIF**：[Code Intelligence 文档](https://docs.gitlab.com/user/project/code_intelligence/)原文「Code intelligence is built into GitLab and powered by LSIF」，SCIP 只能「用 SCIP CLI 转成 LSIF 兼容文件」再上传，没有原生支持。

**「谁赢了」的回答**：格式层面 SCIP 赢了（工具链活跃、设计更适合跨索引），**但赢得很惨淡——赢家的旗舰产品闭源了，输家的最大用户是我们要用的这个平台。** 两边都不能直接给我们想要的东西。

而且哪怕 GitLab 的 LSIF 能用，它也解决不了问题：**「GitLab processes one LSIF file per project」，严格的项目内功能，文档里没有任何跨项目引用的描述**（见 4.4）。

### 6.5 Glean：开源版是内部能力的真子集

[facebookincubator/glean](https://github.com/facebookincubator/glean)，BSD，1403 star，最后 push 2026-09-11（活跃）。定位对得很准：「cross-references like function or method calls」「call hierarchies」正是我们要的。

但三条事实合起来给出一个清晰的落地判断：

1. **GitHub 上 releases 数量为 0。** 没有版本化的二进制产物，得从源码构建——而 Glean 是 **Haskell** 写的。在一个企业内部平台里引入一条 Haskell 构建链，运维成本不是小数。
2. **原生索引器只覆盖 C++/C、Hack、Haskell、JavaScript/Flow、Python。** Go 和 Java **只能通过 LSIF/SCIP 转换**接进来——也就是说你还是得先有 SCIP 索引，Glean 只是个存储和查询层。
3. README 自己写着（[README](https://github.com/facebookincubator/glean#language-coverage)）：

   > "Custom indexers for these languages exist but aren't in the open source release yet; we hope to make these available in the future: Python, Java, Kotlin, Erlang, **Thrift**, Buck and Bazel, C#, Swift"

   **Meta 内部真正在跑的那套（包括 Thrift——也就是 IDL 索引，跟我们的 proto 场景最对口的那块）不在开源版里。**

**判断：Glean 是个正确的设计，但它的开源发行版对我们来说是「先解决更难的问题（拿到 SCIP），才能用上它」，而拿到 SCIP 之后我们其实已经不太需要它了。** 对一个还没验证需求的功能来说，这个投入曲线是反的。

### 6.6 stack-graphs：GitHub 自己宣布不干了

[github/stack-graphs](https://github.com/github/stack-graphs) **已归档**，最后 push 2025-09-09。README 第一行是官方讣告：

> **NOTE:** _This repository is no longer supported or updated by GitHub. If you wish to continue to develop this code yourself, we recommend you fork it._

不用再评估了。它的设计理念（不依赖构建系统、增量、按语言写名字解析规则）本来是最贴合 polyrepo 场景的一个——**「不需要 tap into existing build or program analysis tools」这句恰好是跨仓索引最大的痛点**——但维护方撤了。

### 6.7 kythe：活着，但不是给我们用的

[kythe/kythe](https://github.com/kythe/kythe)，Apache-2.0，2152 star，最后 push 2026-09-09。Google 的跨语言索引框架，仍在动。但它深度绑定 Bazel 式的构建抽象，接入成本以「改造构建系统」计。**在一个 300 仓库、构建方式各异、没有统一构建系统的 polyrepo 里，这是最不现实的一档。**

### 6.8 sourcebot：唯一值得留意的新面孔

[sourcebot-dev/sourcebot](https://github.com/sourcebot-dev/sourcebot)，3934 star，最后 push 2026-09-11。它本质上是给 Zoekt 套了一个现代的 UI 和多代码托管平台的同步层——**正好就是 Sourcegraph 闭源之后留下的那个空位**。

许可证要看清楚，GitHub 上显示为 `NOASSERTION`，读 [`LICENSE.md`](https://github.com/sourcebot-dev/sourcebot/blob/main/LICENSE.md) 原文是 **Functional Source License 1.1（FSL-1.1-ALv2）**，外加 `ee/` 目录走单独的商业许可。FSL **不是 OSI 意义上的开源**，它禁止的是 "Competing Use"：

> A Permitted Purpose is any purpose other than a Competing Use. A Competing Use means making the Software available to others in a commercial product or service that: 1. substitutes for the Software; …

但紧接着的白名单里第一条就是我们的用法：

> Permitted Purposes specifically include using the Software: 1. **for your internal use and access**; …

**结论：企业内部自用完全合规，只有「拿它去卖一个同类产品」被禁。** 另外 `ALv2 Future License` 的含义是两年后自动转为 Apache-2.0。对内部平台来说这个许可证不构成障碍——但 `ee/` 目录里的功能不在此列，要用到哪些得单独核。

能力上它是文本检索（Zoekt）而不是精确索引，所以它的定位跟第 2 节的结论是一致的：**对 gRPC 这种命名高度结构化的场景，文本检索已经够用。**

### 6.9 这一节的收束

把 6.1–6.8 摞在一起，图景是这样的：

| 路线 | 状态 | 判断 |
|---|---|---|
| 买 Sourcegraph 商业版 | 可行 | 采购题，不在本文范围 |
| 自托管开源 Sourcegraph | **已不可能**（2024-09 转私有） | 划掉 |
| 自己攒 SCIP 索引 + 归一化 + 自建 references 查询 | 技术可行 | 成本最高的自建路线，见下 |
| Glean | 开源版是子集 + Haskell + 零 release | 划掉 |
| stack-graphs | GitHub 已弃 | 划掉 |
| kythe | 要改造构建系统 | 划掉 |
| **Zoekt（自托管或走 GitLab exact code search）** | **活跃、Apache-2.0、成本已算出（4.3）** | **留下** |

「自己攒 SCIP」这条路值得再说一句它到底贵在哪，因为它看起来是「最正确」的方案：

- 每个仓库要在 CI 里跑对应语言的 indexer（`scip-go` 要能编译整个模块，`scip-java` 要能跑通构建）——**这等于要求 300 个仓库的 CI 都能完整构建成功，这件事本身在企业里就不成立**；
- 索引产物要集中存储；
- 要自己写版本归一化（6.3）；
- 要自己写 references 查询（把 300 份索引里的 occurrence 按归一化后的 symbol 反向聚合）；
- 要处理增量更新。

**这是一个以季度为单位的工程，而它换来的精度提升，在第 2 节论证过的 gRPC 命名结构面前，边际价值有限。** 这就是我推荐文本检索路线的全部理由。

## 7. 服务目录侧：Backstage 的 catalog 到底能不能装下跨服务关系

ticket 里点名了这一节可能推翻之前的结论，所以我把它当成一个独立命题重查了，没有沿用 [知识库选型](08-知识库选型.md) 的判断。**结论是：之前的结论在它自己的题目上是对的，但那个题目跟这个题目不是一回事，这里的答案不同。** 详细对照放在第 12 节。

### 7.1 关系模型：是一等公民，而且有严格的类型约束

Backstage 的关系不是松散的字符串标签，是有类型定义的。真源在 [`packages/catalog-model/src/kinds/relations.ts`](https://github.com/backstage/backstage/blob/master/packages/catalog-model/src/kinds/relations.ts)，每一对关系都用 `addRelationPair` 声明，带 `fromKind` / `toKind` 约束：

```ts
model.addRelationPair({
  fromKind: 'Component',
  toKind: 'API',
  description: 'A relation from a component to an API it provides for consumption by others.',
  forward: { type: 'providesApi', title: 'provides API' },
  reverse: { type: 'apiProvidedBy', title: 'API provided by' },
});

model.addRelationPair({
  fromKind: 'Component',
  toKind: 'API',
  description: 'A relation from a component to an API it consumes.',
  forward: { type: 'consumesApi', title: 'consumes API' },
  reverse: { type: 'apiConsumedBy', title: 'API consumed by' },
});

model.addRelationPair({
  fromKind: ['Component', 'Resource'],
  toKind: ['Component', 'Resource'],
  description: 'A dependency relation expressing that an entity needs another entity to function.',
  forward: { type: 'dependsOn', title: 'depends on' },
  reverse: { type: 'dependencyOf', title: 'dependency of' },
});
```

三件事从这段源码里直接读出来：

1. **关系是双向物化的。** 你在 Component 上写 `consumesApis: [payment-v1]`，catalog 自动在 API 实体那侧生成 `apiConsumedBy` 的反向边。**「谁消费了这个 API」这个反查是模型内建的，不需要自己扫全表。** 这正是我们要的那个方向。
2. **`consumesApi` 的 `fromKind` 是 `Component`，`toKind` 是 `API`。** 类型是钉死的。
3. **关系是一条纯粹的类型化边，没有属性。** `{fromKind, toKind, forward.type, reverse.type}` 就是全部。

第 3 点是这一节最重要的限制，下面 7.3 展开。

### 7.2 关系可以被程序写入——这条推翻了「没有实体写入接口」

这是本次调研里最出乎意料的发现。`@backstage/plugin-catalog-node` 导出了一个 `@public` 的 `EntityProvider` 接口，[`plugins/catalog-node/src/api/provider.ts`](https://github.com/backstage/backstage/blob/master/plugins/catalog-node/src/api/provider.ts)：

```ts
export type EntityProviderMutation =
  | { type: 'full'; entities: DeferredEntity[] }
  | { type: 'delta'; added: DeferredEntity[];
      removed: (DeferredEntity | { entityRef: string; locationKey?: string })[] };

export interface EntityProviderConnection {
  /** Applies either a full or a delta update to the catalog engine. */
  applyMutation(mutation: EntityProviderMutation): Promise<void>;
  refresh(options: EntityProviderRefreshOptions): Promise<void>;
}

export interface EntityProvider {
  getProviderName(): string;
  connect(connection: EntityProviderConnection): Promise<void>;
}
```

**一个外部程序可以把实体（连同它的 `consumesApis` 关系）程序化地灌进 catalog**，支持全量替换（`full`）和增量（`delta` 含 `added` / `removed`）。

需要把这条说准确，免得矫枉过正。**「没有 REST 写入端点」这半句是准确的，我去 `createRouter.ts` 里数过了**——catalog-backend 的路由只有三个 POST：

```
router.post('/refresh', ...)
router.post('/analyze-location', ...)
router.post('/validate-entity', ...)
```

**没有 `POST /entities`，没有 PUT，没有 DELETE**（[createRouter.ts](https://github.com/backstage/backstage/blob/master/plugins/catalog-backend/src/service/createRouter.ts)）。所以：

- 它**不是** HTTP 写入端点。你得写一个 TypeScript 插件，跑在 Backstage 后端进程里。分析程序本身可以在外面（用任何语言），插件只负责把结果搬进来。**`EntityProvider` 是唯一的程序化写入通路，不是众多通路之一。**
- 每个 provider 由 `getProviderName()` 唯一标识，它发出的实体归它管——**这是一个干净的所有权边界**：人工维护的 `catalog-info.yaml` 归 Location provider 管，自动分析出的依赖边归你的 provider 管，两者不会互相覆盖。
- `full` mutation 的语义是「替换这个 provider 之前发的全部实体」，所以每次全量分析跑完直接推一次 `full` 就能保持同步，不用自己做 diff。

**所以之前那条「没有实体写入接口」在这个场景下是站不住的。** 对「把 300 个仓库的依赖关系自动灌进来」这个诉求，Backstage 是有官方通路的。

### 7.3 但粒度停在服务，进不到方法

回到 7.1 的第 3 点。关系是 `{fromKind, toKind, type}` 的纯边，**edge 上挂不了任何 payload**。

于是能表达的最细粒度是：

> `component:default/order-service` --consumesApi--> `api:default/payment-v1`

表达不了的是：

> order-service 用了 payment-v1 的 `Charge` 和 `Refund`，没用 `Query`，调用点在 `internal/pay.go:88` 和 `internal/refund.go:31`

**这个粒度差异正好卡在我们的痛点上。** ticket 背景里那条已验证的结论是「把关联本身作为一个 review 任务，只带两端的签名和调用点」——**「调用点」这三个字，Backstage 的关系模型装不下。**

理论上可以硬塞：给 API 实体加 annotation（annotation 的值是任意字符串，无长度限制），把调用点列表 JSON 序列化进去。但这是把 catalog 当 KV 存储用，绕过了它的模型，也绕过了它的查询能力（annotation 值不能被结构化检索）。**不该这么干。**

### 7.4 查询能力：反查是现成的，而且能用 HTTP 查

catalog 的实体查询支持按关系过滤，语法在 [`createQueryCatalogEntitiesAction.ts`](https://github.com/backstage/backstage/blob/master/plugins/catalog-backend/src/actions/createQueryCatalogEntitiesAction.ts) 的文档字符串里写得很直白：

> Querying relations - find all entities owned by a specific group:
> `{ query: { "relations.ownedby": "group:default/team-alpha" } }`

> Relations can be queried via `"relations.<type>"` e.g. `"relations.ownedby: user:default/jane-doe"`. **The value there must always be a valid entity reference.**

> When querying for entity relationships, **prefer using relations over spec fields**. For example, use `"relations.ownedby"` instead of `"spec.owner"`…

同一文件里列出的可查关系类型包含 `providesApi/apiProvidedBy`、`consumesApi/apiConsumedBy`、`dependsOn/dependencyOf`。

**所以「谁消费了 payment-v1」是一次 `relations.apiConsumedBy = "api:default/payment-v1"` 的查询，O(1) 级的 API 调用。** 这个能力是实打实的，不需要自己建索引。

注意那句「The value there must always be a valid entity reference」——**过滤值必须是实体引用，不能是 glob、不能是子串**。这既是限制也是好事：它强制你把「payment API」这个东西建成一个有名字的实体，而不是一个字符串约定。

### 7.5 谁来维护这些关系：自动发现有半个答案

- **官方的 GitLab discovery**（`@backstage/plugin-catalog-backend-module-gitlab`）能做的是**扫仓库找 `catalog-info.yaml`**，不是从代码推断实体。它解决的是「别让 300 个仓库一个个手工注册」，不解决「关系从哪来」。
- **`consumesApis` 本身没有官方自动推断方案。** 这条是在整个 Backstage 单体仓库里搜 `consumesApis` 的全部 TypeScript 命中之后确认的——它只出现在三个地方：schema 定义（[`ComponentEntityV1alpha1.ts`](https://github.com/backstage/backstage/blob/master/packages/catalog-model/src/kinds/ComponentEntityV1alpha1.ts)）、把 spec 字段翻译成 relations 的处理器（[`BuiltinKindsEntityProcessor.ts`](https://github.com/backstage/backstage/blob/master/plugins/catalog-backend/src/processors/BuiltinKindsEntityProcessor.ts)）、以及查询动作。**仓库里没有任何一处从代码推断它的逻辑。** 默认路径就是有人在 `catalog-info.yaml` 里手写。
- **但 7.2 的 EntityProvider 给了自己补这一块的正规通路。**

这就把 Backstage 在本项目里的角色框定了：**它不是依赖关系的产生者，是依赖关系的存放处与查询面。产生依赖关系仍然得靠第 2/4/6 节那套分析。**

### 7.6 EventCatalog：模型不对口

EventCatalog 的建模中心是 service / event / command / query / domain / channel，核心关系是 `sends` / `receives`——**它是为异步消息流设计的**。3.x 引入了 `command` 和 `query` 语义，理论上能表达请求/响应，但这仍然是「消息」视角而不是「接口」视角。

对 gRPC 同步调用来说，硬套进去要做一次概念翻译（把一个 RPC 方法翻译成一对 command/reply），翻译之后既不自然也丢失信息。加上上一轮调研已确认的商业授权边界问题（见 [知识库选型](08-知识库选型.md)），**这一条不用再花时间**。

（本节关于 EventCatalog 的判断基于模型契合度，其当前版本的商业功能边界本次未重新核实。）

## 8. OpenAPI / GraphQL 侧：同一个边界，外加一条值得抄的思路

这一侧的工具比 protobuf 侧成熟得多，但**能力边界完全一样：它们都只做 schema-to-schema 比较，都回答不了「谁调用了」**。所以这一节写得短，重点放在 GraphQL 世界里那条 protobuf 世界没有的做法上。

### 8.1 oasdiff：OpenAPI 侧的事实标准

[oasdiff/oasdiff](https://github.com/oasdiff/oasdiff)，Apache-2.0，1358 star，最后 push 2026-09-10，活跃。

规则规模有官方数字（[breaking changes 文档](https://www.oasdiff.com/docs/breaking-changes)）：覆盖 10 个 OpenAPI 领域共 **681 种变更**，其中 **317 种 breaking、17 种 warning、347 种 info**。判定原则写得很清楚：

> "A change is breaking if a consumer that followed the old contract can stop working under the new one."

方向性逻辑值得记，因为它跟 buf 的分档思路是同构的：**请求侧收窄 = breaking（原本合法的请求被拒），响应侧放宽 = breaking（返回了消费方没预期的东西），不确定的一律按 breaking 报**（保守策略）。

严重级别可以用 severity-levels 配置文件按检查项调。CI 里跑有官方 GitHub Action 和 CLI 两条路。「能不能对着远端 URL 基线比」这一条**文档里没有明说，本次未证实**——但它接受两个文件路径，CI 里先 `curl` 下来再比是等价的。

同类的 [OpenAPITools/openapi-diff](https://github.com/OpenAPITools/openapi-diff)（Apache-2.0，1095 star，2026-09-04）与 [Azure/openapi-diff](https://github.com/Azure/openapi-diff)（MIT，290 star，2026-09-11）都还活着。**取舍很简单：oasdiff 是 Go 单二进制、规则数最多、活跃度最高，没有理由选别的**，除非你的 CI 已经是 JVM 环境且不想引新工具链。

### 8.2 graphql-inspector：唯一真正碰到「消费方代码」的工具

[kamilkisiela/graphql-inspector](https://github.com/kamilkisiela/graphql-inspector)，MIT，1767 star，最后 push 2026-09-09，The Guild 仍在维护。

`diff` 命令跟前面几个是一类。真正特别的是 **`coverage`**（[文档](https://the-guild.dev/graphql/inspector/docs/essentials/coverage)）：

```
graphql-inspector coverage DOCUMENTS SCHEMA
```

- `DOCUMENTS` 是**指向 GraphQL 操作文档的 glob**——也就是消费方实际写的查询。
- 产出：类型覆盖率、字段覆盖率、各类操作数量，可以 `-w` 写成 JSON。

**这是本次调研里唯一一个把「schema 变更」和「消费方代码」真正连起来的开源工具。** 它能告诉你「这个字段没有任何一个已知查询用到，删掉是安全的」。

**但它的前提暴露了整个问题的本质：它要求 `DOCUMENTS` 这个 glob 已经能指到全部消费方的查询文件。** 在 monorepo 里这是一个通配符；在 300 仓库的 polyrepo 里，**「把全部消费方的 .graphql 收集到一处」跟原始问题是同一个问题，只是换了个马甲**。graphql-inspector 假设发现问题已经被解决了，它解决的是发现之后的那一步。

**这条观察可以直接推广到所有此类工具：把消费方代码摆到一起，才是真正的难点；摆到一起之后，分析是简单的。** 这也正是我在第 11 节把方案的重心放在「索引」而不是「分析」上的原因。

顺带回答 ticket 里的一个问题：**gRPC 没有 graphql-inspector 的等价物。** 没有任何工具能接受一组 `.proto` 加一组消费方源码，告诉你哪些方法没人用。原因是 GraphQL 的查询是**声明式的、以独立文档形式存在的数据**，天然可被静态收集；而 gRPC 的调用是**命令式代码里的一次函数调用**，收集它就等于做跨仓引用分析。**这是一个语言学上的差异，不是工具成熟度的差异，不会有人补上这个缺口。**

### 8.3 值得抄的那条：用运行时流量判定「是不是真的 breaking」

GraphQL 世界有一个 protobuf 世界完全没有的做法，值得单独摘出来。

Apollo 的 schema checks 和 [graphql-hive](https://github.com/graphql-hive/platform)（MIT，484 star，最后 push 2026-09-11）的 **Conditional Breaking Changes** 走的是同一条路：**不靠猜，靠真实流量数据判断一次 schema 变更要不要拦。**

机制（[Hive 文档](https://the-guild.dev/graphql/hive/docs/schema-registry/management/targets)、[usage reporting](https://the-guild.dev/graphql/hive/docs/schema-registry/usage-reporting)）：

- 运行时由网关/服务端插件（Hive Client）上报**操作元数据**——操作名、类型、用到的字段与参数、客户端标识、时间戳，**不上报数据本身**。
- 配置三样东西：**流量阈值**（百分比或固定操作数）、**时间窗口**（上限取决于数据保留期）、**客户端排除名单**（按 User-Agent 之类识别）。还能跨 target 引用——用生产环境的使用数据去校验 staging 的 schema。
- 规则："An incompatible change is considered as breaking and dangerous if the field was requested by more than [threshold]." 设成 `0 Percent` 就是「有一次调用就拦」，设成 `10 Percent` 就是「用量不到一成就放行」。

**这是把「契约破坏」从一个静态判定改造成一个带证据的风险判定。** 对照 map.md 里那条主线——最难的问题是抑制噪声——这正是一个成熟的噪声抑制机制，而且它抑制的方式不是调阈值猜，是拿实际数据说话。

Hive 自托管是可行的（MIT，官方有 self-hosting 文档），但**基础设施不轻**：PostgreSQL 16 + ClickHouse + Redis + Redpanda/Kafka + MinIO + Caddy，官方还提醒生产环境要把这些单节点容器换成托管服务。自托管版缺 High-Availability CDN 和计费集成。

**对我们的意义不是「去用 Hive」**（我们的契约主要是 gRPC，Hive 只管 GraphQL），**而是把 Conditional Breaking Change 这个模式搬到 gRPC 上**——第 3 节已经论证过数据源是现成的（OTel 的 `rpc.method` 在 client span 上是 Required）。**GraphQL 侧的成熟产品已经证明了这条路走得通，我们只是换一个 telemetry 源。**

## 9. 实践层面：Google 的规矩，以及「第三条路」在哪

### 9.1 AIP-180 给了一条一手的、比 buf 更严的红线

Google 的 API 改进提案 [AIP-180 Backwards compatibility](https://google.aip.dev/180) 是这个题目上最权威的一手规范。两句原文直接解决了第 1 节留下的问题：

> "Existing components (**interfaces, methods**, messages, fields, enums, or enum values) **must not** be removed from existing APIs in the same major version."

**「interfaces, methods」被和 fields 并列写进同一条禁令。** 这正好补上了 protobuf 官方 Do's and Don'ts 里那个空白（见 1.1 末尾）——删方法、删 service 在 Google 的规范里是明令禁止的，只是 protobuf 的通用文档没写。

另一句更值钱：

> "Existing fields and messages **must not** have their type changed, **even if the new type is wire-compatible, because type changes alter generated code in a breaking way**."

**这是第一方对「wire 兼容不等于不破坏」的明确表态**，而且理由跟我在 1.1 推的一模一样：wire 兼容的类型变更照样会破坏生成代码。Google 的红线画在**生成代码**上，不是画在 wire 上。

**所以 1.1 那条配置决策（必须跑 FILE/PACKAGE 档，不能听「WIRE_JSON 起步」）不是我的一家之言，它和业内最严谨的那套 API 规范是一致的。** 而且重命名也被堵死了：「Renaming a component is semantically equivalent to 'remove and add'.」

### 9.2 中心化 IDL 仓库：这条路有活着的一手例证

[googleapis/googleapis](https://github.com/googleapis/googleapis)（8741 star，最后 push 2026-09-10）的自我描述就一句：**"Public interface definitions of Google APIs."** Google 把上百个产品线的全部公开 API proto 放进**一个仓库**。[envoyproxy/data-plane-api](https://github.com/envoyproxy/data-plane-api) 是同一个模式的另一个实例（Envoy 的全部 REST/proto API 定义集中一处）。

**这个模式对我们的价值，不在于「集中管理更整洁」，而在于它把跨仓问题降了一维：**

- proto 全在一个仓库 → `buf breaking` 一次就能扫全组织的契约，不用在 300 个仓库里各配一遍 CI；
- proto 之间的 import 图在一个仓库内完全可见，不需要跨仓解析；
- 契约变更天然产生一个**单一的、集中的 MR**，这个 MR 就是「契约评审单元」的物理载体；
- 谁在改契约、改了什么，有一条统一的审计线。

**它仍然解决不了 B2**（哪行代码调用了）——生成代码的消费方还在 300 个仓库里。但它把「契约那一端」从 300 个分散的位置收敛成一个，这本身就把问题的复杂度砍掉了一半。

代价要如实说：它要求组织接受「改 proto 要提两个 MR（IDL 仓一个、实现仓一个）」这个流程成本，以及生成代码的分发机制（发包还是各自生成）。**这是一个组织决策，不是技术决策，不该由 AI review 平台来推动——但如果组织已经这么做了或者愿意这么做，我们的方案会简单非常多。这条值得在方案里作为一个「如果……则……」的分支写清楚。**

### 9.3 所谓「第三条路」

ticket 问：有没有「先在 monorepo 里跑、polyrepo 靠工具模拟」之外的第三条路。

把全文的材料摆开，确实有，而且不止一条。真正的分歧不在「monorepo 还是模拟 monorepo」，而在**你打算用什么东西当「统一代码视图」的替身**：

| 路 | 替身是什么 | 代表 | 本文证据 |
|---|---|---|---|
| 1 | 把代码真的放一起 | monorepo | —— |
| 2 | 把代码的**索引**放一起 | Sourcegraph / Zoekt / SCIP | 第 4、6 节 |
| 3 | 把**契约**放一起 | 中心 IDL 仓库 / descriptor set 集中 | 1.6、9.2 |
| 4 | 把**运行时观测**放一起 | OTel / mesh / Hive 式 usage reporting | 第 3、8.3 节 |
| 5 | 把**声明的关系**放一起 | Backstage catalog + EntityProvider | 第 7 节 |
| 6 | 谁都不放一起，让 CI 互相触发 | GitLab multi-project pipeline | 4.5 |

**2 到 6 每一条都比 monorepo 便宜，而且它们不互斥。** 下一节的方案建议就是从里面挑了两条拼起来。

（关于 Uber、Airbnb、Spotify 等公司在这个具体问题上的公开材料，本次调研**未找到可直接引用的一手出处**，不做推测。Uber 的 prototool→buf 迁移是有据可查的（见 1.4），但那是工具层面，不涉及影响面分析。）

## 10. 对照表

四个维度：**能检测什么 × 需要什么前置条件 × 自托管成本 × 覆盖的契约类型**。按「能不能回答 B（这次变更打到谁了）」分成两组，因为这是全文最重要的分界。

### 第一组：只能回答 A（契约本身变了吗）

| 手段 | 能检测什么 | 前置条件 | 自托管成本 | 覆盖契约类型 |
|---|---|---|---|---|
| **`buf breaking`** | 契约破坏兼容，FILE/PACKAGE/WIRE_JSON/WIRE 四档，删方法只有前两档拦 | 仓库里有 `.proto`；CI 能取到基线（`.git#branch=main` 即可） | **≈0**。Apache-2.0 单二进制，无中心组件 | protobuf / gRPC |
| **descriptor set 集中**（1.6） | 全组织契约全集；方法/消息签名；proto 间 import 图 | 每个 proto 仓库 CI 加一条 `buf build -o`；一个存放处 | **极低**。一个对象存储桶 + 一个 CI 步骤 | protobuf / gRPC |

| **graphql-inspector `diff`** | schema 变更分级 | 有 GraphQL schema | ≈0，MIT | GraphQL |

### 第二组：能回答 B（这次变更打到谁了）

| 手段 | 能检测什么 | 前置条件 | 自托管成本 | 覆盖契约类型 |
|---|---|---|---|---|
| **GitLab Search API `blobs`**（4.1） | **B1+B2**：仓库 + 文件 + 行号，一次 HTTP 调用 | **Premium/Ultimate**；开了 Advanced Search 或 exact code search；只覆盖默认分支、文件 <1MB | **≈0**（已在平台里），但**要授权档位** | 任意（文本可检索即可） |

| **Pact + 开源 Broker** | **B2，但只覆盖已接入的消费者** | **每个消费方主动写并维护契约测试**——官方自己列为不适用场景（5.5） | **低**：MIT，一容器 + PostgreSQL。gRPC 插件 0.x、17 star、**不支持 streaming** | protobuf（unary）、HTTP、消息 |

| **graphql-hive** | **B2 + 风险加权**：按真实流量判定是否 breaking | 运行时接 Hive Client 上报 | 中：PostgreSQL + ClickHouse + Redis + Kafka + MinIO + Caddy | GraphQL |

| **GitLab multi-project pipeline**（4.5） | **B2 的终极形式**：下游真的编译/测试了 | **得先知道下游是谁**（绕回 B1）；下游 CI 得能跑 | **≈0，Free 档可用**。代价是延迟与算力 | 任意 |

### 从表里直接读出来的三件事

1. **A 组全部接近免费，B 组才是钱和工程量所在。** 所以「要不要做跨仓契约检测」这个问题，真正要决策的只有 B。
2. **B 组里成本最低的两行（GitLab Search API、自托管 Zoekt）是同一件事的两种付费方式**：要么买 GitLab 授权，要么花一台 VM 加一个同步器。**没有第三种更便宜的了。**
3. **要求消费方主动做事的方案（Pact、graphql-inspector coverage）在 300 仓库规模上都会退化成「覆盖率未知的绿灯」**，而这比没有门禁更危险。

## 11. 回答「谁调用了这个方法」的最便宜路径

### 11.1 关键的成本重构：不要建全图，要按需查

先纠正一个容易走偏的默认假设。「回答谁调用了这个方法」听起来需要一张全组织调用图，于是问题变成「怎么建并维护一张 300 仓库的调用图」——那是个昂贵问题。

**但 AI code review 的真实提问模式不是这样的。** 一次 review 面对的是一个 MR，这个 MR 改动的 gRPC 方法通常是**个位数**。我们要回答的是：

> 这 3 个被改动的方法，分别有谁在调？

而不是：

> 全组织 8000 个方法的调用关系图长什么样？

**这个区别把成本模型整个换掉了：从「维护一张图」变成「每次 review 发几次检索」。** 前者要解决增量更新、一致性、存储；后者只要一个能被检索的索引和几次查询。

这是整个方案建议的支点。

### 11.2 推荐方案：四段漏斗

```
① 变更识别（免费）         ② 锚点推导（免费）        ③ 候选收敛（一次检索）      ④ 定位与呈现
   buf breaking              descriptor set             GitLab Search blobs         局部消歧
   FILE/PACKAGE 档      →    查出服务名/方法名     →    搜 PaymentServiceClient →  在 ~10 个仓库里
   找出被改动的方法          推出各语言符号锚点          得到 repo+file+line        搜 .Charge( 并交给 LLM
```

**① 变更识别。** 每个含 proto 的仓库 CI 跑：

```sh
buf breaking --against ".git#branch=$CI_MERGE_REQUEST_TARGET_BRANCH_NAME"
```

`buf.yaml` 里 `breaking.use: [FILE]`（**不是 WIRE_JSON**，理由见 1.1 与 9.1）。产出是结构化的违规列表，其中就有「哪个方法被删/改了」。成本：一个 CI job，Apache-2.0。

**② 锚点推导。** 从 descriptor set（1.6）拿到被改方法所属的 service 全名与 `go_package` / `java_package` 等选项，按第 2 节的 codegen 规则机械地推出各语言的检索锚点：

| 语言 | 锚点 |
|---|---|
| Go | 生成包 import 路径、`PaymentServiceClient`、`NewPaymentServiceClient` |
| Java | `PaymentServiceGrpc`、`PaymentServiceBlockingStub` |
| Python | `PaymentServiceStub`、`payment_pb2_grpc` |

这是纯字符串拼接，没有成本。**注意别用全限定名 `/payment.v1.PaymentService/Charge` 当锚点——它只出现在生成代码里（2.1）。**

**③ 候选收敛。** 每个锚点一次：

```
GET /groups/<top-group>/search?scope=blobs&search=PaymentServiceClient
```

返回 `project_id` + `path` + `startline` + `data`。第 2.4 节论证过这类符号的假阳性极低，所以这一步的产出基本就是干净的消费方清单。

**这一步是整个方案唯一需要基础设施的地方**，两种实现二选一：

- **GitLab 是 Premium/Ultimate**：什么都不用建，直接调（4.1/4.2）。确认 Advanced Search 或 exact code search 已开启。
- **GitLab 是 Free**：自托管 Zoekt（4.3）。一台 VM，21–105 GB 盘 / 7–36 GB 内存，加一个几百行的同步器。**这是本方案的全部基建成本。**

**④ 定位与呈现。** 候选已经收敛到十来个仓库，此时才用贵手段：在这些仓库内搜方法名（Go `.Charge(`、Java `.charge(`、Python `.Charge(`），或者直接把命中文件交给 LLM 判断。**假阳性高的检索，在候选集足够小之后才使用——这是漏斗的全部意义。**

### 11.3 结果落到哪：一张关联表，不是一张图

查询结果写进我们自己的库，作为**投影**（可重建、可过期），而不是真源：

| 列 | 来源 | 说明 |
|---|---|---|
| `provider_method` | descriptor set | `payment.v1.PaymentService/Charge`，全局唯一 |
| `provider_repo` / `provider_signature` | descriptor set | 契约那一端 |
| `consumer_repo` / `consumer_path` / `consumer_line` | 步骤 ③④ | 调用点那一端 |
| `anchor_kind` | 步骤 ② | 靠哪个锚点命中的，用于判断置信度 |
| `last_seen_at` | —— | 过期就重查 |
| `runtime_seen`（可选） | 第 3 节 | 近 90 天有没有真实流量 |

**这张表的每一行就是 ticket 背景里那个「关联评审单元」。** 它天然只带两端签名和调用点，不带任何一端的完整代码——**跟已被原型验证的那条结论严丝合缝，不是事后附会。**

### 11.4 三条要提前说清楚的限制

1. **只覆盖默认分支。** GitLab exact code search 明说只索引默认分支（4.2）。所以查到的是「已合入主线的消费方」，查不到「别人正在开发中的分支里新写的调用」。**这对影响面分析是正确语义，但要在产品文案里说清楚，别让人以为是全量。**
2. **动态调用打不穿。** 通过接口注入、反射、配置驱动的调用形态，文本检索和精确索引都会漏。**这是召回率的天花板，不是实现缺陷**，产品上要表达成「找到了 N 处」而不是「共有 N 处」。
3. **跨语言的方法名大小写。** proto 的 `Charge` 在 Java 里是 `charge()`。锚点推导时必须按语言做大小写变换，否则 Java 侧会整体漏掉。

### 11.5 明确不做什么

- **不建 SCIP 索引。** 它要求 300 个仓库的 CI 都能完整构建（6.9），这个前提在企业里不成立；而它换来的精度提升，在 gRPC 命名结构面前边际价值有限（2.4）。
- **不引入 Pact。** 前提不成立，失败模式是静默假阴性（5.4）。
- **不为此引入 Backstage。** 理由见下一节。
- **不做全量预计算调用图。** 按需查（11.1）。

### 11.6 一个可选的加分项

如果组织已经有 OTel 或 service mesh，把 `runtime_seen` 这一列接上（第 3 节）。它不提升召回，但给每条关联附一个「有没有活人在用」的权重——**这是 GraphQL 世界已经验证过的噪声抑制机制（8.3），而 gRPC 侧的数据源（OTel `rpc.method`，client span 上 Required）是现成的。**

优先级：v1 之后。它依赖的是跨部门拿数据权限，不是技术难度。

## 12. Backstage 二次评估

ticket 明确要求把这一条单独拎出来，和之前「Backstage 装不下编码规范」的结论对照。我按独立命题重查了源码（第 7 节），下面是判决。

### 12.1 先说结论

**在表达跨服务依赖上，Backstage 的 catalog 够用——但只够到服务粒度，进不到调用点。而我们的方案恰恰需要调用点。**

**所以：能力上它合格，但它解决的是我们问题中比较容易的那一半，而且那一半我们有更便宜的做法。**

### 12.2 它做对的三件事（和编码规范那题完全相反）

| | 编码规范（第 08 号调研） | 跨服务依赖（本次） |
|---|---|---|
| 我们数据的主键 | **规范条目**，实体只是它的作用域取值 | **实体**，以及实体之间的边 |
| Backstage 模型的主键 | 实体 | 实体 |
| 方向 | **反的** | **对的** |

具体到能力：

1. **关系是一等公民，且双向物化。** `addRelationPair` 声明的每对关系，catalog 会自动生成反向边——你写 `consumesApis`，API 实体那边自动有 `apiConsumedBy`（7.1）。**「谁消费了这个 API」这个反查是模型内建的**，不需要自己扫表。
2. **关系可被结构化查询。** `relations.apiConsumedBy = "api:default/payment-v1"` 是一次带索引的查询（7.4），官方文档还专门叮嘱「prefer using relations over spec fields」。
3. **关系可以被程序写入。** `EntityProvider` 是 `@public` 接口，`applyMutation` 支持 `full` / `delta`（7.2）。

**第 3 点直接修正了上一轮的一条论据。** 上次的结论里「没有实体写入接口」这一句，作为「不能自动化灌数据」的理由是**不成立的**——`EntityProvider` 就是官方给的自动化通路，而且它有干净的 provider 所有权边界，跟人工维护的 `catalog-info.yaml` 不打架。

需要精确一点：它不是 HTTP `POST /entities`，是一个跑在 Backstage 后端进程里的 TypeScript 插件接口。所以「没有 REST 写入端点」是对的，「没有写入接口」是过强的表述。**这条更正应该回写进第 08 号调研，因为它可能影响那边的其他推理。**

### 12.3 它做不到的那件事，恰好是我们要的

关系是纯粹的类型化边 `{fromKind, toKind, forward.type, reverse.type}`，**edge 上挂不了任何属性**（7.3）。

能表达的最细粒度：

> `component:default/order-service` --consumesApi--> `api:default/payment-v1`

表达不了：

> 用了 `Charge` 和 `Refund`，没用 `Query`；调用点在 `internal/pay.go:88`

**ticket 背景里那条已被原型验证的结论——「只带两端的签名和调用点」——的后半句，Backstage 装不下。** 这不是配置问题，是 `addRelationPair` 的类型定义就没有 payload 位置。硬塞进 annotation 是把 catalog 当 KV 用，同时丢掉查询能力，不该这么干。

### 12.4 更关键的：就算够用，也轮不到它

假设我们接受服务粒度。Backstage 仍然有个绕不过去的问题：**那些边从哪来？**

- `consumesApis` **没有任何官方或社区的自动推断方案**，默认就是有人在 `catalog-info.yaml` 里手写（7.5）。
- 官方的 GitLab discovery 只负责扫仓库找 `catalog-info.yaml`，不从代码推断关系。
- 所以要让它准确，我们**还是得先跑第 11 节那套分析**。

于是链路变成：`我们的分析 → 写 TS 插件 → 灌进 Backstage → 再从 Backstage 查回来`。

**中间那两步是纯粹的损耗。** 我们的分析结果已经比 Backstage 能存的更细（有调用点），存进去要降精度，查回来还要再补。**在「我们已经有了分析能力」这个前提下，把结果写进自己的库（11.3 那张关联表）严格优于绕道 Backstage。**

### 12.5 什么情况下它才真的有用

一个条件判断，不是一个是非题：

**如果组织已经在跑 Backstage 且 catalog 已经有数据**，它有两处真实价值，但都不是「依赖关系」：

1. **归属映射（这个价值被低估了）。** `ownedBy` / `Group` / `User` 那套组织关系，回答的是「这个消费方仓库归谁」。**AI review 发现了跨仓问题之后，得知道把评论发给谁、@谁**——这个映射我们自己建是重复劳动，Backstage 里通常已经有了。而且第 3 节提到的「`service.name` / `source_workload` 映射回 GitLab 仓库」这张表，Backstage 的 Component 实体也常常已经有了。
2. **人工声明作为分析结果的交叉验证。** 人写的 `consumesApis` 和我们分析出的关联对不上时，两边都值得看一眼：可能是我们漏了（动态调用），也可能是人写的过期了。**作为一个低成本的召回率体检手段，它有价值。**

**如果组织没在跑 Backstage：不要为这件事引入它。** 一个 Backstage 后端加一个自写 TS 插件的运维成本，换来的是我们已经有的、且精度更低的数据。

### 12.6 和上一条结论的关系

**不冲突，而且两条结论指向同一个判断依据。**

上一轮说「Backstage 装不下编码规范」，根因写在第 08 号调研里那句话：**现成方案的核心语义是「给已存在的实体挂文档」，而规范要的是「给条目挂适用条件」，方向是反的。**

这一轮的数据形状是「实体和实体之间的边」——**方向对了，所以模型层面它合格。** 两条结论不是一条推翻另一条，是同一把尺子量两种不同形状的数据，得到不同结果。**这恰好说明上一轮那把尺子是对的：它有区分度，不是一概而论地否定。**

真正需要修订的只有一处：**「没有实体写入接口」这句话太强了，应改为「没有 REST 写入端点，但有 `EntityProvider` 插件接口可供程序化灌入」。** 这个更正不改变编码规范那题的结论（那题的拦路虎是字段格式硬墙和模型方向，不是写入通路），但它是一条事实性错误，该改。

### 12.7 一句话版本

> **Backstage 在跨服务关系上是合格的存储与查询层，但它存不下调用点，而且它本身不产生关系。已经在用就顺手接一下它的归属数据；没在用就别为这件事引入它。**

## 14. 给后续 ticket 的三条移交

1. **`buf.yaml` 的 `breaking.use` 必须配 `FILE`（或至少 `PACKAGE`）**，不能用通用建议里的 `WIRE_JSON`。依据：`RPC_NO_DELETE` 与 `SERVICE_NO_DELETE` 不在 wire 档（1.1，源码核实），以及 AIP-180 把红线画在生成代码上（9.1）。这是一条可以直接写进模板的配置结论。
2. **跨仓关联的基建只有一件事要决策：GitLab 的授权档位。** Premium/Ultimate 则零基建（4.1），Free 则自托管 Zoekt 一台 VM（4.3）。**这个前置条件需要尽早向需求方确认，它是唯一会改变方案形状的外部变量。**
3. **[多仓库代码的获取与缓存](../../.scratch/ureview/map.md) 那条待办可以缩小范围。** 按 11.1 的按需查询模型，绝大多数场景不需要 clone 任何消费方仓库——检索 API 直接给到 repo + file + line + 片段。只有漏斗第 ④ 步需要少量文件内容，而那是十来个文件而不是 300 个仓库。

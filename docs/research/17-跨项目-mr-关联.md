# 跨项目 MR 关联的能力与实践

- 对应 ticket：[跨项目 MR 关联的能力与实践](17-跨项目-mr-关联.md)
- 调研时间：2026-09-11
- 参考文档版本：`gitlab-org/gitlab` 仓库 `master` 分支的 `doc/` 源文件，对应 `VERSION = 19.4.0-pre`。当日最新稳定版为 **19.3**。
- 每条结论标注最低版本与版次（Free / Premium / Ultimate）。文档没写引入版本的，写「文档未标注」。
- 文档说不清楚的地方回源码核对，单独标「源码」。源码路径均为该仓库 master。

> [!important]
> **调研重心**：MVP 已确定靠**人工声明**分组，不做自动推断。所以本文的重点在
> §3（哪个原生机制最适合承载声明）和 §6（声明的及时性）。
> §4 的约定推断、§7 的现成工具降为参考。
>
> **结论先放这里**：用 **group label**，命名约定 `cs::<需求ID>`，开发者在 `git push -o merge_request.label=` 里顺手声明。
> 理由是它同时满足四件事 —— 推送时一行搞定且标签不存在会自动创建、webhook 载荷直接带名字、
> 一次 group 级调用拿全组（含子组）、全链路 Free。逐项对比见 §3.2，推荐理由见 §3.3。

> [!warning]
> 一个前置事实：GitLab 没有「跨项目变更集」这个一等概念。
> 唯一原生的 MR↔MR 结构化关联是 **merge request dependencies**（Premium，语义是「合并顺序」而不是「同一组」）。
> label / milestone / issue 都是**借来用**的，它们的语义分别是分类、交付批次、需求条目。
> 所以变更集的成员、状态、生命周期**必须由平台自己存**，GitLab 只能当声明通道和事件源。详见 §10.1。

## 1. GitLab 原生的关联机制

### 1.1 MR ↔ MR：只有 merge request dependencies

文档：[Merge request dependencies](https://docs.gitlab.com/user/project/merge_requests/dependencies/)

**版次：Premium、Ultimate。** 这是 GitLab 里**唯一**的 MR 之间的结构化关联。

原文对跨项目说得很直接：

> A single feature can span several merge requests, spread out across multiple projects,
> and the order in which the work merges can be significant.

创建依赖时接受三种引用格式，第二、三种就是跨项目：

- `!1234`（同项目）
- `gitlab-org/gitlab!1234`（跨项目）
- `https://gitlab.com/gitlab-org/gitlab/-/merge_requests/1234`（全 URL）

许可证只卡**被阻塞**的那一侧（原文）：

> A GitLab Premium project's merge request can depend on any other merge request, even in a GitLab Free project.
> A GitLab Free project's merge request cannot depend on other merge requests.

#### 限制（源码核对）

`ee/app/models/merge_request_block.rb`：

```ruby
MAX_BLOCKS_COUNT = 10
MAX_BLOCKED_BY_COUNT = 10
```

一个 MR 最多阻塞 10 个、最多被 10 个阻塞。对「一个需求 5~6 个仓」够用，对更大的变更集不够。

同文件里唯一的跨边界校验是 organization 隔离：

```ruby
def check_organization_isolation
  return if blocking_merge_request.project.organization_id == blocked_merge_request.project.organization_id
  blocked_org = blocked_merge_request.project.organization
  return unless blocked_org.isolated?
  errors.add(:base, _('The blocking merge request must be in the same organization'))
end
```

即：**只要不跨 isolated organization，任意两个项目的 MR 都能建依赖**。不要求同 group、同 namespace。

其余：

- 嵌套（间接）依赖 **16.7** 起支持，但 UI 不显示嵌套链（[epic 5308](https://gitlab.com/groups/gitlab-org/-/epics/5308) 仍未做）。
- 不能自引用，但**允许成环**（文档明说 "it's possible to create circular dependencies"）。
- 关闭（closed）的 MR 依然阻塞依赖方。
- 项目 import/export **不保留**依赖（[issue #12549](https://gitlab.com/gitlab-org/gitlab/-/issues/12549)）。
- 无权限看的依赖在 UI 上显示为 `1 inaccessible merge request`。

#### API

REST（源码 `ee/lib/api/merge_request_dependencies.rb`，文档 [Merge requests API](https://docs.gitlab.com/api/merge_requests/)）：

```plaintext
GET    /projects/:id/merge_requests/:iid/blocks            # 我被谁挡着（blockee 视角）
GET    /projects/:id/merge_requests/:iid/blocks/:block_id
POST   /projects/:id/merge_requests/:iid/blocks            # 建依赖
DELETE /projects/:id/merge_requests/:iid/blocks/:block_id
GET    /projects/:id/merge_requests/:iid/blockees          # 我挡着谁（反向）
```

跨项目建依赖用 `blocking_project_id` + `blocking_merge_request_iid`：

```shell
curl --request POST --header "PRIVATE-TOKEN: <token>" \
  --url "https://gitlab.example.com/api/v4/projects/1/merge_requests/1/blocks?blocking_merge_request_iid=5&blocking_project_id=2"
```

返回码：`201` 成功 / `403` 读不到 blocking MR / `404` 找不到 / `409` 已存在。

**两个方向都有端点（`/blocks` 和 `/blockees`）**，所以拿到任意一个 MR 都能把整条依赖链爬出来。这是它比其它机制强的地方。

GraphQL（[GraphQL reference](https://docs.gitlab.com/api/graphql/reference/)）：

- 读：`MergeRequest.blockingMergeRequests` → `BlockingMergeRequests { totalCount, hiddenCount, visibleMergeRequests }`。**16.5 引入，至今仍标 Experiment**。注意 `visibleMergeRequests` 的 `max_page_size: 20`（源码 `ee/app/graphql/types/merge_requests/blocking_merge_requests_type.rb`）。
- 写：`Mutation.mergeRequestSetBlockingMergeRequests`，参数 `blockingMergeRequestReferences: [String!]!`，接受 `"!123"` / `"project!456"` 这种引用串。源码 `ee/app/graphql/mutations/merge_requests/set_blocking_merge_requests.rb` 里显式检查 `licensed_feature_available?(:blocking_merge_requests)`，非 Premium 直接 `resource_not_available`。

版次来源（源码）：`ee/app/models/gitlab_subscriptions/features.rb` 的 `PREMIUM_FEATURES` 列表里有 `blocking_merge_requests`。所以是 **Premium 起**，不是 Ultimate。

#### 对评审的意义

语义是「合并顺序」，不是「同一组」。但它是唯一能被程序可靠读写、且双向可查的 MR↔MR 边。
实践上可以**借用**它当变更集的载体：平台识别出一组后，主动 `POST /blocks` 把 proto 仓 MR 设成其它 MR 的 blocker，既表达了正确的合并顺序，又让这组关系变成 GitLab 里可查询的结构化数据。代价是要 Premium，且一组超过 11 个 MR 就撞上限。

### 1.2 MR ↔ MR 的「relates to」：不存在

源码核对：`app/models/` 下只有 `issue_link.rb`（issue↔issue）。没有 `merge_request_link.rb` 这类模型。
`ee/app/models/vulnerabilities/merge_request_link.rb` 是漏洞↔MR，跟这里无关。

[Linked items](https://docs.gitlab.com/user/work_items/linked_items/)（Free）原文第一句：

> Linked items create bi-directional relationships between **work items**

work item = issue / epic / task / objective / key result。**MR 不是 work item**，整篇文档没出现过 merge request。

结论：想在两个 MR 之间打一条「相关」的边，GitLab 只能靠在描述里写引用（产生 cross-reference 系统备注），没有结构化关系可读。

### 1.3 issue → MR：两个端点，跨项目行为完全不同

这是本次调研最值得记的一条。

#### `GET /projects/:id/issues/:issue_iid/related_merge_requests` —— 跨项目可用

文档：[Issues API](https://docs.gitlab.com/api/issues/)。版次 Free。

源码链路：`lib/api/issues.rb:561` → `Issues::ReferencedMergeRequestsService#related_merge_requests`
（`app/services/issues/referenced_merge_requests_service.rb`）。

它的数据来源是**引用抽取**，不是数据库外键：

```ruby
def extract_merge_requests(issue, filter: nil)
  ext = issue.all_references(current_user)
  notes = issue_notes(issue)
  notes = notes.select(&filter) if filter
  notes.each { |note| note.all_references(current_user, extractor: ext) }
  ext.merge_requests
end
```

即：issue 的标题/描述 + issue 上的所有备注（**含系统备注**）里提到的 MR。
当某个 MR 的描述写了 `Closes group/project#123`，GitLab 会在 issue #123 上生成一条
`mentioned in merge request xxx!5` 的系统备注，这条备注被这里抽出来 —— 所以**别的项目的 MR 也能被捞到**。

跨项目那一层过滤器长这样：

```ruby
def filter_readable_by_user(merge_requests)
  cross_project_filter = ->(merge_requests) do
    merge_requests.select { |mr| mr.target_project == project }
  end
  Ability.merge_requests_readable_by_user(merge_requests, current_user,
    filters: { read_cross_project: cross_project_filter })
end
```

`apply_filters_if_needed`（`app/models/ability.rb:189`）只在 `allowed?(user, :read_cross_project)` 为**假**时才套这个过滤器。而 `app/policies/base_policy.rb`：

```ruby
rule { external_authorization_enabled & ~can?(:read_all_resources) }.policy do
  prevent :read_cross_project
end
rule { default }.enable :read_cross_project
```

`read_cross_project` **默认开启**，只有实例开了 external authorization control 才会被剥夺。
所以：**默认配置下这个端点返回跨项目 MR**。自托管实例如果开了外部授权，这条路会静默退化成只返回本项目。

#### `GET /projects/:id/issues/:issue_iid/closed_by` —— 只查本项目

同一份文档，看起来像是更「结构化」的那个（它读的是 `merge_requests_closing_issues` 表，不是文本抽取），
但源码 `lib/api/issues.rb:587` 把范围写死了：

```ruby
merge_request_ids = MergeRequestsClosingIssues.link_type_closes.where(issue_id: issue).select(:merge_request_id)
merge_requests = MergeRequestsFinder.new(current_user, project_id: user_project.id).execute.where(id: merge_request_ids)
```

`project_id: user_project.id` —— **只返回与 issue 同项目的 MR**。
底层表里明明有跨项目的行，端点自己把它们过滤掉了。

这条如果不看源码，光看文档会踩。**要跨项目就用 `related_merge_requests`，不要用 `closed_by`。**

#### GraphQL 侧

`Issue.relatedMergeRequests` 存在，但 reference 里明写：

> This field can only be resolved for **one issue** in any single request.

没法一次查一批 issue 的关联 MR，批量场景只能 N 次请求。

`WorkItemWidgetDevelopment.relatedMergeRequests` 是 **17.6 引入的 Experiment**，语义是「提到该 work item 的 MR」。

### 1.4 MR → issue：`closes_issues` 与 `related_issues`

文档：[Merge requests API](https://docs.gitlab.com/api/merge_requests/)，两个端点都是 Free：

```plaintext
GET /projects/:id/merge_requests/:iid/closes_issues    # 合并后会关掉的 issue
GET /projects/:id/merge_requests/:iid/related_issues   # 从标题/描述/commit message/评论里提到的 issue
```

`related_issues` 文档原文：

> List issues related to a merge request from its title, description, commit messages, comments, and discussions.

源码 `app/models/merge_request.rb:1952`，确实把 title + description + 可见备注 + 所有 commit message 拼起来跑 `ReferenceExtractor`。

**`closes_issues` 有个大坑**（源码 `app/models/merge_request.rb:1932`）：

```ruby
def closes_issues(current_user = self.author)
  if target_branch == project.default_branch
    ...
  else
    []
  end
end
```

**MR 的目标分支不是默认分支时，直接返回空数组。** 往 release 分支提的 MR，`closes_issues` 永远是空。
`related_issues` 没有这个限制。所以做关联推断应该优先用 `related_issues`。

另有 `MAX_CLOSING_ISSUES = 500` 上限（`lib/gitlab/closing_issue_extractor.rb`）。

#### closing pattern 支持跨项目引用

[Closing issues automatically](https://docs.gitlab.com/user/project/issues/managing_issues/#closing-issues-automatically) 列出的引用格式：

- 本项目 `#123`
- **跨项目 `group/project#123`**
- issue 全 URL
- work item 全 URL（project 或 group 级）

关键词：`Close(s|d|ing)` / `Fix(es|ed|ing)` / `Resolve(s|d|ing)` / `Implement(s|ed|ing)`，大小写都认。
仅 `Related to #5` 这种不在关键词里的，只建立关联不关闭。

默认正则（`config/gitlab.yml.example:166`，管理员可改，见 [Issue closing pattern](https://docs.gitlab.com/administration/issue_closing_pattern/)）：

```text
\b((?:[Cc]los(?:e[sd]?|ing)|\b[Ff]ix(?:e[sd]|ing)?|\b[Rr]esolv(?:e[sd]?|ing)|\b[Ii]mplement(?:s|ed|ing)?)(:?) +(?:(?:issues? +)?%{issue_ref}(?:(?: *,? +and +| *,? *)?)|([A-Z][A-Z0-9_]+-\d+))+)
```

末尾那个 `([A-Z][A-Z0-9_]+-\d+)` 就是 **Jira key 的形状**，下面第 4 节要用。

#### 持久化链接表

`app/models/merge_requests_closing_issues.rb`：

```ruby
enum :link_type, { closes: 0, mentioned: 1, related: 2 }, prefix: true
```

写入时机在 `MergeRequest#persist_merge_request_issues!`（`app/models/merge_request.rb:1894`），
每次重建 `from_mr_description` 的行。注意它 `reject { |issue| issue.is_a?(ExternalIssue) }` ——
**Jira 之类的外部 issue 不会写进这张表**，只能通过 `closes_issues` / `related_issues` 端点实时抽取。

`link_type: related` 的显式关联走 feature flag `explicit_mr_work_item_relations`
（`config/feature_flags/wip/explicit_mr_work_item_relations.yml`：milestone `19.1`，`type: wip`，
**`default_enabled: false`**）。也就是说「显式把 MR 挂到 work item 上」这个能力在 19.4 仍未 GA，不能依赖。

### 1.5 Linked issues（issue ↔ issue）

文档：[Linked issues](https://docs.gitlab.com/user/project/issues/related_issues/)、API [Issue Links](https://docs.gitlab.com/api/issue_links/)

- 跨项目：**支持**，原文 "You can link issues in different projects"。引用格式 `#44` / `project#44` / `group/project#44`。
- 版次：基础的 `relates_to` 是 **Free**；`blocks` / `is_blocked_by` 需 **Premium**。
- 权限：17.0 起最低角色从 Reporter 降到 **Guest**，且两个项目都要有角色。
- 只有双方都可见时 UI 才显示关系。

对我们的用法：如果需求被拆成多个 issue（每仓一个），可以用 linked issues 把它们串起来，
再对每个 issue 调 `related_merge_requests`。但这是两跳，且依赖团队真的这么建 issue。

### 1.6 Epic

文档：[Epics API](https://docs.gitlab.com/api/epics/)、[Epic Issues API](https://docs.gitlab.com/api/epic_issues/)

- 版次：**Premium、Ultimate**（不是 Ultimate 独占）。feature 不可用时 API 返回 `403`。
- **Epics REST API 在 17.0 被废弃**，计划在 API v5 移除。17.4~18.0 若启用 epics-as-work-items、以及 **18.1 及以后**，一律改用 Work Items API（见 [epic → work items 迁移指南](https://docs.gitlab.com/api/graphql/epic_work_items_api_migration_guide/)）。新接入不要写 Epics REST。
- 层级：epic → issue（`GET /groups/:id/epics/:epic_iid/issues`），epic **不能直接挂 MR**。要拿 MR 得再走一跳 issue → `related_merge_requests`。
- legacy Epic ID ≠ WorkItem ID，只有 `iid` 一致；响应里有 `work_item_id` 可换算成 `gid://gitlab/WorkItem/123`。

结论：epic 能当「需求」这一层的容器，但到 MR 是**两跳**，且中间那跳（issue→MR）依赖描述里写了引用。
对 300 仓 + 大量微服务的场景，代价是要求每个仓都建 issue 并挂到 epic 上。

### 1.7 `GET /groups/:id/merge_requests`

文档：[Merge requests API](https://docs.gitlab.com/api/merge_requests/)。**Free**。

源码 `lib/api/merge_requests.rb:288`：

```ruby
merge_requests = find_merge_requests(group_id: user_group.id, include_subgroups: true)
```

**总是包含子组**，不需要也没有 `include_subgroups` 参数。

可用过滤（对我们有用的）：

| 参数 | 说明 |
|---|---|
| `labels` | 逗号分隔，多标签是 AND；支持 `None` / `Any` |
| `milestone` | milestone **标题**（不是 ID） |
| `author_id` / `author_username` | 二选一 |
| `source_branch` / `target_branch` | **单个**分支名（精确匹配，不支持通配） |
| `created_after` / `created_before` / `updated_after` / `updated_before` / `merged_after` / `merged_before` | ISO 8601 时间窗 |
| `search` + `in=title,description` | 标题/描述文本搜索 |
| `not` | 取反，接受 `labels` / `milestone` / `author_*` / `assignee_*` / `reviewer_*` / `my_reaction_emoji` |
| `state` | `opened` / `closed` / `merged` / `locked` / `all` |
| `non_archived` | 默认 `true` |
| `scope` | group 级默认 `all`（注意：**instance 级 `GET /merge_requests` 默认是 `created_by_me`**） |

分页 `per_page` 最大 100（[REST API](https://docs.gitlab.com/api/rest/)）。

**GraphQL 的 `Group.mergeRequests` 比 REST 强一点**（源码 `app/graphql/resolvers/merge_requests_resolver.rb`）：

- `sourceBranches: [String!]` 和 `targetBranches: [String!]` 是**数组**，一次能查多个分支名；REST 只能给一个。
- `labelName: [String]`、`milestoneTitle`、`createdAfter/Before`、`or`（`UnionedMergeRequestFilterInputType`）、`not`（negated arguments）。
- 但 `includeSubgroups` 的 **default_value 是 `false`**（`app/graphql/resolvers/concerns/group_issuable_resolver.rb`），跟 REST 行为相反，容易踩。

19.1 起有个 `cache_list_mr_on_group_api_responses` 开关（`type: gitlab_com_derisk`，默认关），
自托管基本用不到，但说明 group 级 MR 列表在大 group 上是有性能压力的。

### 1.8 Milestone 跨项目

文档：[Milestones](https://docs.gitlab.com/user/project/milestones/)。**Free**。

原文：

> You can assign **group milestones** to any issue, epic, or merge request of **any project in that group**.

这是**最便宜的原生跨项目归组手段**：建一个 group milestone，让一个需求的所有 MR 都挂上去。
标题在 group 层级内唯一（含祖先和子孙的 group / project milestone），所以标题可以当稳定的 key。
还能把多个项目的同名 project milestone **promote** 成一个 group milestone（不可逆）。

两种查法，行为不一样：

1. `GET /groups/:id/milestones/:milestone_id/merge_requests` —— 文档 [Group milestones API](https://docs.gitlab.com/api/group_milestones/)，Free。
   **但源码里没传 `include_subgroups`**：`lib/api/milestone_responses.rb:102` 只 merge 了 `group_id: parent.id`，
   而 `app/finders/issuable_finder/params.rb:171`：

   ```ruby
   def find_group_projects
     if params[:include_subgroups]
       Project.where(namespace_id: group.self_and_descendant_ids)
     else
       group.projects          # ← 只有直属项目
     end
   end
   ```

   即 **这个端点只覆盖该 group 的直属项目，不含子组**。300 仓的实例几乎一定用了子组，这条会漏。

2. `GET /groups/:id/merge_requests?milestone=<标题>` —— 走 `include_subgroups: true`，**覆盖全子树**。

**实践上一律用第 2 种。**

### 1.9 CI：multi-project pipeline 和 merge train 跟评审关联无关

- [Downstream pipelines](https://docs.gitlab.com/ci/pipelines/downstream_pipelines/)（Free）：multi-project pipeline 是「A 项目的流水线触发 B 项目的流水线」。它建立的是**流水线之间**的父子关系，不产生 MR↔MR 的关联，也不知道 B 项目有没有对应的 MR。层级默认上限 1000 个下游流水线。
- [Merge trains](https://docs.gitlab.com/ci/pipelines/merge_trains/)（**Premium**）：队列的作用域是**单个项目的单个目标分支**，全文没有任何跨项目语义。两个仓的 MR 不可能进同一列车。
- GitLab CI **没有** Zuul 的 `Depends-On:` 那种跨仓依赖调度（在 `doc/ci/` 全目录 grep `Depends-On` 无结果）。想要「proto 仓的 MR 和服务仓的 MR 一起跑集成测试」，只能自己用 trigger token + 变量传 ref 拼。

唯一沾边的是 §1.1 的 MR dependencies —— 它影响的是**能不能合**，不是能不能一起跑。

## 2. Webhook 侧

文档：[Webhooks](https://docs.gitlab.com/user/project/integrations/webhooks/)、[Webhook events](https://docs.gitlab.com/user/project/integrations/webhook_events/)、[Group webhooks API](https://docs.gitlab.com/api/group_webhooks/)

### 2.1 载荷里有什么、没什么

MR 事件载荷的字段白名单在源码 `lib/gitlab/hook_data/merge_request_builder.rb`（比文档更权威）。

**有的、能当关联信号的**：

| 字段 | 用途 |
|---|---|
| `object_attributes.source_branch` | 分支命名约定的载体 |
| `object_attributes.target_branch` | 判断是否默认分支（影响 `closes_issues` 是否有值） |
| `object_attributes.title` / `description` | 文本里的 issue / MR / Jira 引用 |
| `object_attributes.milestone_id` | **只有 ID**，要拿标题得再查一次 |
| `labels` / `object_attributes.labels` | label 对象数组，**含 name**，不用再查 |
| `object_attributes.last_commit` | **只有 head commit**，含 `message`，可解析 trailer |
| `project` / `object_attributes.source` / `target` | 项目信息 |
| `changes` | 本次变了哪些字段（含 `labels`、`description`） |

**没有的**：

- 兄弟 MR：没有任何字段。
- blocking / blocked MR：`safe_hook_attributes` 里没有。
- 关联的 issue：没有。`closes_issues` 的结果不进载荷。
- commit 列表：只有 `last_commit` 一条，**拿不到整个分支的 commit message**，所以 `Refs:` trailer 写在非 head commit 上就看不见。

结论：**单凭一个 MR 事件的载荷，推不出它的兄弟 MR。** 必须补 API。

### 2.2 补几次 API

从一个 MR 事件出发，找兄弟 MR 的最短路径：

| 路线 | 调用次数 | 前提 |
|---|---|---|
| 走 MR dependencies | 2（`/blocks` + `/blockees`） | Premium，且有人真的建了依赖 |
| 走 issue | 2（`/merge_requests/:iid/related_issues` → 对每个 issue `/issues/:iid/related_merge_requests`） | 实际是 1 + N（N = 关联 issue 数） |
| 走 group milestone | 2（`GET /projects/:id/merge_requests/:iid` 拿 `milestone.title` → `GET /groups/:gid/merge_requests?milestone=<标题>`） | 载荷只给 `milestone_id`。**不要去查 `/projects/:id/milestones/:mid`** —— 那个 ID 可能是 group milestone，会 404；从 MR 详情里取 `milestone` 对象最稳 |
| 走 label | 1（`GET /groups/:gid/merge_requests?labels=<name>&state=opened`） | label 名字载荷里就有，**最省** |
| 走分支名 | 1（`GET /groups/:gid/merge_requests?source_branch=<name>`） | 要求各仓分支名完全一致 |
| 走文本搜索 | 1（`GET /groups/:gid/search?scope=merge_requests&search=PROJ-123`） | basic search 是 Free；精度差 |

最省的是 label 和分支名这两条（各 1 次调用，且 key 直接在载荷里）。

### 2.3 group webhook vs project webhook

| | project webhook | group webhook |
|---|---|---|
| 版次 | **Free** | **Premium**（`doc/user/project/integrations/webhooks.md:58` 的 details 块，API 文档同） |
| 覆盖范围 | 单项目 | 该 group **及其所有子组**的全部项目 |
| 配置权限 | Maintainer / Owner | **group Owner** |
| 载荷 | 同一套 | 同一套，**没有额外的 group 上下文字段** |

文档明说：group 和 project 同时配了相同 webhook，**两个都会触发**（会收到重复事件，去重靠 `Idempotency-Key`）。

关键点：**group webhook 的载荷跟 project webhook 一模一样**，它只是省掉了「给 300 个仓逐个配 hook」的运维成本，
并不会因为是 group 级就多告诉你任何跨项目信息。

对 300 仓的实例，group webhook（Premium）基本是必需的 —— 否则新建仓库就漏事件。
如果只有 Free，替代方案是拿 group 级 service account 的 PAT 批量给每个项目建 project hook，
再用 `project_create` 系统钩子（或定时任务）给新仓补建。

### 2.4 交叉引用的写入早于 webhook（源码）

这条对及时性很关键。`app/services/merge_requests/after_create_service.rb`：

```ruby
def execute(merge_request)
  merge_request.ensure_merge_request_diff
  MergeRequests::AfterCreateEventPublisher.new(merge_request).defer_to_mergeability_check
  prepare_for_mergeability(merge_request)
  prepare_merge_request(merge_request)      # ← 里面做交叉引用
  mark_merge_request_as_prepared(merge_request)
  execute_hooks(merge_request)              # ← webhook 在这之后
end

def prepare_merge_request(merge_request)
  ...
  merge_request.create_cross_references!(current_user)
  todo_service.new_merge_request(merge_request, current_user)
  merge_request.persist_merge_request_issues!(current_user)
  ...
end
```

`create_cross_references!` 和 `persist_merge_request_issues!` 都排在 `execute_hooks` **之前**，同一个
Sidekiq job（`NewMergeRequestWorker`）里。所以：

**收到 `action: open` 的 webhook 时，这个 MR 对 issue 的引用已经落库了，立刻反查 `related_merge_requests` 能看见自己。**

这不解决「兄弟 MR 还没创建」的问题，但至少排除了「自己刚建完但查不到自己」这种竞态。
MR 更新路径（`app/services/issuable_base_service.rb`）同样是 `after_update` 之后才 `execute_hooks`。

## 3. 人工声明分组：用哪个原生机制承载（本次调研重点）

MVP 不做自动推断，改由开发者主动声明「这几个 MR 是一组」。
那问题就变成：**GitLab 里哪个对象最适合当这个声明的载体。**

候选一共五个：group label、group milestone、issue 引用、MR dependencies、MR 描述里的自定义标记。
按四个维度逐个过。

### 3.1 四个维度的判据

- **开发者操作成本**：提 MR 时顺手能不能做完？最好是 `git push` 那一行里就带上，不用开浏览器。
- **读取可靠性与接口便利度**：平台拿到一个 MR，要几次调用才能拿到全组？webhook 载荷里直接有没有？
- **跨项目支持**：是不是真的跨项目，还是要每个项目各配一份。
- **Free 够不够**：自托管 CE 能不能用。

### 3.2 逐个评估

#### 候选 A：label（推荐）

**开发者操作成本：最低。** git push options 直接支持（[Git push options](https://docs.gitlab.com/topics/git/commit/#push-options-for-merge-requests)）：

```shell
git push -o merge_request.create \
         -o merge_request.label="cs::PROJ-123"
```

文档原文：

> `merge_request.label="<label>"` Add labels to the merge request. **If the label does not exist, it is created.**

源码核对（`app/services/merge_requests/push_options_handler_service.rb:181`）：

```ruby
params[:add_labels] = params.delete(:label).keys if params.has_key?(:label)
```

`add_labels` 走 `Issuable::Callbacks::Labels#normalize_and_filter_param`，
`create_when_missing: true` → `Labels::AvailableLabelsService#find_or_create_by_titles`
（`app/services/labels/available_labels_service.rb`），`include_ancestor_groups: true`。

含义很重要：

- **已存在同名 group label → 复用那个 group label**；
- 都没有 → 在**当前 project** 建一个 project label。

所以最好由平台在需求立项时先 `POST /groups/:id/labels` 建一个 group label，
否则 300 个仓会各自堆同名 project label（功能上不影响查询，见下，只是脏）。

其它声明方式：MR 描述里的 quick action `/label ~"cs::PROJ-123"`（需要标签已存在）、
MR 模板预填、REST `PUT /projects/:id/merge_requests/:iid` 带 `add_labels`。

**读取便利度：最高。**

- webhook 载荷**直接带 label 的名字**（`labels` 数组、`object_attributes.labels`，源码 `lib/gitlab/hook_data/merge_request_builder.rb` 的 `labels: merge_request.labels_hook_attrs`）。不用额外查询就知道这个 MR 属于哪个变更集。
  注意载荷里的字段名是 **`title`** 不是 `name`（`app/models/label.rb:271` 的 `hook_attrs`），
  而 API 的过滤参数叫 `labels=`。两者指的是同一个东西 —— `app/models/label.rb:144` 有 `alias_attribute :name, :title`，
  数据库里只有 `title` 列。
  载荷里每个 label 还带 `type`（`"ProjectLabel"` / `"GroupLabel"`）和 `project_id` / `group_id`，
  所以平台能直接判断这次声明用的是 group label 还是各仓自建的 project label。
- 拿全组：**一次调用**
  ```plaintext
  GET /groups/:id/merge_requests?labels=cs::PROJ-123&state=opened&per_page=100
  ```
  含全部子组（源码 `lib/api/merge_requests.rb:288` 写死 `include_subgroups: true`）。
- 变更审计：`GET /projects/:id/merge_requests/:iid/resource_label_events`（[Resource label events API](https://docs.gitlab.com/api/resource_label_events/)，Free），返回每次 `add` / `remove`、操作人、时间戳。对账用。

**跨项目：真跨。** 关键在过滤是**按名字**匹配，不是按 label ID（源码 `app/finders/issuables/label_filter.rb:28`）：

```ruby
relation = relation.joins(:label).where(labels: { name: label_names }) if label_names
```

所以就算每个项目各建了一个同名的 project label，`?labels=cs::PROJ-123` 照样一网打尽。
这条性质让 label 方案在「没有 Premium、没法建 group label 的极端情况」下也能退化工作。

**Free 够用：够。**

| 依赖项 | 版次 |
|---|---|
| [Labels](https://docs.gitlab.com/user/project/labels/) | Free |
| [Group labels API](https://docs.gitlab.com/api/group_labels/) | Free |
| group 级 MR 列表按 label 过滤 | Free |
| [Resource label events API](https://docs.gitlab.com/api/resource_label_events/) | Free |
| label 归档（清理用）| Free，**18.11 GA**（18.3 引入，FF `labels_archive`；group labels API 文档写 18.10 GA） |
| scoped label 的**互斥**语义（`key::value` 同 key 只能有一个） | **Premium** |

注意最后一行：`cs::PROJ-123` 这种写法在 Free 下**只是一个名字里带 `::` 的普通 label**，
不会有「一个 MR 只能属于一个变更集」的强制。要这个强制得 Premium。
MVP 阶段不需要，但要知道 Free 下一个 MR 可以同时挂多个 `cs::*`，平台得自己决定怎么处理。

**缺点**：

- 一个变更集一个 label，长期会堆积。缓解手段是合并后归档（18.11+ GA，Free），归档后 label 仍留在历史 MR 上且仍可搜。19.x 实例没问题，低于 18.11 的实例只能删或者放着。
- label 名字由人手输，拼错了就落到另一个组。要么让平台生成、要么加 CI 校验。

#### 候选 B：group milestone

**开发者操作成本：中。** push option 支持 `-o merge_request.milestone="3.0"`，但源码
（`app/services/merge_requests/push_options_handler_service.rb:187`）是**只找不建**：

```ruby
if push_options[:milestone]
  milestone = Milestone.for_projects_and_groups(@project, @project.ancestors_upto)&.find_by_name(push_options[:milestone])
  params[:milestone_id] = milestone.id if milestone
end
```

milestone 必须先在项目或祖先 group 里存在，且**找不到会静默忽略**（没有报错）。
建 group milestone 需要 group 层的 Planner 及以上角色。比 label 多一道前置。

**读取便利度：中。**

- webhook 载荷只给 `object_attributes.milestone_id`，**没有标题**。要知道是哪个 milestone 得多查一次，
  而且得查 `GET /projects/:id/merge_requests/:iid` 取里面的 `milestone.title` —— 直接查
  `/projects/:id/milestones/:mid` 在这个 ID 是 group milestone 时会 404。
- 拿全组：`GET /groups/:id/merge_requests?milestone=<标题>`，一次调用，按**标题**匹配
  （源码 `app/models/concerns/milestoneable.rb:24`：`where(milestones: { title: title })`），含子组。
- 不要用 `GET /groups/:id/milestones/:milestone_id/merge_requests`，它**不含子组**（见 §1.8）。
- 有 `resource_milestone_events` 做审计。

**跨项目：真跨**（group milestone 可挂给 group 内任意项目的 MR）。标题在 group 层级内唯一，是天然稳定 key。

**Free 够用：够。**

**为什么不推荐当主载体**：

- **一个 MR 只能有一个 milestone。** 团队如果已经用 milestone 管版本/迭代，就被占用了，两种用途互斥。
- 前置成本（必须先建）和读取多一跳，都比 label 差。
- 语义上 milestone 是「一批工作在某个时间点交付」，粒度比「一个需求」粗。

适合的场景：团队本来就没用 milestone，而且一个需求就是一次发布。否则别选。

#### 候选 C：issue 引用（`Closes group/project#123`）

**开发者操作成本：低到中。** 如果团队已经用 GitLab issue 管需求，MR 模板里预填一行就行；
push option `-o merge_request.description="Closes group/project#123"` 也能带。
如果团队不用 GitLab issue（需求在 Jira），这条路直接断（见 §5）。

**读取便利度：差。**

- webhook 载荷**不带关联 issue**，要先 `GET /projects/:id/merge_requests/:iid/related_issues`。
- 再对每个 issue 调 `GET /projects/:id/issues/:iid/related_merge_requests`。
- 合计 **1 + N 次调用**，N = 关联 issue 数。
- 而且 `related_merge_requests` 是**引用抽取**（扫 issue 的描述和系统备注），不是外键查询，
  实例开了 external authorization control 会静默退化成只返回本项目（§1.3）。
- `closed_by` 看着更结构化，但**写死了只查本项目**，不能用。

**跨项目：能**（`group/project#123` 引用格式受支持，`related_merge_requests` 默认跨项目）。

**Free 够用：够。**

**结论：作为第二信号保留，不作主载体。** 它的价值是天然把「需求」和「代码」连起来，
而且是团队本来就在做的事（写 `Closes #123`），零额外心智负担。
平台可以把它当作 label 声明缺失时的兜底。

#### 候选 D：MR dependencies

**开发者操作成本：高。** 声明时必须引用**具体的兄弟 MR**，而兄弟 MR 在提第一个 MR 时通常还不存在。
push option 不支持。只能事后在 UI 或 API 里补。

**读取便利度：好**（双向端点 `/blocks` + `/blockees`，2 次调用拿全链）。

**跨项目：能**（只受 isolated organization 限制）。

**Free 够用：不够，Premium。** 且一个 MR 最多 10 个 blocker / 10 个 blockee。

**结论：不作为声明载体。** 但值得反向用 —— 平台靠 label 识别出一组之后，
主动 `POST /blocks` 把 proto 仓的 MR 设成其它 MR 的 blocker。
这样既表达了正确的合并顺序（GitLab 会拦住提前合并），又让这组关系在 GitLab 里变成可查的结构化数据。
这是「有 Premium 时的增值项」，不是 MVP 必需。

#### 候选 E：MR 描述里的自定义标记（`Change-Set: CS-123`）

**开发者操作成本：低**（模板预填）。

**读取便利度：差。** 没有结构化字段可查：

- 只能 `GET /groups/:id/search?scope=merge_requests&search=CS-123`。basic search 是 Free，但精度差（会命中描述里任何提到这串的 MR），且没有精确匹配语义。
- Advanced search（Elasticsearch）精度好但是 **Premium**（[Search API](https://docs.gitlab.com/api/search/)）。
- 变更感知只有 `changes.description` 的 previous/current，得自己 diff 文本抽标记。

**跨项目：能**（搜索是 group 级的）。

**Free 够用：勉强**（basic search 可用，但不可靠）。

**结论：不推荐。** 除非需要在标记里带结构化载荷（label 名字塞不下的信息），
那可以 label 做 key、描述做 payload。

### 3.3 推荐

**主载体用 group label，命名约定 `cs::<需求ID>`。第二信号保留 issue 引用。有 Premium 时再用 MR dependencies 表达合并顺序。**

理由按权重排：

1. **只有 label 能在 `git push` 那一行里声明完，且标签不存在会自动创建**（源码确认）。其它候选要么要先建对象（milestone）、要么要引用还不存在的东西（dependencies）、要么依赖团队用 GitLab issue（issue 引用）。开发者操作成本是 MVP 能不能落地的第一约束。
2. **webhook 载荷直接带 label 名字（`labels[].title`），拿全组只要一次 group 级调用。** 这是候选里唯一做到「零额外查询就知道自己属于哪组 + 一次查询拿到全组」的。
3. **过滤按名字匹配，group label 和同名 project label 都命中**，所以跨项目是真跨，而且没有「必须先建 group label」的硬前置 —— 前置只是为了干净。
4. **全链路 Free**：group labels API、group MR 列表按 label 过滤、resource label events、label 归档，都是 Free。唯一 Premium 的是 scoped label 互斥语义和 group webhook —— 后者不管选哪个方案都得有。
5. **声明的建立与变更都有事件**（§6.3），不需要轮询兜底（对账除外）。

落地清单：

- 顶层 group 建 label 前缀约定，平台在需求立项时 `POST /groups/:id/labels` 预建 `cs::<需求ID>`（Free）。
- 给开发者一条命令：`git push -o merge_request.create -o merge_request.label="cs::PROJ-123"`。也可以包成 git alias。
- MR 模板里留一行 `Closes <issue 引用>` 当第二信号。
- 平台侧自己维护变更集表，label 只是**声明通道**，不是存储。理由见 §10.1：GitLab 里没有任何对象能表示「一个变更集」，label 被删掉、改名、拼错都不会有人告诉你。
- 变更集合并完成后归档 label（18.11+，Free）。

### 3.4 一个需要提前定的产品问题

Free 下 `::` 只是普通字符，一个 MR 可以同时挂 `cs::PROJ-123` 和 `cs::PROJ-456`。
平台要么允许一个 MR 属于多个变更集（评审时合并上下文），要么按「最后添加的那个」取（`resource_label_events` 能判断先后）。
这个得先定，否则两边实现会打架。

## 4. 约定驱动的推断（降为参考）

MVP 不做自动推断，这节只记录「以后想从人工声明走向半自动时，哪条信号最容易接上去」。

### 4.1 各约定的可靠性与落地成本

| 约定 | 载荷里直接可见 | 读取方式 | 可强制手段 | 可靠性 |
|---|---|---|---|---|
| 分支命名 `feature/PROJ-123-xxx` | **是**（`object_attributes.source_branch`） | `GET /groups/:id/merge_requests?source_branch=<名>`，一次调用 | **Push Rules 的 `branch_name_regex`（Premium）** | 中：名字要各仓完全一致，改名代价高 |
| commit trailer `Refs: PROJ-123` | **否**，载荷只有 `last_commit` 一条 | 要 `GET /projects/:id/merge_requests/:iid/commits` 再解析 | Push Rules 的 `commit_message_regex`（Premium） | 低：trailer 写在非 head commit 上就漏 |
| MR 描述交叉引用 | 是（`description`） | 自己正则，或走 `related_issues` | MR 模板（group 级模板要 **Premium**） | 中 |
| 统一 label | 是（`labels`） | 一次 group 级调用 | CI 校验 / 平台预建 | 高 |
| 统一 milestone | 部分（只有 `milestone_id`） | 一次 group 级调用（多一跳换标题） | — | 高 |
| 时间窗 + 作者启发式 | — | `?author_username=X&created_after=...` | — | 低：误合并，不适合当判据 |

**最容易接上去的是分支命名。** 理由：

- 它是唯一一个**载荷里直接可见、且能用一次 group 级调用精确查全组**的推断信号（`source_branch` 精确匹配）。
- GraphQL 的 `Group.mergeRequests(sourceBranches: [...])` 接受**数组**，一次能查多个候选分支名；REST 只能给一个（§1.7）。
- Push Rules（**Premium**，[Push rules](https://docs.gitlab.com/user/project/repository/push_rules/)、[Group push rules API](https://docs.gitlab.com/api/group_push_rules/)）的 `branch_name_regex` 能在 group 层强制分支名格式，把「人会写错」这个主要失效模式堵掉。group push rule 对新建仓库自动生效，300 仓的运维成本可控。

半自动的形态：平台从分支名解析出候选需求 ID，**生成一个建议**（「看起来这 3 个 MR 属于 PROJ-123，要不要归为一组？」），
让人一键确认成正式声明（即打上 `cs::PROJ-123` label）。推断只用来降低声明成本，不直接当事实。

commit trailer 这条不建议接：webhook 载荷只有 head commit，必须额外拉 commits 列表，
而且 squash / rebase 会改写 trailer 所在的 commit。投入产出比最差。

### 4.2 工业先例

详见 §8.1 / §8.2。一句话：Gerrit 的 **topic**（`git push -o topic=xxx`）和 Zuul 的 **`Depends-On:`** 都是
「开发者主动声明」而不是「系统推断」，和本次 MVP 路线一致，它们踩过的坑可以直接抄作业。

## 5. 外部工单系统（Jira）

文档：[Jira](https://docs.gitlab.com/integration/jira/)、[Jira development panel](https://docs.gitlab.com/integration/jira/development_panel/)。整体 **Free**。

GitLab 有两套 Jira 集成，作用完全不同：

| | Jira issues integration | Jira development panel |
|---|---|---|
| 方向 | GitLab 侧展示 Jira issue；在 GitLab 里提 Jira key 会**在 Jira issue 上留评论** | Jira 侧展示 GitLab 的分支 / commit / MR |
| 实现 | GitLab 自研 | Jira Cloud 用 [GitLab for Jira Cloud app](https://docs.gitlab.com/integration/jira/connect-app/)；Jira DC/Server 用 Atlassian 的 [DVCS connector](https://docs.gitlab.com/integration/jira/dvcs/) |
| 同步延迟 | 实时 | app 实时；**DVCS connector 最长 60 分钟** |
| 分支名里的 Jira key | **不认** | **认** |

### 5.1 对我们有用的部分

**GitLab 侧能直接读到 Jira key。** 开了 Jira issues integration 之后：

```plaintext
GET /projects/:id/merge_requests/:iid/closes_issues
GET /projects/:id/merge_requests/:iid/related_issues
```

会返回外部 issue（源码 `lib/api/merge_requests.rb:997`，把结果 partition 成 `ExternalIssue` 和 `Issue` 两类）：

```json
[ { "id": "PROJECT-123", "title": "Title of this issue" } ]
```

能认出来是因为默认 closing pattern 末尾有 `([A-Z][A-Z0-9_]+-\d+)`（§1.4），
和 `Gitlab::Regex.jira_issue_key_regex`（`lib/gitlab/regex.rb:221`）一致：

```ruby
/#{expression_escape}([A-Z][A-Z_0-9]+-\d+)/
```

**但外部 issue 不落库。** `MergeRequest#persist_merge_request_issues!`
（`app/models/merge_request.rb:1900`）明确 `reject { |issue| issue.is_a?(ExternalIssue) }`。
所以：

- 没有「给我所有关联 PROJ-123 的 MR」这样的反查端点。GitLab 侧只能正查（MR → Jira key），不能反查。
- 反查只能靠 §3 里那几条：label / milestone / 分支名 / group search。

### 5.2 结论

需求真源在 Jira 时：

- **Jira dev panel 已经在 Jira 那边聚合好了跨仓 MR**（按 Jira key 归拢分支、commit、MR），但那是给人看的，GitLab 侧拿不到这份聚合，要读得走 Jira 自己的 API。
- GitLab 侧的关联仍然要靠 §3 的方案。**Jira key 正好可以直接当变更集 ID** —— label 就叫 `cs::PROJ-123`，和 Jira 一一对应，不用再发明一套 ID。这是 Jira 场景下推荐 label 方案的额外理由。
- 用 Jira DC/Server + DVCS connector 的话注意那 60 分钟同步延迟，不要把 Jira 当实时数据源。

## 6. 及时性（人工声明路线下重新回答）

这是 MVP 最需要想清楚的一节。声明是人做的，所以声明**有先后**，而且可能迟到、可能变。

### 6.1 声明可以在 MR 创建那一刻就存在

这是 label 方案相对其它候选的关键优势：

```shell
git push -o merge_request.create -o merge_request.label="cs::PROJ-123"
```

MR 被创建时 label 就已经挂上，`action: open` 的 webhook 载荷里 `labels` 数组**直接带着它**。
平台在第一个事件就知道这个 MR 属于 `cs::PROJ-123`。

用 milestone 或 issue 引用也能在创建时带上（push option 的 `merge_request.milestone` / `merge_request.description`），
但 milestone 要先存在、issue 引用要多查一跳。

### 6.2 「这是一组里的第一个」—— 能知道，但知道的是「声明」不是「事实」

平台在第一个 MR 到达时能知道：**它声明了自己属于 `cs::PROJ-123`，而这个组目前只有它一个成员。**

一次调用就能确认：

```plaintext
GET /groups/:id/merge_requests?labels=cs::PROJ-123&state=opened
```

返回 1 条 → 这是第一个。

但平台**不知道这一组最终会有几个 MR**。GitLab 里没有任何地方能声明「这个变更集预计包含 proto 仓 + 订单服务 + 前端」。
所以「改了契约没改调用方」这类问题，在第一个 MR 到达时仍然看不见 —— 除非平台自己让人在声明时填清单（见 §8）。

这一点和自动推断路线相比没有变好：**人工声明解决的是「这些 MR 是一组」的准确性，没有解决「这一组还缺谁」。**

### 6.3 声明迟到、变更，平台能不能感知 —— 能，有事件，不需要轮询

这是本节的核心结论。

label 的增删走 `MergeRequests::UpdateService` → `app/services/issuable_base_service.rb:368` 的
`execute_hooks(issuable, 'update', old_associations:)`，产生一个 `action: update` 的 MR 事件。
文档里 `changes` 字段的属性清单（[Webhook events](https://docs.gitlab.com/user/project/integrations/webhook_events/)）明确包含：

- `labels`
- `milestone_id`
- `description`
- `title`

格式是 `{ "previous": ..., "current": ... }`，所以能直接算出「加了哪个 label / 删了哪个 label」。

对应到三种迟到场景：

| 场景 | 平台怎么知道 |
|---|---|
| MR 先建，后打 label | 收到该 MR 的 `update` 事件，`changes.labels` 里 current 比 previous 多一个 |
| 组里第二个 MR 后建 | 收到新 MR 的 `open` 事件，载荷里就带 label，直接归组 |
| 有人把 label 删了 / 改到另一个组 | `update` 事件，`changes.labels` 能算出差异 |
| milestone 被改 | `update` 事件，`changes.milestone_id`（**只有 ID**，要换标题） |
| MR 描述里补了 `Closes ...` | `update` 事件，`changes.description`，自己 diff 文本 |

**所以正常路径下不需要轮询。** 但有两个必须补对账的理由：

1. **webhook 会被自动禁用。** [Auto-disabled webhooks](https://docs.gitlab.com/user/project/integrations/webhooks/)：连续失败 4 次 → temporarily disabled（先停 1 分钟，逐次拉长到最多 24 小时）；连续失败 40 次 → **permanently disabled**（17.11 起）。group webhook 的自动禁用 **15.10** 引入；project webhook 在**自托管上由 feature flag `auto_disabling_web_hooks` 控制，默认关**。也就是说自托管的 group webhook 会被禁、project webhook 默认不会 —— 两边行为不一致，得按实例实际情况确认。
2. **事件本身可能丢。** 投递失败重试次数有限。

对账手段（都是 Free）：

- 周期性 `GET /groups/:id/merge_requests?labels=cs::*&updated_after=<上次对账时间>` —— 注意 `labels` **不支持通配**，只能按已知的活跃变更集 ID 逐个查，或者用 `?labels=Any` 拉全量再过滤。
- 单个 MR 的声明历史：`GET /projects/:id/merge_requests/:iid/resource_label_events`，有 `action`（`add`/`remove`）、`user`、`created_at`。这是判断「声明先后顺序」的权威来源，比 webhook 可靠。

### 6.4 一个仍然存在的时间差

即使声明在 MR 创建时就带上，**兄弟 MR 本身还没创建**这件事是没法解决的。

可选的产品策略（都需要平台侧状态，GitLab 不提供）：

- **等**：第一个 MR 到达后不立刻评审，等一个时间窗（或等人点「这组齐了」）。代价是延迟。
- **增量**：先评审第一个，每来一个新成员就把全组上下文重新喂一遍，补发跨 MR 的结论。代价是重复评审和噪声。
- **声明时填清单**：让人在立项时就声明「这个变更集涉及哪几个仓」，平台据此知道还缺谁，缺的时候可以明确说「proto 改了，订单服务的 MR 还没来」。这是唯一能让「改了契约没改调用方」在第一个 MR 时就可见的做法，但把成本推给了人。

## 8. 工业先例与参考链接

### 8.1 Gerrit 的 topic —— 和本次推荐同构的成熟先例

一手文档：[Submitting Changes Across Repositories by using Topics](https://gerrit-review.googlesource.com/Documentation/cross-repository-changes.html)（Gerrit v3.14）

这是公开工程实践里**最接近「人工声明一组跨仓变更」**的东西，而且形状和我们的 label 方案几乎一样。原文要点：

> A topic is a string that can be associated with a change.
> Multiple changes can use that topic to be submitted at the same time.

声明方式 —— 注意和 GitLab 的 `git push -o merge_request.label=` 是同一个手势：

```shell
git push origin HEAD:refs/for/master%topic=[YOUR_TOPIC_NAME]
# 或
git push origin HEAD:refs/heads/master -o topic=[YOUR_TOPIC_NAME]
```

也可以在 UI 上事后补（change 页面的 **ADD TOPIC**）。评审仍然是**逐个 change 单独投票**，
topic 只影响提交（submit）时机：

> When `config.submitWholeTopic` is enabled, submitting a change within a topic
> causes all of the changes in the topic to be submitted together.

Gerrit 自己列出的坑，**每一条都能直接搬到我们的 label 设计上**：

| Gerrit 原文的坑 | 映射到 GitLab label 方案 |
|---|---|
| "A topic can be any string, and they are **not namespaced**; there is a chance for collisions and inadvertently grouping changes together that weren't meant to be grouped." | label 名字同样无命名空间。Gerrit 的建议是**加前缀**（`username-`）；我们用 `cs::<需求ID>` 前缀是同一个思路 |
| "This could even happen with changes **you can't see**" | 对应 §10.5：token 看不到的 MR 会静默消失，反过来也可能有看不见的 MR 混进同名组 |
| "Topics that span multiple repositories simply triggers submission of all changes. **No other guarantees are given** … you could get a partial topic submission." | 跨仓「一起合」本身就没有原子性保证，Gerrit 这种成熟系统也没做到。别在产品上承诺原子合并 |
| "Topics can only be used for changes within a **single Gerrit instance**." | 同理，方案只在单个 GitLab 实例内成立 |

另外 Gerrit 有一个我们值得抄的东西：submit 之后生成一个 **`submission_id`**，可以在搜索栏里查出这次提交涉及的所有 change。
这正是「变更集」作为一等对象的样子 —— GitLab 没有（见 §10.1），得平台自己造。

### 8.2 Zuul 的 `Depends-On:` —— 显式声明跨仓依赖

一手文档：[Zuul — Cross-Project Dependencies](https://zuul-ci.org/docs/zuul/latest/gating.html)

原文：

> Zuul permits users to specify dependencies across projects. Using a special footer,
> users may specify that a change depends on another change in **any repository known to Zuul**.
> In Gerrit based projects this footer needs to be added to the git commit message.
> In GitHub based projects this footer must be added to the **pull request description**.

语法就是 commit message（或 PR 描述）里一行：

```text
Depends-On: https://review.example.com/3
Depends-On: https://github.com/example/test/pull/4
```

语义：有向无环图，单向依赖（A 可以依赖 B，B 不能反过来依赖 A）。
**甚至可以跨系统**（Gerrit 的 change 依赖 GitHub 的 PR）。

调度语义值得注意：

> if change A depends on B, then when they are added to a dependent pipeline, B will appear first and A will follow.
> If tests for B fail, both B and A will be removed from the pipeline.

以及一条限制：

> If changes with cross-project dependencies **do not share a change queue** then Zuul is unable to enqueue them together,
> and the first will be required to merge before the second can be enqueued.

对我们的启发：Zuul 把「声明」放在 **PR 描述**里（GitHub 场景），而不是靠平台推断 —— 和本次 MVP 路线一致。
GitLab 侧最接近的等价物是 MR dependencies（§1.1），但 GitLab CI **没有** Zuul 这种「按依赖关系串起来一起跑」的调度能力（§10.9）。

## 9. 可用的关联信号

按「可靠性 + 及时性」排序。及时性分三档：

- **创建即有**：MR 建出来的那一刻信号就在 webhook 载荷里。
- **可事件感知**：信号后补或变更时，有 `update` 事件能捞到。
- **只能轮询**：没有对应事件，得定期扫。

| # | 信号 | 怎么读 | 调用次数 | 跨项目 | 及时性 | 可靠性 | 版次 |
|---|---|---|---|---|---|---|---|
| 1 | **label（人工声明）** | 载荷 `labels[].title`；`GET /groups/:id/merge_requests?labels=X&state=opened` | **0 + 1** | 真跨（按名字匹配，含子组） | **创建即有**（push option）+ 可事件感知（`changes.labels`） | 高。人工输入可能拼错，可用 CI 或平台预建缓解 | **Free** |
| 2 | MR dependencies | `GET .../blocks` + `GET .../blockees` | 2 | 真跨（只受 organization 隔离限制） | 差。声明时兄弟 MR 常常还不存在，只能事后补；载荷里没有 | 高。结构化、双向、可写 | **Premium**；10 blocker / 10 blockee 上限 |
| 3 | group milestone | 载荷 `milestone_id`（**无标题**）；`GET /groups/:id/merge_requests?milestone=<标题>` | 1 + 1 | 真跨（按标题匹配，含子组） | 创建即有（push option，但 milestone 须先存在）+ 可事件感知（`changes.milestone_id`） | 高。标题在 group 层级内唯一。但一个 MR 只能有一个 milestone | **Free** |
| 4 | issue 引用 → `related_merge_requests` | `GET .../merge_requests/:iid/related_issues` → 对每个 issue `GET .../issues/:iid/related_merge_requests` | **1 + N** | 默认跨；实例开 external authorization 后**静默退化成本项目** | 创建即有（描述里写了就算）+ 可事件感知（`changes.description`） | 中。引用抽取而非外键；`closes_issues` 在非默认目标分支恒为空 | **Free** |
| 5 | 分支名约定 | 载荷 `source_branch`；`GET /groups/:id/merge_requests?source_branch=<名>`（GraphQL 支持数组） | **0 + 1** | 真跨 | **创建即有** | 中。要求各仓分支名完全一致；Push Rules 可强制格式（Premium） | Free（强制要 Premium） |
| 6 | MR 描述自定义标记 | `GET /groups/:id/search?scope=merge_requests&search=X` | 0 + 1 | 真跨 | 创建即有 + 需自己 diff `changes.description` | 低。basic search 无精确匹配语义；Advanced search 精度好但 Premium | Free（精确要 Premium） |
| 7 | commit trailer `Refs:` | 载荷只有 `last_commit`；要 `GET .../merge_requests/:iid/commits` 再解析 | 1 + 全组扫描 | 需自己建索引 | 创建即有（但载荷不全） | 低。trailer 在非 head commit 上就漏；squash / rebase 会改写 | Free（强制要 Premium） |
| 8 | 作者 + 时间窗启发式 | `GET /groups/:id/merge_requests?author_username=X&created_after=...` | 1 | 真跨 | 创建即有 | **很低**。同一个人同时推进多个需求就会误合并 | Free |

一句话：**1 是 MVP 的主载体，4 当第二信号兜底，5 是以后走半自动时最容易接的推断信号，2 是有 Premium 时的增值项（表达合并顺序），7 和 8 不建议投入。**

## 10. 做不到的事

GitLab 层面的硬限制，按对本项目的影响排序。

### 10.1 没有「变更集」这个一等概念

GitLab 里**不存在**任何能表示「一组跨项目 MR」的对象。label、milestone、issue 都是借来用的，
它们的语义分别是「分类」「交付批次」「需求条目」，都不是「变更集」。

后果：

- 变更集的成员列表、状态、生命周期，**必须由平台自己存**。GitLab 只能当声明通道和事件源。
- label 被删掉、改名、拼错，GitLab 不会有任何信号说「这个变更集坏了」。
- 没有任何事件能告诉你「这一组齐了」。

### 10.2 MR 和 MR 之间只有「依赖」，没有「相关」

源码核对：`app/models/` 下只有 `issue_link.rb`，没有 MR↔MR 的通用关系模型。
[Linked items](https://docs.gitlab.com/user/work_items/linked_items/) 只作用于 work item，**MR 不是 work item**。

唯一的 MR↔MR 结构化关系是 [merge request dependencies](https://docs.gitlab.com/user/project/merge_requests/dependencies/)：

- **Premium 起**（源码 `ee/app/models/gitlab_subscriptions/features.rb` 的 `PREMIUM_FEATURES` 含 `blocking_merge_requests`）。
- 语义是「合并顺序」，不是「同一组」。
- 上限 10 blocker / 10 blockee（`ee/app/models/merge_request_block.rb` 的 `MAX_BLOCKS_COUNT` / `MAX_BLOCKED_BY_COUNT`）。
- 允许成环（文档明说）。
- 项目 import/export 不保留（[issue #12549](https://gitlab.com/gitlab-org/gitlab/-/issues/12549)）。
- GraphQL 字段 `blockingMergeRequests` 自 16.5 引入，**至今仍标 Experiment**，`visibleMergeRequests` 分页上限 20。

### 10.3 Webhook 载荷推不出兄弟 MR

`lib/gitlab/hook_data/merge_request_builder.rb` 的字段白名单里**没有**：兄弟 MR、blocking/blocked MR、关联 issue。
而且 `last_commit` **只有 head commit 一条**，拿不到分支上其它 commit 的 message。

group webhook 也救不了：它的载荷和 project webhook **完全一样**，只是省掉了逐仓配置的运维成本，
不会因为是 group 级就多给任何跨项目信息。而且 group webhook 是 **Premium**。

### 10.4 几个端点的行为和名字对不上（不看源码会踩）

| 端点 | 名字暗示的行为 | 实际行为 | 源码 |
|---|---|---|---|
| `GET /projects/:id/issues/:iid/closed_by` | 关闭该 issue 的所有 MR | **只返回同项目的 MR**（`MergeRequestsFinder.new(current_user, project_id: user_project.id)`），底层表里的跨项目行被过滤掉 | `lib/api/issues.rb:587` |
| `GET /projects/:id/merge_requests/:iid/closes_issues` | 该 MR 会关的 issue | **目标分支不是默认分支时恒返回空数组** | `app/models/merge_request.rb:1932` |
| `GET /groups/:id/milestones/:mid/merge_requests` | 该 group milestone 下的所有 MR | **只含该 group 的直属项目，不含子组**（没传 `include_subgroups`） | `lib/api/milestone_responses.rb:102` + `app/finders/issuable_finder/params.rb:171` |
| GraphQL `Group.mergeRequests` | 和 REST 同语义 | `includeSubgroups` **默认 `false`**，与 REST 的「总是含子组」相反 | `app/graphql/resolvers/concerns/group_issuable_resolver.rb` |

### 10.5 跨项目可见性是静默降级的

两处都是「看不到就悄悄少给你，不报错」：

- `Issues::ReferencedMergeRequestsService#filter_readable_by_user` 在 `read_cross_project` 被剥夺时
  （实例开启 external authorization control，`app/policies/base_policy.rb`）
  把 `related_merge_requests` 静默缩成只返回本项目。
- `Ability.merge_requests_readable_by_user` 过滤掉 token 读不到的 MR。
  MR dependencies 那边至少还给个 `hiddenCount`，其它端点连计数都没有。

对我们的直接影响：**group 级 service account 的权限如果没覆盖到某个仓，那个仓的 MR 会从变更集里静默消失，
平台无从察觉。** 必须在接入时校验 token 对全部 300 个仓的可见性，并周期性复核。

### 10.6 外部 issue（Jira）没有反查

`MergeRequest#persist_merge_request_issues!`（`app/models/merge_request.rb:1900`）显式
`reject { |issue| issue.is_a?(ExternalIssue) }`，外部 issue **不写进 `merge_requests_closing_issues` 表**。

后果：GitLab 侧只能正查（MR → Jira key），**没有「列出所有关联 PROJ-123 的 MR」这样的端点**。
Jira dev panel 里那份聚合存在 Jira 侧，GitLab 读不到。

### 10.7 分支名 `123-` 前缀的原生关联必须同项目

[Prefix branch names with a number](https://docs.gitlab.com/user/project/repository/branches/#prefix-branch-names-with-a-number) 原文：

> The branch must be in the same project as the issue or task.

所以 GitLab 内置的「分支号 → 自动关联 issue」对跨仓场景**完全无效**。
跨仓要靠 closing pattern 里的 `group/project#123` 显式引用，或者平台自己解析分支名。

### 10.8 过滤能力的硬边界

- `labels` 过滤**不支持通配或前缀匹配**，只能精确匹配名字列表。想查「所有 `cs::*`」只能逐个 ID 查，或拉全量再过滤。
- REST 的 `source_branch` 只接受**单个**分支名（GraphQL 的 `sourceBranches` 接受数组，这点 GraphQL 更强）。
- `per_page` 上限 100。
- GraphQL `Issue.relatedMergeRequests` 官方标注 "can only be resolved for **one issue** in any single request"，无法批量。

### 10.9 CI 层面没有跨仓协同

- GitLab CI **没有** Zuul 的 `Depends-On:` 等价物（`doc/ci/` 全目录无此关键词）。
- [Merge trains](https://docs.gitlab.com/ci/pipelines/merge_trains/)（**Premium**）的队列作用域是**单项目单目标分支**，两个仓的 MR 不可能进同一列车。
- multi-project pipeline 建立的是流水线之间的父子关系，不产生 MR↔MR 关联。

想要「proto 仓和服务仓的 MR 一起跑集成测试」，只能自己用 trigger token 传 ref 拼。

### 10.10 还在路上的能力，现在不能依赖

| 能力 | 状态 |
|---|---|
| 显式 MR ↔ work item 关联（`link_type: related`） | feature flag `explicit_mr_work_item_relations`，milestone 19.1，`type: wip`，**默认关**。19.4 仍未 GA |
| `WorkItemWidgetDevelopment.relatedMergeRequests` | 17.6 引入，**Experiment** |
| `MergeRequest.blockingMergeRequests`（GraphQL） | 16.5 引入，**Experiment** |
| Epics REST API | **17.0 起废弃**，计划 v5 移除；18.1+ 一律改用 Work Items API |
| MR dependencies 的嵌套链 UI | 16.7 起后端支持，UI 未做（[epic 5308](https://gitlab.com/groups/gitlab-org/-/epics/5308)） |

### 10.11 最根本的一条

**GitLab 里没有地方能声明「这个变更集应该包含哪几个仓」。**

所以「改了契约没改调用方」这类问题，无论用哪个原生机制，
在第一个 MR 到达时都**看不见** —— 平台只能知道「目前这组里有谁」，不能知道「这组还缺谁」。

要让它可见，只有两条路，都得平台自己做：

1. 让人在立项时填清单（把成本推给人）。
2. 平台自己维护服务依赖图（proto 仓的某个 package 被哪些仓引用），从契约变更反推应该有哪些仓的 MR。
   这是知识库那条线（ticket 08）的事，不在本文范围。

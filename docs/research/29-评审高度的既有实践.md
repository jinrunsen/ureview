## 0. 结论先行

**一、「评审高度」这个概念存在，但业界从来没有把它做成一张表。** 唯一一份把「从高到低走」写成**可执行流程**的一手文档，是 Google `eng-practices` 里的 `navigate.md`——三步：这个改动该不该发生 → 主干设计对不对 → 剩下的按顺序过。所有人引用的那张八项清单（Design / Functionality / Complexity / Tests / Naming / Comments / Style / Documentation）**不是分层框架**，它是一张并列的检查清单，全文只有第一项被明确标为「最重要」。把那张清单当高度排序，是我们的推断，不是 Google 的表述。

**二、最强的支持证据不是新的，是 2013 年的，而且带数字。** Bacchelli & Bird 在 Microsoft 对 570 条真实评审评论做卡片分类：**defect 类只占 14%，排第 4/9；其中高层问题只有 6 条。** 论文的原话是 "mostly address '**micro**' level and superficial concerns; while programmers and managers would expect more insightful remarks on **conceptual and design level issues**"。**ticket 那句「行内评论过早陷入细节」，十三年前就被测出来了。AI 不是这个缺口的成因，只是放大器。** 同一篇还记下了受访者的原话：低层评论「easier to write」，被当成 "**the way reviewers use to avoid spending time to conduct good code reviews**"。

**三、Google 明确写了「可以不下降」，而且把继续往下看定性成浪费。** `navigate.md`：发现重大设计问题立刻发出去，**"reviewing the rest of the CL might be a waste of time"**。这直接回答了 ticket 里「能不能不下降、那还算不算成本」那一问。

**四、一条和直觉相反的发现：时间压力下 Google 保留的是高层，不是低层。** `speed.md`：CL 大到没法快评又拆不开时，**"at least write some comments on the overall design of the CL"**。ticket 的反面假设里「先看设计会被时间压力挤掉」这条，**在成文规范里方向是反的**。

**五、但三家独立组织给最高层的答案都是「把它移到代码之前」。** Google 要求新项目走 "an extensive design review, **apart from a code review**"，并说 "A code review is **not the time** to debate design decisions"；Linux kernel 有整整一份文档讲 "**discuss it with the development community before investing in the creation of a body of code**"；Rust 把 "substantial" 改动整个移出 PR 流程走 RFC。**这是本方向最根本的制度性反对**：不是高层不重要，是它重要到不该等到评审阶段才第一次被问。

**六、但那条反对的前提正在失效，而这正是整个方向的支点。** 上述三家的逻辑都建立在「写代码贵，所以值得先讨论」上（Linux 原话是 "before **investing in** the creation of a body of code"）。**AI 把写代码的成本压到接近零，代码常常在任何人讨论之前就已经存在了。** ticket 的立论靠的正是这条：上游的设计讨论通道被 AI 工作流绕过，负载被迫下沉到评审阶段。**这条推理没有任何公开数据支持，必须自己验证。**

**七、Google 自己的田野数据说这件事内部没有共识。** Sadowski 等 2018 的访谈，五个 breakdown 主题之一就叫 **Review subject**：团队之间对「code review 是不是评审设计的合适场合」**存在分歧**，有的要求设计在首轮 review 前定稿，有的要求在 review 里讨论，**"which could cause friction"**。这是最直接的反面证据，而且来自和第三、四条同一个组织。

**八、高度确实被做成了制度，但形态不是界面分层，是权限分层。** Google 的三个 approval bit——LGTM（正确性与可理解性）/ OWNERS（这段代码该不该进我这个目录）/ readability（语言风格与最佳实践）——是一套按高度切开的**审批职责**。既有实践把高度用在「派给谁」上，我们想用在「怎么呈现」上，**后者没有先例。**

**九、决定评审高度的是上下文，不是版式。三条独立数据撞到同一个结论。** ① Czerwonka（Microsoft, 2015）：**没接触过这块代码的评审者，评论有用率只有 33%；看到第三遍升到 67%**。② Bacchelli（2013）：熟悉文件的评审者给的是 "conceptual (better ideas, approaches)"，不熟的给的是 "superficial (naming, mechanical style)"，91% / 82% 的问卷确认。③ Atlassian（2025）：LLM 评审者产出的 design 类评论**比人类少**，原因是不熟悉项目架构与社区惯例。**产品的主要杠杆是上下文积累（规范库、跨仓关联、历史 PR），不是重排版面。护城河在上下文，不在版式。**

**十、有按高度测的采纳率数据，方向不利，但度量器本身只能测行内评论。** Atlassian 在 4,000 条生产 LLM 评论上测出：readability 43.3% > bugs 41.9% > maintainability 36.2% > **design 28.6%**，随高度单调下降。但它的 resolved 判据是「后续 commit 改了评论所在的那一行」，样本只取行内锚定的评论。**Microsoft 2015 的 usefulness 分类器用的是同一个判据（"change triggers"）。业界十年来「哪类评论有价值」的实证基础，几乎全部建在一个按构造就测不出高层评论价值的度量器上。** 它们证明的是「在行内评论这个载体里，越高的建议越难被采纳」——**这恰好是 ticket 的论点，不是反例。而「换个载体会不会好」，一次都没人测过。**

**十一、Uber 的生产数据说价值曲线不是单调的，它在中间见顶。** 实测低价值：readability nits、minor logging tweaks、low-impact perf、stylistic issues；高价值：correctness bugs、missing error handling、coding best-practice violations。**最高价值的不是最高层，是中层。** 同一篇承认 uReview "can't correctly assess overall correctness and **review the system design**"。

**十二、「AI 代码语法干净、毛病在上面」这句话，按字面是错的。** arXiv 2510.03029 实测 code smell 均值 +63.34%，**拆开是 implementation smell +73.35%、design smell +21.42%**——而它的 implementation smell 清单里就有命名不一致、对齐不当、魔数、注释不足，**正是假设认为 AI 做得好的那些**。同一篇作者承认架构级 smell 没测，因为 benchmark 里没有架构。**修正版的说法是「低层问题在到达评审界面之前被 formatter/linter 吃掉了，高层问题不会」——这个修正合理，但同样没有数据。**

**十三、现成工具里没有一个按高度组织输出，而市场正在动的是另一个轴。** 高层内容其实已经被生产出来了（Qodo 的 `High-Level Assessment`、CodeRabbit 的 Walkthrough），但**一律折叠在 `<details>` 里**——这是版面权重问题，不是能力问题。同时 CodeRabbit 的 Change Stack 已经在重组 PR 的组织方式，但它走的是**空间/叙事轴**（"grouped into coherent areas, ordered so foundations come before the code that depends on them"），**不是高度轴**。**「扁平文件列表不对」已经不再是差异化点了；高度轴仍然是空的，但这也意味着没有失败案例可查。**

**一句话**：高度是真的，自顶向下的下降路径有 Google 的一手背书，剪枝有明确许可，缺口有 2013 年的数字。但**「第一层给替代方案 + 推荐意见」这个具体形态，被 Google 的制度性表述、Atlassian 的采纳率数据、Uber 的能力边界三方同时压着**。建议的做法见 §6：四层，但最高层降级成「二值闸门 + 理由」而不是「裁决 + 方案」，最低层默认关闭，主战场放在中间两层。三个必须先做的实验见 §6.5。

## 1. Google：唯一一份把「高度下降」写成流程的一手文档

来源全部是 [`google/eng-practices`](https://github.com/google/eng-practices) 仓库原文（2026-09-12 克隆，最近一次内容提交 2022-03-31）与 [《Software Engineering at Google》第 9 章](https://abseil.io/resources/swe-book/html/ch09.html)。

### 1.1 那张八项清单不是分层框架

ticket 里问：Design / Functionality / Complexity / Tests / Naming / Comments / Style / Documentation 这个顺序是不是有意的高度排序？

**答案：只有第一项的排位是原文明说的，其余的顺序原文没有给任何说明。** `[文档明述]`

[`looking-for.md`](https://github.com/google/eng-practices/blob/master/review/reviewer/looking-for.md) 开头 Design 一节的第一句：

> "The most important thing to cover in a review is the overall design of the CL."

这是全文**唯一**一处对某一项做排位声明。后面七项（Functionality、Complexity、Tests、Naming、Comments、Style、Consistency、Documentation）各自起一节，没有任何「其次」「再次」「最后」之类的排序词，也没有「按重要性排列」的元说明。文末 Summary 那张 bullet 清单只是把各节按同样顺序复述一遍。

**几条支持「顺序是有意的」的间接证据** `[推断]`：

1. 同一个顺序在三处独立出现且一致：`looking-for.md` 的节序、它自己的 Summary 清单、以及 [`review/index.md`](https://github.com/google/eng-practices/blob/master/review/index.md) 的 "What Do Code Reviewers Look For?" 概览清单。
2. 顺序从 2019-09-05 首次开源至今**没变过**（`git log -- review/reviewer/looking-for.md`，最早版本的节标题与今天完全一致）。
3. 七年里只插入过一节：**Consistency**，插在 Style 和 Documentation 之间——插在低层区，不是插在顶上。一个和风格同族的话题被放在风格旁边，说明作者心里这个序列是有语义的。

**但这三条都不构成「原文明述」。** 把这张清单当高度排序来引用，必须标成推断。

另外有一条常被忽略的一手表述，它比清单顺序有用得多：`looking-for.md` 的 **Every Line → Exceptions** 一节明确承认，一个 CL 可以按「方面」而不是按文件派给不同评审者： `[文档明述]`

> "To review only certain aspects of the CL, such as the **high-level design**, privacy or security implications, etc."

**Google 承认「只评审高层设计」是一种合法的评审模式。** 这是清单顺序之外，`looking-for.md` 里对「高度」最实在的一条背书。

### 1.2 真正的分层证据在 navigate.md

[`navigate.md`](https://github.com/google/eng-practices/blob/master/review/reviewer/navigate.md) 全文就是一条三步下降路径，它的 Summary 原文： `[文档明述]`

> 1. Does the change make sense? Does it have a good description?
> 2. Look at the most important part of the change first. Is it well-designed overall?
> 3. Look at the rest of the CL in an appropriate sequence.

对照 ticket 里那张四层草表：

| ticket 的层 | navigate.md 的步 | 对得上吗 |
|---|---|---|
| 一 · 意图与方案 | Step One: Take a broad view of the change | **对得上**，而且 Google 的措辞更狠：`"Does this change even make sense? If this change shouldn't have happened in the first place, please respond immediately"` |
| 二 · 影响与结构 | Step Two: Examine the main parts of the CL | 部分对得上。Google 的 Step Two 是「找到主干文件看设计」，**不含跨仓影响面、重复检测**——那些 Google 没有 |
| 三 · 实现 + 四 · 细节 | Step Three: rest of the CL in an appropriate sequence | **Google 把这两层合并了**，而且明确说「就按工具给的文件顺序过」 |

**结论**：Google 的成文流程是**三层，不是四层**，而且它的第三层是「其余全部」，没有再往下切。ticket 的第三层和第四层在 Google 这里是同一层。`[推断]`

Step One 里还有一条对产品有直接含义的表述 `[文档明述]`：

> "If you get more than a few CLs that represent changes you don't want to make, you should consider re-working your team's development process... so that there is more communication before CLs are written. It's better to tell people 'no' before they've done a ton of work that now has to be thrown away."

即：Google 认为第一层的问题**反复出现就说明流程错了，应该把它移到写代码之前**，而不是在 review 里反复承接。这一条在 §7 的风险里还会再出现。

### 1.3 「能不能不下降」——Google 明说了能，而且把继续看定性成浪费

ticket 问：「如果第一层就判定方案不对，下面三层的分析是不是白做了？」

`navigate.md` Step Two 的原文是本次调研里对这个问题最直接的回答： `[文档明述]`

> "If you see some major design problems with this part of the CL, you should send those comments immediately, even if you don't have time to review the rest of the CL right now. **In fact, reviewing the rest of the CL might be a waste of time**, because if the design problems are significant enough, a lot of the other code under review is going to disappear and not matter anyway."

它还给了两条理由，都是成本理由： `[文档明述]`

> - "Developers often mail a CL and then immediately start new work based on that CL while they wait for review. If there are major design problems... they're also going to have to re-work their later CL."
> - "Major design changes take longer to do than small changes. Developers nearly all have deadlines; ... the developer needs to start on any major re-work of the CL as soon as possible."

**对我们的直接含义** `[推断]`：ticket 里「能不能不下降——那还该不该算成本」这个问题，Google 的答案是**不但能不下降，而且应该立刻中止并发出**。这为「高层判定为否时提前返回、不跑下层 agent」提供了一手依据，省 token 的做法不是偷工，是照着 Google 的流程做。

### 1.4 一条反直觉的发现：时间压力下被保留的是高层

ticket 的第五问里假设「先看设计在实践中经常因为时间压力被跳过」。**在 Google 的成文规范里，这条方向是反的。** `[文档明述]`

[`speed.md`](https://github.com/google/eng-practices/blob/master/review/reviewer/speed.md) 的 Large CLs 一节：

> "If a CL *can't* be broken up into smaller CLs, and you don't have time to review the entire thing quickly, then **at least write some comments on the overall design of the CL** and send it back to the developer for improvement."

同一篇的 Fast Responses 一节：

> "If you are too busy to do a full review on a CL when it comes in, you can still send a quick response that lets the developer know when you will get to it, suggest other reviewers..., or **provide some initial broad comments**."（"broad comments" 链接指向 `navigate.md`）

**两处都把「高层意见」定位成时间不够时的保底产出。** 低层的逐行是可以被牺牲的那部分，高层是不能被牺牲的那部分。

这一条对产品定位很关键：如果「AI 大量产出代码 → 人的评审时间预算被摊薄」成立，那么按 Google 的规范，**被摊薄时应该保留的恰恰是高层评审**。这是本次调研里对 ticket 立论最有利的一条一手材料。`[推断]`

`speed.md` 的其余时间参数（用于 §6 的成本估算）`[文档明述]`：

- `"One business day is the maximum time it should take to respond to a code review request"`
- `"you should do a code review shortly after it comes in"`（不在专注工作中时）
- `"don't compromise on the code review standards or quality for an imagined improvement in velocity"`

### 1.5 Google 把高度做成了权限，不是做成了界面

《Software Engineering at Google》第 9 章列了三个 approval bit： `[文档明述]`

| bit | 原文定义 | 高度 |
|---|---|---|
| **LGTM** | "A correctness and comprehension check from another engineer that the code is appropriate and does what the author claims it does." | 中层（实现正确性 + 可理解性） |
| **Owner approval** | "Approval from one of the code owners that the code is appropriate for **this particular part of the codebase**." | 高层（这段代码该不该进这里） |
| **Readability approval** | "Approval from someone with language 'readability' that the code **conforms to the language's style and best practices**." | 低层（风格与语言最佳实践） |

而且原文明说这三个角色**关注点不同**： `[文档明述]`

> "This allows the two roles to focus on different aspects of the code review and saves review time. The primary reviewer can focus on **code correctness and the general validity** of the code change; the code owner can focus on **whether this change is appropriate for their part of the codebase without having to focus on the details of each line of code**."

> "An approver is often looking for something different than a peer reviewer... They are more concerned with questions such as: 'Will this code be easy or difficult to maintain?' 'Does it add to my technical debt?' 'Do we have the expertise to maintain it within our team?'"

**这是本次调研里除 navigate.md 之外第二强的分层证据，而且它是制度化的、带强制力的**（三个 bit 都得点亮才能提交）。

**但要注意形态的差别** `[推断]`：Google 把高度用在**「这条意见该由谁给」**上，不是用在**「这些意见该怎么排版给人看」**上。三个 bit 落到 Critique 界面里，仍然是同一条评论流。**「按高度组织界面」在 Google 也没有先例。** 这一点我们必须自己承担。

另外，第 9 章还明说了一条容易被忽略的分层维度： `[文档明述]`

> "All code reviews are not alike! Different types of code review require different levels of focus on the various aspects of the review process."

它给的四类是：greenfield / behavioral changes、improvements、optimizations / bug fixes and rollbacks / refactorings and large-scale changes。**高度的权重应该随变更类型变**，不是一套固定权重打天下。这条对 §6 的分层建议有直接影响。

### 1.6 但 Google 把设计评审踢出了 code review

这是对 ticket 第一层设想（「列三个替代方案 + 推荐意见」）最直接的制度性反对，全部来自《SWE at Google》第 9 章： `[文档明述]`

> "At Google, we generally require new code and/or projects to undergo **an extensive design review, apart from a code review**. **A code review is not the time to debate design decisions already made in the past** (and by the same token, a code review is not the time to introduce the design of a proposed API)."

> "To prevent the evaluation of correctness from becoming more subjective than objective, **authors are generally given deference to their particular approach, whether it be in the design or the function of the introduced change. A reviewer shouldn't propose alternatives because of personal opinion.** Reviewers can propose alternatives, **but only if they improve comprehension (by being less complex, for example) or functionality (by being more efficient, for example)**."

> "In general, reviewers should **defer to authors on particular approaches and only point out alternatives if the author's approach is deficient**. If an author can demonstrate that several approaches are equally valid, the reviewer should accept the preference of the author."

同样的规则在 [`standard.md`](https://github.com/google/eng-practices/blob/master/review/reviewer/standard.md) 的 Principles 一节也写了： `[文档明述]`

> "**Aspects of software design are almost never a pure style issue or just a personal preference.** They are based on underlying principles and should be weighed on those principles, not simply by personal opinion. Sometimes there are a few valid options. **If the author can demonstrate... that several approaches are equally valid, then the reviewer should accept the preference of the author.**"

**怎么读这组材料**：Google 没有说「不要看设计」——`looking-for.md` 第一句就说设计最重要。它说的是**两件不同的事**：

- **看设计 = 判断这个改动和现有系统契不契合**（"Do the interactions of various pieces of code in the CL make sense? Does this change belong in your codebase, or in a library? Does it integrate well with the rest of your system?"）——**这个鼓励**。
- **评设计 = 提出「本来还可以怎么做」的替代方案**——**这个受严格限制**，只有当作者的做法「deficient」时才允许，而且不允许出于个人偏好。

**这条界线对我们的产品是可执行的约束** `[推断]`：第一层的产出形态不该是「三个替代方案 + 推荐意见」（Qodo 的 `High-Level Assessment` 就是这个形态），该是「这个改动和系统既有结构的契合度证据 + 问题」。**给方案是越界，给证据是本分。** 见 §6.2。

### 1.7 Google 自己的田野数据：设计该不该进 review，内部没有共识

[Sadowski, Söderberg, Church, Sipko, Bacchelli, "Modern Code Review: A Case Study at Google", ICSE-SEIP 2018](https://research.google/pubs/modern-code-review-a-case-study-at-google/)（[PDF](https://storage.googleapis.com/gweb-research2023-media/pubtools/4476.pdf)）。12 次访谈 + 44 份问卷 + 900 万次变更的日志。

论文归纳出五个 breakdown 主题，其中第三个直接打在我们的方向上： `[文档明述]`

> "**Review subject**: The interviews referenced **disagreements as to whether code review was the most suitable context for reviewing certain aspects, particularly design reviews.** This resulted in mismatched expectations (e.g., **some teams wanted most of the design to be complete before the first review, others wanted to discuss design in the review**), which could cause friction among participants and within the process."

**这是本次调研找到的最直接的反面证据。** 它不是说高层评审没价值，它说的是：**把设计评审塞进 code review 这个容器里，本身就是团队间有争议的做法，而且争议会变成摩擦。** 一个通用开源工具如果默认把第一层顶到最前面，就是在替所有团队做这个有争议的选择。

同一篇的量化数据（对 §6 的可行性判断很关键）`[公开数据]`：

| 指标 | 数字 |
|---|---|
| 变更的中位行数 | **24 行** |
| 只改一个文件的变更占比 | **超过 35%** |
| 只改一行的变更占比 | **超过 10%** |
| 改动文件数 < 10 的变更占比 | 约 90% |
| 评审者数量中位数 | **1** |
| 开发者每周花在评审上的时间 | 均值 3.2 小时，**中位数 2.6 小时** |
| 平均评论数的峰值 | 约 1250 行的变更上达到 12.5 条/变更 |
| 80% 的变更 | "involve at most one iteration of resolving comments" |
| 问卷中说评论找到了 bug 的人数 | **2 人**（44 份问卷） |

**中位 24 行、35% 单文件、10% 单行**——**Google 的绝大多数变更根本没有「高度」可言。** 一个 24 行的变更没有三个替代方案可列，没有影响面图可画。这划出了一条硬边界：**按高度分层的评审只在变更大到有设计内容时才划算。**

这一条反过来又是对 ticket 立论的支持 `[推断]`：ticket 的前提是「AI 产出大量代码」，即变更规模分布整体右移。Google 2018 年的分布（中位 24 行）是**人手写小 CL 的分布**，在那个分布下行内评论是对的形态。假设的成立与否，取决于 AI 时代的变更规模分布是不是真的移到了「有高度可言」的那一侧。**这是必须实测的第一件事**，见 §6.5。

## 2. 其他组织：一个反复出现的模式——把最高层移出评审

查了 Linux kernel、Rust、Chromium、Microsoft、Meta 的成文流程。**没有一家像 Google 的 `navigate.md` 那样写出「评审时先看高层再下降」的流程。** 但有一条更强的共同模式：

> **它们对最高层的制度性回答，不是「在评审里看得更高」，而是「把它移到代码存在之前」。**

### 2.1 Linux kernel：整整一份文档讲「先讨论再写代码」

[`Documentation/process/3.Early-stage.rst`](https://github.com/torvalds/linux/blob/master/Documentation/process/3.Early-stage.rst)（2026-09-12 拉取 master）`[文档明述]`：

> "The moral of the story is to **focus on the problem - not a specific solution - and to discuss it with the development community before investing in the creation of a body of code**."

要求贡献者在动手前先回答三个问题：

> - "What, exactly, is the problem which needs to be solved?"
> - "Who are the users affected by this problem? Which use cases should the solution address?"
> - "How does the kernel fall short in addressing that problem now?"
>
> "**Only then does it make sense to start considering possible solutions.**"

**这三问就是 ticket 第一层的内容，被原封不动地前置到了写代码之前。**

同一节里还有「重造轮子」的正面点名，和 ticket 的假设用词几乎一样 `[文档明述]`：

> "Your author has seen the posting of a complete driver which **duplicated an existing driver** that the new author had been unaware of. **Code which reinvents existing wheels is not only wasteful; it will also not be accepted into the mainline kernel.**"

以及一条对「闭门造车」的经验判断 `[文档明述]`：

> "Years of experience with the kernel development community have taught a clear lesson: **kernel code which is designed and developed behind closed doors invariably has problems which are only revealed when the code is released into the community.**"

[`submitting-patches.rst`](https://github.com/torvalds/linux/blob/master/Documentation/process/submitting-patches.rst) 里有一条**作者侧的高度门**，写法很值得借 `[文档明述]`：

> "**Describe your problem.** Whether your patch is a one-line bug fix or 5000 lines of a new feature, **there must be an underlying problem** that motivated you to do this work. **Convince the reviewer that there is a problem worth fixing and that it makes sense for them to read past the first paragraph.**"

**「说服评审者值得读完第一段」——这就是一道显式的高度闸门**，只不过它的执行者是作者不是工具。`[推断]`

拆分维度上，内核只有**空间维度**，没有高度维度 `[文档明述]`：

> "Separate each **logical change** into a separate patch... The point to remember is that each patch should make an easily understood change that can be verified by reviewers. Each patch should be **justifiable on its own merits**."

**结论**：Linux kernel 有明确的高度意识，但它把高度做成了**时序**（先讨论后写码）和**作者义务**（第一段必须立住），**没有做成评审时的分层界面**。`[推断]`

### 2.2 Rust：把设计评审整个切成了独立流程，而且它的模板就是一份分层文书

[rust-lang/rfcs 的 README](https://github.com/rust-lang/rfcs/blob/master/README.md) `[文档明述]`：

> "Many changes, including bug fixes and documentation improvements **can be implemented and reviewed via the normal GitHub pull request workflow**. Some changes though are '**substantial**', and we ask that these be put through **a bit of a design process** and produce a consensus among the Rust community and the sub-teams."

> "**If you submit a pull request to implement a new feature without going through the RFC process, it may be closed with a polite request to submit an RFC first.**"

**这是「按高度分流」最彻底的一个制度实例**：高度超过某条线的改动，**不走 PR 评审，走另一条流程**。分流判据也是成文的（语言语义/语法变更、移除特性、`std` 的大改动 vs 换形不换义的重构、纯客观指标改善、只有 Rust 开发者能看到的改动）。`[文档明述]`

而 [RFC 模板](https://github.com/rust-lang/rfcs/blob/master/0000-template.md) 本身就是一份**按高度排的文书**，这是本次调研里找到的唯一一份「成文的高度分层结构」`[文档明述]`：

| 模板小节 | 高度 | 原文提示 |
|---|---|---|
| Summary | — | |
| **Motivation** | **最高** | "This section is one of the most important sections of any RFC" |
| **Guide-level explanation** | 高 | "Explain the proposal **as if it was already included in the language and you were teaching it to another Rust programmer**" |
| **Reference-level explanation** | 中 | "**This is the technical portion.** Explain the design in sufficient detail that: its interaction with other features is clear; it is reasonably clear how the feature would be implemented; corner cases are dissected by example." |
| Drawbacks | — | "Why should we *not* do this?" |
| **Rationale and alternatives** | 高 | "Why is this design the best in the space of possible designs? **What other designs have been considered and what is the rationale for not choosing them?** What is the impact of not doing this?" |
| Prior art / Unresolved questions / Future possibilities | — | |

**两条直接可用的东西** `[推断]`：

1. **Guide-level / Reference-level 这个二分，是把同一个东西写两遍、一遍高一遍低。** 这比「分四层各写各的」更接近人的真实需求：读者先读高的那遍，需要细节再读低的那遍，而且两遍讲的是同一组例子（模板明确要求 Reference-level "should **return to the examples given in the previous section**"）。**这是「下降路径」的一个现成范式，而且它解决了「上下层对不上」的问题——靠共享例子锚定。**
2. **"Rationale and alternatives" 的四个提示问题，就是 ticket 第一层想要的产出形态**，而且它比 Qodo 的 `High-Level Assessment` 更克制：它问的是「为什么这个设计是最好的」「考虑过哪些别的、为什么没选」，**主语是作者不是评审者**。对照 §1.6 Google 那条「评审者不得出于个人偏好提替代方案」——**Rust 的做法是让作者自己列替代方案，评审者评判这个列表是否诚实完整。** 这个角色分配绕开了 Google 那条禁令，而且对 AI 工具更可行：**让 AI 补全「作者没说的替代方案」，比让 AI 直接裁决「你该换个做法」安全得多。**

## 3. 学术上的评审评论分类学与实测数据

### 3.1 最重要的一篇不是新的：Microsoft 2013 已经把这个缺口测出来了

[Bacchelli & Bird, *Expectations, Outcomes, and Challenges of Modern Code Review*, ICSE 2013](https://sback.it/publications/icse2013.pdf)。方法：观察 + 17 次访谈 + 两轮问卷（873 名开发者/测试、165 名经理）+ 对 200 个 CodeFlow 评审线程、570 条评论做卡片分类。这是本文引用的所有材料里**最贴 ticket 立论的一篇**，而且它比 AI 早十年。

**（1）期望与产出之间有一条明确的高度缺口。** 卡片分类的结果 `[公开数据]`：

| 类别 | 条数 | 占比 | 名次 |
|---|---|---|---|
| Code Improvements | 165 | **29%** | 第 1（其中 58 条 better practices、55 条删无用代码、52 条可读性） |
| Understanding（澄清提问） | — | — | 第 2 |
| … | | | |
| **Defect** | 78 | **14%** | **第 4 / 共 9 类**（其中 65 条逻辑问题，**只有 6 条 high-level 问题**，5 条安全，3 条异常处理） |

论文的结论句 `[文档明述]`：

> "Review comments about defects are few, comprising one-eighth of the total in our sample, and **mostly address 'micro' level and superficial concerns; while programmers and managers would expect more insightful remarks on conceptual and design level issues**."

推荐一节里说得更直白 `[文档明述]`：

> "review does not result in identifying defects as often as project members would like and **even more rarely detects deep, subtle, or 'macro' level issues**. Relying on code review in this way for quality assurance may be fraught."

**这就是 ticket 那句「行内评论过早陷入细节」的学术版本，而且带数字。** 它说明这个缺口**不是 AI 造成的**——AI 只是把它放大了。

**（2）低层评论被当成逃避真评审的手段，这有受访者原话。** `[文档明述]`

> "Such comments [code improvement] seem easier to write and sometimes interviewees mentioned them as **the way reviewers use to avoid spending time to conduct good code reviews**."

> "I've seen quite a few code reviews where someone commented on **formatting while missing the fact that there were security issues or data model issues**."（司龄 9 年以上的资深开发者）

> "[Some reviewers] focus on formatting mistakes because they are easy [...], but it doesn't really help. [...] In some ways it's kind of embarrassing if someone asks you to do a code review and all you can find are formatting mistakes when there are real mistakes to be found."

**（3）「给替代方案」是开发者想要的，但经理不认，而且它极少真的发生。** `[公开数据]`

- Alternative Solutions 作为评审动机：**147 人（17%）排第一、202 人（23%）排第二、152 人（17%）排第三**——即约 **57% 的开发者把它放进前三**。
- 但**只有 4 名经理（2%）提到过它**。
- 访谈里开发者对它的描述是 "vaguely mentioned"。

**对 ticket 第一层的含义**：「列替代方案」这件事**有真实需求**（开发者侧），但**它在管理侧没有认可度，在实践中极少发生**。做这一层是在填一个真空，不是在抢一块已有的地盘——好处是没有竞品，坏处是没人验证过它的价值，而且预算归属不清。`[推断]`

**（4）为什么高层评论产不出来？论文给了一个单一的、可操作的答案：理解成本。** `[文档明述]`

问卷让开发者按「达成这个产出需要多少理解」给各项动机打分（四档 Likert），结果：

> "The most difficult task from the understanding perspective is **finding defects**, immediately followed by **alternative solutions**. Both clearly stand out from the other items."

> "**if managers and developers want code review to match their need for finding defects, context and change understanding must be improved.**"

机制还有直接的对照证据：**熟悉这些文件的评审者给的是概念级反馈，不熟悉的给的是表面反馈。** `[公开数据]` + `[文档明述]`

- 91%（798 人）确认评审不熟悉的文件更花时间。
- 82%（716 人）确认熟悉文件的评审者给的反馈**不同**。
- 受访者原话：
  > "Comments reflect deeper understanding – more likely to find subtle defects, **feedback is more conceptual (better ideas, approaches) instead of superficial (naming, mechanical style, etc.)**"
  > "**Difference between algorithmic analysis and comments on coding style. The difference is big.**"
  > "**big-picture impact analysis requires contextual understanding.** When reviewing a small, unfamiliar change, it is often necessary to read through much more code than that being reviewed."

**这一条是本次调研里对产品方向最有用的一条结论** `[推断]`：**评审高度不是一个可以靠界面切换的旋钮，它是理解程度的函数。** 想让产出上浮到高层，唯一的杠杆是把上下文喂够——规范库、跨仓关联、既有约定、历史决策。**版式是结果，不是原因。** 这和 §3.6 的结论撞在一起，两边独立得出。

**（5）论文在 2013 年就点名了工具的空白，而且点的正是我们要做的东西。** `[文档明述]`

> "**All code review tools that we see in practice today deliver only basic support for the understanding needs of reviewers – providing features such as diffing capabilities, inline commenting, or syntax highlighting**, which are limited when dealing with complex code understanding."

> "all current code review tools we know of show a highlighted diff of the changed files to a reviewer with **no additional tool support**... **This is a ripe opportunity**."

十三年过去，§5 会说明这个空白基本还在。

**（6）但同一篇里有一条反对自顶向下的观察，必须一起记。** `[文档明述]`

> "some started code reviews by thoroughly reading the accompanying textual description, while others **went directly to a specific changed file**. **In the first group, the time required for putting the first review comments and understanding the change rationale was noticeably longer**"

> "when they own or are very familiar with the files being changed... they often **do not need to read the description**, but they 'go directly to the files they own.'"

**读法** `[推断]`：自顶向下不是一条普遍更优的路径，它是**缺上下文的人**才需要走的路径。文件的 owner 已经把顶层装在脑子里了，强迫他从顶层走一遍是纯浪费，而且论文观察到这条路**出第一条评论更慢**。

**产品含义**：下降路径必须**可从任意高度进入**，而且对「已经知道顶层」的人要能一键跳过。把它做成强制的线性漏斗，会精确地激怒最有价值的那批评审者。

### 3.2 Microsoft 2015：有用性的分类学，以及一个所有人都在用的可疑度量器

[Bosu, Greiler, Bird, *Characteristics of Useful Code Reviews: An Empirical Study at Microsoft*, MSR 2015](https://www.microsoft.com/en-us/research/publication/characteristics-of-useful-code-reviews-an-empirical-study-at-microsoft/)（[PDF](https://www.microsoft.com/en-us/research/wp-content/uploads/2016/02/bosu2015useful.pdf)）。三阶段：访谈（作者本人给自己收到的评论打「有用/有点用/没用」三档）+ 人工标注 + 约 150 万条评论的大规模分析，覆盖 Azure、Bing、Exchange、Office、Visual Studio 五个项目。

**（1）它用的分类法就是 Mäntylä & Lassenius 那套**，Figure 3 的 13 个类别里前 11 个来自那篇，分成两族 `[文档明述]`：

| 族 | 类别（Figure 3 编号） | 高度 |
|---|---|---|
| **Evolvability defects**（可演化性） | 1. Documentation、2. Visual Representation（空行、缩进）、3. Organization（功能怎么切分到方法里）、**4. Solution Approach** | 低 → 高（4 是高层） |
| **Functional defects**（功能性） | 5–11：Resource、Validation、Logical、Synchronization、Supporting library、Defect、API calls | 中 |
| 后加的 | 12. False Positive、13. Other（再拆出：reviewer 提问 / 夸奖 / 替代输出与错误信息 / **讨论设计或新功能**） | — |

论文对 Mäntylä 分类的复述 `[文档明述]`：

> "These four all belong to the class termed **'evolvability defects' as classified by Mantyla et al.** and represent issues that **affect future development effort rather than runtime behavior**."

**（2）评分结果，对我们的方向是混合信号** `[公开数据]`：

- **69%** 的评论被作者评为「有用」或「有点用」；五个项目的 usefulness density 在 **64%–68%** 之间。
- **功能缺陷类（5–11）大多被评为「有用」**。
- **超过 60% 的「有点用」落在前四类**——documentation、visual representation、organization、**solution approach**。
- 明确被评为「没用」的：false positive、reviewer 的提问、夸奖，以及**指向未来工作、当下不需要做的评论**。

原文对最后一条的表述，是「高层评论不可操作」这个批评最直接的一手证据 `[文档明述]`：

> "Some comments pointed out **work that needed to occur in the future, but not during the current development cycle**... **If immediate actions based on these comments are not foreseeable, authors rated such comments as not useful.**"

**注意 "Solution Approach" 的位置。** 它是四个高度最高的 evolvability 类别之一，也是 ticket 第一层想做的那种评论，而它和「缩进」「空行」一起被归进了「有点用」那一档。`[公开数据]`

**（3）但它对高层评论也有正面证据**，两条 `[文档明述]`：

> "Code review is very useful for the new members to learn the project design, constraints, available tools, and APIs. Authors that were new to the team considered comments with suggestions regarding **APIs to use, designs to follow, team coding conventions**, etc. to be **useful**."

> 后加的两个类别里，"suggestions for alternate output or error messages" 和 "**discussions on design or new features**" —— "in most of the cases they considered the last two categories as **useful** comments."

**读法** `[推断]`：**「讨论设计」有用，「提议重做」有点用，「指向未来工作」没用。** 三者的差别不在高度，在**当下可操作性**。这条比「高层评论没用」精确得多，而且它给出了第一层的设计约束：**高层输出必须绑定到「这个 MR 里现在就能做的事」，一旦变成「以后应该重构」就立刻掉到「没用」档。**

**（4）这一篇和 Atlassian 那篇用了同一个可疑的度量器，相隔十年。** `[文档明述]`

> "We observed that **useful comments very often trigger changes in close proximity to the comment-highlighted lines** (recall that a comment is associated with a highlighted portion of the code) in subsequent iterations. We refer to these comments that appear to induce a change in the code as **change triggers**."

Microsoft 2015 的自动分类器就建在这个信号上；Atlassian 2025 的 resolution rate（§3.5）用的是同一个判据。

**这是本次调研里我认为最值得单独记下的一条观察** `[推断]`：

> **「哪类评论有价值」这个问题，业界十年来的实证基础，几乎全部建立在「评论锚定的那几行有没有被改」这个度量器上。这个度量器按构造就只能测行内评论，而且系统性地低估那些「改的是别处」的高层评论。**

这不是说那些结论是错的，而是说**它们的适用范围被度量器限死在行内评论上**。任何引用它们来论证「高层评论没价值」的说法，都超出了数据的射程。反过来，我们也不能拿它们来论证高层评论有价值——**这个方向根本没被测过**。

**（5）还有两条和变更规模有关的数据，对 §6 有用** `[公开数据]`：

> "The trendline shows that **as number of files in the change increases, the proportion of comments that are useful drops**... reviewers may opt for **cursory review of large changesets** and may miss some changes. This may lead to false positives or more questions to the author."

- 按文件类型：源码 **70%**，build 文件 **65%**，VS solution 文件 **57%**，makefile **53%**。论文的解释是这类文件「**the impact of changes on the overall system are sometimes harder to assess**」——即**影响面难判断的文件，评审有用性最低**。这恰好是第二层（影响与结构）要解决的东西。`[推断]`

### 3.3 同年另一篇 Microsoft：熟悉度把有用率从 33% 拉到 67%

[Czerwonka, Greiler, Tilford, *Code Reviews Do Not Find Bugs — How the Current Code Review Best Practice Slows Us Down*, ICSE-SEIP 2015](https://www.microsoft.com/en-us/research/publication/code-reviews-do-not-find-bugs-how-the-current-code-review-best-practice-slows-us-down/)（[PDF](https://www.microsoft.com/en-us/research/wp-content/uploads/2015/05/PID3556473-1.pdf)）。四条数据，条条有用 `[公开数据]` `[文档明述]`：

**（1）评审产出的类别构成，和 Bacchelli 一致**：

> "Contrary to the often stated primary goal of code reviews, they often do not find functionality defects that should block a code submission. **Only about 15% of comments provided by reviewers indicate a possible defect**, much less a blocking defect. Rather, it is feedback related to the **long-term code maintainability** that comprises a much larger portion of comments provided by reviewers; **at least 50% of all**."

**（2）本次调研里量化「上下文 → 价值」最狠的一条**：

> "**Without prior exposure to the part of code base being reviewed, on average only 33% of any reviewer's comments are deemed useful** by the author of a change. However, reviewers typically learn very fast. **When reviewing the same part of code base for the third time, the usefulness ratio increases to about 67%** of their comments. By the fourth time, it is equivalent to the project's long-term average."

**同一个人、同一套技能，只因为看过这块代码三遍，有用率翻倍。** `[推断]` 这条给 AI 评审工具设了一个不低的门槛：**一个没有仓库历史上下文的评审者，基线有用率只有 33%**。它同时也说明产品的主要杠杆在哪——不是版式，是上下文积累。这和 §3.1（4）、§3.6 加上本条，三处独立撞到同一个结论。

**（3）规模阈值，比 Bosu 那条更精确**：

> "Code review usefulness is negatively correlated with the size of a code review... **The decrease however only starts to be noticeable for reviews with 20 or more changed files.**"

**20 个文件是一条可用的分界线** `[推断]`：低于它，行内评论的有用率不受规模拖累；高于它，开始掉。这可以直接当成「什么时候该启用高度分层」的第一版触发条件——见 §6.3 规则五。

**（4）成本**：

> "Modern code review process is expensive. Developers spend on average **six hours a week** reviewing changes of others."

（对照 Google 2018 的 3.2 小时均值 / 2.6 小时中位，§1.7。两个数不矛盾：不同组织、不同年份、不同统计口径。）

### 3.4 唯一一篇直接按高度测采纳率的：Atlassian 2025

[Goldman 等 14 人（Atlassian + 墨尔本大学 + Monash），*What Types of Code Review Comments Do Developers Most Frequently Resolve?*，arXiv:2510.05450，2025-10-06](https://arxiv.org/abs/2510.05450)。这就是 ticket 里已知那条线索的出处，核实无误，而且它比线索说的要有用得多。

**它的分类法是五类，由 6 名 Atlassian 工程师做卡片分类得出** `[文档明述]`：

| 类别 | 论文定义（原文） | 高度 |
|---|---|---|
| Readability | （可读性） | 低 |
| Bugs | （缺陷） | 中 |
| Maintainability | （可维护性） | 中 |
| **Code Design** | "Concerns regarding **code complexity and structure, appropriate implementation patterns, design principles, and architecture**." | **高** |
| No issue | "Not directly relevant to code readability, code bugs, maintainability or code design." | — |

**RQ2 的采纳率数据**（4,000 条生产环境 LLM 评论，3,746 个 PR，1,007 个仓库，2025 年 6–7 月）`[公开数据]`：

| 类别 | 采纳率 | 分母 |
|---|---|---|
| Readability | **43.3%** | 586 / 1,354 |
| Bugs | **41.9%** | 399 / 952 |
| Maintainability | **36.2%** | 483 / 1,333 |
| **Code Design** | **28.6%** | — |

论文原话： `[文档明述]`

> "Readability, bug, and maintainability-related comments exhibited higher resolution rates compared to those focused on code design."

> "code design issues often involve more complex, architectural considerations that **require deeper understanding and broader changes, making them harder to resolve quickly or automatically**. As a result, developers may hesitate to address these suggestions without further discussion or context."

**采纳率随高度单调下降，这对「把高层提为主角」是明确的不利数据。**

### 3.5 但这篇论文的度量器本身只能测行内评论

这是我读下来最重要的一条，而且它是论文自己写在方法和 Threats 里的： `[文档明述]`

> "We consider a given code review comment to be resolved if **a subsequent commit modified the exact line where the comment was placed**."

> "To mitigate this, **we focused exclusively on comments anchored to specific code lines**, as these are likely to be specific and directly related to the code."

两条合起来意味着：

1. 样本**只有行内评论**，非行内的（总结、walkthrough、设计意见）根本不在数据集里。
2. 「已解决」的判据是**评论所在那一行被后续 commit 改过**。

**这个判据按构造就对高层评论不利** `[推断]`。一条设计评论如果被采纳，典型后果是那段代码被挪走、删掉、或者改的是别的文件——**评论锚定的那一行很可能根本不再存在，或者压根没被碰**。而一条命名评论被采纳，必然表现为那一行被改。这是系统性的测量偏差，不是随机噪声。

所以这篇论文严格说证明的是：**在行内评论这个载体里，越高的建议越难被采纳。** 这**正好是 ticket 的论点**——行内评论形式配不上高层内容——而不是它的反例。

**但也不能反过来当支持用。** 这篇没有测「同样的设计意见换成非行内载体呈现，采纳率会不会上去」。**那个实验没人做过。** 这是我们如果要证明方向正确，必须自己补的实验，见 §6.5。

### 3.6 同一篇的另一条数据：LLM 评审者本来就产不出高层评论

RQ1 的分布数据 `[公开数据]`：

| 场景 | 类别 | LLM 评审者 | 人类评审者 |
|---|---|---|---|
| Atlassian 内部项目 | Bugs | **18.2%**（128/702） | 6.5%（30/465） |
| | Maintainability | **26.8%**（188/702） | 19.1%（89/465） |
| | Readability | 33.2%（233/702） | **46.0%**（214/465） |
| OSS 项目 | Maintainability | **37.9%**（476/1,256） | 23.6%（236/1,000） |
| OSS 项目 | **Design** | **比人类少** | **比 LLM 多** |
| OSS 项目 | No issue | 0.6% | 9.0% |

论文原话与解释： `[文档明述]`

> "For OSS projects, the LLM reviewer generated more maintainability-related comments but **fewer design-related comments than human reviewers did**."

> "In OSS projects, ... human reviewers—**often more familiar with the project's architecture and community norms**—may provide more design-related feedback."

**这条数据对我们是双向的** `[推断]`：

- **利好**：现有 LLM 评审工具在高层上确实产出不足，且论文把原因归到「不熟悉项目架构与社区惯例」——这正是我们打算用规范库和跨仓关联去补的那块。这条给「高层是空位」提供了实证。
- **利空**：它同时说明高层评论稀缺的原因是**上下文缺失**，不是**呈现形式**。换个版式不会凭空产出高层评论。**先解决上下文，再解决版式。**

### 3.7 Uber 生产数据：价值曲线在中层见顶，不在顶层

来自 [uReview: Scalable, Trustworthy GenAI for Code Review at Uber](https://www.uber.com/us/en/blog/ureview/)（2025-08-12），引文见 [我们此前的拆解](04-uber-ureview-架构拆解.md) §6.2。`[文档明述]`

> "**Readability nits, minor logging tweaks, low-impact performance optimizations, and stylistic issues** consistently received poor ratings. In contrast, **correctness bugs, missing error handling, and coding best-practice violations**—especially when paired with examples or links to internal docs—scored well."

排一下高度：

| 高度 | 类别 | Uber 实测评价 |
|---|---|---|
| 高（系统设计） | — | **uReview 做不到**，见下 |
| 中上 | coding best-practice violations | **好** |
| 中 | correctness bugs / missing error handling | **好** |
| 低 | readability nits / stylistic issues | **差** |
| 低 | minor logging tweaks / low-impact perf | **差** |

同一篇的能力边界声明： `[文档明述]`

> "uReview today only has access to the code, and **not to other artifacts like past PRs, feature flag configurations, database schemas, technical documentation**, and so on, because of which **it can't correctly assess overall correctness and review the system design**."

**两条合起来**：Uber 花了大力气做出来的生产系统，实测**价值最高的是中层，最高层做不到**。ticket 里「层数越高价值越高」的假设，在 Uber 的数据里**只在低层到中层这一段成立，再往上是断的**。`[推断]`

Uber 还有一条 2026 年补的约束，直接打在「四层全跑」这个设想上（S3 转录 [6:46–7:19]）`[文档明述]`：

> "we need to have **guardrails for the agent. So we need to tell the agent what NOT to waste turns doing.** Like code review is something that has to happen in a **specific time span**. And then if it starts spending time doing things that it should not be doing, leads to a bad quality code review."

**review 有固定时间预算，浪费的轮次直接换成质量下降。** 这条是对「高层扫描 + 按需下降」这个设计的支持（剪枝省下来的轮次是真收益），同时也是对「四层都跑一遍」的反对。

## 4. AI 生成代码的缺陷在各高度的分布

### 4.1 三条已知线索，全部核实通过，但其中一条的含义和预期相反

ticket 给的三个 arXiv 编号，逐个用 arXiv API 核对了标题、作者、日期、摘要，**编号和数字都对**：

| 编号 | 标题 | 日期 | 关键数字 |
|---|---|---|---|
| [2510.03029](https://arxiv.org/abs/2510.03029) | *Investigating The Smells of LLM Generated Code*（Paul, Zhu, Bayley） | 2025-10-03 | 见 §4.2 |
| [2504.12608](https://arxiv.org/abs/2504.12608) | *Code Copycat Conundrum: Demystifying Repetition in LLM-based Code Generation*（Liu 等 12 人） | 2025-04-17 | 19 个模型、3 个 benchmark、**20 种重复模式**的分类法 |
| [2502.02368](https://arxiv.org/abs/2502.02368) | *Evaluating the Effectiveness of LLMs in Fixing Maintainability Issues in Real-World Projects*（Nunes 等） | 2025-02-04 | Llama few-shot **44.9%**、Copilot Chat **32.29%**、Llama zero-shot **30%**；"most solutions introduced errors or new maintainability issues" |

其中 2504.12608 的摘要原文 `[文档明述]`：

> "repetition is **pervasive** and manifests at various granularities and extents, including **character, statement, and block levels**. We further summarize a taxonomy of **20 repetition patterns**."

注意：它测的是**同一次生成内部的结构性重复**（字符/语句/块级），**不是「重造了仓库里已有的轮子」**。ticket 把它当成「重造轮子」的证据是**过度引申**——它不支持那个结论。`[推断]`

### 4.2 一篇直接测量，把假设的措辞顶了回来

假设的原话是：「模型写出来的代码通常**语法干净、格式规整**、错误处理看着齐全——这些正是行内评论擅长挑的。而它真正的毛病在上面。」

arXiv 2510.03029 的摘要，是本次调研里对这句话最直接的一次测量 `[公开数据]`：

> "The average smell increase across all LLMs was 63.34%, comprising **73.35% for implementation smells and 21.42% for design smells**."

拆开看是：LLM 生成的代码相对专业参考解法，**实现级 smell 多 73.35%，设计级 smell 只多 21.42%**。**方向和假设相反。**

更要命的是它的 implementation smell 清单 `[文档明述]`：

> 1. Inconsistent Naming Convention 2. Excessive Complexity 3. Incompleteness 4. Redundant Elements 5. **Improper Alignment and Placement** 6. **Magic Number** 7. Dead Code 8. Resource Handling 9. Documentation

**「命名不一致」「对齐与位置不当」「魔数」「注释不足」——正是假设认为 AI 做得好、行内评论擅长挑的那一族。** 这篇说 AI 在这一族上比人差得**更多**。

它的 design smell 清单是 Suryanarayana 的四族：Abstraction / Encapsulation / Modularisation / Hierarchy smell。

**方法细节（决定这条数据的射程）** `[公开数据]`：
- 数据集：ScenEval（教科书题 + StackOverflow 高分答案），Java。
- 基线：教科书作者或 StackOverflow 上被专业程序员高分认可的参考解法。
- 模型：**Gemini Pro、ChatGPT、Codex、Falcon**——按今天（2026-09）的标准是**上一代甚至上上一代模型**。
- 工具：PMD + Checkstyle + DesigniteJava。

### 4.3 但这篇作者自己划掉了它对「架构层」的射程

同一篇正文里有一句话，把它对我们这个问题的适用范围直接砍掉了一半 `[文档明述]`：

> "we believe that **architectural smells were not detected because there is no architectural level code generated by the test cases**. For the same reason, **architecture code smells were not detected in our work**."

即：**这篇没测架构层，因为 benchmark 任务里根本没有架构。** 它测的「design smell」是 Suryanarayana 体系里的**微架构级**（类级 OO 设计），不是「重造轮子、抽象错位、不符合本项目既有约定」那个层次。

所以准确的表述是 `[推断]`：

> **在单文件、无上下文的编码题这个尺度上，LLM 代码的实现级 smell 比设计级 smell 恶化得更厉害。这篇对仓库级架构问题没有发言权，作者自己承认了。**

### 4.4 假设怎么修才站得住

原假设（「AI 代码语法干净、格式规整」）**按字面读被 §4.2 证伪**。但它有一个修正版，我认为是站得住的，而且修正之后对产品设计的含义更清楚 `[推断]`：

> **不是「AI 写不出实现级问题」，而是「实现级问题在到达评审界面之前就被工具链吃掉了，设计级问题不会」。**

推理链：
1. §4.2 测的是**模型裸输出**，没过格式化器、没过 linter、没过 CI。
2. 它的 implementation smell 清单里，Inconsistent Naming Convention、Improper Alignment and Placement、Magic Number、Redundant Elements、Dead Code、Documentation 这六项，**在有 CI 的仓库里全部或部分被 formatter / linter 拦掉**（见 [编码规范的表达形式与可执行性谱系](09-规范表达形式谱系.md) 的第一档）。
3. design smell 四族（Abstraction / Encapsulation / Modularisation / Hierarchy）**没有一项有通用的确定性检测器**。架构层更是一个检测器都没有。
4. 所以**到达人眼的那份 diff 上，两族的残余比例和裸输出的比例是两码事**。假设说的是前者，2510.03029 测的是后者。

**这个修正有一条可以自己测的推论**，应该进 [评估基线](../../.agents/notes/proposed/testing/2026-09-12-evaluation-baseline-benchmark.md)：

> 取一批真实的 AI 生成 MR，**在跑完仓库自己的 formatter + linter + CI 之后**，再统计残余问题按高度的分布。如果修正版成立，残余里低层占比应该显著低于裸输出。**这个数字我们没有，业界也没有，必须自己测。**

**在这个数字拿到之前，「AI 代码的毛病在上面」只能写成待验证假设，不能写成立论。** 这和 [24 号调研](24-防护过度与-ai-生成代码的缺陷模式.md) 第九条的处境是一样的。

## 5. 工具：没有一个按高度组织，但有一个正在按「叙事」重组

### 5.1 逐个看主交互形态

| 工具 | 主交互形态 | 有没有高层版式 | 高层是主角吗 |
|---|---|---|---|
| **PR-Agent / Qodo Merge** | 行内建议表 + PR 正文改写 | **有两个**：`High-level` 建议分类（独立版式，Examples + Before/After 走查，不用 diff）、`High-Level Assessment`（列 3 个替代方案 + ➕/➖ + Recommendation） | **不是**。前者排在建议表最前面但仍在表内，后者折叠在 walkthrough 的 `<details>` 里 |
| **CodeRabbit** | 行内评论 + 顶部 Walkthrough 汇总 | **有**：Walkthrough（分组文件摘要、Mermaid 时序图、1–5 评审工作量分、相关 issue / 相关 PR / 建议评审人）、Security Architecture Review（付费 Security 模块） | **不是**。Walkthrough 默认整块折叠在 `<details>` 里 |
| **GitHub Copilot code review** | 行内评论（带 High/Medium/Low 严重度）+ 可一键应用的 suggested changes | 只有一句 overview 里的 "approval assessment" | **不是** |
| **Uber uReview**（内部） | 行内评论，带 `domain:subtype` 分类 + severity | 无。官方承认做不了系统设计评审 | **不是** |
| **Greptile / Graphite Diamond / Cursor BugBot / Amazon CodeGuru** | 未在本轮取到官方一手说明 | — | `[未查证]` |

**PR-Agent / Qodo 的细节**见 [Qodo 产品形态调研](25-qodo-产品形态.md) §1.8、§2.A2b、§7，那份是从真实产出样本反推的，比官方文档细。`[文档明述]`

**GitHub Copilot code review** `[文档明述]`（[官方文档](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/request-a-code-review/use-code-review)）：

> "Copilot labels each comment with a severity level of 'High,' 'Medium,' or 'Low' to help you prioritize the issues it finds based on their importance."
> "Every Copilot code review includes an approval assessment in the overview comment."

**注意它用的是 severity 不是 altitude。** 整个市场的排序维度都是严重度，没有一个是高度。`[推断]`

### 5.2 CodeRabbit 的 Change Stack：市场在动的是另一个轴

本次调研里唯一一个「明确否定扁平文件列表」的产品形态，是 CodeRabbit 的 **Change Stack** `[文档明述]`（[官方文档](https://docs.coderabbit.ai/change-stack)）：

> "it takes the same pull request and presents it as a structured artifact — **grouped into coherent areas, ordered so foundations come before the code that depends on them**."

> "A **layer** is a checkpoint in the change — a coherent step, with the files and review context that belong to it."

> "layers are numbered in **the order someone would explain the change**, which is roughly the order it was built rather than commit order or diff order."

> "**File and directory boundaries are treated as evidence, not as rules**, so a layer can span directories and a single directory can split across layers."

> "a contract and the code that implements it and the tests that cover it belong in one layer, not three."

**关键判读** `[推断]`：它的 "layer" **不是高度层，是叙事层**。它重排的是**空间/顺序**维度——把扁平文件列表重组成「先讲地基、再讲依赖它的东西」的讲解顺序。

这正好对上 ticket 里那两个正交轴：**Change Stack 做的是空间轴（分治），ticket 要做的是高度轴（下降）。市场已经有人在动空间轴了，高度轴仍然是空的。**

这对 [开源定位](../../.agents/notes/proposed/feature/2026-09-12-open-source-positioning.md) 是一条要更新的情报：**「扁平文件列表不对」已经不是差异化点了，CodeRabbit 正在解决它。差异化必须落在高度轴上，不能落在「比 diff 更好的组织方式」这个泛泛的说法上。**

### 5.3 高层内容不是没有，是被折叠起来了

一个反复出现的形态细节，三家一致：

- Qodo 的 `High-Level Assessment` —— 在 `<details>` 里。
- CodeRabbit 的 Walkthrough —— "By default, the entire walkthrough is wrapped in a collapsible `<details>` block"。`[文档明述]`
- Qodo 的 `High-level` 建议 —— 在建议表的 `<details>` 行里。

**高层内容已经被生产出来了，但它在版面上的地位是「默认折叠的附录」。** `[推断]`

这给了 ticket 的立论一个更准确的说法：**问题不是「没人做高层评审」，是「高层产出被压进了折叠块，而行内评论占据了主版面」。** 把它反过来，是一个版面权重问题，不是一个能力问题。这个改动比「发明一种新的评审能力」现实得多——但也意味着**护城河更浅**，见 §7.8。

### 5.4 架构级评审的自动化：确定性那一半是成熟的，判断那一半不是

- **CodeRabbit Security Architecture Review** `[文档明述]`（[官方文档](https://docs.coderabbit.ai/security/architecture-review)）："Assess the **security implications of architecture-level changes** in pull requests"，做法是「映射变更组件、追踪安全相关数据在系统中的流动、把风险判断锚定到代码里的具体证据」。**注意它把范围死死限定在安全上**——不是通用架构评审。`[推断]` 这大概率是刻意的：安全有相对客观的判据（信任边界、数据流），通用架构没有。
- **架构一致性检查（architecture conformance）** 这一族工具——ArchUnit、Sonargraph、CodeScene 等——本轮未取到官方一手说明，`[未查证]`。但从 [18 号跨仓库契约一致性检测](18-跨仓库契约一致性检测.md) 的结论可以外推 `[推断]`：这类工具的共同前提是**架构约束必须先被写下来**（ArchUnit 写成测试、Sonargraph 写成分层规则）。这和 [24 号调研](24-防护过度与-ai-生成代码的缺陷模式.md) 的第四条是同一条判据——**能机械证明的前提是已经被写下来了**。

**对我们的含义** `[推断]`：第二层（影响与结构）里，「有没有违反已写下的架构约束」是可以做成确定性检查的；「这个抽象层次对不对」不行。**这两件事必须在产品里分开，不能混成一个「架构评审」。**

### 5.5 代码地图与影响面可视化

- CodeRabbit 的 walkthrough 里有 **Mermaid 时序图** `[文档明述]`："Mermaid sequence diagrams showing the updated flow"（限于影响组件交互和 API 调用的 PR），以及 **related PRs**："Merged and open PRs that **touched the same areas of the codebase**"。
- Qodo 的 walkthrough 里有 **Diagram**（架构流向图），见 [25 号调研](25-qodo-产品形态.md) §356。
- 更成熟的「代码地图」类产品本轮未取到一手材料，`[未查证]`。

**能确认的只有一条** `[推断]`：**影响面的可视化在市场上已经存在，形态收敛到了「LLM 生成 Mermaid 图 + 折叠在 walkthrough 里」。** 它不是一个未解决的技术问题，它是一个「放在哪、谁会看」的版面问题。

## 6. 分层建议

### 6.1 建议：四层，但默认只有一层产出行内评论

ticket 那张草表的**层数是对的，产出形态有两层要改**：最高层不发评论、最低层默认不发。下面这版的每一行都对应到前面的一手依据。

| 层 | 问什么 | 判定依据住在哪 | **产出形态** | AI 可靠性预期 | 主要依据 |
|---|---|---|---|---|---|
| **L0 · 闸门** | 这个变更该不该以这个形态存在？有没有先决问题？ | MR 描述、关联需求、仓库既有方向 | **不是评论，是一个二值判断 + 理由**：`继续` 或 `停，这里有个先决问题` | **最低**。误报代价最高 | §1.2 navigate.md Step One；§2.1 Linux「说服评审者读完第一段」 |
| **L1 · 契合与影响** | 重造了什么？跨了哪些边界？违反了哪条写下来的约定？波及谁？ | **仓库 + 规范库 + 跨仓关联 + 历史 PR** | **证据清单 + 影响面图**，不用行内评论 | 中。**取决于喂进去多少上下文** | §1.1 Google Design 三问；§1.5 OWNERS bit；§2.1 内核重造轮子；§3.2（5）影响面难判断的文件有用性最低 |
| **L2 · 实现正确性** | 逻辑、边界、并发、错误处理对不对？ | 变更本身 + 局部上下文 | **行内评论 + 证据**。这一层行内评论就是对的形态 | **最高** | §3.7 Uber 实测本层价值最高；§3.4 bugs 采纳率 41.9%；§1.5 LGTM bit |
| **L3 · 细节** | 命名、格式、注释、风格 | 代码文本 + 风格规范 | **默认不产出**；仅在仓库没有 formatter/linter 时降级开启 | 高，但价值低 | §3.7 Uber 实测本层评价最差；§4.4 工具链应先吃掉这层 |

### 6.2 三处和 ticket 草表不一样的地方，以及理由

**（1）第一层的产出从「三个替代方案 + 推荐意见」改成「二值闸门 + 理由」。**

理由有三条，互相独立：

- Google 明确禁止评审者出于偏好提替代方案，只有作者的做法「deficient」时才允许（§1.6）。给方案是越界。
- Bosu 的数据说「指向未来工作、当下不可操作」的评论被作者评为**没用**（§3.2）。一份「你本来还可以这么做」的清单，如果不能在这个 MR 里落地，就是这一类。
- L0 是 AI 最不可靠的一层（§7.9），而误报代价最高。**二值输出的误报是可以被一眼否掉的；一份三选项对比表的误报会先骗走用户半小时。**

**如果确实要做「替代方案」这件事，Rust RFC 的角色分配是更安全的形态**（§2.2）：**让 AI 补全「作者没在描述里说清的替代方案与取舍」，交给作者去答**，而不是让 AI 直接裁决。主语从评审者换成作者，就绕开了 Google 那条禁令。

**（2）ticket 的第三层和第四层保持分开，但第四层默认关闭。**

Google 的成文流程把这两层合并成一句「按工具给的顺序过一遍」（§1.2）。但 Uber 的生产数据说这两层的**实测价值差别极大**（§3.7：correctness bugs 好 / readability nits 差），不该合并。合并会让低价值的第四层稀释第三层。**分开，然后把第四层默认关掉**——这是 Uber 的 comment category filter 已经在做的事（§3.7）。

**（3）增加一条草表里没有的：L1 内部必须区分「已写下的约定」和「没写下的判断」。**

前者（违反 ArchUnit 规则、违反写在规范库里的模块边界）可以做成确定性检查，要给高置信度；后者（这个抽象层次对不对）只能是提问。§5.4 和 [24 号调研](24-防护过度与-ai-生成代码的缺陷模式.md) 的第四条两边独立得出同一个判据：**能不能机械证明，取决于那条约定有没有被写下来。** 混成一个「架构评审」会同时毁掉两者的可信度。

### 6.3 下降路径的五条规则

**规则一：可以不下降，而且不下降是省钱不是偷工。** `navigate.md` 原话说继续往下看 "might be a waste of time"（§1.3）。L0 判 `停` 时直接返回，不跑 L1–L3。

**规则二：剪枝只能是全有或全无。** 不能用「L0/L1 过了」当作「L2/L3 可以少看」的理由（§7.3 Google Every Line）。L0 是「打回 vs 全看」的开关，不是「看多细」的旋钮。**如果因为成本确实跳过了某些部分，必须显式告诉用户跳过了什么**——AI 的静默漏检没有人兜底。

**规则三：可从任意层进入，而且默认入口应该按人来定。** 对这块代码的 owner，默认进 L2（Bacchelli 观察到 owner 直接进文件、不读描述，强制走顶层会拖慢他出第一条评论，§7.7）。对不熟悉的评审者，默认从 L0/L1 进。**这条需要知道「谁在看」，是产品要额外拿的一个信号。**

**规则四：层间用共享锚点连接，不要各说各的。** Rust RFC 模板要求 Reference-level "should return to the examples given in the previous section"（§2.2）。我们的对应做法：**L1 指出的每一处「契合度问题」，都要能一键跳到 L2/L3 里对应的具体位置**；反过来 L2 的 finding 要能上溯到它属于 L1 的哪个问题。**上下层不共享锚点，分层就退化成四份互不相关的报告。**

**规则五：分层不是默认开启，它有一个规模阈值。** Czerwonka 的数据说有用性随规模下降**从 20 个文件以上才开始明显**（§3.3）；Google 的变更中位数是 24 行、35% 是单文件（§1.7）。**第一版建议：变更文件数低于阈值时直接走 L2（行内），只有超过阈值才启用完整下降路径。** 阈值初值取 20 个文件，然后用自己的数据校准。

### 6.4 一条草表里没有、但材料反复指向的东西：权重随变更类型变

《SWE at Google》第 9 章 `[文档明述]`：

> "All code reviews are not alike! **Different types of code review require different levels of focus on the various aspects of the review process.**"

它给的四类是 greenfield / behavioral changes、improvements、optimizations / bug fixes and rollbacks / refactorings and large-scale changes，并对 greenfield 单独说了 "A greenfield review is **the most important time** to evaluate whether the code will stand the test of time"。

**含义** `[推断]`：L0/L1 的权重应该在 greenfield 和大重构上最高，在 bug fix 和自动生成的大规模改动上最低（后者 Google 甚至要求评审者**限制评论范围**："we encourage reviewers to limit comments in the associated change and only flag concerns that are specific to their code, not the underlying tool"）。**变更类型分类是启用分层之前就要做的一步**，它比规模阈值更准。

### 6.5 投入之前必须先测的三件事

这三条都没有公开数据，而且每一条单独失败都足以推翻方向。

**（一）CI 之后的残余缺陷按高度的分布。** 取一批真实 AI 生成的 MR，跑完仓库自己的 formatter + linter + CI，统计残余问题落在 L0–L3 的比例。**整个立论建立在「低层残余少、高层残余多」上，而现有唯一的直接测量（§4.2）说的是反话。** 这是第一优先级。

**（二）同样的高层意见，换成非行内载体，采纳率会不会变。** 现有全部实证（§3.2、§3.4）都用「评论锚定行是否被改」当判据，按构造测不出高层评论的价值（§3.5）。**「换个载体能提高高层建议采纳率」这个假设，业界一次都没测过，我们必须自己测。** 做法：同一批 design 类发现，A 组发行内评论，B 组发独立版式，比采纳率和用户评分。

**（三）按高度分层统计 AI 的准确率，而不是算总分。** ticket 已经提了，这里补两条具体要求：①误报率必须按层分开报，因为**误报代价在各层不同**（§7.9）；②要单独测「无上下文基线」——Czerwonka 那条 33% 是人类无上下文时的有用率（§3.3），我们的 L1 如果不喂规范库和跨仓关联，应该以它为对照。这条要进 [评估基线](../../.agents/notes/proposed/testing/2026-09-12-evaluation-baseline-benchmark.md)。

## 7. 这条路的风险：最可能死在哪里

**先给答案，按致命程度排。** 三条我认为真的会杀死这个方向，四条会让它长不大，两条只是要处理好。

| # | 死法 | 致命性 | 判据 |
|---|---|---|---|
| 1 | **立论的事实基础是错的**——AI 代码的残余缺陷其实还是集中在低层 | **致命** | §6.5 实验（一）。现有唯一的直接测量（§7.5）方向相反 |
| 2 | **L0 的误报代价过高**——可靠性最低的层，误报代价最高 | **致命** | §7.9。一条错的「你该重做」浪费一天，用户第二次就不看了 |
| 3 | **团队说「这不是 review 该干的事」**——Google / Linux / Rust 三家的制度都把最高层放在代码之前 | **致命** | §7.1、§7.2 |
| 4 | 高层建议采纳率本来就低（28.6% vs 43.3%），用户感知价值更低 | 长不大 | §7.4 |
| 5 | 多数变更太小，没有高度，默认开启是做负功 | 长不大 | §7.6 |
| 6 | 护城河浅，版面权重可被一个 sprint 复制 | 长不大 | §7.8 |
| 7 | 买单的人（经理）不认「替代方案」这个价值 | 长不大 | §7.4 末行 |
| 8 | 强制线性下降会惩罚最有价值的评审者（owner） | 可处理 | §7.7，解法见 §6.3 规则三 |
| 9 | 剪枝错了是静默漏检 | 可处理 | §7.3，解法见 §6.3 规则二 |

**一句话回答「最可能死在哪里」**：**死在第 1 条和第 2 条的组合上**——立论没有数据支撑，而第一层又恰好是 AI 最容易一本正经胡说的地方。一个建立在未验证假设上、又把最不可靠的输出放在最显眼位置的产品，第一次误报就会失去用户，而且**没有数据可以用来说服自己「再调调就好了」**。

**这两条都有解，而且解法相同：先测，再做。** §6.5 的三个实验做完之前，不要把第一层顶到主版面。

下面是全部反面证据的出处，前面章节出现过的只做索引，不重复引文。

### 7.1 三家独立组织给最高层的答案都是「把它移到代码之前」

| 组织 | 成文做法 | 出处 |
|---|---|---|
| Google | 新项目走 "an extensive design review, **apart from a code review**"；"A code review is **not the time** to debate design decisions already made in the past" | §1.6 |
| Linux kernel | "**discuss it with the development community before investing in the creation of a body of code**"；写代码前先答三问 | §2.1 |
| Rust | "substantial" 改动不走 PR，走 RFC；未走 RFC 的特性 PR "**may be closed with a polite request to submit an RFC first**" | §2.2 |

**这是本方向面临的最根本的制度性反对** `[推断]`：不是「高层不重要」，而是**「高层重要到不该在评审阶段才第一次被问」**。一个把第一层顶到最前面的工具，很可能收到的回应是「这些我们在设计评审里已经过了」。

**但这条反对有一个正在失效的前提，必须一起写下来** `[推断]`：上述三家的做法都建立在「**写代码很贵，所以值得先讨论**」上。Linux 那段原话的逻辑是 "before **investing in** the creation of a body of code"。**AI 把「写代码」的成本压到接近零，这个前提就松了**——现在代码常常在任何人讨论之前就已经存在了。ticket 的立论要成立，靠的正是这条：**上游的设计讨论通道被 AI 工作流绕过了，所以负载被迫下沉到评审阶段。**

这条推理是整个方向的支点，而且它**没有公开数据支持**。它是一个关于工作流变化的断言，必须自己去验证（比如：统计团队里有多少 AI 生成的 MR 走过了设计讨论）。

### 7.2 Google 自己的田野数据：把设计塞进 review 会产生摩擦

Sadowski et al. ICSE-SEIP 2018 的 "Review subject" 主题，见 §1.7。团队之间对此**没有共识**，且论文明确说 "could cause friction among participants and within the process"。`[文档明述]`

**一个通用开源工具的默认行为，是在替所有团队做一个有争议的选择。** `[推断]` 这条的现实含义是：**分层必须可配置、可关闭，默认值要保守**。

### 7.3 Google 同一套文档里有一条和「剪枝」直接冲突的规定

`looking-for.md` 的 Every Line 一节 `[文档明述]`：

> "In the general case, look at **every** line of code that you have been assigned to review. Some things like data files, generated code, or large data structures you can scan over sometimes, but **don't scan over a human-written class, function, or block of code and assume that what's inside of it is okay**."

而 `navigate.md` 说重大设计问题出现时 "reviewing the rest of the CL might be a **waste of time**"。

**两条怎么共存** `[推断]`：Every Line 的适用前提是「你已经决定要评审这个 CL」。剪枝发生在那之前——设计不过关就整个打回，根本不进入逐行阶段。所以不矛盾，但**它划出了剪枝的边界：剪枝只能是全有或全无（打回 vs 全看），不能是「设计 OK，所以下面随便扫扫」**。

**对产品的硬约束**：不能用「高层扫完没发现问题」当作「低层可以少看」的理由。人类评审者剪枝错了还有别人兜底；**AI 剪枝错了是静默漏检，没有人知道它跳过了什么。** 这是剪枝的真实成本，必须有兜底机制（至少要明确告诉用户「哪些部分没看」）。

### 7.4 高层建议的采纳率、有用性、可操作性，三项数据都不利

| 数据 | 数字 | 出处 |
|---|---|---|
| design 类评论采纳率 | **28.6%**，四类中最低（readability 43.3%） | §3.4 |
| "Solution Approach" 的有用性评级 | 落在「有点用」档，与缩进、空行同档 | §3.2 |
| 指向未来工作、当下不可操作的评论 | 作者评为**「没用」** | §3.2 |
| 无上下文评审者的整体有用率 | **33%** | §3.3 |
| 开发者把「替代方案」列进动机前三 | 57%，但**只有 2% 的经理提到它** | §3.1（3） |

**最后一行是一个容易被忽略的商业问题** `[推断]`：开发者想要「替代方案」，但**买单的人（经理）不认这个价值**。一个企业内平台如果把资源压在这一层，会面临「谁为它付费」的问题。

### 7.5 「AI 代码语法干净、毛病在上面」这句话，按字面是错的

arXiv 2510.03029 的 implementation smell +73.35% vs design smell +21.42%，见 §4.2。**假设里被点名为「AI 做得好」的那几项（命名、对齐、魔数、注释），恰恰是这篇测出 AI 做得最差的那一族。** 修正版见 §4.4，但修正版**没有数据**。

`[推断]` 如果 §4.4 那个实验（CI 之后的残余分布）跑出来发现低层残余依然占大头，**这个方向的立论就塌了**，产品应该退回「更好的行内评论」。这条必须在投入之前测。

### 7.6 多数变更根本没有高度

| 数据 | 数字 | 出处 |
|---|---|---|
| Google 变更中位行数 | **24 行** | §1.7 |
| Google 单文件变更占比 | **35%+**；单行变更 **10%+** | §1.7 |
| 有用性开始随规模下降的阈值 | **20 个文件以上** | §3.3 |

`[推断]` 在 20 文件以下的变更上，分层是纯开销：多跑几轮模型、多占一屏版面、多让用户点几下，换不来任何东西。**默认全量开启分层，会在绝大多数 MR 上做负功。**

### 7.7 自顶向下不是人的自然评审路径

Bacchelli & Bird 的现场观察，见 §3.1（6）`[文档明述]`：

> "In the first group [先通读描述的那组], the time required for putting the first review comments and understanding the change rationale was **noticeably longer**"

> "when they own or are very familiar with the files being changed... they often **do not need to read the description**, but they 'go directly to the files they own.'"

`[推断]` **自顶向下是缺上下文者的补偿路径，不是普遍更优的路径。** 对已经掌握顶层的 owner，强制走一遍是纯损失，而且会拖慢他出第一条评论的时间——**而 owner 恰恰是产出最高价值评论的那批人**（§3.3：第三次看同一块代码时有用率 67%）。

**把下降路径做成强制线性漏斗，会精确地惩罚最有价值的用户。**

### 7.8 护城河比想象的浅

- 高层内容**已经被三家工具生产出来了**，只是被折叠（§5.3）。
- CodeRabbit 的 Change Stack 已经在重组 PR 的组织方式（§5.2），只不过走的是空间轴。
- Qodo 的 `High-Level Assessment` 已经是「三个替代方案 + 推荐」这个形态（§5.1）。

`[推断]` **「把高层提为主角」是一个版面权重决策，不是一项新能力。** 它可以在一个 sprint 内被任何一家竞品复制。真正难复制的是**让高层内容变准**所需要的上下文积累（规范库、跨仓关联、历史 PR）——这和 §3.1（4）、§3.3、§3.6 三处的结论一致。**护城河在上下文，不在版式。**

### 7.9 AI 在最高层最不可靠，而误报代价在最高层最高

- Uber 官方承认 uReview "can't correctly assess overall correctness and **review the system design**"（§3.7）。
- 无上下文评审者的有用率 33%（§3.3）——AI 的默认处境就是「无上下文」。
- Atlassian 那篇明说 LLM 评审者产出的 design 类评论**比人类少**，原因是不熟悉项目架构与社区惯例（§3.6）。
- LLM 独立修可维护性问题成功率 30%–44.9% 且 "most solutions introduced errors"（§4.1）。

`[推断]` 三条独立来源指向同一件事：**AI 越往高层走越不可靠**。而 ticket 自己也点出了误报代价的不对称——一条错的命名建议只是烦人，一条错的「你该重构」会浪费一整天。**可靠性最低的层，误报代价最高。这是本方向最危险的一处。**

## 调研范围的一次收窄

本文最初的任务是「C/C++ 检测手段与 LLM 的分工」，覆盖内存安全的全部谱系。调研进行中需求方明确：**忽略 C 语言的内存问题，那是遗留问题，不在本产品范围内**。

- 「GPT 模型写的代码防护过度」
- 「不符合团队规范，而且没有有效的规范建设机制」

## 0. 结论先行

**一、「防护过度」不是一个类别，是六个**，它们的归宿完全不同。区分它们的唯一变量是：判定「这处防护多余」所需的那条信息**住在哪里**。

**二、工具能测的那部分，比预判的多；但能测的原因，恰好证明了预判的内核是对的。** 主流生态里有一整族命名直白的「冗余防御」规则（Go staticcheck 十余条、Error Prone `UnnecessaryCheckNotNull` 是 ERROR 级、Go `nilness` 的标题就叫 "check for redundant or impossible nil comparisons"）。但把它们的判定依据归拢，只有三种，无一例外：**语言/库语义被硬编码进工具**、**同一函数内的控制流或类型收窄**、**契约被显式写成了注解**。三者共同的前提是「不可能为空」这件事**已经以某种形式被写下来了**。前提一失效，规则一条不剩。

**三、想用复杂度度量当代理指标这条路走不通。** 它无方向（分不清「业务本身复杂」和「防护过度」），而且对最典型的过度防御形态——平铺的守卫子句——最不敏感：三条多余的守卫只贡献 +3 认知复杂度，离 PMD 默认阈值 15 和 clang-tidy 默认阈值 25 都很远。SonarSource 白皮书自己也承认圈复杂度与代码行数高度相关、"of little use above the method level"。

**四、这条线不是「难不难」，是「能不能被机械证明」——而且这个判据两边独立得出。** 工具侧是上面那三种依据；规范侧是 NASA/JPL Power of Ten 的 Rule 5：*"Any assertion for which a static checking tool can prove that it can never fail or never hold violates this rule."* 两边说的是同一件事。

**五、剩下那部分之所以测不了，是因为它根本不是代码的属性。** NASA/JPL **要求**每个函数平均两条断言、**要求**每个函数内部校验参数（Rule 5、Rule 7）；Google code review 指南**要求** reviewer 警惕 over-engineering。同一段代码，两份权威文本结论相反。**「防护过度」是「代码 × 团队风险偏好」的函数**，不存在通用判据。

**六、因此第二条痛点和第三条痛点是同一条。** 「GPT 写的代码防护过度」之所以成为痛点，不是缺工具，是这个团队**从没把「防护到什么程度算够」写下来过**。

**七、LLM 的增量价值真实存在，但很窄，且来自信息通道而非推理能力。** 按信息所在位置分四层：

| 层 | 判定依据在哪 | 归属 |
|---|---|---|
| 1 | 同一函数内 | **工具**。LLM 增量为零甚至为负 |
| 2 | 同仓库跨函数 | 工具（贵，我们养不起）→ 降级为「确定性检索 + LLM 判断」 |
| 3 | **注释、文档、命名、接口约定** | **只有 LLM**。这是产品的主战场 |
| 4 | 只在人脑子里 | 谁都不行。**先把它写下来，变成第 3 层** |

**八、三条必须一起接受的限制**（都有公开数据）：LLM 独立修可维护性问题在真实项目上只有 30%–44.9% 成功率且"most solutions introduced errors"，所以**改写建议不得自动应用**；LLM 评判者对低 perplexity（即「熟悉」）输出的评分显著高于人类，**而 GPT 风格的冗余防护恰恰是同族模型最熟悉的形态**，这条必须专门做 benchmark 验证；design 类评论的采纳率天然低于 bug 类，指标要单独设档。

**九、没有数据支持的那一条，要诚实说出来。** 「AI 生成代码 code smell 更多」有量化数据（均值 +63.34%）、「结构性重复普遍」有量化数据（19 个模型、20 种模式），但**「AI 代码的典型缺陷是防护过度」没有找到任何直接研究**。它目前只是这个团队的主观观察，需要先测量再立项。

**十、一句话**：**「防护过度」不是检测问题，是规范缺失问题。** 产品的第一优先级不是做检测器，是先让团队把这条线写下来。

## 1. 先把「防护过度」拆开

需求方给的是一句话：「GPT 模型写的代码防护过度」。这句话在工程上不可判定，必须先拆成可以分别回答「工具能不能测」的子类。下面这六类是我按「判定所需信息」拆的，不是抄来的分类法——第 4 节会说明，**公开的 code smell 目录里根本没有「过度防御」这个条目**，所以没有现成分类可抄。`[推断]`

| # | 子类 | 典型形态 | 判定「它是多余的」需要知道什么 |
|---|---|---|---|
| A | **语义上多余的判空** | 对一个刚 `new`/刚由工厂返回的对象判空；对调用方保证非空的参数判空 | 该值在此处不可能为空 |
| B | **重复校验** | 同一个参数在入口、中间层、底层各校验一次 | 上游已经校验过，且上游一定会被走到 |
| C | **吞异常** | `catch (...) {}`、`catch (Exception e) { log.debug(...) }` 后继续往下走 | 这个异常是否应该被吞 |
| D | **不可能分支** | 对枚举穷举后再写 `default: return error`；对 `len(x) < 0` 判断 | 该分支不可达 |
| E | **过深嵌套 / 层层守卫** | 五层 `if` 守卫，每层返回不同错误码 | 这些守卫哪些是必要的 |
| F | **投机性通用化** | 为没有的需求预留参数、抽象、扩展点 | 这个扩展点现在没有使用者，且可预见地不会有 |

这张表的价值在最后一列。**这一列决定了子类的归宿**——它是「同一段代码文本内可推导」，还是「需要程序文本之外的信息」。第 2 节全部围绕这一列展开。

## 2. 工具侧：现有静态分析到底能测哪几类

### 2.1 一个反直觉的开局

调研前的预判是「基本没有工具能测过度防御代码」。**这个预判在规则清单面前先被推翻了一半**：主流生态里存在一整族专门检测「冗余防御性检查」的规则，而且数量不少、命名直白。

### 2.2 关键的一步：这些规则凭什么判定「多余」

把上面所有规则的判定依据归拢，只有**三种**，一条都不例外。`[推断]`（推理链：逐条读官方描述，看它的判定前提是什么）

**依据一：语言或库的语义被硬编码进了工具。**

staticcheck 那一整族 `S10xx` 规则全属此类。`S1009` 能说「slice 的 nil 判断是冗余的」，是因为 Go 语言规定 `len(nil slice) == 0`；`S1033` 能说「delete 前的 map 判空是冗余的」，是因为 Go 规定 `delete` 作用在 nil map 上是 no-op；`SA4022` 能说 `&x == nil` 无意义，是因为取地址永不为 nil。工具没有推理任何东西，**它只是被人预先告知了这些语言事实**。

Error Prone 的 `ImpossibleNullComparison` 是这一类最露骨的例子。它的别名就叫 `ProtoFieldNullComparison`，官方解释：`[文档明述]`

> "This checker looks for comparisons of protocol buffer fields with null. If a proto field is not specified, its field accessor will return a non-null default value. Thus, the result of calling one of these accessors can never be null, and comparisons like these often indicate a nearby error."

也就是说，它之所以敢断言「这个判空多余」，是因为**有人把 protobuf 这一个具体库的行为写进了这条规则**。换一个库，规则就失效。

**依据二：同一个函数内的控制流或类型收窄。**

Go 的 `nilness` 明说分析范围是 "the control-flow graph of each function"——**函数内**，靠 CFG 推出 `x` 在这一点上必非 nil。typescript-eslint 的 `no-unnecessary-condition` 明说判定依据是 "as determined by the type of the expression"——靠类型系统。

这一依据的边界，官方自己写得很清楚。typescript-eslint 列出的局限：`[文档明述]`

> "By default, TypeScript optimistically assumes that indexed access will always return a value. This means that cases like the following will be erroneously flagged as unnecessary conditions"

> "typescript-eslint assumes that all object types represent JavaScript objects, which are always truthy. This is not always the case, because object types only represent the shape of values."

还有一条指向 TypeScript 自身的窄化能力上限：值在函数调用中被修改时，"This occurs due to limitations of TypeScript's type narrowing. See microsoft/TypeScript#9998 for details."

**注意这里的失败方向**：这条规则的误报来自**类型标注比现实更乐观**。也就是说，工具相信的不是代码事实，是**有人写下的类型**。

**依据三：契约被显式写了下来。**

这是第三条路，也是唯一一条能把「A 类：语义上多余的判空」真正机械化的路。代表是 Uber 的 NullAway（[README](https://github.com/uber/NullAway)）：`[文档明述]`

> "NullAway assumes every method parameter, return value, and field is _non-null_, i.e., it can never be assigned a `null` value."

默认非空、可空必须显式标 `@Nullable`。一旦这个契约写下来，「对一个未标 `@Nullable` 的值判空」就变成了一条**机械可判定**的规则。代价是标注负担，而 NullAway 官方对自己的定位也很坦率：

> "NullAway is also _practical_: it does not prevent all possible NPEs in your code, but it catches most of the NPEs we have observed in production while imposing a reasonable annotation burden."

性能上它给了一个具体数字：`[公开数据]`

> "In our measurements, the build-time overhead of running NullAway is usually less than 10%."

[JSpecify](https://jspecify.dev/docs/start-here/) 是同一条路上的标准化努力——把 nullness 契约做成跨工具的统一注解，官方目标是让使用者"拥有单一的真实信息源来指导代码注解方式，而不是为了迎合某个工具而牺牲其他工具的支持"。`[文档明述]`

### 2.3 裁决：预判证实了一半，推翻了一半

**被推翻的部分**：说「基本没有工具能测」是不准确的。工具不但能测，而且有专门命名的规则族，Error Prone 里 `UnnecessaryCheckNotNull` 的 severity 是 ERROR——这是 Google 敢在编译期直接失败的档位，说明其误报率被认为接近零。

**被证实的部分，也是决定性的部分**：这些规则能成立，全都因为「不可能为空」这件事**已经以某种形式被写在了程序文本或工具内部**——语言规定、库行为被硬编码、类型标注、`@Nullable` 注解。

**一旦这个前提不成立，规则一条都不剩。** `[推断]`

需求方抱怨的 GPT 代码恰恰落在前提不成立的那一侧。原因可以直接推出来：**LLM 在缺上下文的地方加防护**。它不知道调用方保证了什么，不知道这个内部函数只被一个地方调用过，不知道团队约定"配置读取层已经做过校验"——所以它在那里加判空。而工具同样不知道这些，**因为这些事实从来没有被写下来过**。

这不是巧合。两者的信息盲区是同一个盲区。

### 2.4 六个子类的归宿

把第 1 节的六类对上第 2.2 的三种依据：

| 子类 | 现成工具能测吗 | 靠哪种依据 | 失败模式 |
|---|---|---|---|
| **A 语义上多余的判空** | **只能测最退化的一小部分** | 依据一/二/三 | 值来自跨函数、跨模块、或调用方约定时，一条都报不出 |
| **B 重复校验** | **基本不能** | —— | 需要知道上游一定走到且一定校验过，这是跨过程 + 可达性问题 |
| **C 吞异常** | **能，且准** | 语法层，不需要语义 | 只能测「空」，测不了「记了一行 debug 日志就往下走」 |
| **D 不可能分支** | **能测一部分** | 依据一/二 | 分支的不可达性依赖外部约束时报不出 |
| **E 过深嵌套 / 层层守卫** | **只能测「深」，测不了「多余」** | 复杂度度量 | 见第 3 节，度量无方向 |
| **F 投机性通用化** | **能测最表层的「完全没有使用者」** | 死代码/未使用检测 | 有一个调用点就失效 |

**C 是唯一一个干净可测的子类。** CWE 也是这么认的：CWE-1071 "Empty Code Block" 的 Detection Methods 里，Automated Static Analysis 的 Effectiveness 评级是 **High**（[CWE-1071](https://cwe.mitre.org/data/definitions/1071.html)）。`[文档明述]`各生态都有现成规则，已逐条核实存在：PMD `EmptyCatchBlock`、staticcheck `SA9003`、clang-tidy `bugprone-empty-catch`、ESLint [`no-useless-catch`](https://eslint.org/docs/latest/rules/no-useless-catch) 与 `no-empty`。`[文档明述]`

但要注意 C 的真实边界。**空 catch 能测，「假装处理了」的 catch 测不了。** GPT 生成的代码更常见的是后者——`catch` 里记一行日志、返回一个默认值、然后继续往下走。语法上它非空、有内容、看起来负责任；语义上它把一个本该中止的流程变成了带着坏数据继续跑。要判定这一类，需要知道「这个错误是否可恢复」「返回这个默认值下游能不能接受」，又回到了程序文本之外。`[推断]`

## 3. 复杂度度量能不能当「过度防御」的代理指标

既然直接判定不了，一个自然的替代想法是：**用复杂度度量当代理**——圈复杂度高、认知复杂度高、嵌套深，就说明防护过度。这个想法值得认真对待，也值得认真否掉。

### 3.1 两个度量各自在测什么

**McCabe 圈复杂度**测的是控制流图上的独立路径数，等价于「完全覆盖这个方法所需的最少测试用例数」。

**Cognitive Complexity** 是 SonarSource 2016 年提出、G. Ann Campbell 执笔的度量（[白皮书 v1.7, 2023-08-29](https://www.sonarsource.com/docs/CognitiveComplexity.pdf)）。它对圈复杂度的批评写得很直白：`[文档明述]`

> "while it accurately calculates the minimum number of test cases required to fully cover a method, it is not a satisfactory measure of understandability. This is because methods with equal Cyclomatic Complexity do not necessarily present equal difficulty to the maintainer, leading to a sense that the measurement **'cries wolf'** by over-valuing some structures, while under-valuing others."

它给出的三条基本规则：

> 1. "Ignore structures that allow multiple statements to be readably shorthanded into one"
> 2. "Increment (add one) for each break in the linear flow of the code"
> 3. "Increment when flow-breaking structures are nested"

**默认阈值**：PMD `CognitiveComplexity` 为 15，clang-tidy `readability-function-cognitive-complexity` 为 25。`[文档明述]`

### 3.2 圈复杂度和代码行数高度相关——SonarSource 自己承认

这条常被当成外部批评，但其实白皮书里自己写了：`[文档明述]`

> "it is widely acknowledged that the Cyclomatic Complexity scores of applications correlate to their lines of code totals. In other words, **Cyclomatic Complexity is of little use above the method level**."

**读法**：圈复杂度的解释力有相当一部分来自「代码更长」这个平凡事实。用它当「防护过度」的指标，很可能只是在报「这个函数长」。`[推断]`

我没有找到独立于 SonarSource 的、量化 Cognitive Complexity 与理解耗时相关性的一手实证。`[推断]`（依据：arXiv 检索 `cognitive complexity` × `comprehension` 无结果；可能存在于 ACM/IEEE 而未被 arXiv 收录。这一条应标记为未取到一手依据。）

### 3.3 决定性的问题：度量没有方向

两条，都是致命的。`[推断]`

**第一，度量分不清「业务本身复杂」和「防护过度」。** 一个函数认知复杂度 30，可能是它在实现一个真有 30 个分支的状态机，也可能是它在做 30 层无谓守卫。度量给出同一个数字。**要区分两者，需要知道哪些分支是必要的——正好是第 2 节论证过的、工具做不到的那件事。** 代理指标没有绕过原问题，只是把它藏起来了。

**第二，更糟的是：过度防御的代码不一定复杂度高。** 按白皮书的规则 3，只有**嵌套**的流程中断结构才吃嵌套增量。而 GPT 最典型的过度防御形态是**平铺的守卫子句**：

```c
int process(Item *it, int qty, const char *tag) {
    if (it == NULL)   return -1;   /* +1，无嵌套增量 */
    if (qty < 0)      return -2;   /* +1 */
    if (tag == NULL)  return -3;   /* +1 */
    /* ... 真正的逻辑 ... */
}
```

三条多余的守卫，认知复杂度一共 +3，离 PMD 的 15 和 clang-tidy 的 25 都很远。**最典型的过度防御形态，恰好是这个度量最不敏感的形态。**

而且这还是往坏里说。白皮书明确说规则 1 要"incent good coding practices"——把可读的简写形式**不计分**（例如 null-coalescing 运算符计 0，而等价的显式 `if (a != null)` 计 +1）。也就是说，度量的设计目标是**奖励可读**，不是**惩罚冗余**。这两件事只是偶尔重合。

### 3.4 结论

**复杂度度量不能当「过度防御」的代理指标。** 它无方向（测不出冗余还是必要），且对最典型的过度防御形态（平铺守卫）不敏感。

它仍然有用，但用途不同：**当作「这个函数值得人看一眼」的排序信号**，而不是「这里有防护过度」的判定。放在 [大 PR 的递归拆分与动态规范选取](../../.agents/notes/proposed/architecture/2026-09-12-large-pr-splitting-and-rule-routing.md) 的注意力分配上是合理的，放在检测规则上不合理。`[推断]`

## 4. 「防护过度」在标准与学术里的地位：它连名字都没有

这一节的结论对产品决策很重要，因为它决定了我们**能不能指望买到或抄到一套现成规则**。

### 4.1 CWE 里最接近的三条，都不是它

| CWE | 名称 | 定义原文 | 自动检测有效性 |
|---|---|---|---|
| [CWE-1164](https://cwe.mitre.org/data/definitions/1164.html) | Irrelevant Code | "The product contains code that is not essential for execution, i.e. makes no state changes and has no side effects that alter data or control flow, such that removal of the code would have no impact to functionality or correctness." | —— |
| [CWE-571](https://cwe.mitre.org/data/definitions/571.html) | Expression is Always True | "The product contains an expression that will always evaluate to true." | Automated Static Analysis：**High** |
| [CWE-1071](https://cwe.mitre.org/data/definitions/1071.html) | Empty Code Block | "The source code contains a block that does not contain any code, i.e., the block is empty." | Automated Static Analysis：**High** |

`[文档明述]`

CWE-1164 的子条目是 Dead Code（CWE-561）、Assignment to Variable without Use（CWE-563）、Empty Code Block（CWE-1071）以及两条 Struts 专属变体。

**注意 CWE-1164 定义里的那个限定词**："such that removal of the code would have no impact to functionality or correctness"。一个多余的判空**并不满足这个定义**——它是一个真实的分支，改变控制流；只有在你已经知道该值不可能为空的前提下，删掉它才无影响。**「已经知道」正是缺失的那一环。** 所以「防护过度」不是 CWE-1164 意义上的 irrelevant code，它是一类**条件性冗余**，而 CWE 的分类法里没有这个格子。`[推断]`

CWE-571 的自动检测有效性是 High，但它的适用面同样卡在「always」这个词上——必须是**恒**真，不是「在当前调用图下碰巧总是真」。

### 4.2 Fowler 的 Speculative Generality 只覆盖了第 F 类

最常被拿来对应「过度设计」的具名 smell 是 Speculative Generality。它的通行定义（[refactoring.guru](https://refactoring.guru/smells/speculative-generality)，该页面**未注明引自 Fowler 原书**，属二手转述，本文只作参考）：

> Signs and Symptoms: "There's an unused class, method, field or parameter."
>
> Reasons: "Sometimes code is created 'just in case' to support anticipated future features that never get implemented."

`[公开数据]`（二手）

关键点：它的判据是 **unused**——没有使用者。这覆盖的是第 1 节的 F 类（投机性通用化），而且是 F 类里最表层的那部分。**它完全不覆盖 A 到 E。** 一个多余的判空不是 unused 的，它每次调用都在执行。`[推断]`

我没有在任何公开的 code smell 目录里找到「过度防御 / 冗余校验」作为一个具名条目。`[推断]`（依据：查了 CWE 的 Irrelevant Code 子树、Fowler smell 的通行转述、SonarSource 的 clean code taxonomy。若有遗漏，这条结论应被推翻。）

**这件事本身就是一个结论**：一个连名字都没有的缺陷类别，不可能有成熟的规则集、benchmark 或误报率数据。我们不是在选型，我们是在定义。

### 4.3 唯一一份把它当回事的权威文本，是给人看的

Google 的 code review 指南（[What to look for in a code review](https://google.github.io/eng-practices/review/reviewer/looking-for.html)）里有一段直接命名了这件事：`[文档明述]`

> "A particular type of complexity is **over-engineering**, where developers have made the code more generic than it needs to be, or added functionality that isn't presently needed by the system."
>
> "**Reviewers should be especially vigilant about over-engineering.** Encourage developers to solve the problem they know needs to be solved _now_, not the problem that the developer speculates _might_ need to be solved in the future."
>
> "The future problem should be solved once it arrives and you can see its actual shape and requirements in the physical universe."

摘要清单里也列了一条："The developer isn't implementing things they _might_ need in the future but don't know they need now."

**请注意这段文字出现的位置**：它在 *reviewer* 指南里，不在任何 linter 配置里。Google 有全世界最强的静态分析基建（Tricorder、Error Prone，且 Error Prone 敢把 `UnnecessaryCheckNotNull` 定成 ERROR 级），但对 over-engineering 这件事，它写的是「**reviewer 要格外警惕**」，而不是「我们有一条规则」。`[推断]`

这是本节最硬的一条证据：**业界最有能力把它工具化的组织，选择了把它留给人。**

## 5. 界在哪、谁来划：同一段代码，在两个团队里结论相反

这一节是整份调研里唯一一条**能被硬证据钉死**的结论，也是产品形态的分水岭。

### 5.1 主张「防护越多越好」的一方，说得非常具体

NASA/JPL 的 [The Power of Ten – Rules for Developing Safety Critical Code](https://spinroot.com/gerard/pdf/P10.pdf)（Gerard J. Holzmann, NASA/JPL Laboratory for Reliable Software, 2006）里有两条规则，字面上要求的正是需求方称为「防护过度」的那种代码。`[文档明述]`

**Rule 5 —— 强制断言密度：**

> "The *assertion density* of the code should average to a minimum of two assertions per function. Assertions are used to check for anomalous conditions that should never happen in real-life executions."

注意「should never happen in real-life executions」这半句——**它明确要求为「不可能发生」的情况写检查**。rationale 里还把这件事和防御性编程直接挂钩：

> "Use of assertions is often also recommended as part of a strong defensive coding strategy. Assertions can be used to verify pre- and post-conditions of functions, parameter values, return values, and loop-invariants."

**Rule 7 —— 强制层层校验：**

> "The return value of non-void functions must be checked by each calling function, and the validity of parameters must be checked inside each function."

「the validity of parameters must be checked **inside each function**」——这就是第 1 节里的 B 类（重复校验），逐层重复，被当成规则写下来。Holzmann 自己也知道这条最有争议：

> "This is possibly the most frequently violated rule, and therefore somewhat more suspect as a general rule. In its strictest form, this rule means that even the return value of *printf* statements and file *close* statements must be checked. One can make a case, though, that if the response to an error would rightfully be no different than the response to success, there is little point in explicitly checking a return value."
>
> "By keeping the general rule, we make sure that exceptions must be justified, with mechanical checkers flagging violations. Often, it will be easier to comply with the rule than to explain why non-compliance might be acceptable."

最后这句是关键的设计取舍：**JPL 明知这条规则会产生冗余代码，仍然选择保留它，理由是「让例外必须被解释」比「让防护可选」更安全。**

### 5.2 主张「防护过度是缺陷」的一方，同样具体

就是第 4.3 节引过的 Google code review 指南：reviewer 要"especially vigilant about over-engineering"，要求开发者只解决"the problem they know needs to be solved now"。

### 5.3 两边都对，因为判据里有一个隐变量

把两份文本放在一起看，结论只有一个：**「这个判空是否多余」不是代码的属性，是「代码 × 团队风险偏好」的属性。** `[推断]`（推理链：同一段「在每个函数入口校验参数」的代码，按 P10 Rule 7 是合规，按 Google 指南是 over-engineering 的候选。程序文本完全相同，判定结论相反。）

这恰好命中了[规范表达形式谱系](09-规范表达形式谱系.md)第 6.2 节那条判据的反例形式：

> **能不能写出一个反例，使得程序文本完全相同但判定结论不同？** 能写出来 → 必须交给 LLM；写不出来 → 理论上可静态化，剩下的是成本问题。

「防护过度」的反例不用构造，**它已经以两份权威文本的形式现成摆在那里**。所以按 09 的判据，它不可能被做成一条通用静态规则。

### 5.4 但 NASA 顺手给了我们一条可用的判据

P10 的 Rule 5 里还有一句容易被略过、但对我们非常有用的话：`[文档明述]`

> "**Any assertion for which a static checking tool can prove that it can never fail or never hold violates this rule.** (I.e., it is not possible to satisfy the rule by adding unhelpful 'assert(true)' statements.)"

翻译成我们的语言：**NASA 自己承认「无用的防护」是存在的，而它给出的判据是「静态工具能证明它恒成立或恒不成立」。**

这和第 2.2 节从工具侧归纳出来的三种判定依据，是同一条线。两边独立走到了同一个地方：

> **能被机械证明恒真的防护 = 客观多余，全世界都同意。**
> **不能被机械证明的防护 = 是否多余取决于团队约定。**

这条线就是本文的中轴。它把第 1 节六个子类劈成两半：左半边归工具，右半边归规范——**而不是归 LLM**。LLM 能不能在右半边干活，是第 7、8 节要回答的另一个问题，和这条线的位置无关。

### 5.5 推论：两条痛点其实是一条

需求方给的第二、三条痛点是：

- 「GPT 模型写的代码防护过度」
- 「不符合团队规范，而且没有有效的规范建设机制」

按 5.3 的结论，**第一条是第二条的一个实例**。「防护过度」之所以成为痛点，不是因为没有工具，而是因为**这个团队从来没有把「我们这里的防护到什么程度算够」写下来过**。没写下来，就没有判据；没有判据，reviewer 各说各的，GPT 更是无从对齐。`[推断]`

这条推论如果成立，产品的第一优先级就不是「做一个检测过度防御的规则」，而是「让团队第一次把这条线写下来」。这直接落到 [规范冷启动](../../.agents/notes/proposed/feature/2026-09-12-rule-cold-start.md) 和 [规范的领域模型与生命周期](../../.agents/notes/proposed/architecture/2026-09-12-rule-domain-model.md) 两张 ticket 上。

**这条推论需要向需求方验证**，问法很具体：*「你们能不能举出三个例子，说这段防护是多余的？三个人给的例子一致吗？」* 如果不一致，本节结论成立。

## 6. 「GPT 写的代码防护过度」——公开证据支持到什么程度

需求方的这句话有两层：(a) AI 生成的代码质量确实更差；(b) 差的具体形态是「防护过度」。这两层的证据强度**差很远**，必须分开说。

### 6.1 (a) 层：AI 代码 code smell 更多，有直接量化数据

[Investigating The Smells of LLM Generated Code](https://arxiv.org/abs/2510.03029)（2025-10）用 Java 程序对照「专业人写的参考解法」测 code smell 增量：`[公开数据]`

> "We find that LLM-generated code has a higher incidence of code smells compared to reference solutions. Falcon performed the least badly, with a smell increase of 42.28%, followed by Gemini Pro (62.07%), ChatGPT (65.05%) and finally Codex (84.97%). The average smell increase across all LLMs was 63.34%, comprising 73.35% for implementation smells and 21.42% for design smells."

还有一条对我们特别重要：

> "the increase in code smells is greater for more complex coding tasks and for more advanced topics"

**读法**：平均多出 63% 的 smell，且**实现层 smell（+73.35%）远多于设计层 smell（+21.42%）**。任务越复杂越差。

**必须标注的局限**：这篇测的模型是 Codex、Falcon、Gemini Pro、ChatGPT，属于较早一代。结论不能直接外推到当前模型。`[推断]`

[Code Copycat Conundrum: Demystifying Repetition in LLM-based Code Generation](https://arxiv.org/abs/2504.12608)（2025-04）测了 19 个代码 LLM 的**结构性冗余**：`[公开数据]`

> "One significant issue is code repetition, which refers to the model's tendency to generate structurally redundant code, resulting in inefficiencies and reduced readability. ... revealing that repetition is pervasive and manifests at various granularities and extents, including character, statement, and block levels. We further summarize a taxonomy of 20 repetition patterns."

「结构性冗余普遍存在、跨 19 个模型、总结出 20 种重复模式」——这是离「层层叠加的冗余校验」最近的一条硬证据。

### 6.2 反向证据：必须一起摆出来

[Echoes of AI: Investigating the Downstream Effects of AI Assistants on Software Maintainability](https://arxiv.org/abs/2507.00788)（2025-07）是一个**两阶段对照实验，151 名参与者、95% 是职业开发者**：`[公开数据]`

> "Phase 2 revealed no significant differences in subsequent evolution with respect to completion time or code quality. ... Overall, we did not detect systematic maintainability advantages or disadvantages when other developers evolved code co-developed with AI assistants."

但它在结论里明确把我们关心的这件事列为待研究项：

> "Future work should examine risks such as **code bloat from excessive code generation** and cognitive debt as developers offload more mental effort to assistants."

**读法**：到目前为止，「AI 代码更难维护」在受控实验里**没有被证实**。smell 计数变多是事实，但没有转化成可测量的下游维护成本。诚实的表述是：证据支持「AI 代码 smell 更多」，不支持「AI 代码更难改」。`[推断]`

### 6.3 (b) 层：「防护过度」这个具体形态，没有找到直接研究

我在 arXiv 上按多组关键词检索（`defensive programming` × `large language model`、`over-engineering` × `code`、`redundant code` × LLM、`verbosity` × `code generation`、`exception handling` × `LLM-generated`），**没有找到任何一篇以「LLM 生成代码过度防御 / 冗余校验」为研究对象的论文**。`[推断]`（依据：arXiv API 检索，2026-09-12；检索覆盖摘要字段。非穷尽，但覆盖了最直接的措辞组合。）

最接近的是 5.1 那篇「结构性重复」，但它测的是重复，不是防御性。

**结论要说清楚**：

| 命题 | 证据状态 |
|---|---|
| AI 生成代码 code smell 显著多于人写代码 | **有公开量化数据**（+63.34% 均值），但模型代次偏旧 |
| AI 生成代码结构性重复普遍 | **有公开量化数据**（19 模型、20 种模式） |
| AI 代码导致下游维护更困难 | **受控实验未证实**（151 人对照实验无显著差异） |
| **AI 生成代码的典型缺陷是「防护过度」** | **未找到任何直接研究。这一条目前只是这个团队的主观观察。** |

最后一行是本节最重要的一行。**我们不能假装有数据支持它。** 要么承认它是一条待验证的团队假设，要么就去测：从团队自己的 MR 历史里抽样，统计「被 reviewer 指出防护多余」的评论占比。这个测量本身就是产品的第一个评估基线，正好接 [评估基线 benchmark 构造](../../.agents/notes/proposed/testing/2026-09-12-evaluation-baseline-benchmark.md)。

## 7. 用 LLM 来检测这件事，靠谱吗

### 7.1 一个直接相关的实验：用 Copilot 修 Copilot 写出来的 smell

[Copilot-in-the-Loop: Fixing Code Smells in Copilot-Generated Python Code using Copilot](https://arxiv.org/abs/2401.14176)（2024-01）构造了 102 个「Copilot 生成代码里的 code smell」数据集：`[公开数据]`

> "The results show that 8 out of 10 types of code smells can be detected in Copilot-generated Python code, among which **Multiply-Nested Container** is the most common one. For these code smells, Copilot Chat achieves a highest fixing rate of **87.1%**, showing promise in fixing Python code smells generated by Copilot itself. In addition, the effectiveness of Copilot Chat in fixing these smells can be improved by providing more detailed prompts."

**这篇要非常小心地读**。87.1% 是**修复率**，不是检出率——smell 是先由传统检测工具标出来的，Copilot Chat 只负责改。`[推断]`

这个分工形态恰恰是本文要推的那一条：**工具定位，LLM 改写。** 而且它还给了一条操作性结论：prompt 越具体，效果越好——对应到我们这里就是「规范写得越具体，LLM 越有用」。

### 7.2 反向：LLM 修可维护性问题的成功率并不高

[Evaluating the Effectiveness of LLMs in Fixing Maintainability Issues in Real-World Projects](https://arxiv.org/abs/2502.02368)（2025-02），127 个真实仓库里的可维护性问题：`[公开数据]`

> "Llama with few-shot prompting successfully fixed 44.9% of the methods, while Copilot Chat and Llama zero-shot fixed 32.29% and 30%, respectively. **However, most solutions introduced errors or new maintainability issues.**"

人工可读性评估里 68.63% 的参与者认为可读性变好了，但作者的总结是 "their introduction of errors highlights their current limitations"。

**读法**：在真实项目上（不是构造数据集），LLM 修可维护性问题的成功率是三到四成，而且**大多数修复引入了新问题**。这条必须写进产品设计：**LLM 给的改写建议不能自动应用，必须人确认。**

### 7.3 一个结构性风险：LLM 评审者偏好「熟悉」的代码

这一条直接威胁我们的方案可行性，因为我们的场景是**用 LLM 去评审 GPT 写出来的代码**。

[Self-Preference Bias in LLM-as-a-Judge](https://arxiv.org/abs/2410.21819)（2024-10）给出了机制层面的解释：`[公开数据]`

> "Our experimental results demonstrate that GPT-4 exhibits a significant degree of self-preference bias. To explore the causes, we hypothesize that LLMs may favor outputs that are more familiar to them, as indicated by lower perplexity. ... **Our findings reveal that LLMs assign significantly higher evaluations to outputs with lower perplexity than human evaluators, regardless of whether the outputs were self-generated.** This suggests that the essence of the bias lies in perplexity and that the self-preference bias exists because LLMs prefer texts more familiar to them."

[LLM Evaluators Recognize and Favor Their Own Generations](https://arxiv.org/abs/2404.13076)（2024-04）补上了因果链：`[公开数据]`

> "By fine-tuning LLMs, we discover a linear correlation between self-recognition capability and the strength of self-preference bias; using controlled experiments, we show that the causal explanation resists straightforward confounders."

**推到我们的场景**：`[推断]`（推理链：GPT 生成的过度防御代码，对同族模型而言是低 perplexity 的典型输出 → 按 2410.21819 的结论，LLM 评判者会给低 perplexity 输出打出比人更高的分 → 因此 LLM 最可能**看不出**正是 GPT 风格的那种冗余防护。）

这不是一个可以忽略的边角风险，**它正好打在我们要解决的那个问题上**。它也给出了一条明确的验证动作：**构造一批「GPT 写的过度防御代码」和「人写的等价简洁代码」，让 LLM 评审，看它是否系统性地对前者更宽容。** 这条必须进 benchmark。

### 7.4 工业界的现实数字

[BitsAI-CR: Automated Code Review via LLM in Practice](https://arxiv.org/abs/2501.15134)（2025-01，字节跳动）是目前能找到的最实在的一组生产数据：`[公开数据]`

> "Empirical evaluation demonstrates BitsAI-CR's effectiveness, achieving **75.0% precision** in review comment generation. For the Go language which has predominant usage at ByteDance, we maintain an **Outdated Rate of 26.7%**. The system has been successfully deployed at ByteDance, serving over **12,000 Weekly Active Users**."

注意它的架构：**两段式 —— RuleChecker 先按一套规则分类法检出，ReviewFilter 再做精度过滤**，而不是让一个大模型自由发挥。75% 精度是在这个架构下取得的。

[What Types of Code Review Comments Do Developers Most Frequently Resolve?](https://arxiv.org/abs/2510.05450)（2025-10）给了一条对我们**很不利**的发现：`[公开数据]`

> "readability, bugs, and maintainability-related comments had higher resolution rates than those focused on **code design**."

「防护过度」在这个分类里最靠近 code design。**也就是说，即便我们检出了、说对了，它也是最不容易被开发者真正去改的那一类评论。** 这条直接关系到 [成功指标与沉默优于噪声的判据](../../.agents/notes/proposed/process/2026-09-16-success-metrics-and-silence-over-noise.md)：如果拿采纳率当北极星，这一类天然吃亏，指标设计要为它单独设档。

## 8. 落点：把「判定所需信息」分层，增量价值自然浮出来

前面几节各自给出了一块拼图。这一节把它们拼起来，得到本文的可操作结论。

判定「这处防护是多余的」，需要一条信息：**该值在此处不可能出问题**。这条信息**住在哪里**，决定了谁能做这个判断。四层，逐层往外：`[推断]`（推理链：由第 2.2 节归纳出的三种工具判定依据反推，再按信息所在位置外推两层）

### 第 1 层：信息在同一个函数里

```c
Config *cfg = create_config();   /* 本函数内刚创建 */
if (cfg == NULL) { return -1; }  /* 若 create_config 契约是永不返回 NULL，这里就多余 */
...
```

判定所需信息：`create_config` 的返回契约 + 本函数的控制流。如果契约已知（注解、语言语义、工具内置知识），CFG 一走就出结论。

- **谁能做**：工具。Go `nilness`、typescript-eslint `no-unnecessary-condition`、Error Prone `UnnecessaryCheckNotNull` 全在这一层。
- **LLM 的增量**：**零，甚至为负**。工具在这一层是确定性的，LLM 是概率性的。

### 第 2 层：信息在同一个仓库的另一个函数里

```c
int handle_request(Request *r) {
    if (r == NULL) return -1;     /* 多余：唯一调用方已保证非空 */
    ...
}
```

判定所需信息：`handle_request` 的全部调用点，以及每个调用点传入值的可空性。这是跨过程分析。

- **谁能做**：原则上是跨过程静态分析（CodeQL、Infer、Semgrep Pro）。但代价高——[规范表达形式谱系](09-规范表达形式谱系.md) 第 2.6 节记过 CodeQL 的许可硬约束，Semgrep 跨文件要付费。
- **LLM 的增量**：**中等，但形态是「检索 + 阅读」而不是「推理」**。让 LLM 找出调用点并读一遍，比自建跨过程分析便宜得多，代价是没有 soundness 保证——漏掉一个调用点，结论就反了。**这一层的正确做法是让确定性工具做检索（grep/LSP 找引用），LLM 只做最后一步判断。** `[推断]`

### 第 3 层：信息在文档、注释、命名、接口约定里

```c
/* 调用方须保证 buf 已由 alloc_buffer() 分配且未释放 */
int write_frame(Buffer *buf, const uint8_t *data, size_t len) {
    if (buf == NULL || buf->data == NULL) return -1;   /* 契约说了不会发生 */
    ...
}
```

判定所需信息：**那条注释**。它不在类型里、不在 CFG 里，静态分析读不懂自然语言。

- **谁能做**：**只有 LLM。** 这是 LLM 在本题上唯一无可替代的一层——它能读注释、读 README、读 ADR、从命名和上下文推断约定。
- **这一层的价值大小，完全取决于团队有多少约定真的写下来了。** 如果注释稀薄，这一层就很薄。

### 第 4 层：信息只在人的脑子里

```c
int apply_discount(Order *o, int rate) {
    if (rate < 0 || rate > 100) return -1;   /* 多余还是必要？取决于谁能调它 */
    ...
}
```

判定所需信息：「调用方是不是只有内部可信模块」「rate 有没有在入口层校验过」「我们团队约定校验放在哪一层」。这些没有任何一处写在代码或文档里。

- **谁能做**：**谁都做不了**，包括 LLM 和资深 reviewer 里不熟悉这块的人。
- **唯一的出路是把它写下来**——也就是变成第 3 层。这正好是「规范建设机制」那条痛点。

### 这张分层图的三条读法

| 层 | 信息在哪 | 归属 | 我们该做什么 |
|---|---|---|---|
| 1 | 同函数内 | **工具** | 直接接现成 linter，别让 LLM 重判一遍 |
| 2 | 同仓库跨函数 | 工具（贵）或 LLM（便宜但不 sound） | 确定性检索 + LLM 判断的两段式 |
| 3 | 文档/注释/命名 | **只有 LLM** | 这是产品的主战场 |
| 4 | 人脑 | 谁都不行 | **先把它变成第 3 层**——这是规范建设，不是检测 |

**第一条读法：LLM 的增量价值集中在第 3 层，而第 3 层的厚度是团队自己决定的。** 团队写下来的约定越多，LLM 越有用。这把产品价值和规范建设绑死在一起了——不是「先做检测，规范以后再说」，而是**规范建设本身就是提升检测能力的手段**。

**第二条读法：第 4 层才是需求方真正的痛点。** 「没有有效的规范建设机制」这句话，在本文的框架里就是「大量判定依据卡在第 4 层」。第 5.5 节已经论证过这两条痛点是一条，这里给出了它的机制。

**第三条读法：这个分层对「防护过度」之外的规范同样成立。** 它其实是 [规范表达形式谱系](09-规范表达形式谱系.md) 那条「能不能写出程序文本相同而结论不同的反例」判据的一个更细的刻度——把「交给 LLM」那一大格，进一步拆成了「LLM 能做（第 3 层）」和「LLM 也做不了（第 4 层）」。**这是本文对上游那份谱系的补充。**

### 9.1 条目数与工具覆盖的实测对比

| 规范 | 条目规模 | 现成工具覆盖 | 覆盖比例 |
|---|---|---|---|
| **C++ Core Guidelines** | **约 445 条**规则（页面上带 `X.N:` 编号的条目共 466 个，扣除 21 条 FAQ）`[公开数据]`（2026-09-12 实测自 [官方单页](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines)） | clang-tidy `cppcoreguidelines-*` **35 条** `[公开数据]` | **约 8%** |

**C++ Core Guidelines 那一行是这张表里信息量最大的**：一份由 Bjarne Stroustrup 和 Herb Sutter 领衔、每条都带 Enforcement 小节的规范，业界最主要的开源实现只落地了约 8%。`[推断]`（需注意：部分 Core Guidelines 条目由 clang-tidy 的 `modernize-`、`bugprone-`、`performance-` 等其他分组间接覆盖，也有 MSVC 的 Core Guidelines Checker 另行实现，所以 8% 是**单一分组的直接对应率**，不是能力覆盖率的全貌。）

### 9.2 这些规范里强制「防御」的条目——第 5 节的补充证据

**CERT C 的 ERR33-C "Detect and handle standard library errors"**（[规则页](https://cmu-sei.github.io/secure-coding-standards/sei-cert-c-coding-standard/rules/error-handling-err/err33-c)）`[文档明述]`：

> "It is essential that programs detect and appropriately handle all errors in accordance with an error-handling policy."
>
> "Assuming that all calls to such functions will succeed and failing to check the return value for an indication of an error is a dangerous practice."

它和 NASA P10 的 Rule 7 是同一条要求。而且它用的机制也一样：**给出一个 Exceptions 小节（ERR33-C-EX1）列出可以不检查的函数（`putchar`、`puts`、`printf`、`memcpy`、`strcpy` 等），并要求「若要忽略返回值，应显式转型为 `(void)`」。**

这个设计模式值得单独记下来，因为它对我们做规范很有借鉴价值：`[推断]`

> **不是「你可以自行判断要不要检查」，而是「默认必须检查；不检查的，用一个显式标记声明你是故意的」。**

这把一个不可判定的语义问题（这个返回值重不重要）转成了一个可判定的语法问题（有没有 `(void)`）。NASA P10 Rule 7 的原话也是同一个思路："we make sure that exceptions must be justified, with mechanical checkers flagging violations"。

**这条对我们的「防护过度」直接可用**：与其让工具或 LLM 去猜「这个判空是不是多余」，不如让团队规定「哪些层默认不判空；要判的，写一行注释说明为什么」。判定立刻从第 4 层落到第 1 层。

### 9.3 Linux 内核：官方明说 checkpatch 不是权威

内核文档对 checkpatch 的定位写得极其克制（[Checkpatch 文档](https://docs.kernel.org/dev-tools/checkpatch.html)）`[文档明述]`：

> "Checkpatch (scripts/checkpatch.pl) is a perl script which checks for **trivial style violations** in patches and optionally corrects them."
>
> "**Checkpatch is not always right. Your judgement takes precedence over checkpatch messages. If your code looks better with the violations, then its probably best left alone.**"

两条都很有用：一是它自认只管 trivial style；二是**一份世界级项目的官方文档，明文规定人的判断优先于工具输出**。

这条对我们的产品形态是直接的背书：[ticket 01](../../.agents/notes/proposed/feature/2026-09-12-ai-intervention-points-and-human-division.md) 里那个「人的逃生口」不是一个贴心功能，**它是内核这种级别的项目在官方文档里写死的基本原则**。

### 9.4 排序

按「可自动检查比例」从高到低：`[推断]`

1. **CERT C** —— 每条规则自带 Automated Detection 清单，但高覆盖依赖商业工具。
2. **MISRA C** —— 有官方的可判定性分类（本次未取到比例数字），生态成熟，开源侧 cppcheck 覆盖约 130 条。
3. **Google C++ Style Guide** —— cpplint 覆盖 69 类，但近三成是 whitespace，真正的语义条目覆盖低。
4. **C++ Core Guidelines** —— 条目最多（约 445），单一 clang-tidy 分组直接对应率约 8%。
5. **Linux kernel coding style** —— 官方自认 checkpatch 只管 trivial style。

**这个排序有一条反直觉的读法**：排名靠后的不是「质量差的规范」，而是**表达力更强、因而更难机械化的规范**。C++ Core Guidelines 讲所有权和生命周期，Linux 内核讲品味，这些本来就不该指望 linter。**可执行性低不是缺陷，是这条规范所处的档位决定的。**

## 10. 成本感：一百人、每周一百多个 PR 这个量级

这个规模很小，不要按大厂量级估。下面是各手段的接入与运维量级，标注清楚哪些是有依据的、哪些是我的估算。

| 手段 | 接入工作量 | 持续运维 | 依据 |
|---|---|---|---|
| 现成 linter 的冗余规则组（staticcheck / clang-tidy / ESLint / PMD） | 人天级：装上、选规则、跑一遍存量、拉一条基线把存量豁免掉 | 低。规则升级时处理新增告警 | `[推断]` |
| 引入 NullAway 类的注解契约 | **月级**，因为要给存量代码加注解 | 中。新代码要持续标注 | 编译期开销官方数字 "usually less than 10%" `[公开数据]` |
| LLM 评审（第 3 层） | 周级：接 MR webhook、拼上下文、调模型 | **主要成本在规范与阈值的持续调优，不在算力** | `[推断]` |
| 规范建设机制（把第 4 层挪到第 3 层） | **这是唯一的长期投入**，没有捷径 | 持续。见 [规范的领域模型与生命周期](../../.agents/notes/proposed/architecture/2026-09-12-rule-domain-model.md) | `[推断]` |

两条和规模直接相关的判断：

**算力不是约束。** ticket 01 的对话记录里已经算过：每周一百多个 PR，按 Uber 每次约四毛七美元算是每周几十美元。**这个量级下可以负担远比 Uber 昂贵的单次流水线。** 所以「用 LLM 多跑几轮、把调用点都读一遍」这种在大厂要精算的做法，在这里是免费的。这直接支持第 8 节第 2 层那个「检索 + LLM 判断」的两段式。

**人力才是约束。** 一百人的团队大概率没有专职的静态分析工程师。这意味着：**自建跨过程分析（第 2 层的重武器）基本不可行**，写 CodeQL query、调 Infer 的活没人干得起。反过来，「装现成 linter」和「写自然语言规范」这两件事是这个规模下真正做得动的。

**推论**：第 2 层在我们这里应该直接跳过重武器，走「LLM + 确定性检索」的轻量路线；省下来的力气全部投到第 3 层和规范建设上。`[推断]`

## 11. 分工线

要回答的问题：**「防护过度」这类判断型问题，LLM 相比现有工具的增量价值到底有多大？**

答案：**有，但比直觉上小得多，而且是有条件的。** 它不是「LLM 比工具聪明所以能看出更多」，而是「有一类判定依据只存在于自然语言里，工具连读都读不了」。价值来自**信息通道**，不来自**推理能力**。下面逐条落。

### 11.1 交给编译器和现成 linter —— 因为更准更便宜

**范围**：第 8 节的第 1 层，加上第 1 节里的 C 子类（空 catch）和 D 子类可证明的部分。

**具体做什么**：把各语言现成的冗余检查规则组直接打开——Go 的 `SA4031`/`SA4022`/`SA4023`/`SA4024`/`S1009`/`S1020`/`S1031`/`S1033`/`S1036`/`SA9003`、`nilness`；Java 的 Error Prone `UnnecessaryCheckNotNull`/`ImpossibleNullComparison`、PMD `EmptyCatchBlock`；TypeScript 的 `no-unnecessary-condition`/`no-useless-catch`；C/C++ 的 `bugprone-redundant-branch-condition`/`bugprone-empty-catch`/`readability-redundant-*`。

**判断依据**：这些规则的判定是**确定性**的，误报率低到 Error Prone 敢把 `UnnecessaryCheckNotNull` 定成 ERROR 级（编译失败）。CWE 给 CWE-571 和 CWE-1071 的自动检测有效性评级都是 **High**。在同一件事上放一个概率性的 LLM 进去，只会降低准确率、增加成本。

**这一条是硬线：凡是现成规则已经覆盖的，LLM 侧必须跳过。** 落法见 [规范表达形式谱系](09-规范表达形式谱系.md) 第 6.3 节第 1 条——规范实体上带 `executable_by[]`，有可执行实现且覆盖当前语言时，LLM 侧直接跳过这条。

### 11.2 不交给跨过程静态分析 —— 因为我们养不起

**范围**：第 8 节的第 2 层。

**判断依据**：技术上 CodeQL / Infer / Semgrep Pro 能做，但一百人的团队没有专职静态分析工程师，CodeQL 还有许可硬约束。**这一档在我们这里直接降级**：用确定性检索（LSP 找引用、grep 找调用点）把候选圈出来，再让 LLM 读那几处做判断。牺牲 soundness，换掉一个养不起的能力。算力成本在这个规模下可以忽略（第 10 节）。

### 11.3 只能交给 LLM —— 第 3 层，而且仅限第 3 层

**范围**：判定依据写在注释、文档、命名、接口约定里的那些。

**判断依据**：静态分析读不懂自然语言，这不是工程能力问题，是输入格式问题。这一层是 LLM 在本题上**唯一无可替代**的地方。

**但要同时接受三条被公开数据证实的限制**：

1. **LLM 不能当独立检测器，只能当「工具定位之后的判读与改写」。** 依据：Copilot 修 Copilot 代码那篇的 87.1% 是**修复率**，smell 是传统工具先标出来的；而 LLM 在真实项目上独立修可维护性问题只有 30%–44.9% 成功率，且"most solutions introduced errors or new maintainability issues"。**改写建议不得自动应用。**

2. **LLM 评审者存在偏向「熟悉代码」的结构性偏差，而这个偏差正好打在我们要解决的问题上。** GPT 风格的冗余防护对同族模型是低 perplexity 输出，而 LLM 对低 perplexity 输出的评分显著高于人类评分者。**这条必须在 benchmark 里专门验证**，方法见第 7.3 节末尾。在验证通过之前，不要假定 LLM 看得出 GPT 的过度防御。

3. **即便说对了，这类评论的采纳率天然偏低。** 公开研究显示 design 类评论的 resolution rate 低于 readability / bug / maintainability 类。指标设计上要为它单独设档，不要和 bug 类评论比采纳率。

### 11.4 谁都不行的那一层，答案是规范建设

**范围**：第 8 节的第 4 层——判定依据只在人脑子里。

**判断依据**：本文第 5 节用两份权威文本证明了这条线是团队相对的。NASA/JPL 的 Power of Ten **要求**每个函数平均两条断言、**要求**每个函数内部校验参数合法性；Google 的 code review 指南**要求** reviewer 警惕 over-engineering。同一段代码，两边结论相反。**不存在一个放之四海而皆准的「防护过度」判据**，因此也不可能有一条通用规则或一个通用 prompt。

**所以这一层的正确动作不是「让 LLM 猜得更准」，是「把线写下来」**，把第 4 层的依据挪进第 3 层，LLM 才接得住。

NASA 自己顺手给了一个可以直接借用的写法（第 5.4 节）：*凡是静态工具能证明恒成立的断言，就是无用断言*。这是一条团队可以照抄的、明确的最低线。团队要补的是它上面那几档——哪些层做校验、哪些层信任上游、错误吞不吞。

比这更可落地的是 CERT C 的 ERR33-C 用的那个套路（第 9.2 节）：**默认必须做某件事，不做的用一个显式标记声明是故意的**（CERT 用 `(void)` 转型，NASA 用「例外必须被解释」）。照搬到我们这里就是：

> 规定哪些层默认不做防护；**确实要加的，写一行注释说明为什么**。

这一招的价值在于**它把判定从第 4 层直接搬到了第 1 层**——「有没有那行注释」是语法可判定的，一条 lint 规则就够，连 LLM 都不需要。凡是能这样转化的规范，都应该优先这样转化。

### 11.5 一句话总结，以及一条要当面确认的事

> **「防护过度」不是一个检测问题，是一个规范缺失问题。** 工具能测的那部分（恒真条件、空 catch）现成规则已经覆盖，不需要我们做；工具测不了的那部分，之所以测不了，是因为团队从没把判据写下来——而这同样不是 LLM 能替人决定的。LLM 的真实位置，是在团队把判据写下来之后，**充当唯一能读懂那份自然语言判据的执行器**。

因此产品的第一优先级不是「做一个过度防御检测器」，而是**先让团队把这条线写下来**，这条路径已经在 [规范冷启动](../../.agents/notes/proposed/feature/2026-09-12-rule-cold-start.md) 和 [规范的领域模型与生命周期](../../.agents/notes/proposed/architecture/2026-09-12-rule-domain-model.md) 上。

**要当面确认的一件事**（第 6.3 节已提，这里重申，因为它是本文唯一一个没有数据支撑的关键前提）：

> 请需求方各自独立举出三个「这段防护是多余的」的真实例子。**如果三个人给的例子对不上，本文第 5 节和第 11.4 节的结论成立，产品应该先做规范建设；如果高度一致，说明团队心里其实有一条共识线，那就先把它写成规范，再让 LLM 执行。** 无论哪种结果，下一步都是「写下来」，区别只在写起来有多快。

## 0. 结论先行

一条编码规范从「一句话」走到「一条可执行规则」，中间不是一个台阶，是**八个台阶**。每上一级，准确率上升、维护成本上升、能表达的东西变窄。

| 档 | 形态 | 典型载体 |
|---|---|---|
| 0 | 口头约定 | 没有载体，靠人传人 |
| 1 | 散文规范 | wiki、Google Style Guide 正文 |
| 2 | 结构化自然语言 | `AGENTS.md`、`CLAUDE.md`、`.github/copilot-instructions.md` |
| 3 | 自然语言 + 结构化元数据 | Cursor `.mdc`、Copilot `.instructions.md`、CodeRabbit `path_instructions`、Claude `SKILL.md` frontmatter、Qodo Rule |
| 4 | 语法级模式匹配 | ast-grep、Semgrep OSS（语法层）、Checkstyle、PMD XPath、ESLint（无类型） |
| 5 | 单过程语义分析 | typescript-eslint type-aware、Error Prone、staticcheck、NullAway、Semgrep OSS taint |
| 6 | 跨过程/跨文件数据流 | CodeQL global dataflow、Semgrep Pro、Infer/Zoncolan、Pysa、Go `Facts` |
| 7 | 类型系统契约 | Checker Framework `@MustCall`/`@Owning`、Rust 所有权 |

正交于这条主线，还有两族：**改写型**（OpenRewrite、Refaster、Coccinelle —— 以"给出确定性修复"为第一公民）和**流程型**（Danger、GitHub rulesets、OPA —— 约束的对象是 PR 元数据而不是代码）。

三条分界线（详细论证见第 6 节）：

1. **能在「单文件 + 语法树 + 可选类型信息」上判定的，一律落到静态检查**（档 4-5）。这是天花板明确、成本最低、准确率最高的区间。
2. **需要跨过程数据流才能判定的**，先算账：CodeQL 有许可硬约束，Semgrep 跨文件要付费，自建成本高。这一档在企业内部平台里**大概率不是自建，而是复用现有工具的产出**。
3. **判定依据里出现「意图」「是否贴切」「是否和某份文档一致」「这么写读者能不能看懂」的，静态检查一条都表达不了**，只能交给 LLM。这不是工程能力问题，是这类规范的判定函数根本不是程序文本的函数。

灰色地带的判据只有一条可操作的：**能不能写出一个反例，使得程序文本完全相同但判定结论不同？** 能写出来 → 必须交给 LLM；写不出来 → 理论上可静态化，剩下的是成本问题。

## 1. 这条谱系为什么存在

### 1.1 uReview 那条原则的原文

Uber 的原话（[uReview: Scalable, Trustworthy GenAI for Code Review at Uber](https://www.uber.com/en-DE/blog/ureview/)）：

> "Traditionally, linters (or static analysis tools) have been used to enforce certain best practices. For simple or syntactic patterns, linters are accurate, reliable, and cheap—we should continue using them."
>
> "However, some properties are hard to check with linters... one needs some semantic code understanding to know that a certain integer variable represents time, and LLMs perform far better in these cases."
>
> "So, best practices that aren't checkable by linters are often a great fit for LLMs."

注意这条原则的**分界依据不是「难不难」，是「checkable by linters」**——能不能被表达成一条判定规则。Uber 举的例子（"知道某个整型变量代表的是时间"）本质是**领域语义不在程序文本里**，这一点后面第 2.7 节会展开。

同一篇里还有一条对我们规范领域模型直接相关的：

> "The Best Practices Assistant enforces Uber-specific coding conventions by referencing a shared registry of style rules."

Uber 有一个**共享的 style rule registry**，但这篇博客没有公开这个 registry 的数据结构。这正是本次调研要补的空白。

uReview 公开的精度数字（同一来源）：75% 的评论被工程师标为 useful，65%+ 的评论被实际处理；作为对照，**人工写的评论只有 51% 被作者认定为 bug 并在同一 changeset 里修掉**。覆盖每周约 65,000 个 diff 的 90%+。

### 1.2 code review 到底在看什么

Google 的 [eng-practices](https://google.github.io/eng-practices/review/reviewer/looking-for.html) 列了评审者要看的 12 项：Design、Functionality、Complexity、Tests、Naming、Comments、Style、Consistency、Documentation、Every Line、Context、Good Things。

同一份文档里有一句很重要的分界：

> "the style guide is the absolute authority: if something is required by the style guide, the CL should follow the guidelines"

以及 [standard.html](https://google.github.io/eng-practices/review/reviewer/standard.html)：

> "On matters of style, the style guide is the absolute authority."
>
> "Reviewers should always feel free to leave comments expressing that something could be better, but if it's not very important, prefix it with something like 'Nit: ' to let the author know that it's just a point of polish that they could choose to ignore."

**Google 自己就把评审内容分成了两类**：style guide 规定的（强制、有权威裁决）和不是的（可以说，但不能拦）。这 12 项里，能落到静态检查的只有 Style 全部、Naming 的一小部分（命名格式而非贴切度）、Tests 的一小部分（有没有测试文件，而不是测得够不够）。**其余 9 项半，静态检查一条都碰不到。**

### 1.3 一条规范要「可执行」必须跨过的三道坎

从工具能力反推，一条自然语言规范要变成可执行规则，要依次跨过：

1. **可定位**：判定对象必须能在语法树上定位到一个节点或节点集合。「函数不要太长」可以（数行数），「这个抽象不合理」不行。
2. **可判定**：判定条件必须是程序文本（含类型信息）的函数。「不要用 `time.Now()` 做 ID」可以，「这个 int 代表的是毫秒还是秒」不行——除非类型系统里有这个信息。
3. **可负担**：判定所需的分析范围必须在预算内。单文件 AST 最便宜，跨过程数据流最贵，跨仓库基本不可行。

**这三道坎决定了档 4-7 的分层**：档 4 只过第一道（语法可定位），档 5 过了第二道的一部分（有类型信息），档 6-7 是在第三道上花钱买第二道的能力。

## 2. 可执行的一端

### 2.1 能力矩阵：跨文件 / 数据流 / 时序约束

这是本节最核心的一张表。所有「能/不能」都有一手依据。

| 工具 | 跨文件 | 数据流 | 类型信息 | 「调用 A 必须调用 B」 |
|---|---|---|---|---|
| **ESLint**（核心） | 否，单文件 | 否，只有 scope analysis | 否 | 否 |
| **typescript-eslint** type-aware | 类型可见（借 tsc program），但规则仍是逐文件运行 | 否 | 是 | 基本否 |
| **ast-grep** | 否 | 否（官方明确） | 否（官方明确） | 否 |
| **Semgrep OSS** | 否 | 有 taint，但**仅过程内** | 部分（typed metavariable） | 同文件同函数内勉强 |
| **Semgrep Pro** | 是（`--pro` + `interfile: true`，仅部分语言） | 跨过程 + 跨文件 | 是 | 有可能 |
| **CodeQL** | 是（global dataflow） | 是（local/global/taint） | 是 | 是（有现成的 resource leak query） |
| **Go `go/analysis`** | 是（靠 `Facts` 机制显式传递） | 需自己基于 SSA/CFG 写 | 是（`go/types`） | 是（`lostcancel` 就是现成例子） |
| **Error Prone** | 单编译单元为主 | 有限 | 是（javac 内部类型） | 有限 |
| **NullAway** | 靠注解契约跨方法 | "type-based, local checks" | 是 | 专用于 null，不通用 |
| **Checker Framework** RLC | 模块化（靠签名注解） | 过程内 | 是（类型系统扩展） | **是，而且是最正统的表达方式** |
| **PMD** | 否 | 否 | 有限 | 否 |
| **Checkstyle** | 否（官方明确逐文件、不推导类型） | 否 | 否 | 否 |
| **ruff** | 重写中（多文件分析在做） | 否 | 否 | 否 |
| **Pysa**（Python） | 是 | 是（taint） | 靠 model 文件声明 | 否（面向污点不是 typestate） |
| **OpenRewrite** | 是（LST 带跨项目类型归属） | 有限 | 是 | 有限 |
| **Coccinelle** | 单文件为主 | `...` 沿控制流路径匹配 | C 语义有限 | 是（内核里大量成对 alloc/free 检查） |

一手依据逐条：

**ESLint 单文件**：官方 [Custom Rules](https://eslint.org/docs/latest/extend/custom-rules) 的规则 API 里，`context` 暴露的全部是当前文件的信息；关于变量使用，官方原话是 "ESLint itself only knows about the standard rules of variable access"。跨文件能力（如 `eslint-plugin-import`）是插件自己去读文件系统实现的，不是 ESLint 提供的分析能力。

**ast-grep 明确不做语义分析**：官方 [FAQ](https://ast-grep.github.io/advanced/faq.html) 直接列出不支持的能力——scope analysis、type information、control flow analysis、data flow analysis、taint analysis、constant propagation，并举例说明做不到 "Find variables that are not defined/used in the current scope"、"Find variables of a specific type"、"Find code that is unreachable"。这是整份调研里**对自身边界交代得最诚实的一份官方文档**，值得在设计规范模型时直接引用。

**Semgrep OSS 的 taint 只在过程内**：[taint-mode 文档](https://docs.semgrep.dev/writing-rules/data-flow/taint-mode) 原话 "Taint propagators only work intraprocedurally, that is, within a function or method."；跨过程要 `--pro-intrafile`（跨函数、单文件内），跨文件要 `--pro` 且规则里写 `interfile: true`，且只支持部分语言。[语言支持页](https://docs.semgrep.dev/supported-languages) 列出支持跨文件数据流的只有 C#、Go、Java、JavaScript、Kotlin、Python、TypeScript 七种；JSX、Ruby、Scala、Swift、Rust、PHP、Terraform 只到跨函数。

> **对企业内部平台的直接影响**：如果打算用 Semgrep 表达「跨文件」的规范，开源版做不到，这是一条采购决策而不是技术决策。

**Checkstyle 明确说了自己不做什么**：官方定位原文是逐文件处理、不推导表达式类型、不构建完整继承层次。所以 Checkstyle 只能表达格式、命名、导入、Javadoc、类结构这一类**纯语法**规范。

**Go 的 `Facts` 是跨包分析的唯一标准机制**：[`go/analysis`](https://pkg.go.dev/golang.org/x/tools/go/analysis) 里 Analyzer 有 `FactTypes` 字段，通过 `Pass.ExportObjectFact` / `ImportObjectFact` 把分析结论附着在对象上并序列化，下游包分析时直接导入。官方类比是 "Facts are analogous to type export data in a build system"，实现的是 "separate analysis"——包 P 依赖 Q 时不需要重新分析 Q 的源码。

**「调用 A 必须调用 B」有三种正统表达方式**，成本递增：

- **CFG 可达性（最便宜）**：Go 的 [`lostcancel`](https://pkg.go.dev/golang.org/x/tools/go/analysis/passes/lostcancel)。官方描述："The cancellation function returned by context.WithCancel, WithTimeout, WithDeadline... must be called, or the new context will remain live until its parent context is cancelled." 实现上 `Requires: [inspect.Analyzer, ctrlflow.Analyzer]`——先定位调用，再在控制流图上判断 cancel 是否在所有路径被调用。**只在函数内有效**：cancel 被传出函数就分析不了了。
- **数据流 query（中等）**：CodeQL 有现成的 [Potential database resource leak](https://codeql.github.com/codeql-query-help/java/java-database-resource-leak/)、[Potential input resource leak](https://codeql.github.com/codeql-query-help/java/java-input-resource-leak/)。
- **类型系统契约（最贵也最完备）**：Checker Framework 的 [Resource Leak Checker](https://checkerframework.org/manual/#resource-leak-checker)，用 `@MustCall`（对象回收前必须调用哪些方法）、`@Owning`（所有权/转移语义）、`@EnsuresCalledMethods`（后置条件）三个注解表达。它的类型检查 **"works modularly and intraprocedurally: when verifying a method, it examines only the signature... of other methods, not their implementations."**——**它不做跨过程分析，它让你把跨过程的约束写进方法签名**。这是一个重要的设计启示：真正可靠的时序约束表达，靠的不是更强的分析，而是把约束前移到接口上。

  成本方面官方给了缓解路径：不要求整库标注，建议 "Start small... run just one checker"、"Don't annotate the whole program, but work module by module. Start annotating classes at the leaves of the call tree."

**Coccinelle 的 `...` 是路径匹配而不是 AST 匹配**：这是 SmPL 和纯 AST 工具的根本差别。内核文档（[kernel.org coccinelle](https://www.kernel.org/doc/html/latest/dev-tools/coccinelle.html)）描述了 `make coccicheck` 的四种模式（report / patch / context / org）。截至本次调研，`scripts/coccinelle/` 下共 **76 个 `.cocci` 文件**（按 GitHub contents API 逐目录计：api 20 + api/alloc 3 + free 8 + hid 1 + iterators 5 + locks 4 + misc 27 + null 4 + tests 4）。内核文档也明确："As with any static code analyzer, Coccinelle produces false positives. Thus, reports must be carefully checked, and patches reviewed."

### 2.2 各生态写一条规则的最低成本

| 生态 | 最低成本路径 | 要写什么 | 调试手段 |
|---|---|---|---|
| JS/TS | ESLint 自定义规则 | 一个 `{meta, create(context)}` 对象，visitor 里判定 + `context.report()` | AST Explorer、`RuleTester` |
| 多语言 | ast-grep YAML | 一段 `rule:`，atomic/relational/composite 三类算子组合 | playground、`sg test`（valid/invalid 快照） |
| 多语言 | Semgrep YAML | `id/message/severity/languages` + 一个 pattern 算子 | playground、`semgrep --test` |
| Java（格式/结构） | PMD XPath 规则 | 一段 XML 里内嵌 XPath，`class` 指向 `XPathRule`，**不用写 Java** | PMD Rule Designer（可视化查 AST、调 XPath、导出规则 XML） |
| Java（正确性） | Error Prone BugChecker | `@BugPattern` 注解 + `Matcher` 组合子 + `@AutoService` | 单元测试框架 |
| Go | `go/analysis` Analyzer | `Analyzer{Name, Doc, Requires, Run}` | `analysistest` |
| Go（接入 CI） | golangci-lint Module Plugin | `.custom-gcl.yml` 声明版本+插件模块，`golangci-lint custom` 编译专用二进制 | —— |
| Python | **无低成本路径** | 见下 | —— |
| Java（跨过程语义） | CodeQL query | QL 语言 + `DataFlow::ConfigSig` + `Global<>` | VS Code CodeQL 扩展 |

几个成本上的坑：

**ruff 不支持自定义规则**。官方 [FAQ](https://docs.astral.sh/ruff/faq/) 原话："Ruff does not yet support third-party plugins, though a plugin system is within-scope for the project."；以及 "Ruff implements all rules natively and does not support custom or third-party rules."。长期 meta issue [astral-sh/ruff#283](https://github.com/astral-sh/ruff/issues/283) 自 2022-09 开到现在未落地，维护者 2024-05 的表态是 "It will probably be a while before we evaluate solutions for a plugin system because we're currently in the middle of rewriting Ruff's compiler infrastructure to support multifile analysis."。

> **对我们的影响**：Python 侧「用现成规则」成本最低（ruff 官方称 "over 900 lint rules"，覆盖 40+ flake8 插件），但**「写业务专属规则」在 ruff 上是死路**，必须退回 pylint（`BaseChecker` + `msgs` 字典，自定义 checker 的消息 ID 前两位官方保留 51-99）、flake8（entry point + AST visitor）或 bandit（`@checks` 装饰器 + entry point，安全类专用）。这意味着 Python 团队的规范可执行化成本显著高于 JS/Go/Java。

**golangci-lint 的 Go plugin(.so) 路子不要走**。官方明确 "We recommend using Module Plugin System instead of the Go Plugin System."，并警告插件和主二进制必须为同一环境编译、所有重叠库版本必须完全一致。Go 官方 `plugin` 包文档也说版本不一致时 "Runtime crashes are likely to occur"，且不支持 Windows。

**staticcheck 没有插件机制**（官方 FAQ 未提供任何插件入口，已核实；标注为"未找到一手依据支持存在插件机制"）。要在 Go 生态加自定义检查，路径是 `go/analysis` + golangci-lint module plugin，或者 gocritic 的 ruleguard DSL（成本最低但只能做局部 AST 模式匹配，拿不到 Facts）。

**CodeQL 的成本有两块非技术的**：一是编译型语言必须先能真实构建出 database（CI 里要用 `codeql database trace-command` 包裹构建），二是许可（见 2.6）。

### 2.3 元数据：各家规则携带的字段

这一节是给[规范领域模型](../../.agents/notes/proposed/architecture/2026-09-12-rule-domain-model.md)直接备料的。

**ESLint `meta`**（[custom-rules](https://eslint.org/docs/latest/extend/custom-rules)）：
`type`（problem/suggestion/layout）、`docs.description`、`docs.url`、`docs.recommended`、`docs.frozen`、`fixable`（code/whitespace）、`hasSuggestions`、`schema`、`defaultOptions`、`messages`、`deprecated`、`replacedBy`。

注意两点设计：`fixable` 和 `hasSuggestions` 是**强制声明**的（不声明就报错），这是把「能不能自动修」提升成了一等元数据；`deprecated` + `replacedBy` 是把「规则退休」也做进了元数据。

`fix` 和 `suggestion` 的分工官方说得很清楚：当 "a fix potentially changes functionality or if there are multiple valid ways to fix a rule" 时应该给 suggestion 而不是 fix；fix 应该 "as small as possible" 且避免 "changes that could change the runtime behavior of code"。

**Semgrep 规则 YAML**（[rule-syntax](https://docs.semgrep.dev/writing-rules/rule-syntax)）：
必填 `id` / `message` / `severity`（`LOW`/`MEDIUM`/`HIGH`/`CRITICAL`）/ `languages` / 一个 pattern 算子；可选 `options` / `fix` / `metadata` / `min-version` / `max-version` / `paths`（include/exclude glob）/ `category`。

模式算子：`pattern`、`patterns`（AND）、`pattern-either`（OR）、`pattern-regex`；过滤算子 `pattern-not`、`pattern-inside`、`pattern-not-inside`、`pattern-not-regex`；元变量约束 `metavariable-regex`、`metavariable-pattern`、`metavariable-comparison`、`metavariable-name`、`focus-metavariable`。

`metadata` 官方定义是 "Arbitrary user-provided data; attach data to rules without affecting Semgrep behavior."，社区约定里常见 CWE / CVE / OWASP / references / confidence。[规则仓库贡献指南](https://docs.semgrep.dev/contributing/contributing-to-semgrep-rules-repository/) 定义了 `confidence` 三档：HIGH = "high true positives"，MEDIUM = "some false positives"，LOW = "fair amount of false positives, similar to audit style rules"。

**ast-grep 规则 YAML**（[rule reference](https://ast-grep.github.io/reference/rule.html)）：
三类算子——atomic（`pattern`、`kind`、`regex`、`nthChild`、`range`）、relational（`inside`、`has`、`precedes`、`follows`，都带 `stopBy`：`neighbor` 默认 / `end` / 一个规则对象；`inside` 和 `has` 还有 `field`）、composite（`all`、`any`、`not`、`matches` 引用 util 规则）。

**CodeQL query metadata**（[metadata-for-codeql-queries](https://codeql.github.com/docs/writing-codeql-queries/metadata-for-codeql-queries/)）：
`@name`、`@description`、`@kind`（problem / path-problem）、`@id`、`@tags`、`@problem.severity`（error/warning/recommendation）、`@precision`。

`@precision` 官方定义：**"broadly indicates the proportion of query results that are true positives, while also considering their context and relevance"**，取值 low / medium / high / very-high。**官方没有给出各档对应的百分比阈值**（已核实 metadata 页与 query-metadata-style-guide，均无量化定义）。

**Error Prone `@BugPattern`**（[API](https://errorprone.info/api/latest/com/google/errorprone/BugPattern.html)）：
`severity`（必填）、`summary`（必填）、`name`、`altNames`、`linkType`、`link`、`tags`、`explanation`、`disableable`、`suppressionAnnotations`、`documentSuppression`。

**PMD 规则 XML**：`name`、`language`、`message`、`class`、`priority`（1-5）、`description`、`example`。

**pylint `msgs` 字典**：`{消息ID: (显示模板, symbol, 描述)}`，消息 ID 是 4 位数字 + 类别字母（C/W/E/F/R），自定义 checker 的保留区间是前两位 51-99。

### 2.4 多语言广度

| 工具 | 语言覆盖 |
|---|---|
| Semgrep | GA 21 种、Beta 1 种（APEX）、Experimental 19 种；跨文件数据流仅 7 种 |
| CodeQL | C/C++、C#、GitHub Actions、Go、Java(含 Kotlin)、JS/TS、Python、Ruby、Rust、Swift（Swift 需 macOS） |
| ast-grep | 基于 tree-sitter，语言由 parser 决定，可注册自定义语言 |
| ESLint | JS/TS 为主；v9 的 language plugin 扩展到 JSON / Markdown / CSS |
| PMD | 主规则集覆盖 Java/Apex/JS/Visualforce/Kotlin/Swift/Modelica/PL-SQL/Velocity/JSP/WSDL/POM/HTML/XML/XSL；CPD 还覆盖 C/C++/C#/Go/Python/Ruby/Rust |
| Checkstyle | Java only |
| Error Prone / NullAway / Checker Framework | Java only |
| staticcheck / go/analysis | Go only |
| ruff | Python only |
| OpenRewrite | Java 为主，另有多语言 recipe |
| Coccinelle | C only |

补一条 ESLint 的口径：v9.7.0+ 引入的 language plugin 不只是「跑内置规则」，官方明确 "ESLint core is generic and can be used to lint any programming language."，一个 language 由 parser + `SourceCode` 对象 + language 对象三部分构成，**自定义规则一样能为非 JS 语言写**。但这要求先有人把目标语言接进来，实际可用的目前是 JSON / Markdown / CSS。

**结论**：要在一个多语言 monorepo 环境里做「一条规范一次表达、多语言生效」，**只有 Comby 勉强够得着**（一套模式跨 50+ 语言，代价是不认识语法节点种类）。Semgrep 和 ast-grep 覆盖最广，但它们的模式本身是按语言写的——同一条语义规范在 Go 和 Java 上要写两条规则。

> 这直接决定了规范领域模型里，「一条规范」和「一条可执行规则」必须是**一对多**关系，而不是一对一。

### 2.5 误报率：公开数据与两条准入线

这是整份调研里数字最硬的一块。

**Google，[Lessons from Building Static Analysis Tools at Google](https://storage.googleapis.com/gweb-research2023-media/pubtools/4365.pdf)（CACM 2018, DOI 10.1145/3188720）**

先给了一个关键定义：

> "We consider an issue to be an 'effective false positive' if developers did not take positive action after seeing the issue."

——**误报率不按分析器正确性算，按开发者有没有动手算。** 分析器报对了但开发者没看懂所以没改，也算误报。

然后是两条准入线：

编译期（会 break build）：

> "A compiler check at Google should be easily understood; actionable and easy to fix (whenever possible, the error should include a suggested fix that can be applied mechanically); **produce no effective false positives** (the analysis should never stop the build for correct code); and report issues affecting only **correctness rather than style or best practices**."

代码评审期：

> "analysis results shown during code review are allowed to include **up to 10% effective false positives**."

四条判据：Be understandable / Be actionable and easy to fix / Produce less than 10% effective false positives / Have the potential for significant impact on code quality。

下线机制：

> "Tricorder also provides a 'Not useful' button... The Tricorder team tracks such not-useful clicks, computing the ratio of 'Please fix' vs. 'Not useful' clicks. **If the ratio for an analyzer goes above 10%, the Tricorder team disables the analyzer until the author(s) improve it.**"

还有一个对「介入点」的论证：

> 调查显示编译期标出的问题有 **74%** 被开发者认为是 "real problems"，已提交代码里扫出来的只有 **21%**；"critical" 分别是 **6%** 和 **0%**。原因是 "survivor effect"——代码提交时，错误已经被测试和评审等更贵的手段筛掉了。

规模（2018-01）：Error Prone 有 **733 个检查、162 位作者**；每天分析约 **50,000** 次 code review 变更，峰值 3 次/秒；"Please Fix" 点击 >5,000 次/天，自动修复被应用约 3,000 次/天，"Not useful" 250 次/天。

**Tricorder（ICSE 2015，[PDF](https://www.cs.umd.edu/class/spring2019/cmsc414/papers/tricorder-building-a-program-analysis-ecosystem.pdf)）** 补充了几个数字：

- 编译期要求 "false positive rate must be essentially zero"，且编译开销 < 5%。
- 评审期："We still enforce a very low effective false positive rate here (< 10%)"，且默认**只在改动行上展示结果**，分析要在 5-10 分钟内出结果（评审平均时长 > 1 小时）。
- 分析器下线契约三条：没人修针对它提的 bug / 资源占用影响平台 / 结果在惹恼开发者。
- 实测："Our most successful analyzers have not-useful rate between 0-3%"。
- **一个反直觉的数字**：某个分析器 **75%** 的投诉 bug 是因为**提示文案写得让人误解**，改了文案就没人投诉了。

**Meta，[Scaling Static Analyses at Facebook](https://discovery.ucl.ac.uk/id/eprint/10084236/1/O'Hearn%20AAM%20scaling-static-analysis-at-facebook.pdf)（CACM 2019, DOI 10.1145/3338112）**

这篇给的是整份调研里最重要的一个对比：

> "we were greeted by near silence. We assigned 20-30 issues to developers, and almost none of them were acted on. We had worked hard to get the false positive rate down to what we thought was **less than 20%**, and yet the fix rate—the proportion of reported issues that developers resolved—was near zero."
>
> "Next, we switched Infer on at diff time. The response of engineers was just as stunning: **the fix rate rocketed to over 70%. The same program analysis, with same false positive rate, had much greater impact when deployed at diff time.**"

摘要里的对照句：diff time 部署 **70% fix rate**，批量/离线部署 **0% fix rate**。

**同一个分析器、同一个误报率，介入点不同，采纳率差 70 个百分点。** 这条比任何误报率数字都重要。

**Error Prone 的准入判据**（[criteria](https://errorprone.info/docs/criteria)）和 Google 的论文完全一致，但写得更细：

- `Severity.ERROR`（默认开启、会 break build）：问题一眼能看懂；修复简单（"Swap the order of these arguments"、"Delete this semicolon"）；**"In essentially no cases should the detected code actually be working as intended."**；"The bug should represent a correctness issue... **not enforce best practices or style rules**"；出现频率 "a small but noticeable frequency"。
- `Severity.WARNING`：**"Developers should feel that we are pointing out an actual issue at least 90% of the time."**

**SonarSource** 给了按类别分档的精度目标（[rules overview](https://docs.sonarsource.com/sonarqube-server/10.8/user-guide/rules/overview.md)）：

> "Under maintainability and reliability, **zero false positives** are expected."
>
> "For vulnerabilities, the goal is to have more than **80%** of issues be true positives."
>
> "Security hotspot rules draw attention to security-sensitive code. After being reviewed by a developer, more than **80%** of issues are expected to be quickly resolved as 'reviewed.'"

**AI code review 侧的公开数字**（都是厂商自述，口径不统一，只能当量级参考）：

| 产品 | 公开数字 | 来源 |
|---|---|---|
| Uber uReview | 75% 标为 useful；65%+ 被处理 | [uber.com/blog/ureview](https://www.uber.com/en-DE/blog/ureview/) |
| Greptile v4 | 43% comment acceptance rate；月评 700K+ PR | [greptile.com/blog](https://www.greptile.com/blog) |
| Cursor Bugbot | "70%+ of flags get resolved before merge" | [cursor.com/bugbot](https://www.cursor.com/en/bugbot) |
| CodeRabbit | 客户案例 65%-70% 采纳率 | coderabbit.ai 案例页 |
| Qodo / Graphite Diamond | **未找到公开的评论采纳率或误报率** | —— |

**三条可直接用的经验值**：

1. **人工评审的基线只有 51%**（uReview 的对照数字）。AI review 的目标不是 0 误报，是**别比人差太多、且噪声总量可控**。
2. **10% 是评审期误报率的行业共识线**（Google 两篇 + Error Prone WARNING 判据 + Tricorder 脚注称这和 Coverity 用的阈值一致）。
3. **介入点比误报率更重要**（Meta 的 70% vs 0%）。这对 uReview 的架构含义是：**规范检查必须在 MR 评审时给出，而不是攒成报表**。

### 2.6 一条企业硬约束：CodeQL 的许可

[github/codeql-cli-binaries LICENSE](https://github.com/github/codeql-cli-binaries/blob/main/LICENSE.md) 原文：

> "These Terms do not authorize using the Software to generate any CodeQL database for or during automated analysis, CI or CD in any other context, or to use the Software in connection with any codebase that is not an Open Source Codebase (**e.g., code in a private repo in GitHub**)."
>
> "If your use of the Software is under a paid customer license for GitHub Advanced Security, the restrictions with respect to automated analysis, CI, and CD and use in connection with non-Open Source Codebases do not apply."

**结论：没有 GitHub Advanced Security 付费许可，企业在私有代码库上自建 CodeQL CI 流水线不在许可允许范围内。** 对一个自托管、对接 GitLab 的内部平台来说，这条先于任何技术评估——CodeQL 那一档（档 6）在我们这里基本不可用，除非另外采购。

这反过来抬高了两个替代方案的权重：Semgrep Pro（付费但按需）、以及各语言原生的分析框架（Go `go/analysis` + Facts、Java Error Prone/Checker Framework）。

### 2.7 静态检查这一端根本表达不出来的四类规范

这是 ticket 特别点名的部分。四类，按「为什么表达不出来」分：

**第一类：判定依据不在程序文本里（领域语义）**

Uber 的例子最典型：「知道某个 int 变量代表的是时间」。程序文本里 `int64` 就是 `int64`，它是毫秒、秒还是纳秒，是**命名、注释、周边调用、业务文档**共同暗示的，不是类型系统里的信息。

同类：
- 「这个金额字段的单位是分还是元」
- 「这个 ID 是用户可见的还是内部的」
- 「这个接口返回的 list 是不是已经排过序」

**理论上的出路是把领域语义搬进类型系统**（Checker Framework 的 Units Checker、Go 的 named type、TS 的 branded type）。但这要求代码本身先改造完——对存量代码库不成立。

**第二类：判定函数不是程序文本的函数（意图与合理性）**

- 设计是否合理、抽象是否恰当
- 这个改动应不应该放在这个模块里
- 错误处理的**策略**是否合适（不是「有没有处理」，是「这里该重试还是该快速失败」）
- 并发设计是否必要

Google eng-practices 的 12 项里，Design、Functionality、Complexity、Context 全部落在这一类。

判据：**能写出「程序文本完全相同但结论不同」的反例**。同一段代码，在一个上下文里是合理抽象，在另一个上下文里是过度设计。既然判定不是文本的函数，就不存在一个读文本的程序能判定它。

**第三类：判定需要和一份外部文档比对**

- 「这个 API 的行为要和 `docs/api-contract.md` 一致」
- 「新增的事件要在 EventCatalog 里登记过」
- 「这个改动违背了 ADR-017 的决定」
- 「日志字段命名要符合可观测性规范里的枚举」

这类**不是不能机械判定**，而是判定依赖的知识在另一个系统里，且对比方式是语义对比而非字符串对比。少数情况下可以降级成可执行的（比如「事件名必须在某个白名单里」可以变成一条 Semgrep 规则 + 一个生成的白名单），但大多数情况降不下来。

> 这一类是 uReview 这种「有知识库的 AI review 平台」相对普通 linter 的**核心增量**，值得在产品上重点做。

**第四类：判定标准本身是模糊的（可读性、命名贴切度）**

- 命名是否贴切（不是命名格式——格式能查，贴切不能）
- 注释是否解释了「为什么」而不是「是什么」
- 函数是不是「做了太多事」（行数能查，职责单一性不能）
- 代码读起来是否清晰

Google eng-practices 对这类的处理是 `Nit:` 前缀——**承认它是意见而不是规则，不能拦 CL**。

**这一分类对产品的直接含义**：

| 类别 | 能否静态化 | 谁来判 | uReview 里的处理 |
|---|---|---|---|
| 领域语义 | 除非改造类型系统，否则否 | LLM（需要 context） | 需要喂周边代码 + 领域术语表 |
| 意图与合理性 | 否（原理上） | LLM（且要谨慎，容易噪声） | 高置信度阈值、可能只在大改动上开 |
| 与外部文档比对 | 部分可降级 | LLM + 检索 | 知识库检索是关键能力 |
| 模糊标准 | 否 | LLM，且默认 `Nit:` 级 | **默认不发评论，或单独一档不阻塞** |

### 2.8 改写型与流程型：两个正交的家族

**改写型**——把规范表达成「从 A 改成 B」而不是「A 是错的」：

- **Refaster**（[errorprone.info/docs/refaster](https://errorprone.info/docs/refaster)）：用两段 Java 代码表达一条规则，`@BeforeTemplate` 标出要替换的写法（可以有多个），`@AfterTemplate` 标出目标写法。支持 `@AlsoNegation`（自动匹配逻辑取反）、`@Placeholder`（匹配任意代码块）、`@MayOptionallyUse`。编译成 `.refaster` 文件后由 Error Prone 应用，产出 unified diff 供审阅。

  **这是整份调研里学习曲线最低的规则表达形式**——不用学 DSL，直接写目标语言的代码。代价是只能表达「表达式/语句级的等价改写」，表达不了任何带条件的判定。

- **OpenRewrite**（[docs.openrewrite.org](https://docs.openrewrite.org/concepts-and-explanations/lossless-semantic-trees)）：核心是 LST（Lossless Semantic Tree）——**带类型归属且保留格式**。官方原话：类型信息 "even if it isn't defined in the same source file or even the same project"；格式方面 "Whitespace before and after LSTs are preserved in the tree so the tree can be printed out to reconstitute the original source code without clobbering formatting."。两种写法：YAML 声明式组合已有 recipe，或写 Java Visitor。

  **与 linter 的根本差别是把自动修复当第一公民**，因此它天然适合「规范变更后的存量迁移」，而不是「新代码的门禁」。

- **Coccinelle**：见 2.1。SmPL 的 `...` 沿控制流路径匹配，是 C 生态里表达「成对调用」类规范最久经考验的工具。

- **Comby**（[comby.dev/docs/overview](https://comby.dev/docs/overview)）：介于正则和 AST 之间的一档。官方自述："Comby lets you search and change many kinds of code structures with greater ease than what regular expressions alone allow."；实现方式是 **"It doesn't implement a full parser for every language, but rather a more general grammar so that it works on a lot of languages."**——只认识配对的括号、字符串字面量、注释这些跨语言共性结构，因此一套语法能覆盖 50+ 语言，还带一个 generic matcher 作为未支持语言的兜底。

  **它是「多语言广度」和「结构感知」之间唯一的折中点**：ast-grep/Semgrep 每语言一套 parser、规则也要每语言写一遍；Comby 一条模式能跨语言用，代价是它不知道语法节点的种类。对「一条规范要在 6 个 monorepo 上生效」这种场景值得单独评估。

**流程型**——约束的对象不是代码，是 PR 元数据与流程：

- **Danger**（[danger.systems/js](https://danger.systems/js/)）："Danger runs during your CI process, and gives teams the chance to automate common code review chores."。Dangerfile 里用 JS/TS 写断言，API 是 `message()` / `warn()` / `fail()` / `markdown()`。官方给的典型规则：改了 `package.json` 没改 `yarn.lock` 要告警、PR 缺 CHANGELOG 条目要告警、PR 太大要提示拆分、没指派 reviewer 要 fail、改了代码没改测试要告警。

  **这一族的价值被严重低估**：「改了 X 必须同时改 Y」「PR 描述必须含工单号」「超过 N 行必须拆」这类规范，AST linter 一条都表达不了，但 Danger 一行就够。而它们恰恰是团队规范里占比不低的一类。

- **GitHub rulesets / Gerrit submit requirements / OPA+conftest**：把规范提升成平台级门禁。适合表达「必须有 N 个审批」「必须过某个 check」「某些路径需要 CODEOWNERS 批准」这类**组织约束**。

- **`.editorconfig`**：最小可执行规范的下限，只管缩进/换行/编码，但胜在被所有编辑器认。

### 3.2 作用域机制只有四种范式

把上面这些扒开，作用域机制其实只有五种，而且各家的命名不同但语义一一对应（第五种只有 Continue 有）：

| 范式 | Cursor | Windsurf | Claude Skill | Copilot | 特点 |
|---|---|---|---|---|---|
| **总是注入** | `alwaysApply: true` | `trigger: always_on` | （CLAUDE.md 承担） | `copilot-instructions.md` | 100% 触发，但占常驻 context |
| **glob 匹配** | `alwaysApply:false` + `globs` | `trigger: glob` + `globs` | `paths` | `applyTo` | 确定性触发，前提是规范能按路径切 |
| **模型自选** | `alwaysApply:false` + `description` | `trigger: model_decision` | description 匹配 | —— | 省 context，**但触发率不可靠** |
| **显式引用** | `@ruleName` | `trigger: manual` | `/skill-name` | —— | 完全可控，但要人记得用 |
| **内容匹配** | —— | —— | —— | —— | 仅 Continue 的 `regex`：按**文件内容**而非路径决定是否注入 |

第五种值得单独拎出来：Continue 的 [rules 文档](https://docs.continue.dev/customize/deep-dives/rules) 里 `regex` 是 "Content patterns for conditional inclusion"。**这是唯一一家把作用域绑到代码内容而不是路径上的**。对我们很有用——很多规范的适用条件本来就是「这个 diff 里出现了 `sql.Query(`」而不是「这个文件在 `dao/` 目录下」。用一个轻量的内容匹配做规范预筛，比让模型看 description 自选可靠得多，成本也低得多。

Continue 还有一个运营细节值得抄：规则文件**按文件名字典序加载**（"you can prefix them with numbers to control the order"），拼进 system message 的顺序是确定的。规范一多，注入顺序就会影响冲突时的表现，这个得是确定的而不是随机的。

Cursor 的官方表（[cursor.com/docs/context/rules](https://cursor.com/docs/context/rules)）：

| 类型 | frontmatter | 触发 |
|---|---|---|
| Always Apply | `alwaysApply: true` | "Always included. Globs and description are ignored." |
| Auto-Attached | `alwaysApply: false` + `globs` | "Auto-attached when a matching file is in context." |
| Agent-Selected | `alwaysApply: false` + `description` | "Agent reads the description and pulls the rule in when relevant." |
| Manual | `alwaysApply: false`（无 globs/description） | "Included only when you @-mention the rule in chat." |

Windsurf 的四档（[docs](https://docs.devin.ai/desktop/cascade/memories)）语义完全对应，只是写成 `trigger: always_on / glob / model_decision / manual`。`model_decision` 的机制官方描述得很清楚："Only the description is shown in the system prompt. Cascade reads the full rule file when it decides the description is relevant."

**目录继承**只有 AGENTS.md 一族有正经定义。Codex 的实现（[learn.chatgpt.com/codex/agent-configuration/agents-md](https://learn.chatgpt.com/codex/agent-configuration/agents-md)）：

> "Starting at the project root (typically the Git root), Codex walks down to your current working directory."
>
> "In each directory along the path, it checks for `AGENTS.override.md`, then `AGENTS.md`, then any fallback names"，且 "Codex includes at most one file per directory."
>
> "Codex concatenates files from the root down, joining them with blank lines. **Files closer to your current directory override earlier guidance because they appear later in the combined prompt.**"
>
> "Codex skips empty files and stops adding files once the combined size reaches the limit defined by `project_doc_max_bytes` (32 KiB by default)."

注意这里的「覆盖」是**靠位置靠后实现的语义覆盖，不是丢弃远处的文件**。agents.md 官网的通俗说法是 "the closest one takes precedence"，和实现不完全是一回事——设计规范模型时要明确自己用哪种语义。

[agents.md](https://agents.md) 的 FAQ 还确认了两件事：没有必填字段（"AGENTS.md is just standard Markdown"）；冲突时 "The closest AGENTS.md to the edited file wins; explicit user chat prompts override everything."

**Copilot 的合并规则**是四种载体里最值得抄的一条（[add-repository-instructions](https://docs.github.com/en/copilot/how-tos/configure-custom-instructions/add-repository-instructions)）：

> "Personal instructions take the highest priority. Repository instructions come next, and then organization instructions are prioritized last. **However, all sets of relevant instructions are provided to Copilot.**"

**优先级 ≠ 互斥覆盖**——三层全部注入，优先级只影响冲突时模型的倾向。官方也顺带建议 "Whenever possible, try to avoid providing conflicting sets of instructions."

### 3.3 渐进式加载：怎么做的，和它的代价

**Claude 的三层模型**（[Agent Skills overview](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/overview)）：

| 层 | 加载时机 | token 成本 | 内容 |
|---|---|---|---|
| Level 1 Metadata | 总是（启动时） | **~100 tokens / skill** | frontmatter 的 `name` + `description` |
| Level 2 Instructions | skill 被触发时 | **under 5k tokens** | SKILL.md 正文 |
| Level 3+ Resources | 按需 | **访问前为 0** | 捆绑文件；脚本只有输出进 context |

官方对这个设计的说法：

> "There's no practical limit on bundled content: Files don't consume context until accessed, so Skills can include comprehensive API documentation, large datasets, or extensive examples."

Claude Code 的实现里还有一条字数约束（[code.claude.com/docs/en/skills](https://code.claude.com/docs/en/skills)）：**description 与 `when_to_use` 合并后在 skill 列表里截断到 1,536 字符**。而独立分发的 Agent Skills 规范层面，`name` ≤ 64 字符、`description` ≤ 1,024 字符、`compatibility` ≤ 500 字符。两套数字不矛盾，是两个规范层：分发规范约束单字段长度，Claude Code 约束列表里的展示预算。

Vercel OpenReview 用的是同一套模式（`.agents/skills/<name>/SKILL.md`，agent 系统提示里只有 name + description，匹配上了才调 `loadSkill` 拉全文）。

**代价：渐进式加载会显著降低触发率。**

这是本节最重要的一手数据。Vercel 公开了一组 eval（[AGENTS.md outperforms skills in our agent evals](https://vercel.com/blog/agents-md-outperforms-skills-in-our-agent-evals)），测的是让 agent 用训练数据里没有的 Next.js 16 API（`connection()`、`'use cache'`、`cacheLife()`、`forbidden()`、异步 `cookies()`/`headers()`）：

| 配置 | 总分 | Build | Lint | Test |
|---|---|---|---|---|
| 无文档（baseline） | 53% | 84% | 95% | 63% |
| Skills（默认，模型自选） | **53%** | 84% | 89% | 58% |
| Skills + 明确指示先调用 skill | 79% | 95% | 100% | 84% |
| AGENTS.md（8KB 压缩索引，常驻） | **100%** | 100% | 100% | 100% |

关键发现：

> "in **56%** of eval cases, the skill was never invoked"（没有明确指示时）

以及作者给出的解释：

> passive context 之所以有效，是因为 "there's no moment where the agent must decide 'should I look this up?'"

**结论**：渐进式加载省的是 token，付出的是**触发率**。在「省 token」和「一定生效」之间，它站在省 token 那边。

> **对 uReview 的直接含义**：规范的加载策略不能一刀切。
> - **必须每次都查的规范**（安全、资损、不可逆操作）→ 常驻注入，别指望模型自己想起来。
> - **按文件类型确定的规范** → 走 glob 作用域，这是确定性触发，不是模型自选。
> - **只在特定场景才需要的规范** → 才用渐进式加载，且要接受它有相当比例不会被触发。
>
> 这也意味着「动态规范选取」（[ticket 12](../../.agents/notes/proposed/architecture/2026-09-12-large-pr-splitting-and-rule-routing.md)）不应该做成「把规范列表丢给模型让它挑」，而应该**先用确定性手段（路径 glob、语言、改动类型）把候选集缩小**，再让模型在小集合里选。

### 3.4 怎么写一条 LLM 能稳定执行的规范

一手依据主要来自 Anthropic 的 [Skill authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)、Windsurf 的 rules 最佳实践、GitHub 的 [response customization](https://docs.github.com/en/copilot/concepts/prompting/response-customization)。

**（一）触发信息和判定信息要分开写**

Anthropic 对 description 的要求：

> "**Always write in third person.** The description is injected into the system prompt, and inconsistent point-of-view can cause discovery problems."
> - Good: "Processes Excel files and generates reports"
> - Avoid: "I can help you process Excel files" / "You can use this to process Excel files"

> "The `description` field enables Skill discovery and should include **both what the Skill does and when to use it**."

官方给的好例子：

```yaml
description: Extract text and tables from PDF files, fill forms, merge documents. Use when working with PDF files or when the user mentions PDFs, forms, or document extraction.
```

明确标为要避免的：

```yaml
description: Helps with documents
description: Processes data
description: Does stuff with files
```

**（二）匹配「自由度」和规范的脆弱性**

Anthropic 给了一个三档框架，我认为可以直接搬进规范领域模型当一个字段：

| 自由度 | 用什么表达 | 什么时候用 |
|---|---|---|
| 高 | 纯文字指引 | "Multiple approaches are valid / Decisions depend on context / Heuristics guide the approach" |
| 中 | 伪代码或带参数的模板 | "A preferred pattern exists / Some variation is acceptable" |
| 低 | 确定的脚本、明确的禁止 | "Operations are fragile and error-prone / Consistency is critical / A specific sequence must be followed" |

官方的比喻："Narrow bridge with cliffs on both sides" vs "Open field with no hazards"。

**（三）要不要带例子：官方立场是「输出质量依赖示例时才带，且必须是具体的」**

Anthropic 的 Examples pattern：

> "For Skills where output quality depends on seeing examples, provide input/output pairs just like in regular prompting."
>
> "Examples convey the desired style and level of detail to Claude more clearly than descriptions alone."

发布前检查清单里的对应项是 "Examples are concrete, not abstract"。

**未找到**任何厂商发布的「带正例 vs 带正反例 vs 不带例子」的对照实验数据。这是一个公开的空白，我们自己可以补。

**（四）简洁不是美德，是预算**

> "The context window is a public good."
>
> "**Default assumption: Claude is already very smart.** Only add context Claude doesn't already have. Challenge each piece of information: 'Does Claude really need this explanation?' 'Can I assume Claude knows this?' 'Does this paragraph justify its token cost?'"

Windsurf 的说法更直白：

> "Keep rules simple, concise, and specific. **Rules that are too long or vague may confuse Cascade.**"
> "Format your rules using bullet points, numbered lists, and markdown."
> "XML tags can be an effective way to communicate and group similar rules together."

**（五）GitHub 给了一张明确的 don't 清单**

[response customization](https://docs.github.com/en/copilot/concepts/prompting/response-customization) 里列为**会出问题**的指令类型：

- "Requests to refer to external resources when formulating a response."（要求引用外部资源）
- "Instructions to answer in a particular style."（要求特定风格作答）
- "Requests to always respond with a certain level of detail."（要求固定详细程度）

以及对应的 do：写项目概览、写编码标准与约定、写用到的工具/库/版本；并且用 "short, self-contained statements"。

还有一句免责很值得引用到我们自己的产品文案里：

> "Due to the non-deterministic nature of AI, Copilot may not always follow your custom instructions in exactly the same way every time they are used."

**（六）评估先于文档**

Anthropic 力推的流程：

> "**Create evaluations BEFORE writing extensive documentation.** This ensures your Skill solves real problems rather than documenting imagined ones."

五步：识别差距（不带 skill 时 agent 在哪儿失败）→ 建三个评估场景 → 建立基线 → 写刚好够过评估的最小指令 → 迭代。

> 这条对「规范冷启动」有直接指导意义：**一条规范的价值不该由写它的人声称，而应该由「不带这条规范时 review 会漏掉什么」来证明。** 这天然给出了规范的验收方式，也给出了后面 5.3 节度量的抓手。

**（七）把上面拼起来，一条自然语言规范的可用模板**

````markdown
---
id: go-context-timeout            # 稳定 ID，用于追溯与去重
title: 对外调用必须带超时           # 一句话，人读
description: >                    # 给模型判断"要不要看这条"用，第三人称，含触发词
  Checks that outbound RPC/HTTP calls set an explicit timeout via context.
  Use when reviewing Go files that call internal gRPC services or net/http.
scope:
  languages: [go]
  paths: ["services/**/*.go"]      # 确定性作用域优先于模型自选
  change_types: [added, modified]
severity: high                     # 影响门禁行为
freedom: low                       # 高/中/低，对应表达方式
executable_by: [semgrep]           # 若已有可执行规则，这里指过去；LLM 就不必再判
source:                            # 追溯
  origin: mined_from_pr
  ref: "https://gitlab.internal/.../merge_requests/1234#note_5678"
---

## 约束

对外调用必须显式设置超时。不允许直接使用 `context.Background()` 作为 RPC/HTTP 调用的 ctx。

## 适用条件

- 调用方是 `services/` 下的服务代码。
- 被调方是内部 gRPC 服务或任意 `net/http` 出站请求。

## 例外

- 后台常驻任务的根 context（需在代码里注明 `// long-running: no deadline`）。
- 测试代码。

## 反例

```go
resp, err := client.GetUser(context.Background(), req)   // 没有超时
```

## 正例

```go
ctx, cancel := context.WithTimeout(ctx, 300*time.Millisecond)
defer cancel()
resp, err := client.GetUser(ctx, req)
```

## 判定提示

只看调用点，不要推断调用链。看不到 ctx 来源时不要报。
````

最后一段「判定提示」是我加的，不是任何一家的官方约定，但它对应 Tricorder 那个 **75% 的投诉来自文案措辞** 的教训：**规范里要明确写出「什么情况下不要报」，否则误报会从这里来**。

## 4. 中间地带

### 4.1 「自然语言 + 结构化元数据」已经是事实标准

本次调研里，凡是被真实产品采用的规范载体，**没有一个是纯自然语言**，全都是「一段 Markdown + 一段 frontmatter/YAML」：

| 产品 | 自然语言部分 | 结构化部分 |
|---|---|---|
| Cursor `.mdc` | 规则正文 | `description` / `globs` / `alwaysApply` |
| Windsurf rule | 规则正文 | `trigger` / `description` / `globs` |
| Claude `SKILL.md` | 正文 + 引用文件 | 20 个 frontmatter 字段（含 `paths`、`metadata`、`license`、`compatibility`） |
| Copilot `.instructions.md` | 指令正文 | `applyTo` glob |
| CodeRabbit `path_instructions` | `instructions` 多行文本 | `path`（minimatch glob） |
| CodeRabbit `custom_checks` | `instructions`（≤10,000 字符） | `name`（≤50 字符）、`mode`: `off`/`warning`/`error` |
| Qodo Rule | 规则描述 | 来源（manual / file / mined）、作用域路径、启用状态 |

**CodeRabbit 的 `.coderabbit.yaml` 是这一族里字段最全的一个**（[yaml-template](https://docs.coderabbit.ai/reference/yaml-template)），值得整个抄一遍：

- `reviews.path_instructions[]`：`path`（minimatch glob）+ `instructions`，每条上限 20,000 字符。
- `reviews.profile`：`quiet` / `chill`（默认）/ `assertive` —— **把「噪声阈值」做成了一等配置**。
- `reviews.tools.ast-grep`：`rule_dirs` / `util_dirs` / `packages`（`owner/repo`）/ `essential_rules`。
- `pre_merge_checks.custom_checks[]`：`name`（≤50 字符）+ `instructions`（≤10,000 字符）+ `mode`（`off`/`warning`/`error`）。
- `knowledge_base.code_guidelines`：可以直接把 `.cursorrules`、`.github/copilot-instructions.md` 当规范源读进来，也能引用外部仓库路径（`engineering-standards:frontend/react.md`）。
- `knowledge_base.learnings.scope`：`local`（仓库）/ `global`（组织）/ `auto`。

三个可以直接搬的设计：

1. **同一个平台上并置两档**：`path_instructions`（自然语言，LLM 执行）和 `tools.ast-grep`（可执行规则，确定性执行）是**同一份配置里的两个 key**。这就是「能静态检查就不用 LLM」在产品形态上的落地方式——不是两个系统，是一份配置的两档。
2. **`mode: off/warning/error`**：自然语言规范也可以有门禁级别。
3. **跨体系互认**：把别家的规范文件（`.cursorrules`、`copilot-instructions.md`）当成自己的规范源。这条对企业内部平台很重要——团队已经有的 `AGENTS.md` 不该被要求迁移。

官方对 `path_instructions` 的使用建议也值得记（[review-instructions](https://docs.coderabbit.ai/guides/review-instructions)）：把它当 "a targeted supplement, not a replacement"，建议先观察几轮评审、**只在「某处被持续漏掉」时才加规则**。这和 Anthropic 的「评估先于文档」是同一个思路。

### 4.2 元数据字段的并集：规范领域模型的候选字段

把各家的元数据取并集，再对照 SARIF 这个唯一被广泛实现的互操作标准，得到一份候选字段清单。

**SARIF 2.1.0 的 `reportingDescriptor`（即「规则」）**（[OASIS spec](https://docs.oasis-open.org/sarif/sarif/v2.1.0/os/sarif-v2.1.0-os.html) §3.49）完整字段：

`id`、`deprecatedIds`、`guid`、`deprecatedGuids`、`name`、`deprecatedNames`、`shortDescription`、`fullDescription`、`messageStrings`、`helpUri`、`help`、`defaultConfiguration`、`relationships`。

其中两个特别值得注意：

- **`defaultConfiguration`**（§3.50）是一个 `reportingConfiguration`，含 `enabled` / `level` / `rank` / `parameters`。`rank` 是 0.0-100.0 的数值，缺省 -1.0 表示未知——**这是一个和 `level` 正交的连续优先级**，恰好对应我们需要的「置信度/重要度」。`parameters` 是规则自身的可配参数（规范里明确要求参数**不能**放在 property bag 里，必须放这儿）。
- **`relationships`**（§3.49.15 + §3.53）是一个有向关系数组，`kinds` 的推荐取值是 `equal` / `superset` / `subset` / `disjoint` / `incomparable` / `relevant`（缺省 `relevant`）。**SARIF 已经给了「规则之间关系」的标准词表**——这正是第 5.1 节「怎么避免规范互相矛盾」需要的数据结构。

**SonarSource 的规则分类**（[rules overview](https://docs.sonarsource.com/sonarqube-server/10.8/user-guide/rules/overview.md)、[software qualities](https://docs.sonarsource.com/sonarqube-server/10.8/core-concepts/software-qualities.md)）：

- **Software quality**：security / reliability / maintainability。一条规则可以同时影响多个。
- **Impact severity**：Blocker / High / Medium / Low / Info，每个都有明确定义（Blocker = "significant probability of severe unintended consequences... should be fixed immediately"）。
- **Clean code attribute**（14 个，分 4 类）：

  | 类别 | 属性 | 大致对应的规范类型 |
  |---|---|---|
  | Consistency | `FORMATTED`、`CONVENTIONAL`、`IDENTIFIABLE` | 格式、约定、命名——**全部落在档 4，静态检查的主场** |
  | Intentionality | `CLEAR`、`LOGICAL`、`COMPLETE`、`EFFICIENT` | 清晰、逻辑正确、完整、高效——档 5-6 能覆盖一部分，`CLEAR` 基本只能靠 LLM |
  | Adaptability | `FOCUSED`、`DISTINCT`、`MODULAR`、`TESTED` | 职责单一、无重复、模块化、有测试——除 `TESTED` 的一部分外，基本是 LLM 的活 |
  | Responsibility | `LAWFUL`、`TRUSTWORTHY`、`RESPECTFUL` | 合法（许可）、可信（无密钥泄漏）、得体——`TRUSTWORTHY` 有成熟静态规则，其余靠人或 LLM |

  （14 个属性名来自 [规则总览页](https://docs.sonarsource.com/sonarqube-server/10.8/user-guide/rules/overview.md) 的筛选项；四分组来自同一文档站的问答接口返回，其中 `TESTED` 按剩余项归入 Adaptability。右列的「对应档位」是我自己的映射，不是 Sonar 的说法。）

  > **这张表本身就是一个现成的「规范分类法」**，而且它的四个类别恰好和我们的分界线对得上：Consistency 一整类可以无脑静态化，Adaptability 一整类基本静态化不了。如果不想自己发明分类，直接用 Sonar 这套是最省事的——它有 14 个 attribute 的既有词表，也有和 severity 正交的 software quality 维度。
- **Rule status**：Beta / Deprecated / Ready。
- 另有 Language、Tag、Repository（哪个分析器贡献的）、Available since、Template（可用来生成自定义规则的模板规则）。

Sonar 这套的关键设计是**把「影响什么」和「有多严重」拆开了**：一条规则声明它影响哪些 software quality，每个影响各自有 severity。这比单一的 severity 字段表达力强得多，我们应该抄。

**合并后的候选字段表**（给 ticket 11 直接用）：

| 字段 | 取值 | 出处 | 为什么要 |
|---|---|---|---|
| `id` | 稳定字符串 | 全部 | 追溯、去重、抑制 |
| `deprecated_ids` | 数组 | SARIF | 改名后老 ID 还能对上 |
| `title` / `short_description` | 一句话 | SARIF、ESLint `docs.description` | 人读 |
| `description` | 含「做什么 + 何时用」 | Claude Skill | **模型用它决定要不要加载** |
| `full_description` / 正文 | Markdown | SARIF `fullDescription`、SKILL.md 正文 | 判定依据 |
| `languages` | 数组 | Semgrep、Sonar | 作用域 |
| `paths` | glob include/exclude | Semgrep `paths`、Cursor `globs`、Copilot `applyTo`、CodeRabbit `path` | **确定性作用域，优先于模型自选** |
| `software_qualities[]` | security / reliability / maintainability | Sonar | 一条规范可同时影响多项 |
| `impacts[].severity` | blocker/high/medium/low/info | Sonar | 每项影响各自定级 |
| `mode` | off / warning / error | CodeRabbit | 门禁行为 |
| `rank` | 0.0-100.0 | SARIF | 和 severity 正交的排序权重（喂给 Grader） |
| `precision` / `confidence` | very-high/high/medium/low | CodeQL `@precision`、Semgrep `confidence` | 决定阈值 |
| `autofixable` | bool / suggestion-only | ESLint `fixable`+`hasSuggestions` | 影响能不能直接给补丁 |
| `freedom` | high / medium / low | Anthropic | 决定用什么形式表达 |
| `examples.positive[]` / `negative[]` | 代码片段 | Anthropic、PMD `example` | LLM 判定质量 |
| `exceptions[]` | 文本 | 无标准，自加 | **降误报的主要手段** |
| `status` | draft / active / deprecated | Sonar | 生命周期 |
| `replaced_by` | 规则 ID | ESLint `replacedBy` | 淘汰路径 |
| `relationships[]` | `{target, kinds}`，kinds ∈ equal/superset/subset/disjoint/incomparable/relevant | SARIF | **冲突与重叠检测** |
| `executable_by[]` | 工具 + 规则 ID | 自加 | 「已有静态规则就别让 LLM 判」的实现基础 |
| `source` | manual / imported / mined + 来源链接 | Qodo Rule Miner | 追溯与信任分级 |
| `metrics` | 命中数 / 采纳数 / not-useful 数 | Tricorder、Meta | 度量与淘汰 |

### 4.3 从自然语言到可执行规则：自动生成

**学术侧，最有说服力的是 KNighter**（[arXiv 2503.09002](https://arxiv.org/abs/2503.09002)，SOSP 2025，UIUC）。

它的关键洞察不是「让 LLM 去扫代码」，而是**让 LLM 去合成 checker**：

> "Rather than using LLMs to directly analyze massive systems, our key insight is leveraging LLMs to generate specialized static analyzers guided by historical patch knowledge. KNighter implements this vision through a multi-stage synthesis pipeline that **validates checker correctness against original patches** and employs an automated refinement process to **iteratively reduce false positives**."

结果：在 Linux kernel 上，合成出的 checker 发现了 **92 个新的严重 bug（平均潜伏 4.3 年），77 个被确认，57 个被修复，30 个分配了 CVE**。

**两个可直接抄的机制**：
1. **用产生这条规范的原始 patch 当 checker 的验收测试**——生成出来的规则必须能在原 patch 的 before 版本上报出问题、在 after 版本上不报。
2. **自动迭代降误报**——生成后在大规模代码库上跑，误报多就让 LLM 改。

**SemOpt**（[arXiv 2510.16384](https://arxiv.org/abs/2510.16384)）做的是同一件事的另一半：从 commit 里提取优化策略，再**让 LLM 生成 Semgrep 规则**来定位「这个策略适用的位置」。151 个 C/C++ + 150 个 Python 任务上，成功优化数相对 baseline 提升 1.38-28 倍（C/C++）和 4.60-6.33 倍（Python）。

> 这两篇合起来说明：**「LLM 生成静态规则」已经不是设想，而是有公开可复现结果的工程手段**，而且它的价值不在于省人力，在于把「一次性的 LLM 判定」变成「可复用、确定性、零 token 成本的规则」。对 uReview 而言，这是一条从 LLM 侧向静态检查侧「回流」的通道。

**IRIS**（[arXiv 2405.17238](https://arxiv.org/abs/2405.17238)，UIUC）走的是第三条路：不生成规则，而是**用 LLM 补上规则缺的那部分规格**。

> "Program analysis tools to detect them have limited effectiveness in practice due to their **reliance on human labeled specifications**... We propose IRIS, a neuro-symbolic approach that systematically combines LLMs with static analysis to perform whole-repository reasoning."

做法是让 LLM 推断 taint specification（哪些是 source、哪些是 sink），再交给 CodeQL 跑分析。在 CWE-Bench-Java（120 个人工校验过的真实 Java 漏洞）上：CodeQL 基线检出 27 个，IRIS + GPT-4 检出 **55 个**，另外发现 4 个此前未知的漏洞，false discovery rate 比 CodeQL 低 5 个百分点。

> **这三条路对应了三种把 LLM 塞进静态分析的位置**：合成整个 checker（KNighter）、生成定位规则（SemOpt）、补规格而保留分析引擎（IRIS）。**IRIS 那条路对我们最实用**——它承认静态分析引擎是对的，只是缺「这个项目里什么算 source」这种项目特定知识，而这恰好是团队规范里最多的一类。

**厂商侧**：Semgrep 有 Semgrep Assistant（规则生成、误报分类、autofix、memories）。本次调研**未能在官方文档里找到 Assistant 的准确率或采纳率的公开数字**，标注为未找到。

### 4.4 从代码库/评审历史归纳规范

**经典源头**：Engler et al., *Bugs as Deviant Behavior: A General Approach to Inferring Errors in Systems Code*（SOSP 2001，[PDF](https://web.stanford.edu/~engler/deviant-sosp-01.pdf)）。这篇是「从代码库自动归纳规范」的鼻祖，方法论今天依然适用：

核心是把代码里隐含的 **belief** 分成两类：

> "MUST beliefs are directly implied by the code, and there is no doubt that the programmer has that belief. A pointer dereference implies that a programmer must believe [the pointer is non-null]... **MAY beliefs are cases where we observe code features that suggest a belief but may instead be a coincidence. A call to 'a' followed by a call to 'b' implies the programmer may believe they must be paired, but they may not be.**"

处理方式不同：MUST belief 一旦矛盾直接报错；MAY belief 先假定成立，再**用统计排序**筛：

> "a call to 'spin_lock' followed once by a call to 'spin_unlock' implies that the programmer may have paired these calls by coincidence. **If the pairing happens 999 out of 1000 times, though, then it is probably a valid belief and the sole deviation a probable error.**"

论文里用一个 `z(N, E)` 假设检验统计量给候选规则排序——**一条候选规则通过的检查越多，它的少数违例就越可信，排名就越高**。作者做了六个 checker，在 Linux 和 OpenBSD 上找到数百个 bug，且相对手写规格 "find ten to one hundred times more rule instances"。

最后一句最关键：

> "The key feature of this approach is that it requires **no a priori knowledge of truth**: if two beliefs contradict, we know that one is an error without knowing what the correct belief is."

> **给我们的启示有两条**。第一，「从代码库归纳规范」的正确姿势不是「找出最常见的写法」，而是**找出「几乎总是这样、但有少数例外」的模式**——例外才是产出，共识只是筛选器。第二，`z` 统计量给出了一个可直接抄的**候选规范置信度公式**：支持数 N 越大、违例数 E 越小，这条候选规范越可信。这比「这条规则被提过 3 次」这种朴素计数强得多，而且它天然给出了一个排序，可以直接接到人工审批队列上。

**工业侧最完整的公开实现是 Qodo 的 Rule Miner**（[docs.qodo.ai/governance/rule-enforcement/rule-miner](https://docs.qodo.ai/governance/rule-enforcement/rule-miner)），细节值得整段抄：

- **挖的是 PR 讨论，不是代码**："Qodo scans pull request discussions across your connected repositories and identifies recurring review patterns: comments that were accepted by developers and led to code changes, recurring behaviors that reviewers consistently flag, and the accept/reject patterns that follow."
- **样本量**：初次分析约 **1,000 个最近合并的 PR**。
- **候选筛选极严**：只考虑「作者真的照做改了代码」的评论；泛泛的夸奖、提问、小挑刺都排除；且通常要求**跨多个 PR 复现**，除非来自有强 code ownership 的评审者。
- **产出节流**：首轮每仓库最多 **10 条**，之后每两周最多 **5 条**新规则。
- **可追溯**：每条规则带一个回溯到来源 PR 的链接。
- **人审队列**：默认进 Rules > Suggestions 等管理员审批（较新的组织默认自动批准）。
- **对产量的预期管理**："A repository can be perfectly healthy and still produce only a few rules, or none at all. That's normal."

Qodo 的规则还有三个来源并列（[rule-enforcement](https://docs.qodo.ai/governance/rule-enforcement)）：portal 里用自然语言手写、从 `AGENTS.md`/`CLAUDE.md` 之类文件导入、Rule Miner 挖掘。

**同类机制**：
- CodeRabbit 的 `knowledge_base.learnings`（scope 可设 local/global/auto），从评论交互里学团队偏好。
- Cursor 的 `/create-rule`——"Type `/create-rule` in Agent and describe what you want. Agent generates the rule file with proper frontmatter and saves it to `.cursor/rules`."（[cursor.com/docs/context/rules](https://cursor.com/docs/context/rules)）
- Windsurf 把 Memories（Cascade 自动生成、本地、不进版本控制、一次性事实）和 Rules（人写、进版本控制、可共享、长期知识）明确分开，并建议 "for durable knowledge prefer Rules or AGENTS.md"。

> **对「规范冷启动」的直接结论**：Qodo 的做法给出了一条完整可抄的路径——**不要让团队坐下来写规范，而是从他们过去的 MR 评论里挖**，且挖的时候只认「作者真的改了」的评论（这天然过滤掉了无效意见），产量要节流（每两周 5 条），每条要能追溯到来源 MR，且必须过人工审批才生效。这几条约束加起来，把「自动归纳规范」从一个容易失控的功能变成了可运营的功能。

### 4.5 同一条规范的两个身份

「自然语言版给人看、可执行版给工具跑」这件事，业界最大规模的现成案例是 **style guide + 对应 lint config** 这一对：

- Airbnb JavaScript Style Guide（39 个大类章节）与 `eslint-config-airbnb`。
- Google 各语言 style guide 与 Error Prone / 各语言 linter。

但**本次调研未找到任何一家公开过「style guide 里有多少条能被 linter 覆盖、多少条不能」的统计**。这是一个公开空白。

从工具侧倒推，能给一个粗估：ESLint 在废弃 77 条格式化规则时的官方说法是规则总数增长到 **300 条**；而一份典型 style guide 的条目数在同一量级。考虑到 style guide 里有相当比例是设计与可读性建议（前面 2.7 节的第二、四类），**「可执行覆盖率」大概率在一半以下**。

## 5. 运营：几百条规范之后

### 5.1 规范互相矛盾怎么办

**ESLint 的设计原则是「不该有冲突」，而它自己承认这条守不住了**。[废弃格式化规则的公告](https://eslint.org/blog/2023/10/deprecating-formatting-rules/) 里第一条理由就是：

> 原本的设计约束是 "no two rules should flag the same problem nor will any two core rules give conflicting advice"，但 "as the number of rules grew to 300, this became nearly impossible"。

**300 条是一个有一手依据的「规则集失控临界点」。** 这个数字应该直接写进我们的运营预案。

**工业界给出的解法是「冲突消解层」而不是「冲突检测器」**：`eslint-config-prettier` 的存在本身就是答案——一个**只关闭规则、不开启任何规则**的 config，专门关掉和格式化器冲突的那些；另有一组「特殊规则」（`curly`、`quotes`、`max-len`、`no-unexpected-multiline` 等）只在某些配置下才冲突，配置对了可以留着。CLI helper（`npx eslint-config-prettier <file>`）扫配置文件报冲突，退出码 0 = 无问题、2 = 有冲突。

**Sonar 的解法是 quality profile 的继承与覆盖**：子 profile 继承父 profile 的激活规则并随父联动；子 profile 若覆盖了某规则的参数，该规则就脱离联动；规则被 deprecate 后在所有继承 profile 中自动停用。

**SARIF 给了描述冲突的词表**（见 4.2）：`relationships[].kinds` 的 `equal` / `superset` / `subset` / `disjoint` / `incomparable`。

> **可落地的做法**：在规范领域模型里为每条规范存 `relationships`，并在「新增规范」时跑一次重叠检测（可以用 LLM 判两条规范是否 equal/superset/subset/incomparable，这正好是 LLM 擅长而静态方法做不了的）。检出 `incomparable`（交叉但互不包含，最容易产生矛盾建议）时强制人工裁决。

### 5.2 过时的规范怎么淘汰

两种截然不同的运营哲学，都有一手依据：

**ESLint：标记但永不强制删除**。[规则弃用政策](https://eslint.org/docs/latest/use/rule-deprecation)：

> "Rules will never be removed from ESLint unless... replaced by another core rule... [or] a plugin exists with a functionally equivalent rule."

2023-11 的 v8.53.0 一次性废弃了 **77 条**格式化规则，但它们仍然随 ESLint 发布，只是产生弃用警告，且**至少要到 v10.0.0 才会真正移除**。目前约有 100 条处于 deprecated 状态。

**Sonar：明确的强制退休期**。功能保留 "at least 6 months... dropped in the year following"；Plugin API 破坏性变更需至少 2 年废弃期。

**机制上，两家都靠同一对字段**：`deprecated` + `replacedBy`（ESLint `meta.deprecated` / `meta.replacedBy`；SARIF `deprecatedIds` / `deprecatedGuids` / `deprecatedNames` + `relationships`）。

> **我们该选哪种**：内部平台建议学 Sonar（有明确退休期），因为规范是团队共识而不是公共库 API，长期挂着 deprecated 的规范只会制造噪声。但**必须保留 `deprecated_ids`**，否则历史 finding 就对不上规则了。

**还有一类「规范自动过期」**：Uber 的 Piranha 是为「feature flag 过期后自动删除相关代码」做的。同样的思路可以用在规范上——**一条规范如果绑定的是某个正在退役的框架/库，它应该随之退役**。（本次未取到 Piranha 官方文档原文校对，标注为**二手**。）

### 5.3 每条规范的价值怎么度量

三套现成的、都有一手依据的度量：

| 来源 | 指标 | 阈值 / 动作 |
|---|---|---|
| Google Tricorder | "Please fix" : "Not useful" 点击比 | 超 10% → 禁用该分析器（CACM 2018）；ICSE 2015 版本是超 25% 进缓刑 |
| Google Tricorder | not-useful 率 | 最成功的分析器在 **0-3%** |
| Meta | fix rate（报告的问题被解决的比例） | diff time 70% vs batch 0%；RacerD 约 50% |
| Meta | action rate | Zoncolan "close to 80%" |
| Semgrep | `metadata.confidence` | HIGH / MEDIUM / LOW，自述式 |
| CodeQL | `@precision` | very-high / high / medium / low，**无量化定义** |

**这三套合起来给出了一个可用的规范价值仪表盘**（每条规范一行）：

1. **命中数**（这条规范在过去 N 个 MR 里被触发了多少次）——太低说明该退休或该改作用域。
2. **采纳率**（命中后代码被改了的比例）——对应 Meta 的 fix rate，**是最能代表价值的单一指标**。
3. **not-useful 率**（开发者点了「没用」的比例）——对应 Tricorder，**超 10% 自动停用**。

三个数都能从 MR 评论的生命周期里直接采集，不需要额外埋点。

**未找到**任何第三方公开的「命中数 / 采纳率 / 误报率」三件套仪表盘实践文章，这是一块空白。

### 5.4 规模的经验值

| 对象 | 规模 | 来源 |
|---|---|---|
| ESLint 核心规则 | 增长到 300 条时"规则互不冲突"变得几乎不可能 | ESLint 官方公告 |
| ESLint 已废弃规则 | 约 100 条（其中 77 条是 2023 年一次性废弃的格式化规则） | 同上 |
| Google Error Prone | 733 个检查、162 位作者（2018-01） | CACM 2018 |
| ruff | "over 900 lint rules" | ruff 官方 |
| semgrep/semgrep-rules 公共规则库 | 2,178 个规则 YAML 文件（单文件可含多条规则） | GitHub trees API 实测（`develop` 分支） |
| Linux kernel Coccinelle | 76 个 `.cocci` | GitHub contents API 实测 |
| Airbnb JS Style Guide | 39 个大类章节 | Airbnb |
| Qodo Rule Miner 产量 | 首轮 ≤10 条/仓库，之后 ≤5 条/两周 | Qodo 官方 |

> **对我们的启示**：Qodo 的节流数字（每两周 5 条）可能比看起来更重要。**规范集的增长速率应该被主动限制**，因为规范集增长到几百条时，冲突检测和价值度量的成本会指数上升（ESLint 的 300 条就是前车之鉴）。一个团队的活跃规范集，**合理量级可能在 30-100 条，而不是几百条**。

## 6. 对照表与分界线建议

### 6.1 谱系对照表

评分说明：表达力 = 能表达的规范种类广度；准确率 = 判定结论可信程度（对 LLM 档，拆成「触发率 × 判定准确率」两项，因为它们是两个独立的失败模式）；维护成本 = 写一条 + 长期维护的总成本；多语言 = 一条规范能否一次表达多语言生效。

| 档 | 形态 | 典型载体 | 表达力 | 准确率 | 维护成本 | 多语言 |
|---|---|---|---|---|---|---|
| **0** | 口头约定 | —— | 无上限 | 极低（靠人记） | 零（也无法维护） | 无关 |
| **1** | 散文规范 | wiki、style guide 正文 | 无上限 | 低（人读人执行，执行率取决于自觉） | 低 | 天然多语言 |
| **2** | 结构化自然语言 | `AGENTS.md`、`CLAUDE.md`、`copilot-instructions.md` | 无上限 | 触发率高（常驻注入）；判定准确率中 | 低 | 天然多语言 |
| **3** | NL + 结构化元数据 | Cursor `.mdc`、Copilot `.instructions.md`、`SKILL.md`、CodeRabbit `path_instructions` | 无上限 | 触发率**取决于作用域机制**（glob 高 / 模型自选低，Vercel 实测 56% 未触发）；判定准确率中高（有作用域和例外约束） | 中低 | 天然多语言 |
| **4** | 语法级模式 | ast-grep、Semgrep OSS、Checkstyle、PMD XPath、ESLint | 窄（只能表达语法上可定位可判定的） | 高（可达 Error Prone ERROR 的"近乎零误报"） | 中（写规则 + 维护语法变化） | 差：每语言各写一条 |
| **5** | 单过程语义 | typescript-eslint type-aware、Error Prone、staticcheck、NullAway、Semgrep taint(OSS) | 中（多了类型与过程内数据流） | 高（Error Prone WARNING 判据要求 ≥90% 真阳） | 中高（要懂类型系统/CFG） | 差 |
| **6** | 跨过程/跨文件数据流 | CodeQL、Semgrep Pro、Infer/Zoncolan、Pysa | 较宽（能表达资源泄漏、污点、时序） | 高（Zoncolan action rate ~80%） | **很高**（QL/DSL 学习曲线 + database 构建 + 分析时长） | 中（各家覆盖 7-10 种语言） |
| **7** | 类型系统契约 | Checker Framework `@MustCall`/`@Owning` | 窄但深（把时序约束固化进签名） | 极高（类型检查器保证） | **极高**（要给存量代码加注解） | 极差（单语言） |
| **旁支 A** | 改写型 | OpenRewrite、Refaster、Coccinelle | 中（只能表达等价改写） | 高 | **低**（Refaster 只要写两段代码） | 差 |
| **旁支 B** | 流程型 | Danger、GitHub rulesets、OPA | 窄但正交（约束 PR 元数据而非代码） | 极高（都是确定性判定） | **极低** | **天然多语言** |

几个容易被忽略的读法：

- **旁支 B 的性价比最高**：维护成本极低、准确率极高、天然多语言，但**表达的是另一类规范**（流程而非代码）。很多团队规范里的「改了 X 必须改 Y」「PR 必须带工单号」被错误地当成了 code review 的事，其实一个 Danger 规则就够。做 uReview 时应该把这一类**从 LLM 的工作量里摘出去**。
- **档 3 的准确率有两个独立的失败模式**：没被触发（作用域机制的问题）和触发了但判错（规范写法的问题）。产品上要分开度量，因为解法完全不同。
- **档 7 的表达力「窄但深」**：它不是比档 6 更强，它是把成本从「分析时」挪到了「编码时」。对存量代码库不可行，对新建的核心库值得考虑。

### 6.2 分界线建议

**硬性落到静态检查（档 4-5），LLM 不应该再判一遍：**

判据：判定函数是「当前文件的语法树 + 可选的类型信息」的函数，且判定不依赖任何文件外的语义。

具体类别：
- 命名格式（大小写、前缀后缀、禁用词）
- 导入约束（禁止 import 某个包、层级依赖方向）
- 具名 API 误用（禁止用 `time.Now()` 做随机、禁止 `==` 比较浮点、禁止某个废弃函数）
- 并发原语的语法层误用（在 `defer` 里忘了 `Unlock`、`sync.WaitGroup` 按值传递）
- 错误处理的语法形态（`err` 被忽略、`panic` 出现在库代码里）
- 资源释放的函数内形态（`lostcancel` 这一类，CFG 可达性够用）
- 格式化（全部交给 formatter，不要做成规则——ESLint 的教训）

**必须交给 LLM（档 2-3），静态检查连表达都表达不了：**

判据：存在「程序文本完全相同但判定结论不同」的反例。

具体类别（对应 2.7 的四类）：
- 领域语义（这个 int 是毫秒还是秒、这个金额单位是分还是元）
- 设计意图与合理性（抽象是否恰当、该不该放这个模块、错误处理策略选得对不对）
- 与外部文档的一致性（和 ADR / API 契约 / EventCatalog 是否吻合）
- 模糊标准（命名贴切度、注释是否解释了 why、可读性）

**中间的灰色地带，四问定档：**

```
一条规范拿到手，依次问：

Q1. 判定对象能在语法树上定位吗？
    否 → 要么是流程规范（走旁支 B: Danger/ruleset），要么交给 LLM。
    是 → 继续。

Q2. 判定条件是程序文本（含类型）的函数吗？
    能写出「文本相同、结论不同」的反例 → 交给 LLM，别再纠结。
    写不出反例 → 继续。

Q3. 判定需要的分析范围有多大？
    单文件/单函数 → 落档 4-5，这是最优解，立刻做。
    跨过程但不跨文件 → 落档 5（Semgrep --pro-intrafile / go SSA）。评估收益。
    跨文件 → 先看这条规范值不值：CodeQL 有许可硬约束、Semgrep 跨文件要付费。
             多数情况下的正确答案是：**先交给 LLM，攒够样本后再考虑用 KNighter 式的方法合成规则**。

Q4. 能不能自动修？
    能 → 优先做成改写型（Refaster/OpenRewrite），价值远高于只报不修。
         Google 的数据：自动修复每天被应用约 3,000 次。
    不能 → 至少要给出「怎么改」的提示。Google 四条判据里
           "Be actionable and easy to fix" 和误报率同等重要。
```

**还有一条时间维度的分界线**，来自 Google 和 Meta 的数据：

| 介入点 | 准入误报率 | 允许的规范类型 | 依据 |
|---|---|---|---|
| 编译期 / pre-commit | **essentially zero** | 只能是 correctness，不能是 style 或 best practice | Google CACM 2018、Error Prone criteria |
| MR 评审期 | **< 10% effective FP** | correctness + best practice 都可以 | Google CACM 2018、Tricorder ICSE 2015 |
| 离线批量扫描 | —— | **别做**，fix rate 会是 0 | Meta CACM 2019 |

**「离线批量扫描没人修」是这份调研里最确定的一条结论**（Meta：同一个分析器、同样的误报率，diff time 70% vs batch 0%）。uReview 的所有规范检查都必须在 MR 上下文里发生。

### 6.3 给 uReview 规范领域模型的五条直接建议

1. **「规范」和「可执行规则」是一对多，不是一对一。** 多语言、多工具决定了这一点。规范实体上要有 `executable_by[]` 指向零到多条具体规则（工具 + 规则 ID）。**一旦某条规范有了可执行实现且覆盖了当前语言，LLM 侧就应该跳过它**——这是「能静态检查就不用 LLM」在数据模型上的落地点，而不是一句口号。

2. **作用域必须优先用确定性机制。** 路径 glob、语言、改动类型、**diff 内容正则**（Continue 的 `regex` 那一招）都是确定性的；「让模型看 description 自己挑」是最后手段。Vercel 的 56% 未触发是硬证据。ticket 12 的「动态规范选取」应该是**先确定性收窄、再让模型在小集合里选**的两段式。

3. **元数据照 4.2 那张表来。** 特别是三个别家有而容易漏掉的：`rank`（和 severity 正交的连续排序权重，直接喂 Grader）、`relationships`（SARIF 的六种 kind，用于冲突检测）、`source`（规范从哪来，manual / imported / mined + 来源 MR 链接，决定信任度和审批路径）。**分类法直接用 Sonar 的 14 个 clean code attribute + 三个 software quality**，不要自己发明——它已经被一个成熟产品验证过，而且它的四个类别恰好和「该不该静态化」这条线基本重合。

4. **规范生命周期要带三个度量，且 not-useful 率超 10% 自动停用。** 直接抄 Tricorder。规范不是写完就完了，它和分析器一样需要被下线。

5. **冷启动走 Qodo Rule Miner 的路子，并抄它的四条约束**：只认「作者真的改了」的评论；要求跨 MR 复现；产量节流（首轮 ≤10 条、之后 ≤5 条/两周）；每条带回溯链接 + 人工审批。再补两条：
   - **从代码库挖时用 Engler 的 MAY/MUST 二分和 `z(N, E)` 排序**——支持数 N 大、违例数 E 小的候选规范才靠前，而不是按出现次数排。这给审批队列一个天然的优先级。
   - **用 Anthropic 的「评估先于文档」验收**：一条候选规范要能举出「不带它时 review 漏掉了什么」的具体 MR，才允许转正。这同时也给了它第一条评估用例。

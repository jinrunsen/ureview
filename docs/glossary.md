# 领域词汇

这份词汇表是规格、场景、工单与代码共用的一套词。写测试名、接口名、提交信息时以它为准；同一个概念在不同地方换词，实现时就会长出两套东西。

## 评审对象

| 词 | 指什么 |
|---|---|
| **PR** | 代码平台上的一次合并请求。GitLab 叫 MR，我们统一写 PR。 |
| **评审** | 对某个 PR 某一轮提交的一次评审，产出一份解读加一组 finding。PR 有新提交就产生新的一次，历史轮次不丢。 |
| **评审状态** | 四态：待评审 / 进行中 / 已完成 / 失败。描述的是评审这个对象本身。**PR 已否合并是 PR 自己的属性，另列一列**，不和评审状态挤在一个字段里。 |
| **评审档位** | 按变更行数定：快速（< 200 行）、标准（200–1000 行）、深度（> 1000 行）。定档理由写命中的阈值。 |

## 产出

| 词 | 指什么 |
|---|---|
| **解读** | 每轮评审默认生成的实现讲解，与 Generator 同时开始、互不参考。讲清 PR 改了什么、改动前后怎么工作、关键代码怎么读；**只讲实现，不找问题，不做判断**，问题由 finding 负责。章节为概要、背景、改动范围、方案与行为变化（含改前改后对比图）、接口配置与数据变化、测试、代码导读、术语表。第一稿完成后由读者审读，再修订一轮。 |
| **解读状态** | 进行中 / 已完成 / 失败，与评审状态分别保存。尚未启动、旧轮次及全部变更被排除的轮次为未运行。 |
| **代码导读** | 解读中按推荐阅读顺序讲解的代码，摘录由宿主从工作副本截取，可附逐行注释。 |
| **需求来源快照** | 本轮读取的 PR 标题与描述、提交信息、PR 关闭的 GitLab issue 标题与描述。解读在背景中引用原文，宿主核对引用出自对应来源。 |
| **读者审读** | 用 Grader 的模型槽位扮演没读过这个模块的工程师，通读解读第一稿，指出照抄缩写、术语未解释、标题说不清、顺序跳跃、图没讲清、说法与代码不符、越界做了评价等问题；写作会话按意见修订一轮。审读失败不影响已完成的解读。 |
| **依据来源** | 这次评审用了什么：注入了多少条规范、来自哪一级、启用了哪些 skill、跨仓上下文开没开、评审档位加定档理由。它让人能判断结论有多少依据，而不是把一个黑盒结论塞给人。 |
| **finding** | 一条评审结论，覆盖两类：规范违规，以及缺陷（含需求未达成、PR 描述与最终代码不一致）。字段：命中的规范 id（若是规范违规）、标题、描述、证据链接表、修复提示词、严重度、锚、状态。 |
| **证据链接表** | 一条 finding 参考过哪些文件。横跨多个文件是常态，**不需要任何「跨文件关联」机制**——给 agent 足够的调查预算就行。每条证据保存评审时读取的代码，在评审页内定位，不跳转到代码平台。 |
| **修复提示词** | 一段可以直接交给编码助手的文字，说清楚问题、修改重点、推荐修法。 |
| **严重度** | 高危 / 中危 / 低危。Git 规则与普通缺陷按具体问题判定；数据库规则违规使用管理员设置的规则严重级别：错误对应高危、警告对应中危、建议对应低危；判断题规范的错误级别对应中危，提交高危时要求模型纠正后重试。高危与中危展示并带代码锚，低危直接丢弃。 |
| **锚** | 文件 + 行号 + 代码内容指纹。不回写平台，所以不迁就任何平台格式。指纹用于 rebase 之后重定位。 |

## 状态与处置

| 词 | 指什么 |
|---|---|
| **处置** | 团队对一条 finding 的当前表态。成员可采纳、驳回或撤回处置；变更携带版本，记录操作人、时间、前后状态与理由。 |
| **`Pending`** | 初始状态，系统给的。 |
| **`Resolved`** | 人**采纳**了这条 finding。 |
| **`Dismissed`** | 人**驳回**了，理由类别为误报、规范不适用、规范有误、不值得修改或其他；其他类必须补充说明。 |
| **`Ignored`** | 系统判定：PR 合并了但没人处置过它。 |
| **`Outdated`** | 系统判定：锚点失效，重定位不回去。**绝不锚到错误的行上**——锚错比不锚更糟。 |

人可采纳、驳回，以及撤回已有处置。撤回后回到 `Pending`，`Ignored` 与 `Outdated` 由系统判定。当前操作使本轮全部展示的 finding 都有处置时，为操作人记录本轮看完。

跨轮对比使用同文件的代码片段指纹，或同文件、同一非空规范 ID 与标题。标记为新出现、上一轮也有；上一轮没有匹配项时列为本轮未再出现。上一轮处置供参考，本轮状态独立。

## 规范

| 词 | 指什么 |
|---|---|
| **规范** | 团队的一条编码约定。来源包括 Git 文件和工作台数据库；数据库规则还包含名称、正反例、分类、严重级别、作用范围、状态和版本。 |
| **规范层级** | 原则、通用、语言、团队四层，与仓库作用域独立。原则用于指导判断，不能被 finding 命中。 |
| **判断题** | 需要结合上下文判断的启发式规范属性。命中时说明可能的问题、代码依据与例外，严重度最高中危；与团队规范冲突时以团队规范为准。属性进入当轮规范快照。 |
| **适用语言** | 通过文件扩展名匹配的语言列表；空列表适用于全部语言。与路径条件同时匹配同一文件。 |
| **覆盖** | 更具体层级对上层规范的显式替代，只影响双方同时适用的文件。原则不能参与覆盖。 |
| **仓库豁免** | 管理员为指定仓库停用一条团队全局规范，保留理由、操作者及设置和撤销时间。 |
| **规范会话** | 管理员编写规范时保留的多轮对话，包含生成结果和当前编辑稿；可以重新打开并继续调整。保存或启用规范须显式确认。 |
| **作用域** | 全局规范保存在数据库中；Git 规范只作用于所在仓库。数据库规范可选择当前团队全部仓库，或指定多个仓库及各自的路径模式。全局范围不跨团队。 |
| **lint 配置** | 仓库 `.agents/lints/` 中 `.mjs` 注册文件声明的机械检查配置，包含路径条件、脚本和参数。工作台只读同步，不代表检查已执行，不计入规范命中统计。 |
| **导入** | 服务管理员上传 Markdown 或文本规范文件，经确定性切片、模型规划与逐片生成，形成可预览、调整和发布的实例级任务。 |
| **导入规范集** | 从上传文件生成的一组规范库条目，发布后供实例内各团队浏览与应用；应用产生独立的团队规范。 |
| **规范库关联** | 工作台规范记录所应用条目的 ID、规范库版本及当时正文；重复应用按条目关联跳过已有规范。 |
| **规范提案** | 新增或修改规范的审核项，来源为规则生成、规范库、历史挖掘或驳回反馈，状态为待审核、已采纳、已拒绝或已撤回。管理员审核，拒绝需理由；待审核反馈全部撤回后，提案由系统标为已撤回。 |
| **候选** | 从历史人工评审挖掘、尚未提交到 Git 的建议，带原评论及代码采纳证据。与工作台规范草稿一同进入提案审核。 |
| **生效** | Git 规范已进入对应规范文件；数据库规范由管理员启用。只有适用范围匹配的生效规范进入评审。 |
| **规范快照** | 一轮评审实际注入的规范正文、匹配路径及来源。保存层级、语言、原适用路径、生效路径及覆盖或豁免依据；Git 规则保存提交，数据库规则保存版本、分类、严重级别和正反例。仓库规范随读取发现并累积；预算不足而只展示索引的条目不进入快照。规则更新或停用不改变旧评审依据。 |
| **挖掘** | 扫历史 PR 的人工评论产出候选规范。只认作者真的照做过、且跨 PR 复现过的。 |
| **硬过滤** | 由程序确定规范适用范围：数据库规则在评审前按团队、仓库、变更路径与语言筛选；仓库规范按实际读取路径匹配 Markdown 的 `paths` 与语言，并计算逐文件覆盖。只有已注入且匹配 finding 主位置的规范可以被引用。 |

## 度量

| 词 | 指什么 |
|---|---|
| **评审覆盖率** | 多少比例的 PR 是在这里被评审的。**北极星**，回答「人愿不愿意来」。 |
| **采纳率** | 最近四周展示的 finding 中，`Resolved / (Resolved + Dismissed)`。分母为零时显示暂无处置，撤回按当前状态计算。**质量护栏**，回答「来了之后有没有用」。 |
| **未经评审就合并** | 评审覆盖率的补数。**这个数不用来罚谁**，用来让团队自己看见约定有没有被执行。 |
| **误报率** | 上限一成，口径按「**开发者有没有动手改**」算，不按我们判断对错算。一条技术上正确但没人改的，算误报。 |

## 集成

| 词 | 指什么 |
|---|---|
| **平台端口** | 评审使用的代码平台只读抽象，**八个方法零个写方法**：`onEvent` / `getPullRequest` / `getDiff` / `getFileContent` / `getGroupingSignals` / `cloneOrUpdate` / `getCommits` / `getClosingIssues`。 |
| **WebhookReader** | 仓库接入检测的独立读取接口，通过 GET 读取项目 webhook 配置，不提供创建或更新方法。 |
| **provider** | 端口的某个平台实现。首发 GitLab。provider 声明自己支持什么，上层按能力降级，不写两套分支。 |
| **工作副本** | `cloneOrUpdate` 落在真实卷上的代码副本。大 PR 拿不到完整 diff 时从这里算。 |
| **拆分** | 变更量超预算时按调用簇切。**只做一层，不递归**——每深一层就重新拆散一次跨文件关联。拆完仍装不下的，明说覆盖不全。 |

## 企业登录

| 词 | 指什么 |
|---|---|
| **企业账号** | 员工在企业统一认证中使用的身份，通过绑定对应到工作台账号。首次登录可建立无密码的工作台账号。 |
| **身份源** | 实例配置的 OIDC 或 OAuth2 认证服务。OIDC 以 Issuer、OAuth2 以去掉查询参数的令牌端点区分身份命名空间。 |
| **账号关联** | 首次企业登录按配置的用户名或邮箱找到已有工作台账号，并保存身份源用户标识与该账号的绑定；后续登录使用绑定。 |

（source: [企业账号登录规格](../requirements/01-v1-qodo-reproduction/26-enterprise-sso-login/spec.md)）

## 接缝

| 词 | 指什么 |
|---|---|
| **接缝** | 观察行为的公开边界。测试只写在确认过的接缝上。 |
| **`@layer:api`** | 服务自己的 HTTP 接口。真跑服务、PostgreSQL 与 dsh，打桩代码平台 provider 与 LLM。管数据正确性与状态流转。 |
| **`@layer:e2e`** | 浏览器。只管 API 层断言不了的交互路径与降级展示，**不重复断言数据正确性**。 |
